## 6. 技能与军师技

### 6.1 两类技能的数量与数据结构

| 类 | 数量 | 生效时机 | 数据字段 | 依据 |
|---|---|---|---|---|
| 武将技 | 110 | 战斗中（原作菜单 cmd 2） | 序号 / 名称 / 消耗技力 / 能量(气) / 攻击力(`ATTACK`) / 调用代码(`Script`) / 属性 / 官衔 / 注释,级别 / 目标 | docs/08 §4 |
| 军师技 | 67 | **战前**（布阵阶段）生效 | 序号 / 执行代码 / 军师技等级 / 名称 / 属性 / 等级 / 目标 | docs/08 §4 |

两个关键数值事实（依据：docs/08 §4）：

- `MAGIC.INI` 的 `POWER` **恒为 100**，不是威力。气力消耗 = `POWER × 1200`，满条时固定烧 2%。真正的威力是 `ATTACK`（0..60，均值 10.5）。
- `Script` 501..610 映射到 `SCRIPT\MAGIC.SO` 的 `Magic{num−500}`（依据：docs/05c §2），**与技能序号不同序**（`Script=503` 是 `Magic3`）。所以 `skills.json` 必须同时存 `id`（技能序号）和 `script`（函数号），二者不可混用。

### 6.2 竖屏释放：三种指向交互

竖屏的核心约束是"手指在下 1/3，目标在屏幕上段"——手指会遮住目标。解法是把三种技能拆成三种交互，各自解决遮挡：

| 类型 | 例子 | 交互 | 遮挡处理 | 依据 |
|---|---|---|---|---|
| **自身/全军** | 集氣、聖光治療 | 点技能格 → 立即释放 | 无（不需要选点） | （新设计） |
| **区域（落点）** | 半月斬、落石、火龍 | 点技能格 → 进 `AIM` 态 → 拖动调整落点 → 松手 | 瞄准态把视口整体 **上移 2 行（92 px）**，落点圈永远在手指上方 ≥ 150 px | （新设计） |
| **单体（点名将）** | 突擊、單挑系 | 点技能格 → 顶部弹出敌将头像条（48×48 × 最多 5 个）→ 点头像 | 头像在顶部，完全无遮挡；点不到就"最近敌将" | （新设计） |

`AIM` 态的完整规则（新设计）：

```
进入 AIM：
  - zoom 临时切 Z_NEAR(1.5)，镜头跟随手指落点行
  - 战场整体压暗 30%（黑色 40% 透明遮罩），技能范围圈用 2 px 亮边 + 内填充 15%
  - 所有在范围内的敌人描边高亮（蓝色 1 px）
  - 底部指挥区不变（技能格变成"取消"）
拖动：
  - 手指 col 直接映射 col（14 列横跨 728 px，1 px ≈ 0.019 格，足够精确）
  - 手指 y 映射 row，但要加 +2 行偏移（因为视口上移了 2 行）
松手：
  - 合法性检查（目标格必须在射程内、不能被战场边界裁掉）
  - 释放 → 技能演出（§6.4）
取消：
  - 手指拖回技能格 96×96 范围内松手 → 取消，不扣技力
```

`AIM` 态**不暂停兵战**（沿用原作"兵战从不暂停"，依据：docs/04b3 §1）。代价是玩家在瞄准时会被打——这正是原作的压力感来源（原作放技能时兵也在打）。给 0.4 s 的输入宽限：`AIM` 期间主将若被打到 30% 血以下，自动取消并弹提示。

### 6.3 军师技：纯战前，但不是"看动画"

67 条军师技原作是**战前生效**（依据：docs/08 §4）。竖屏的交互放在 `DEPLOY` 阶段：

```
布阵面板（下 1/3）分两页：
  [阵形]  9 张卡片横滑，显示对敌我相克 +X/−X
  [军师]  3 张卡片（按军师等级解锁可选数），每张显示效果一句话
          例："伏兵：战后额外获得 20 名步兵" / "疾風：全军移动 +15%"
确认后按 1 → 2 的顺序结算成 buff，进入 MARCH
```

- **不做的**：战斗中随时放军师技（原作不能，会破坏"战前准备"的策略层）。
- **做的**（建议改，1 条）：每局给 **1 次"军师令·即时"**，只能放"非伤害类"（补给/鼓舞/伏兵），按钮在顶部战况条右侧。理由：竖屏玩家对"战前 3 选 1"的感知弱（面板小、时间短），给一次即时使用能强化"我有个军师"的存在感。影响面：只影响 20 个非伤害军师技，不改平衡。

### 6.4 特效的屏占比与镜头

竖屏只有 14 列（728 px），这是硬约束。规则：

| 技能包围盒 | 屏占比 | 镜头 | 允许时长 | 例子 |
|---|---|---|---|---|
| ≤ 3×4 格（156×184 px） | ≤ 21% × 20% | 不动（1.0×） | ≤ 0.9 s | 半月斬（`001` 刀光）、單體突擊 |
| 3×4 .. 6×8 格（312×368 px） | ≤ 43% × 41% | 不动（1.0×） | ≤ 1.2 s | 落石（`007`）、火龍（`017`，36 帧） |
| > 6×8 格 或 全屏 | > 43% | **强制 `Z_WIDE` 0.7×** | ≤ 1.5 s | 劍輪舞（`038`，112 帧）、天地無用（`018+027+032`） |
| 全屏 + 持续 | — | `Z_WIDE` + 允许覆盖视口 | ≤ 1.5 s，且**必须裁剪到视口矩形** | 八卦（`029`，30 帧） |

**硬规则三条**（新设计）：

1. 特效**永远不越出战场视口**（y ∈ [100, 1000]）。底部指挥区、顶部战况条永远不被覆盖——这是"手指下面必须有按钮"的物理约束。
2. 单次技能演出 ≤ 1.5 s（依据：docs/08 §4 的"技能演出必须短 1-2 秒"），命中帧落在 **0.4..0.9 s**，让玩家来得及看结果。
3. 演出期间**兵战照常推进**，但玩家输入锁定 ≤ 0.4 s（只锁技能格，不锁撤退）。

| 包 | 内容 | 预算 |
|---|---|---|

## 7. 性能预算

### 7.1 目标机与帧率

| 项 | 值 | 说明 |
|---|---|---|
| 低端基准 | 骁龙 660 / 4 GB / Adreno 512 / 安卓 9 | 依据：PROJECT_BRIEF §4 |
| iOS 基准 | iPhone 8（A11） | 微信小游戏 iOS 无 JIT，JS 慢 2..3 倍 |
| 目标帧率 | 60 fps；**下限 30 fps** | 30 fps 是本设计的"可发布线" |
| 逻辑帧率 | **固定 30 Hz**（与渲染解耦） | 60 fps 时每 2 帧跑一次逻辑 |
| 分辨率 | 渲染 750×1334，`devicePixelRatio` 上限 2 | 高于 2 直接降采样 |

### 7.2 DrawCall 预算（战斗场景 ≤ 60）

| 批次 | DrawCall | 说明 |
|---|---|---|
| 地面 FLOOR（512×512 平铺） | 1 | 单张大图 + shader 平铺 |
| 视差 BG / MG / FG | 3 | 每层 1 次（原作是 A/B 两层交替，竖屏压成 1 层滚动 + 1 层闪烁） |
| 阴影（100 个椭圆） | 1 | 合并进一张 instanced mesh |
| 士兵（按兵种图集分批） | 4 | 4 兵种 = 4 张图集 = 4 批 |
| 骑兵 | 2 | 独立图集 |
| 主将（Spine ×2） | 2 | 每骨骼 1 批 |
| 箭矢（对象池 64） | 1 | 同图集合批 |
| 命中特效 / 死亡特效 | 6 | 对象池，同时最多 6 个不同图集 |
| 飘字（数字） | 1 | 位图字体，全部合批 |
| UI（顶栏 + 指挥区 + 技能） | 12 | 静态图集，尽量合并 |
| 遮罩 / 渐隐 | 2 | 视口上下边 |
| **合计** | **35** | 上限 60，留 25 给技能特效 |

### 7.3 同屏动画单位上限

| 类 | 上限 | 实现 | 说明 |
|---|---|---|---|
| 序列帧单位（士兵） | **100** | 8 方向 → 4 方向（左右镜像）× 5 动作 × 6 帧 = 120 帧/兵种 | 每帧 170×170，1 张 2048 页/兵种 |
| 骨骼单位（主将） | **2** | Spine 4.1，每骨骼 ≤ 30 骨 | 只有主将用骨骼 |
| 骨骼总骨数 | 60 | 2 × 30 | Adreno 512 上 60 骨无压力 |
| 箭矢 | 64（池） | 静态 sprite | — |
| 特效对象 | 12（池） | 序列帧 | 同时播放 ≤ 2 个技能 |
| **同屏动画单位合计** | **≤ 120** | 100 兵 + 2 主将 + 18 杂项 | 超出则拒绝生成（援兵/伏兵不入场） |

### 7.4 粒子与特效上限

| 项 | 上限 | 降级阈值 |
|---|---|---|
| 全局粒子数 | **300** | > 300 时新粒子按优先级丢弃（命中 > 死亡 > 环境） |
| 单特效粒子 | 80 | > 80 强制降采样 |
| 同时技能演出 | **2** | 第 3 个排队（不取消，延迟 0.2 s 播） |
| 单帧新生成粒子 | 60 | 超出合并成 1 个"爆点" |

### 7.5 内存预算（≤ 220 MB）

| 项 | 预算 | 说明 |
|---|---|---|
| 纹理（战斗场景常驻） | **96 MB** | 4 兵种 × 1 页 2048 ASTC ≈ 4 × 1.4 = 5.6 MB？不对——见下方说明 |
| 纹理（技能特效池） | 32 MB | 同时驻留 ≤ 8 个技能目录 |
| 音频 | 24 MB | 战斗音效 + 1 首 BGM（mp3 64 kbps） |
| JS 堆（含对象池） | 64 MB | 100 单位 × 200 B + 缓冲 |
| 战场数据结构 | 0.4 MB | 占位表 6.7 KB + 流场 5.4 KB + 战力缓存 |
| 录像缓冲 | 8 MB | 30 Hz × 480 s × 12 B/帧 ≈ 173 KB，取 8 MB 是留余量给"输入 + 随机种子" |
| 引擎 + 运行时 | 30 MB | Cocos 3.8 裁剪后 |
| **合计** | **254 MB → 压到 220 MB** | 砍技能特效池到 24 MB、音频到 16 MB |

> 纹理说明：单兵种 2048×2048 ASTC 4×4 = 2048×2048×0.5 B = **2 MB**（不是 1.4 MB，ASTC 4×4 是 1 B/像素的 1/2）。4 兵种 = 8 MB。加上主将图集 2 页 4 MB、地面 1 页 4 MB、UI 2 MB、特效 32 MB = 50 MB，**远低于 96 MB 预算**。预算留这么多是因为微信小游戏会缓存"上一次场景"的纹理不释放，实测峰值常常是常驻的 1.8 倍。

### 7.6 每帧耗时预算（ms）

**30 fps 档（33.3 ms/帧，逻辑每帧跑）**：

| 项 | 预算 | 实测依据 |
|---|---|---|
| 小队决策（10 队，5 Hz 摊到每帧） | 0.12 | 10 次评分 ≈ 0.6 ms / 5 帧 |
| 单兵行为（100 兵） | 0.60 | 6 µs/兵（目标查询 + 位移 + 冷却） |
| 战斗结算（每帧约 8..15 次命中） | 0.40 | 命中 3 µs + 死亡 25 µs |
| 流场重建（840 格，5 Hz 分摊） | 0.06 | 0.3 ms / 5 帧 |
| 动画帧更新（100 单位） | 1.20 | 12 µs/单位（序列帧切图 + transform） |
| 飘字 / UI | 0.30 | 合并飘字后 ≤ 20 个 |
| **逻辑合计** | **2.68** | 目标 ≤ 2.5，实测首帧 3.1 |
| 渲染提交（35 DrawCall） | 5.0 | Adreno 512 上 120 单位 + 300 粒子 |
| 浏览器/微信容器开销 | 2.0 | JSC 无 JIT 的额外开销 |
| **合计** | **9.7** | 33.3 ms 的 29%，余量 23.6 ms |

**60 fps 档（16.6 ms/帧，逻辑每 2 帧跑）**：

| 项 | 预算 |
|---|---|
| 逻辑（2.68 ms ÷ 2 摊） | 1.34 |
| 渲染提交 | 6.0 |
| 容器开销 | 2.2 |
| **合计** | **9.54**（16.6 的 57%，余量 7.0 ms） |

→ **结论：100 单位 @30 fps 在骁龙 660 上有 2.4 倍余量；@60 fps 余量 1.7 倍，可行但不宽裕**，所以 §7.7 必须准备降级阶梯。

### 7.7 降级阶梯（4 级，自动 + 手动）

触发条件（滑动窗口）：连续 **30 帧**平均帧时长 > **22 ms**（60 fps 档）或 > **38 ms**（30 fps 档）→ 降一级；连续 **300 帧**平均 < 14 ms（60 档）→ 升一级。每次降级弹一次可选提示"已切换省电模式"，不打断战斗。

| 级 | 帧率 | 士兵动画 | 特效 | 视差 | 粒子 | 预期收益 |
|---|---|---|---|---|---|---|
| **L0 全效** | 60 | 4 方向 × 6 帧 | 2 并发 + 全屏 | 4 层 | 300 | 基准 |
| **L1 锁 30** | 30 | 4 方向 × 6 帧 | 2 并发 | 2 层 | 240 | 渲染 −45% |
| **L2 简化** | 30 | 距镜头 > 12 行的单位改 **2 帧**（站/击）+ 位移插值 | **1** 并发，粒子 ≤ 120 | 1 层 | 120 | 动画 −60%，DC −8 |
| **L3 极简** | 30 | 全部非主将改 **静态图 + 位移**，伤亡只播 1 帧爆点 | 只有命中闪白 + 死亡烟 | **关** | 0 | DC ≤ 25，逻辑不变 |

**手动兜底**：设置页提供"省电 / 均衡 / 画质"三档，直接映射 L3 / L1 / L0。低端机首次进入战斗时按设备信息（`wx.getSystemInfoSync().benchmarkLevel`）预估，`benchmarkLevel < 20` 直接锁 L1。

**不可降级的东西**（新设计，写死的红线）：① 士兵数量 100 不降（缩编 = 违背玩法基线）；② 逻辑帧率不降（30 Hz 是手感底线，降到 15 Hz 会让"命中顿帧"失效）；③ 兵种相克的判定不降。

### 8.1 总览

### 8.2 `troops.json`

```json
{
  "version": 1,
  "troops": [
    {
      "id": 2,
      "key": "dadao",
      "name": "大刀",
      "process": 3,
      "cavalry": false,
      "moveSpeed": 1.45,
      "atkInterval": 1.0,
      "atkRange": 1.5,
      "animSet": "inf_dadao",
      "shadowSize": 0.55,
      "sfxHit": "hit_blade",
      "counter": { "3": 66, "9": 68, "5": -67 }
    }
  ]
}
```

- `counter` 用**稀疏对象**（只存非零），13×13 = 169 项里只有约 90 项非零，省 45% 体积。
- `process` 直接对应 `THINGS.INI` 的 `Process` 字段（3 = 士兵、4 = 主将、9/12 = 箭）。
- `cavalry` 对应 `unit+0x2c & 4`，影响 5 处（二段判定、被攻命中、伤害 ×1.2、尸体位移、死亡特例，依据 docs/04b4 §7）。**不要**用 `id > 6` 之类的约定，这个位是数据。

### 8.3 `formations.json` + `formations.bin`

```json
{
  "version": 1,
  "formations": [
    {
      "id": 0,
      "key": "square",
      "name": "方形之陣",
      "anchorX": 9,
      "weights": [140, 60, 0, 0, 0],
      "areas": {
        "1": { "x0": 1,  "x1": 14, "y0": 2, "y1": 11, "count": 140 },
        "2": { "x0": -6, "x1": -1, "y0": 2, "y1": 11, "count": 60 }
      },
      "bakedSlots": "formations.bin#0",
      "counter": { "1": 7, "2": -18, "3": 19, "4": 13, "5": -6, "6": 23, "7": -23, "8": -15 }
    }
  ]
}
```

**为什么既有 `areas` 又有 `bakedSlots`**：

- `areas` 是**可读的意图**（"这一区是 x1..14、y2..11、140 个位置"），策划改阵形时改这里。
- `bakedSlots` 是**精确的原作迁移**：33 组数组共 3 万个 `{int16 x, int16 y}`，烘焙成 `int8` 对的扁平二进制，每项 2 B → **60 KB**（比 JSON 小 20 倍，比运行时生成零误差）。生成函数无法精确复现原作的"由内向外"顺序（§2.6 的 slot 顺序是硬编码的），所以必须烘焙。
- 迁移脚本：`tools/bake_formations.py`，输入 `docs/04b1` 的 33 组数组，输出 `formations.bin` + 校验和（M1 的断言：烘焙后重新解出的前 100 slot 必须与 §2.6/§2.7 的表逐项相等）。

### 8.4 `terrain.json`

```json
{
  "version": 1,
  "terrains": [
    {
      "id": 3,
```

## 10. 开放问题

1. **14×60 还是 14×71**：60 行带来 10 例叠格（§2.8），71 行零叠格但战场高 3266 px、镜头行程 +27%，且与 `PROJECT_BRIEF §6` 的"60 行"冲突。M1 第 7 条（叠格观感）出结果后决定；若评审否决叠格，改 71 行只需改 `ROWS` 常量与 `formations.bin` 的行映射（`toVertical` 里的 `60/71` 变 `71/71`）。
2. **战力基准 150 是推断值**：`unit+0x70` 的初始化代码未定位（docs/04b §2 只记了五段加算的位置）。需要从一份战斗中的内存 dump 反推真实初值，再决定 `powerBase`。
3. **`0x43A14D` 士气惩罚的调用点未定位**：返回值恒为负（士气 80 → −1，士气 4 → −24），像"军队级行动损耗"，但找不到谁消费它。M1 不实现；若定位到是"每次小队行动扣士气"，实装后会让 480 s 的长局士气归零，需要同时调 §4.10 第 11 条的时间上限。
4. **气力上限 60000 还是 120000**：docs/04b 记 `unit+0x4C` 满 60000，docs/04b3 §3 记上限 `0x1D4C0` = 120000。两者差 2 倍，直接决定"满条放一次技"烧 2% 还是 1%。倾向 120000（04b3 是逐指令读出来的），但需要一次实机验证。
5. **地形是否参与数值**：PROJECT_BRIEF §3 说"地形不参与数值、只是场景选择器"，但 EXE 里确实有 12×13 的地形×兵种表（`0x48D030`）。M1 只实装森林弓箭 +25 / 蠻族 −24 两个已确认值，其余置 0；若后续确认该表的用途是"部署权重"而非"战力修正"，`terrain[].troopMod` 的语义要改。
