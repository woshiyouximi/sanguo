## 3. 战斗流程状态机

### 3.1 状态枚举与总图

```ts
enum BattleState {
  INIT,        // 加载战场、建双方单位、算战力（对应原作 0x43A1C4 → 0x442EFA/0x443498 → 0x44D450）
  COUNTDOWN,   // 读秒 3 s，镜头从本阵推到前列
  DEPLOY,      // 布阵（9 阵可选，≤ 20 s，可跳过）
  MARCH,       // 进军：双方按阵形向前推进
  CONTACT,     // 首次接敌：顿帧 + 镜头微调，持续 0.6 s
  MELEE,       // 混战主循环
  DUEL_NEAR,   // 主将相遇（MELEE 的子状态，不阻塞兵战）
  ROUT,        // 溃逃：一方存活率 < 25% 或主将阵亡（对应原作 0x4447B7 全军撤退）
  RESOLVE,     // 胜负判定（对应原作 0x447037，返回 1 败 / 2 大胜 / 3 平手）
  SETTLE,      // 结算 → 战后处理（对应原作 0x41048D）
}
```

```
INIT ──> COUNTDOWN ──> DEPLOY ──> MARCH ──[接敌]──> CONTACT ──> MELEE ──┬─[主将≤2格]─> DUEL_NEAR ─┐
                          │                       ▲                     │                        │
                          │                       └─────[脱离3格]───────┘<───────────────────────┘
                          │                                             │
                          └─[跳过布阵]──────────────────────────────> MARCH
                                                                        │
                                        [存活率<25% 或 主将阵亡] ──> ROUT ──> RESOLVE ──> SETTLE
                                        [主将体力≤0] ──────────────────────────┘
                                        [时间≥480 s] ─────────────────────────┘
```

**与原作的对应**（依据：docs/04b §1）：原作没有显式的状态枚举，靠 `[0x4A8144]`、`army+0x2c`、`army+0x80`、`[0x4A665C]` 四个标志位拼出流程；竖屏版把它形式化成 10 个状态，但**每个状态的进入条件与退出条件都锚定到原作的那个标志位**，方便 M1 逐条对照。

### 3.3 读秒与布阵的交互细节

- **读秒 3 s 是新增的**（原作进入战场直接开始），目的是给玩家 3 秒看清"我方是什么阵、敌人在哪一行"。改动的代价：单局时长 +3 s，可以接受。
- **布阵阶段允许换阵**：`DEPLOY` 里换阵 = 重新跑一遍 §2.6 的 slot 分配（100 次 `toVertical` + 占位写入，< 0.3 ms），旧单位沿最短路径 0.5 s 内走到新位置（不是瞬移，避免"闪现"破坏观感）。若玩家在 `MARCH` 之后想换阵，不允许——只能撤退。
- **阵形相克的可见性**：`DEPLOY` 面板上对每个阵形显示"对我方当前阵 +X / −X"以及"对敌方当前阵 +X / −X"（数据来自 11×11 表 `0x48D2A0`，依据 docs/04b §2）。这是把原作藏在数值里的 ±25 变成玩家可决策的信息（新设计），也是 §9 第 4 条验收项的实现手段。

### 3.4 进军与接敌

进军不是"全体直线前压"，而是**按小队的锚点推进**（§5.3）：每小队有自己的目标 row（= 我方前锋线 + 队内偏移），前锋线每 0.5 s 前进 0.4 行，直到接触。这样做的原因：原作 `0x43C4C0` 走位器是"逐格逼近目标格"，整军同速推进会让 100 个兵像一堵墙平移，非常死板（新设计）。

接敌判定：

```
每逻辑帧：
  for each unit in bothArmies:
     if unit.state in (MARCH, ADVANCE):
        nearest = queryEnemyInRadius(unit, 1.5 格)
        if nearest: unit.state = ENGAGE; unit.target = nearest
  if 本帧首次出现 ENGAGE 且 全局仍为 MARCH: 进入 CONTACT
```

### 3.5 混战

混战是唯一真正的循环：每帧只做四件事——**选目标、移动、判定命中、结算死亡**。原作同样是"每单位每帧跑自己的 Process"（Process 3 = 士兵 `0x43DDBF` → `0x43D125`，依据 docs/04b3 §1），所以这个结构是忠于原作的。

关键节奏参数（新设计，但锚定原作的三个数）：

| 参数 | 值 | 原作的对应 | 依据 |
|---|---|---|---|
| 单兵攻击间隔 | 1.0 s（近战），动画 8 帧中的第 4 帧出判定 | 动画命中帧回调 `OM_ATTACK` | docs/04b3 §2 |
| 单兵攻击后摇 | 0.2 s | `0x43B574` 冷却 40 帧的简化 | docs/04b3 §5 |
| 主将攻击间隔 | 1.6 s | `0x43B574` 冷却 40 帧 | docs/04b3 §5 |
| 主将受击后摇 | 0.4 s | `0x2c & 0x4000` 时 46 帧 | docs/04b3 §5 |
| 命中顿帧 | 3 帧（100 ms） | 无（原作只有 HIT01 特效） | （新设计） |
| 死亡倒地停留 | 3 s 后淡出 | `0x421E1B(obj, 0x40)` 倒地 | docs/04b3 §6 |

### 3.6 主将相遇：沿用"没有单挑"的结论

**结论不变**（依据：docs/04b3 §1）：原作全 EXE 没有单挑子系统，没有"單挑/一騎/挑戰"字符串，Process 表里没有单挑类，兵战从不暂停。玩家感知到的"单挑"就是双方主将（Process 4）按普通攻击链互砍，只是恰好站得近。

竖屏版**不新增单挑暂停**，但把"主将相遇"做成一个**观感事件**（新设计），因为竖屏一屏 19 行、主将只有 26 px 高，玩家会完全错过：

1. **距离触发**：双方主将格距 ≤ 2（`dist2 ≤ 2.5²`）且都存活 → 进 `DUEL_NEAR`，强制 `CAM_DUEL` + zoom 1.5。此时屏幕可见 9 列 × 13 行，主将精灵放大到 1.5×≈39 px 高，脸上有表情帧可读。
2. **将战条**：视口顶部（y=100 下方 12 px）出现 44 px 高的横条：左我方名将脸 100×120 缩放到 44×53 + 名字 + 体力条；右敌方镜像；中间一个"交叉刀"图标随攻击节奏闪。**这条不遮挡战场**（战场视口从 y=160 开始算，仍留 840 px）。
3. **命中演出**：命中瞬间 —— 3 帧顿帧、白闪 8%、伤害数字放大到 32 px、木鱼声。这个"顿帧"是玩家能感知"打中了"的唯一手段（原作靠 `HIT01` 特效 + 数字，竖屏要把强度拉高）。
4. **自动脱战**：距离 > 3 格 或 一方死亡 → 退出 `DUEL_NEAR`，镜头 0.4 s 缓动回 follow。**不暂停、不让玩家选择"接受/拒绝"**——因为原作不能选。
5. **玩家可干预的两件事**（都来自原作菜单）：`突击`（cmd 3 武將出擊）让主将主动冲向敌将；`待机·后退`（cmd 4）让主将缩回本阵。这两个按钮在 `DUEL_NEAR` 时高亮。
6. **技能插入**：`DUEL_NEAR` 中玩家可以放"武将技"（原作菜单 cmd 2），技力够就放。这是"单挑"里唯一的策略深度。

> **一条被否掉的设计**：曾考虑"主将相遇时全屏 cinematic（黑边 + 慢动作 + 兵战减速到 0.2×）"。否掉的理由：① 原作不暂停，违背基线；② 竖屏小游戏单局 3-5 分钟，每次将战停 3 秒会打断 100 人兵战的"人海流动"观感；③ 100 个兵在慢动作里会显得各自为战、暴露 AI 破绽。慢动作的替代方案是只在**命中帧**做 0.1 s 的 0.35× 局部减速，只作用于主将两个单位的时间轴（新设计）。

### 3.7 胜负与结算

| 结果码 | 条件 | 结算 | 依据 |
|---|---|---|---|
| 1 我方败 | 我方主将体力 ≤ 0 | 敌方 AI 处置我方被俘将（`0x40452E`） | docs/04b3 §7、docs/04b2 §1 |
| 2 大胜 | 敌方主将体力 ≤ 0 且 我方存活率 ≥ 60% | 玩家处置敌方被俘将（招降/斩首/释放） | docs/04b2 §1 |
| 2 胜 | 敌方主将体力 ≤ 0 且 我方存活率 < 60% | 同上 | docs/04b2 §1 |
| 3 平手 | 480 s 到 且 存活率差 ≤ 10% | 双方都不抓将 | （新设计，原作无时间上限） |
| 1 我方败 | 480 s 到 且 我方存活率低 10% 以上 | 同"我方败" | （新设计） |

- **主将体力 ≤ 0 立即结束**是原作的硬规则（`0x441E61` 在 `0x441EC2` 跳过战场更新，依据 docs/04b3 §7），竖屏保留。所以"只剩主将、被 100 兵围住"是必输局——这与原作一致，也是玩家必须保护主将的压力来源。
- **时间上限 480 s 是新增的**（原作无）。理由：微信小游戏单局必须可预期，且 480 s 后战场会因尸体堆积、士气归零而变成"互相打不中"的僵局。480 s 的选择依据：原作典型战斗 60..180 s（依据：docs/04b §7 的 `S#` 加速与 04b2 战后计时），留 2.7 倍余量。

### 3.8 状态机的实现骨架

```ts
class BattleFSM {
  state: BattleState = BattleState.INIT;
  private t = 0;                    // 当前状态已持续的逻辑帧数

  step(dt: number) {                // dt 固定 1/30
    this.t++;
    switch (this.state) {
      case BattleState.COUNTDOWN:
        if (this.t >= 90) this.enter(BattleState.DEPLOY);
        break;
      case BattleState.DEPLOY:
        if (this.t >= 600 || this.skipDeploy) this.enter(BattleState.MARCH);
        break;
      case BattleState.MARCH:
        if (army.anyEngaged()) this.enter(BattleState.CONTACT);
        else if (this.t >= 480) this.enter(BattleState.ROUT);
        break;
      case BattleState.CONTACT:
        if (this.t >= 18) this.enter(BattleState.MELEE);
        break;
      case BattleState.MELEE:
        ai.update(dt);                 // §5
        combat.update(dt);             // §4
        if (generalDist() <= 2 && bothHeroAlive()) this.state = BattleState.DUEL_NEAR;
        else if (this.state === BattleState.DUEL_NEAR && generalDist() > 3) this.state = BattleState.MELEE;
        if (hero.hp <= 0 || army.survivalRate() < 0.25) this.enter(BattleState.ROUT);
        break;
      case BattleState.ROUT:
        if (this.t >= 120) this.enter(BattleState.RESOLVE);
        break;
      // ...
    }
  }
}
```

`enter()` 里做三件事：重置 `t`、触发镜头强制机位、播 UI 事件。**所有状态迁移都是"单帧内完成"**，没有跨帧的中间态，这样录像回放可以逐帧对齐（§1.3 的定点数就是为这个服务的）。

## 4. 数值：完整公式与改动清单

### 4.1 战力五段（`unit+0x70`）

原作的战力是**五段直接相加、不乘任何系数**（依据：docs/04b §2：`+ TroopCounter(g->+0x8B, enemy->+0x8B)`、`+ TerrainMod(...)`、`+ FormationCounter(...)`、`+ (全局+0x32)/100`、`+ (士气−0x32)/5`）。

```ts
// base = 150：中性命中率 50% 的基准（推断，见下方说明）
function computePower(att, def, terrain, globalAtk): i32 {
  const c1 = TROOP_COUNTER[att.troopId][def.troopId];        // -68..+68，对角 0
  const c2 = TERRAIN_MOD[terrain][att.troopId];              // 12×13，约 -25..+25
  const c3 = FORMATION_COUNTER[att.formId][def.formId];      // -25..+25，零和
  const c4 = idiv(globalAtk + 50, 100);                      // 通常 -1..+1（原式 idiv 100）
  const c5 = idiv(att.morale - 50, 5);                       // -10..+10（士气 0..100）
  return 150 + c1 + c2 + c3 + c4 + c5;
}
```

**关于 `base = 150`（重要，标注为推断）**：

- 原作 `unit+0x70` 的初始化代码未定位到（docs/04b §2 只记录了五段的加算位置，没记录初值）。
- 但命中判定是 `rand() % 300 < power`（依据：docs/04b4 §3），而武将命中的基准值恰好是 `150`（依据：docs/04b4 §3 的 `p = 150;`）。两个 150 出现在同一套判定里，**推断士兵战力基准也是 150**，否则中性条件下命中率为 0%，游戏不可玩。
- 若 M1 发现手感不对（例如 100 兵对撞 8 秒就打完），第一个要调的旋钮就是这个 `base`，而不是五段系数。M1 验收项 §9 第 3 条专门测这个。

**取值范围**（用于调平衡时判断"是否已经极端"）：

| 段 | 最小 | 最大 | 典型绝对值 | 玩家是否能感知 |
|---|---|---|---|---|
| 兵种相克 c1 | −68 | +68 | 0 或 ±66 | **极强**（命中率差 44%） |
| 地形修正 c2 | −25 | +25 | 0 或 ±25 | 强（差 17%） |
| 阵形相克 c3 | −25 | +25 | 0 或 ±23 | 强（差 15%） |
| 全局 c4 | −1 | +1 | 0 | **不可感知**（差 0.7%） |
| 士气 c5 | −10 | +10 | +6（士气 80） | 弱（差 6.7%） |
| 合计 power | 21 | 279 | 150±40 | 命中率 7%..93% |

### 4.2 士兵命中（`0x43D400`）

```ts
// 士兵（Process 3）与箭矢（Process 12）共用
function soldierHit(att, def): bool {
  let p = att.power;                                   // 4.1 的结果
  if (def.isGeneral) p = 150 - def.wuli * 20 / 100;    // 打武将：武力越高越难命中
  if (!def.arrivedAtTargetCell) p = p * 2 / 3;         // 目标在移动 → ×2/3
  if (rand() % 300 < p) return true;
  if (att.isCavalry) {                                 // 骑兵二段判定
    if (rand() % 300 < (p * 2 / 3)) return true;
  }
  return false;
}
```

依据：docs/04b4 §3 的 `0x43D400` 全文（`p = unit+0x70`、打武将 `150 − 武力*20/100`、移动目标 `p*2/3`、`rand()%300`、骑兵位 `a->+0x2c & 4` 失败后二次判定）。

> **注意口径**：士兵打武将用 `150 − 武力×20/100`（武力 85 → 133），武将打武将用 `150 + (攻武−守武)/2`（依据：docs/04b4 §3 的 `0x43D4CB`）。**两个公式不能混用**，原作就是两套。

### 4.3 武将命中（`0x43D4CB`）

```ts
function generalHit(att, def): bool {
  let p = 150;
  if (def.isGeneral)      p = 150 + (att.wuli - def.wuli) / 2;
  else if (def.isCavalry) p = 150 + att.wuli / 3;
  else                    p = 150 + att.wuli / 2;
  if (att.buffFlags & 0x200) p += att.buffValue;       // 军团级命中加成（原作 +0x40->+0x74）
  if (!def.arrivedAtTargetCell) p = p * 2 / 3;
  return rand() % 300 < p;
}
```

武将对士兵时 `p = 150 + 武力/2`：武力 85 → 192 → 64% 命中，这就是"主将走进兵堆里像切菜"的数值来源。**不必削弱**，因为主将一旦被围，士兵打他的命中率是 133（44%），每命中 1 次 3..5 伤害（4.4），从两侧夹击时 8 个兵同时出手 → 主将每秒掉 12 点，这才是"主将不能乱冲"的真正约束。

### 4.4 伤害（`0x43EC54`）

```ts
function computeDamage(att, def): i32 {
  let d: i32;
  if (att.isGeneral) {                   // 攻方是武将
    const h = att.wuli, half = idiv(h, 2);
    const r = half + rand() % (h - half);  // rand[武/2, 武)
    d = idiv(r, 10);
  } else {                               // 攻方是士兵/箭
    let p = att.power;
    if (att.isCavalry) p = idiv(p * 120, 100);   // ×1.2（原作 p*0x78/0x64）
    d = idiv(p * 4, 192);                        // = p/48（原作 p*4/0xC0）
  }
  return d < 1 ? 1 : d;                          // 下限 1
}
```

依据：docs/04b4 §4。**没有防御/减伤项**，原作就是这样——这也是"兵种相克必须靠命中率体现，不能靠减伤"的根本原因。

- 士兵互砍：**命中即死，不进伤害公式**（依据：docs/04b4 §4 的 `0x43E077`：播 `HIT01` + 自转 `OM_DEATH`，无 HP 池）。`computeDamage` 只在"打武将"和"武将打武将"时调用。
- 士兵打武将：`p = 150±40` → `d = 3..4`；骑兵再 ×1.2 → `4`。武将 `BaseHP + 等级×2×武力/100`（依据：docs/04b §4），30 级武力 85、BaseHP 100 → 151 HP。

### 4.5 士气

**三处独立**，不要混为一谈：

| # | 位置 | 公式 | 作用 | 依据 |
|---|---|---|---|---|
| 1 | 战力第 5 段 | `(morale − 50) / 5` | 直接影响命中率，±10 | docs/04b §2 |
| 2 | `0x43A14D` 独立函数 | `m > 50 ? −1 : clamp(m,4,50) × 6` | **返回值是负数**，用途未定位 | docs/04b §2 |
| 3 | 战后 | 被俘者 `士气 −20`、`忠诚 −= (10−节操)×2` | 战后惩罚 | docs/04b2 §6 |

- 第 2 条：`0x43A14D` 的返回值符号恒为负（士气 80 → −1；士气 4 → −24），看起来像"军队级每次行动的损耗"。**M1 不实现**，因为它的调用点未定位，贸然实现会让士气崩塌过快。记入 §10 开放问题 2。
- 第 3 条：**只对被俘（status==3）的将领**，不是全体。docs/04b 记的"战后全体士气 −20"是偏移误读，以 docs/04b2 §6 为准。

### 4.8 战后补兵

function refillTroops(g, city) {
  if (g.cityId === 0) return;                       // 必须"在城内"
  const need = (g.infMax - g.infCur) + (g.cavMax - g.cavCur);
  let avail = city.reserve;                         // city+0x86

### 4.9 三组算例（用来校验实装）

**算例 A：兵种相克到底有多强**（大刀 vs 弓箭，同士气 80、平地、同阵形、全局 0）

| 方向 | c1 | 士气段 | power | 命中率 |
|---|---|---|---|---|
| 大刀 → 弓箭 | +66 | +6 | 222 | **74%** |
| 弓箭 → 大刀 | −66 | +6 | 90 | **30%** |

（相克值来自 docs/04b §2 的实测：大刀→弓箭 +66、大刀→藤甲 +68、長槍→藤甲 +66、飛刀→藤甲 −67。）→ 玩家感知极强，不需要额外强化。**这就是 §9 第 4 条验收的量化标准：同一对兵种正反打的命中率差必须 ≥ 40 个百分点。**

**算例 B：士气 20 vs 80**

| 士气 | 士气段 | power（其余为 0） | 命中率 |
|---|---|---|---|
| 80 | +6 | 156 | 52% |
| 20 | −6 | 144 | 48% |

→ 只差 4 个百分点，**玩家感知不到**。这是原作的固有缺陷（五段权重极不均）。处置见 §4.10 第 6 条。

**算例 C：8 个兵围一个主将（武力 85，HP 151）**

| 项 | 值 |
|---|---|
| 单兵命中率 | `150 − 85×20/100 = 133` → 44%，骑兵二段判定后实际 ≈ 62% |
| 单兵单次伤害 | `power/48 ≈ 150/48 = 3`（骑兵 4） |
| 8 兵 × 每 1.2 s 出手 | 4.4 次命中/s × 3 ≈ **13 点/s** |
| 打死 151 HP 主将 | **≈ 11.6 s** |

→ 主将硬闯兵堆 = 12 秒必死。这个数与原作一致（原作主将走进兵堆也是这个下场），**保留**。

## 5. 士兵 AI 与小队

### 5.1 组织：100 = 10 小队 × 10 人

原作是 100 兵分 10 个小队，每队 10 人（依据：PROJECT_BRIEF §3）。但**原作的小队指令槽只有 8 个**（`army+0x94+idx*4`，idx 0..7，槽 0 是主将，依据：docs/04b3 §4），也就是说 7 个槽控制 10 个小队——原作是靠"槽 0x101 = 除主将外全军"来批量下命令的。竖屏版把这个矛盾解决掉：

```ts
interface Squad {
  id: number;              // 0..9
  units: Unit[];           // 10 个
  mode: 1|2|3|4|5;         // 来自阵形分区（§2.3），决定它的"阵位方向"
  anchor: { col: number; row: number };   // 小队锚点（逻辑坐标）
  state: SquadState;
  targetSquad: Squad | null;
  moraleLocal: number;     // 小队级士气，用于溃逃判定
}
```

**分队规则**：slot `i` 属于小队 `floor(i / 10)`。由于骑兵占每个分区的**低位 slot**（依据：docs/04b1 §3.1），slot 0..13 是骑兵 → **squad 0 是纯骑兵队，squad 7..9 是纯步兵**，中间是混编。这带来一个免费的好处：骑兵队天然是"先锋队"，步兵队是"垫底队"，与原作"骑兵靠中心"的布阵意图吻合。

### 5.2 小队状态机

```ts
enum SquadState {
  IDLE,      // 布阵完成，等开战
  ADVANCE,   // 向目标 row 推进（未接敌）
  ENGAGE,    // 与目标小队交战中
  FLANK,     // 绕后：向目标小队的 col ± 3 偏移
  WITHDRAW,  // 回本阵（cmd 9 回本阵，依据 docs/04b3 §4）
  ROUT,      // 溃逃
  DEAD,      // 全灭
}
```

| 从 | 到 | 条件 |
|---|---|---|
| IDLE | ADVANCE | 全局进 `MARCH` |
| ADVANCE | ENGAGE | 队内有兵进入 1.5 格接触 |
| ENGAGE | FLANK | 相克优势 ≥ +20 且目标小队已 `ENGAGE` 且本队不在目标正面（`|Δcol| ≤ 2`） |
| FLANK | ENGAGE | 到达侧翼位置 |
| 任意 | WITHDRAW | 玩家点"撤退" |
| 任意 | ROUT | 本队存活 < 3，或 全军存活率 < 25% |
| 任意 | DEAD | 存活 = 0 |

### 5.3 小队决策（每 0.5 s 一次，100 兵只有 10 次决策）

```ts
function decideSquad(s: Squad, enemies: Squad[], dt: number) {
  if (s.state === SquadState.DEAD || s.state === SquadState.ROUT) return;

  // 1) 选目标：距离 + 相克 + 是否已被别人打
  let best = null, bestScore = -1e9;
  for (const e of enemies) {
    if (e.state === SquadState.DEAD) continue;
    const d = dist(s.anchor, e.anchor);                       // 格
    const counter = TROOP_COUNTER[s.dominantTroop][e.dominantTroop];  // -68..68
    const busy = e.engagedBy.size;                            // 已被几队缠住
    const score = 60 / (d + 2)                                // 距离项：越近越优先
                + counter * 0.35                              // 相克项：±24
                - busy * 8;                                   // 别都挤一队
    if (score > bestScore) { bestScore = score; best = e; }
  }
  s.targetSquad = best;

  // 2) 阵位锚点：保持阵形几何，锚点随本队几何中心滑动
  const cx = mean(s.units.map(u => u.logicX));
  s.anchor.col = clamp(round((cx - 128) / 256), 0, 13);

  // 3) 绕后：有相克优势 + 不在正面
  if (s.state === SquadState.ENGAGE && best) {
    const counter = TROOP_COUNTER[s.dominantTroop][best.dominantTroop];
    const dCol = s.anchor.col - best.anchor.col;
    if (counter >= 20 && Math.abs(dCol) <= 2 && s.units.filter(u => u.alive).length >= 6) {
      s.state = SquadState.FLANK;
      s.flankTargetCol = best.anchor.col + (dCol >= 0 ? 3 : -3);
    }
  }
}
```

**为什么小队级决策而不是每兵独立决策**：① 100 次/0.5 s 的评分函数在低端机上是 0.6 ms 的固定开销，10 次只要 0.06 ms；② 原作的小队本质上就是一个"组"，`0x43D125` 里整队共享 `flag`（必杀标记 `[0x4A6668]`），说明原作也是按队算的（依据：docs/04b3 §6）；③ 玩家看到的是"一群兵一起冲"，不是 100 个独立个体，小队级更符合观感。

### 5.4 单兵行为

```ts
function updateSoldier(u: Unit, dt: number) {
  if (!u.alive) return;
  switch (u.state) {
    case ENGAGE: {
      // 1.5 格内最近的敌人
      const t = queryNearestEnemy(u, 1.5);
      if (t) {
        u.face = atan2(t.y - u.y, t.x - u.x);
        if (u.atkCd <= 0 && dist2(u, t) <= 1.5 * 1.5 * 65536) {
          u.atkCd = 30;                     // 1.0 s
          resolveAttack(u, t);              // §4.2 命中 → 死亡或伤害
        }
      } else if (dist2(u, u.squad.anchor) > 2.5 * 2.5 * 65536) {
        moveToward(u, u.squad.anchor, dt);  // 归队
      }
      break;
    }
    case FLANK:
    case WITHDRAW:
    case ROUT:
      followFlowField(u, dt);               // §5.5
      break;
    default:
      moveToward(u, u.squad.anchor, dt);
  }
}
```

- **单兵不做独立寻路**：默认只朝"小队锚点 + 队内槽位偏移"移动，遇敌就打。这样 100 个兵的移动是 10 个锚点 + 100 次位移，没有搜索。
- 只有在 `FLANK / WITHDRAW / ROUT` 三种"要绕开障碍物"的状态才用流场。

### 5.5 寻路：流场 vs A*（性能取舍）

| 方案 | 100 兵的成本 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 单兵 A* | 100 次 × 每次 40..80 节点，2 Hz 更新 → 8000..16000 节点/s，约 **1.2..2.4 ms/s**，但**峰值单帧可达 0.4 ms 抖动** | 路径最优 | 100 个兵各算各的，热门格抢用冲突；峰值抖动 | 仅用于"绕后"的少数单位 |
| 共享流场 | 840 格 BFS，5 Hz → **0.06 ms/帧分摊**，无峰值 | 全队共享同一张"往敌人去"的图，天然不打架 | 目标是"所有敌人"而不是某个敌人，绕后需要额外目标点 | **主方案** |

```ts
// 5 Hz 重建（每 6 个逻辑帧）
function rebuildFlowField() {
  const dist = new Int16Array(COLS * ROWS).fill(0x7fff);
  const q = new Int32Array(COLS * ROWS);
  let head = 0, tail = 0;
  // 多源 BFS：所有"有敌方单位"的格作为源，距离 0
  for (const e of enemyUnits) {
    if (!e.alive) continue;
    const i = cellIndex(e.col, e.row);
    dist[i] = 0; q[tail++] = i;
  }
  while (head < tail) {
    const i = q[head++], d = dist[i] + 1;
    for (const n of NEIGHBORS8[i]) {
      if (isBlocked(n)) continue;            // 目前只有战场边界，无地形障碍（§8.4）
      if (dist[n] > d) { dist[n] = d; q[tail++] = n; }
    }
  }
  // 梯度：每格取 8 邻域里 dist 最小的方向，打包成 3 bit
  for (let i = 0; i < COLS * ROWS; i++) {
    if (dist[i] === 0x7fff) { flowDir[i] = 0; continue; }
    flowDir[i] = argminNeighbor(dist, i);
  }
}
```

- 内存：`dist` 1680 B + `flowDir` 315 B（840 格 × 3 bit 打包进 Uint8）+ 队列 3360 B ≈ **5.4 KB**。
- 8 方向移动 + 连续坐标，避免"格子中心对齐"的锯齿：`u.x += dirX * speed * dt`，`dirX/dirY` 是 8 方向单位向量（定点表）。
- 流场只在 `FLANK/WITHDRAW/ROUT` 且 **本帧需要移动** 时才查询，平时（ADVANCE/ENGAGE）完全不碰它。

**弹道设计**（新设计，忠于原作的"落格判定"）：

```ts
class Arrow {
  from: Vec2; toCell: {col,row};     // 发射时记录目标**格**，不记录目标 unit
  t = 0; dur = dist / ARROW_SPEED;   // 秒
  step(dt) {
    t += dt;
    // 视觉：抛物线抬升 0.35 格
    visY = lerp(from.y, cellY(toCell)) - Math.sin(PI * t/dur) * 0.35 * 256;
    if (t >= dur) {
      // 逻辑：到达时才结算，且以"当前在格里的敌人"为受击者
      const target = randomEnemyInCell(toCell);      // 可能已经走了 → 落空
      if (target) { if (soldierHit(shooter, target)) resolveAttack(shooter, target); }
      else spawnMissEffect(toCell);                  // 落空箭头插地
      recycle(this);
    }
  }
}
```

**这个设计让"移动目标 ×2/3"变成物理事实**：敌人在箭飞行的 0.7 s 里走了 1 格，箭就落在旧格。此时若再乘 2/3，等于惩罚两次（§4.10 第 10 条）。竖屏选择"只保留物理落格"，因为**玩家能看见箭落在哪里**——这是竖屏唯一比横屏强的地方（视野宽，能看到整条弹道）。

**箭矢对象池**：64 个，超池则最旧的直接回收（不生成新对象，避免 GC）。同屏 64 支箭 = 64 个 sprite，可以合批（同一图集）。
