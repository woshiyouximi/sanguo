# 201 透视边界与摄像机

> 任务：R193 把战场从等距改成原作式透视之后，**摄像机夹取还停在「常数投影时代」的 ±6.3 行**，
> 镜头顶到老端点时最近一排会被控制台盖住。本轮把夹取接到单一真值 `field.clampCameraX()`，
> 并补 11 条边界测试 + 四张现场截图 + 像素核对。
>
> 结论：**已修复**。`camera()` 的夹取区间从 `[6.30, 63.70]` 变成 `[6.2874, 64.4877]`，
> 两端都由「透视带沿 + 精灵身位」反解，不再是 `FIELD_H/2/ROW_PX` 这个常数投影的遗留值。
>
> 标注约定：`[确认]` = 本轮实测/读码直接得到；`[推测]` = 由公式外推、未逐帧肉眼验证。

## 0. 结论（TL;DR）

| 项 | 修前 | 修后 | 依据 |
|---|---|---|---|
| 夹取下限 | `6.30`（`450/ROW_PX`） | `6.287355`（`-rowOfScreenY(162)`） | `game/src/core/field.ts:209` [确认] |
| 夹取上限 | `63.70`（`70-450/ROW_PX`） | `64.487665`（`70-rowOfScreenY(968)`） | `game/src/core/field.ts:210` [确认] |

| camX=63.7 时 gx=70 的帧底 | `1065.79`（整条腿＋阴影在控制台后面） | `998.35`（< `FIELD_BOTTOM`=1000） | `game/tests/persp_edge.test.ts:194` [确认] |

一句话根因：`camera()` 的夹取用的是 `half = 450 / ROW_PX`，这是 `sy = 550 + (x-camX)*ROW_PX`
那套**常数投影**下「半屏 = 450px」的换算；透视投影下同一个 `sy` 对应的行距随行变化（`rowScreenY(r)`
是 `e^{kr}` 曲线），`450/ROW_PX` 不再是「半个可视带」，于是夹取端点整体偏窄 0.79 行。

## 1. 缺陷

### 1.1 现场

`camX=63.7`、我方占据 `gx=66..70`（`work/persp_edge/cam_old_endpoint.png` 的布局）：

- `gx=69` 正常，`sy=950.36`，站在草地上；
- `gx=70` 的 `sy=1034.59` —— 比 `FIELD_BOTTOM=1000` 低 **34.59px**，脚、腿、阴影全被控制台面板压住，
  画面上只剩**半个头盔尖**从面板上沿露出来（`work/persp_edge/cam_old_endpoint_crop_bottom.png`，已肉眼核对）。

这正是 `project/193_透视投影.md` §7.1 记的那个 `sy=1034.6`。

### 1.2 根因（file:line）

修前 `game/src/core/battle.ts`（从 cocos 旧副本还原时退回了 R198 之前的写法）：

```ts
// 修前 :3074-3095
export function camera(world: World): number {
  const half = 450 / ROW_PX;          // ← 常数投影时代的「半屏」，= 6.3 行
  ...
  return Math.max(half, Math.min(GRID_W - 1 - half, cam));   // ← 夹取只用它
}
```

`450` 是「设计高度 900 的一半」，只有在 `sy` 与行号线性相关时它才等于半屏行数 [确认]：
常数投影下 `sy = 550 + (x-camX)*ROW_PX`，所以「上下各 450px」⇔「±450/ROW_PX 行」；
透视投影下 `rowScreenY(r) = 550 + ROW_PX·S0·(e^{kr}-1)/k`（`field.ts:163`），
`r=-7.4339` 才到 `FIELD_TOP=100`、`r=+5.8936` 才到 `FIELD_BOTTOM=1000` —— **上下不对称**，
一个 `half` 无论如何都盖不住两端。

### 1.3 为什么「不对称」

[确认] `ROW_K=0.035 > 0` ⇒ 近处行距被拉大（`SCALE_NEAR=1.1830`）、远处行距被压小（`SCALE_FAR=0.7420`），
所以从中心往上能装 `ROWS_FAR=7.4339` 行、往下只能装 `ROWS_NEAR=5.8936` 行，
合计 `ROWS_VISIBLE=13.3274` 行。旧夹取取的是「对称的 6.3」：
- 下限 `6.30` 比正确的 `6.2874` 略保守（远端多留了一点点，没出事）；
- 上限 `63.70` 比正确的 `64.4877` **少了 0.7877 行**，这就是「镜头推不过去、最后一排掉到控制台下面」的来源。

2. **窗口近沿的行，帧底可能略过 1000** [确认]。例：camX=6.3 时 `gx=12` 的 `sy=983.70`（在带内、脚在草坪上），
   帧底 `1014.25`。越过面板的只是 `sy` 下方 `26·scale` 的**阴影/透明 padding**，不是脚。
   这是「`sy ∈ [带沿, 带沿]` 判据 + 精灵脚下有 padding」的必然结果，任何处于窗口近沿的行都会这样。
   `CAM_MARGIN_NEAR_PX=32` 保证的是**网格最后一行 `gx=70` 在镜头到 `CAM_MAX` 时整帧在带内**（998.35）。
3. **`CAM_HALF_ROWS` 仍是 6.3** [确认]。它是 `450/ROW_PX`，在透视下**不再是半屏行数**，
   只用于 `camera()` 的换镜判据（`aMin - bMax > 2 * half`）。本轮刻意不动它 —— 那是换镜手感，不是边界。
4. **`battle.ts:3069-3072` 的 `project(camX,x,y)` 仍用线性公式** [确认]。它只服务 core 内部（不考虑透视），
   屏幕绘制一律走 `view/projection.ts`，所以不影响视觉。本轮没动它（属于「战斗逻辑」）。
5. **夹取只保证 `camX ∈ [CAM_MIN, CAM_MAX]`，不保证「任何 camX 下所有网格行都在带内」** [确认]：
   camX 停在中间时，窗口外的行本来就在带外（`gx=70` 在 camX=63.7 时 `r=6.3 > ROWS_NEAR`），
   这在 `persp_edge.test.ts:178` 里当**语义**显式断言，不是靠夹取去掩盖。
