# R87 技能等待语义（`WAITFOR` / 旋龍恒「未命中」）

> 结论：**根因不是命中判定，而是 `WAITFOR` 被实现成空语句**。智能脚本 `MAGIC.SO` 用
> `WAITFOR "同名脚本"` 当「每帧一次的节流点」，我们的 runtime 直接跳过 ⇒ 旋龍 554 的主循环
> 在同一帧里空转到 20 万条指令预算、被当死循环截断 ⇒ 会话战果为空 ⇒ web 飘 MISS。
> 顺带修掉第二个真缺陷：`0x129/0x10D` 的唯一实参是**阵营**（`g5 ^ 1`），不是句柄；
> 旧实现当句柄解析 ⇒ 恒 0 ⇒ 旋龍的 dummy 生成在 `(0,0)`、整技能 0 命中。
>
> 改动文件：`game/src/core/smartscript/runtime.ts`、`syscalls.ts`、
> `game/tests/r87_waitfor.test.ts`（新增 9 条）、`game/tests/smartscript_audio.test.ts`（1 条期望值，见 §7）。
> `vm.ts`、`battle.ts` **未改**。

## 2. 根因链（证据）

### 2.1 脚本侧：`0x130D8` 是「每帧一圈」的循环

`export/script/magic_so.dis.txt`（旋龍 `@0x12B..0x131F4`）：

```
10828 L12DEC: 0800000009000000 LDSL loc9        ; dummy（资源 2501）
10831         050000001200000001000100 SYSCALL 0x12  ; 物件还在 ⇒ 0
1083?         JNZ L131B8                        ; 不在了 ⇒ 收尾
...
10925 0130D8 LDSL loc14 / LDSL loc15 / LDSL loc1 / LDSL loc2 / CALL GetSpeed → loc16
10933          STG g14 = loc16 * 2
10934-10940   CALL GetDir(loc14,loc15,loc1,loc2) → STG g15
10944 01316C SYSCALL 0x19 argc=3 (loc9, loc12, loc16)   ; dummy 朝 loc12 以 loc16 飞
10945-10950   PUSHS "WaitTarget"; LDSL loc9; LDSL loc1; LDSL loc2; PUSHI 0; CALLS
10951 0131A4  PUSHS "WaitTarget" / 10952 WAITFOR
10953         JMP L12DEC                        ; 回循环头
```

整圈**只有 `WAITFOR` 一个同步点**：没有 `WAIT`、没有别的挂起。
`L12DEC` 的退出条件是 `0x12(loc9)`（dummy 过期）；dummy 是 `0x11` 生成的物件，
寿命 = `DEFAULT_OBJECT_FRAMES = 96` 虚拟帧（`runtime.ts:201`）。
⇒ 只要每圈推进 ≥1 虚拟帧，循环必在 ~96 圈内结束；一圈都不推进就必然打光指令预算。

### 2.2 引擎侧：`WAITFOR` 的真实语义 = **每帧检查一次**的等待

- `docs/04-脚本引擎SmartScript.md:370`：`0x45 WAITFOR` 弹名字串，**等待同名脚本结束**；
  handler `0x4658A0` 把名字交给 `0x464D70(0x465820, name, 2)` 装等待回调。
- 同文件 `:372`：`0x465820` 在活动 VM 列表 `0x4A686C` 里按「当前函数名」查找，
  找到就继续挂起、找不到才恢复。
- 关键在**检查时机**：`0x467E70`（检查等待回调）只在 `0x467F10` 的**每帧入口**被调一次
  ⇒ 一次 `WAITFOR` 至少跨过一帧，**即使同名脚本根本不存在**。
- `docs/04:408`：`CALLS（0x47）` 形如 `PUSHS name; <a>; <b>; <c>; <d>; CALLS` → `name(a,b,c,d)`。

所以「同步模型下怎么等价实现」的答案是：**不能跳过，必须让出一虚拟帧再继续**
（记一笔 `waitfor:<name>` 后 `tickClock(1)` / `requestWait(1)`）。
我们的 `CALLS` 是同栈内联（`vm.ts` `case 0x47` 的 `callInline`），被调脚本在 `WAITFOR`
之前就已经跑完，不存在"还挂在活动列表里的同名子 VM"，所以「等同名脚本结束」
在我们的模型里退化成「至少让出一帧」——与原作每帧轮询同粒度。

### 2.3 为什么恰好是 `pc=0x130d8`

`vm.ts:316-330` 的预算：`this.steps++ - this.stepsAtPump > this.budget`（200000）即抛。
`waitFor()` 旧实现只 `this.calls.push('waitfor:'+name)`（`runtime.ts:653-655`）⇒ 循环一圈
不消耗虚拟帧、`0x12(loc9)` 恒「还在」⇒ 越转越深，最后一个 JMP 落在 0x130D8。

### 2.4 第二个缺陷：`0x129` / `0x10D` 的实参是**阵营**，不是句柄

- 反汇编：`syscall 0x10D @0x00420518`（`syscall_handlers.asm.txt:1213`）→ `0x43A7AC(arg1)`；
  `syscall 0x129 @0x00420809`（`asm.txt:1541`）→ `0x43B375(arg1)`。两者都只吃一个实参。
- 脚本侧：`magic_so.dis.txt` 里这两条 syscall 的**全部 55 个调用点**（0x10D 24 处 +
  0x129 31 处，如 10736、10745、10840、10890、…）都是同一形状：

```
LDG 5 / PUSHI 1 / XOR / SYSCALL 0x129|0x10D argc=1     ; 实参 = g5 ^ 1（对面阵营）
```

  旧实现把它当句柄（`ctx.isUnit(a(0)) ? a(0) : ctx.handleOfObject(...)` / `ctx.objectOf(a(0))`）
  ⇒ 恒返回 0。旋龍里 `012B68 JNZ L12BC4` 会带着 `loc8 = 0` 一路走到
  `0x11(0, 2501, 0, 0)`，而 `0x11` 的 arg1 是单位句柄（`asm.txt:214-244`：
  `0x421a80(arg1)` 解析失败就不生成）⇒ **dummy 生成在 (0,0)**，整技能 0 命中。
- 修复后 dummy 落在主将身边 `(24.4, 6.2)`，命中从 0 变 15（见 §4）。

### 2.5 syscall `0x19` 的参数序（证实，但不实施运动）

`syscall_handlers.asm.txt:466-494`（`@0x0041FD98`）：

```
eax = [ebp+8]  (arg1) → call 0x421a80 → [ebp-0xc]  (objA)
ecx = [ebp+0xc] (arg2) → call 0x421a80 → [ebp-0x14] (objB)
if (objA != 0 && objB != 0) call 0x4225f8(objA, objB, arg3)
```

⇒ 三参是 **(物件/单位, 物件/单位, 数值)**，旧实现 `const o = ctx.objectOf(a(0)); o.motion = a(1)`
把第 2 个**句柄**当数值存了。`0x4225f8` 的本体不在 export 里（没有 EXE，全仓也搜不到），
所以「A 追 B」只是 `[推测]`；实测把它实现成"朝 B 直线飞"后旋龍的 dummy 会朝一个我们
解析不到真目标的全局（`loc12` 的 `g3` 兜底）飞走，效果反而从 15 hits / 8 dmg / 5 kills
掉到 6 hits / 0 dmg / 2 kills ⇒ **故意不实施运动**，只把参数序改正（把第 3 参记进
`o.motion`）并在注释里留证据。

## 5. `CastResult` 为什么仍然是 `{hit:false,hits:0,damage:0}`

多帧技第 0 帧只有特效、没有结算，`cast()` 返回的是**第 0 帧**的结果。
这条语义被既有测试钉死：`game/tests/battle_feedback.test.ts:104-117`（R84）

```ts
assert.equal(r.killed, 0);
assert.equal(r.hit, false);   // 注释：第 0 帧没生效：这就是旧 UI 判 MISS 的时刻
```

所以本轮**没有**去改 `cast()` 的 hit 语义（改了就是语义反转：打空的技能第 0 帧也会报"命中"）。
web 那句 MISS 由视图层压掉：

- `game/web/main.js:1131-1137`（冻结文件）用 `result.hit === true || (result.hits ?? 0) > 0` 判命中，
  否则飘 `MISS`；
- `game/src/view/battleView.ts:1142-1149`：`dropWebMiss = skillPending || freshMark`，
  `skillPending = world.sessions.length > 0`（`battleView.ts:537-539` 传入）
  ⇒ 技能还在解算时，web 的 MISS 一定被丢弃；真战果由内核 `world.skillMarks` 逐条画。
- 内核保证"真打空"才补 `miss` 标记：`battle.ts:1940-1943` 的会话收尾逻辑。

新增测试 `R87 web 那句「未命中」不再飘出来` 就是钉这条链路的：cast 当帧
`buildFrame()` 输出里没有 `MISS`，战果落地后同一帧里出现 `-8`。

## 8. `[推测]` 与没做到的

1. **`[推测]` `0x4225f8` 的语义**：按 handler 形状推是「objA 追 objB」，但函数体不在
   export 里（没有原 EXE），无法证实。实测按此实现会让旋龍 dummy 飞错方向
   （15→6 hits、8→0 dmg），所以**保留不实施**，只纠正参数序（见 §2.5）。
2. **未解：`WaitTarget` 的实参对不上**。调用点压了 `loc9, loc1, loc2, PUSHI 0`（4 个值），
   而 `WaitTarget argc=3`；按我们已验证的「最后压栈者 = arg1」，函数体里
   `0x12(arg3)`（判物件存活）拿到的是**坐标**而不是 `loc9`，于是「等 dummy 到目标附近」
   这条条件在我们模型里永远查不到真物件（实际退化成 `|y坐标| < 24` 的偶然判断）。
   可能的解释是那多出来的 `PUSHI 0` 是"返回值槽"，引擎会先弹掉它再取 3 个实参；
   但这会牵动**所有** `CALLS` 的映射，风险太大（`CreateDummyRef`/`GetSpeed` 都被
   「最后压栈者 = arg1」解释得通），本轮不动，记为待查。
   → 影响：旋龍的循环节流完全靠 `WAITFOR` 让出的那 1 帧在推进（这正是修复的核心），
   `WaitTarget` 本身几乎是空转；视觉上"狂风追着目标扫"的细节没有复现。
3. **`SetObjectMotion` 的 rebase** 只解决"中途改向不瞬移"，没有做真正的逐帧弹道积分
   （`posOf` 仍是解析式外推）。
4. **`CastResult.hit` 没有改成 `true`**（与 R84 冲突，见 §5）；web 不飘 MISS 靠视图层压。
   若 lead 要求 CastResult 也满足 `hit||hits||damage`，需要先改 R84 的期望值并接受
   "多帧技第 0 帧报命中"的语义反转。
5. `battle.ts` 一行没改：`CaseResult/session` 汇总逻辑本身没问题，问题全在脚本语义层。
