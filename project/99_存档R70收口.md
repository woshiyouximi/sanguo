## 2. 为什么升 v3

### 2.1 必须升的理由

1. **只加键不改 `v` → "已是最新"的判定会骗人。** `snapshotIsCurrent()` 的判据是
   `v === SNAPSHOT_VERSION && 每个必填键都在`。若把 6 个新键塞进必填而 `v` 留在 2，
   那么一份**真的 v2 旧档**（缺这 6 键）与"当前档"就无法区分 → `upgradeSnapshot` 每次读档都要
   深拷贝 10 个槽、`normalizeStore` 每次 `saveStore` 都要重算摘要（v2 时代专门优化过这点，
   `saves.js:466` 的 `!up.changed && hasMeta → 浅拷贝`）。升版本号是**唯一**能让"要不要迁移"
   一次判定的事。
2. **`.v` 是给人和给后续 agent 看的契约。** `campaign.html:1391` 的提示串直接插
   `${Saves.SNAPSHOT_VERSION}`（升 3 自动显示 v3），`98_对照复查R84.md:208`、`80_对照复查R83.md:390`
   之类复查都靠 grep 这个常量判断"存档动过没有"。
3. **迁移要有可断言的形状。** 本轮要求 `steps` 能断言 v2→v3 这一步；只有引入
   `SNAPSHOT_STEPS = [{0→2},{2→3}]` + 逐跳循环，`['v0→v2','v2→v3']` / `['v2→v3']` 才是
   可以写进测试的事实，而不是一段注释。

### 2.2 为什么不升 `STORE_VERSION`（容器版本）

容器（`{v:2,last,slots[10]}`）的**形状**没变：还是 10 个槽、还是 `{...summary, snapshot}`。
只有槽里那份 snapshot 长了字段 —— 那是 `SNAPSHOT_VERSION` 的事。`STORE_VERSION` 保持 2，

### 2.3 为什么不干脆叫 v4

v3 里**没有**任何"推翻 v2 语义"的改动：v2 的 29 个键一个没删、一个没改语义。

## 4. 迁移：v2 → v3，v0 → v3

### 4.1 `SNAPSHOT_STEPS` 与逐跳 `steps`

```js
export const SNAPSHOT_STEPS = Object.freeze([
  Object.freeze({ from: 0, to: 2 }),
  Object.freeze({ from: 2, to: 3 }),
]);
// upgradeSnapshot 内：
for (const hop of SNAPSHOT_STEPS) {
  if (hop.to > from && hop.to <= SNAPSHOT_VERSION) out.steps.push('v' + hop.from + '→v' + hop.to);
}
```

| 进来的档 | `from` | `steps` | `to` |
|---|---|---|---|
| 没有 `v` 字段 | 0 | `['v0→v2','v2→v3']` | 3 |
| `v: 2` | 2 | `['v2→v3']` | 3 |
| `v: 3` 且字段齐 | 3 | `[]` | 3（`changed:false`，**不拷贝**） |
| `v: 3` 但缺键 | 3 | `['v3→v3']` | 3（只补缺，`filled` 会列出补了谁） |
| 坏输入（null/字符串/数组） | `-1`（'invalid'） | `[]` | 3 |

> 为什么"v3 缺键"也记一跳：`steps` 的语义是「**发生过结构补齐**」，不是「版本号变了」。
> `yearsettle_r7.test.ts` 之类守护测试用它判断"这次读档有没有被动过"，宁可多报。

### 4.2 补齐（`ensureSnapshotShape`）的 v3 规则

| 键 | 规则 |
|---|---|
| `year` | 永远按 `yearOf(month)` 重算（**唯一**允许覆盖已有值的键） |
| `yearFlag` | 非 0/1 → 夹回（`f ? 1 : 0`） |
| `generalStatus`/`weapon`/`horse`/`thing` | `strMapAt()`：非对象→`{}`；非字符串值丢弃；`trim()`；空串不存。**只清洗、不猜值**（不替在野猜成"在城"） |
| `ledger` | 只在**已存在**时清洗（`year<1` 回填 `yearOf(month)`、`months/income/salary` 取整且 ≥0）；**缺失就让它缺失** |

### 4.3 `filled` 会列出什么

`upgradeSnapshot(v2档).filled` 实测：`["year","yearFlag","horse","thing","v"]`
（`generalStatus`/`weapon` 因为在夹具里被故意写成坏值，走了"清洗"而不是"补键"，所以不在 `filled` 里
—— 值确实被改了，但键本来就在。这一点在测试里钉住了。）

### 4.4 `newCampaign` 一次写全

```js
save.year = 1; save.yearFlag = 0;
save.generalStatus = {}; save.weapon = {}; save.horse = {}; save.thing = {};
```

必须一次写全，否则 `yearsettle_r7.test.ts:295-303` 的
`assert.equal(S.upgradeSnapshot(plain).changed, false)` 会红（那条测试的用意就是抓"新档还没结构完"）。

### 4.5 `ledger` 为什么**不**进 `SNAPSHOT_REQUIRED`（本轮的一次设计反转）

初版把 `ledger` 放进必填、并且 `newCampaign` 直接写 `{year:1,months:0,income:0,salary:0}`。
结果 **`yearsettle_r7.test.ts:89` 立刻红**：

```ts
// game/tests/yearsettle_r7.test.ts:96
assert.equal(save.ledger, undefined, '不能为了"看起来像结过账"而写空账本');
```

这条断言的语义是对的：R7 的规则是「**没结过账就没有账本**」，账本由 `ledgerAdd` 在月推进时
（`campaign.html:3486/3521`，每月调两次）→ `ledgerOf()` → `ensureYear()` 自动建，并从当月开始累计。
迁移替一份老档造一个 `{months:0}` 的空账本，等于伪造"已经结过账、这 12 个月一分钱没进"，会污染
年度结算的 5 段。

**处理方式（lead 给的两条路里选了 1）**：
- `newCampaign` 不写 `ledger`；
- `SNAPSHOT_REQUIRED` 不含 `ledger`；
- `ensureSnapshotShape` 只在 `'ledger' in s` 时清洗，**缺就不补**。

于是：新档 → 首年 `ledger === undefined`（守 R7 语义）；玩家推进一个月 → `ledgerAdd` 建账本 →
之后每份存档都有 `ledger`（正常在玩的档不会缺）；老档迁移 → 原来有就原样留着，没有就继续没有。

> **落到档里的事实**：`ledger` 依然会入档（R7 的 `ledgerOf` 每月都跑），只是"入档"由运行时决定，
> 不由迁移决定。测试同时钉住了两个方向：`newCampaign().ledger === undefined` 与
> `upgradeSnapshot({ledger:{...}})` 后 `ledger` 深等保留。

## 5. 真 bug 修复：手动存档劫持自动存档目标槽

### 5.1 复现（lead 提供，另一路 agent 真点验证）

1. 新局 → 右上「存 檔 槽 1」→ 浮层点**槽 2「存」**；
2. 推进一月 → 打一场 → 回大地图 → notice 写「自動存到**槽 2**」，`#btnSave` 变「存 檔 槽 2」；
3. F5 重进 → 槽 2 是新的自动存档，槽 1 才是玩家手动存的旧档（**期望正好相反**）。

### 5.2 根因

`writeSlot()` **无条件** `store.last = i + 1`，不管是手动存档还是自动存档：

```
campaign.html:1245  saveToSlot()  → Saves.writeSlot(store, i, ...)   // 手动 → 也改 last
campaign.html:1124  let bootSlot = Saves.lastUsed(store) + 1;        // 启动就跟着 last 跑
campaign.html:1227  const n = slotNo();                              // autosave 写 activeSlot = bootSlot
```

于是「手动存槽 2」把 `last` 设成 2 → 下次启动 `bootSlot = 2` → 自动存档写槽 2 → 手动档被盖。

### 5.3 修法（在 `saves.js` 内，文档化语义）

| 导出 | 行为 |
|---|---|
| `writeSlot(store, i, snap, opts)` | **默认不动 `store.last`**（`opts.touchLast === true` 才动） |
| `writeSlotAuto(store, i, snap, opts)` | `= writeSlot(..., {...opts, touchLast: true})`，**自动存档专用** |
| `lastUsed(store)` | 语义收窄为「**自动存档目标槽**（0 基），默认 0=槽 1」，手动存档不参与 |
| `migrateLegacy()` | 改用 `writeSlotAuto`（迁移出来的就是玩家唯一那份档，理应成为自动存档目标） |

`normalizeStore` **不重算** `last`（`intOr(raw.last,1,1,SLOT_COUNT)` 原样保留）——
这是刻意留的兼容口：老容器里那份"被手动存档带偏的 `last`"不会被我们悄悄改掉，
下一次自动存档会写到它指向的槽（等价于旧行为），玩家再手动存一次也不会把目标搬走。

### 5.4 这个修法在 campaign.html 打补丁前也安全

`campaign.html` 的 4 个 `writeSlot` 调用点（`1231` 自动、`1245` 手动、`1762` 新局、`1830` 演示种档）：

- **打补丁前**：`last` 永远停在默认值 1（或老容器里的历史值），`bootSlot` 恒定 →
  自动存档固定写槽 1，手动存到别的槽**绝不会**被自动档盖掉（这就是本条 bug 的核心危害，直接消失）。
  代价只是「上次玩的是槽 3，重进游戏默认读槽 1」，且 `campaign.html:1125-1128` 还有
  「上次那个槽是空的 → 用 `newestSlot`」的兜底。
- **打补丁后**（§9 的 P0，2 行）：`last` 精确等于自动存档槽，行为回到"上次玩哪槽就进哪槽"。

### 5.5 测试钉住的东西（`saves_r70.test.ts`）

1. `writeSlot 不碰 last；writeSlotAuto 才推进 last` —— 手动存槽 4 后 `store.last === 1`；
   `writeSlotAuto(store, 6, ...)` 后 `last === 7`；`{touchLast:true}` 与 `writeSlotAuto` 等价；
   手动写的那一槽内容不被 `touchLast` 的写入覆盖。
2. `bootSlot 推导：手动存档后自动存档仍写原槽` —— 复刻 `campaign.html:1124-1128` 的推导：
   自动存槽 1 → 手动存槽 2（`ts=200`）→ `bootSlot` 仍 1 → 再 autosave → 槽 1 变 `ts=300`，
   **槽 2 仍是 200**；把自动档换到槽 5 后 `bootSlot === 5`，槽 2 依旧 200；
   老容器（`last=2` 的历史数据）读回后 `last` 原样保留（兼容代价显式断言）。

`work/saves84/verify_v3.mjs` 第 8 段同样演示这三个事实（PASS 45 / FAIL 0 整脚本）。

## 12. 「SSAV 逐字节仍不做」的理由是否仍成立

**成立，而且本轮让这个结论更硬。** 三条理由逐条复核：

1. **没有样本可对。** `SAVES\` 实测是空目录（`37a:113` 原话：「`SAVES\` 实测为空目录，07 号文档自己
   也没做字节级比对；做「格式还原」没有可对的样本」）。本轮没有新增任何 `.SAV` 样本。
   —— 没有样本的"逐字节兼容"无法验证，等于写一个自认为对的二进制编码器。
2. **上游已经定调。** `31_还原清单.md:49`：「10 槽 + 结构不同（localStorage）· **体验等价，格式不还原**」；
   `44_交接简报.md:62`、`37a:171/214/288`、`66:163/197`、`80:190/390`、`98:208` 全部登记为
   「不做 / 非缺陷」。本轮没有推翻任何一条的依据。
3. **本轮的交付物本来就不是字节。** 任务书要求的是「字段语义对齐 + 最小完整」。
   字节级兼容能带来的**唯一**增量是"把我们的档塞进原版 EXE 能读"——而项目里没有原版 EXE 运行环境
   （`SAVES\` 空），也没有第二个消费者。

**什么情况下这条结论会变**：拿到至少一个真实 `SANGO01.SAV`（哪怕只是原版玩家分享的），
且有人要"用原版读我们的档"。那时该做的是：写 `SSAV` **编码器**（头部 0x1D0 + 七段定长数组，
用 `04c`/`07b` 的偏移表），并用那个样本做逐字节 diff。工作量仍≈16h（`37a:80`），不含本轮的对齐成果。

**本轮真正做掉的部分**（对齐 04/07 的语义，不含字节布局）：
`generalStatus`（+0x0B9）、`weapon`（+0x0C3）、`horse`（+0x0C1）、`thing`（+0x0C5）、
`year`（+0x58）、`yearFlag`（+0x5E）、城 `officers`（+0x028 的派生）、城 `flag`（段1 旗号）。
⇒ 若将来真要写编码器，这 8 个字段**已经有值可取、有 `GENERAL_STATUS_CODE` 可换算**，
不用再从零设计。
