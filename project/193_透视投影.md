## 1 原作证据 → 像素参数

### 1.1 实测是什么

`project/190` §2 在同一排上量相邻两单位的间距（= 1 格），得到「格尺随屏 y 变」：

| 屏 y | px/格 | 备注 |
|---|---|---|
| 94 | **53 ± 5** | battle A 敌弓兵散兵线（n=7，47…57） |
| 124 | 57.6 | |
| 136 | 64.0 | |
| 164.5 | **84.5 ± 8.5** | 主将所在排 |
| 170 | 81 | |

190 给出的闭式拟合是 `pitch_B(y) = 9170/(283 − y)`。

### 1.2 为什么**不**直接用这条闭式

`[确认]` 把 y 代进去对不上：`9170/(283−94) = 48.5`（不是 53），`9170/(283−164.5) = 77.4`（不是 84.5）。190 §2 自己列的拟合点是 y=124/136/170（算得 57.67/62.4/81.2，与实测 57.6/64/81 吻合），**y=94 与 164.5 是外推**，落在外推误差里（48.5 比 53 低 8.5%；77.4 比 84.5 低 8.4%，两者都在 190 §7 声明的 ±10% 带内）。

⇒ 本次**锚定的是 190 首页给的两个实测端点 53 / 84.5**，不是拟合式。这样缩放比 `84.5/53 = 1.5943` 与 190 §0 第 4 条「1.89 = 1.59×透视 + 1.19×行动」里的 1.59 完全一致；如果改用拟合式，比值会变成 77.4/48.5 = 1.596（比值几乎不变，只是整体小 9%）。`[推测]` 想定死绝对 px 只能等原作的视口投影矩阵被定位（190 §7 已登记这个缺口，`project/02_战斗重构设计.md:895` 同样登记）。

### 1.3 这条「53..84.5」落在哪根轴上（建模选择，[推测]）

原作量的是**同一排内、相邻两车道**的水平间距。我们的格阵轴与原作屏幕轴互为转置：`game/src/core/battle.ts:67-88` 里 `x`（0..70）= 纵深 → 屏幕 y，`y`（0..13）= 车道 → 屏幕 x；`game/src/core/battle.ts:3070` 的 `project()` 就是 `sx = y·LANE_PX`、`sy = 550 + (x−camX)·ROW_PX`。

三条理由支持把 53..84.5 当作**纵深轴（行）的格距**：

1. 我们的 `ROW_PX = 71.43` 正落在 53..84.5 的**中段**（53/71.43 = 0.742、84.5/71.43 = 1.183）——这不是巧合，是 `ROW_PX` 本来就是「原作 96 px 格 × 750/1008」的换算，而原作同屏格距在 53..85 之间。
2. 若把 53..84.5 用在**车道轴**上，行距不变 ⇒ 每个兵 sprite 的缩放不变 ⇒ 屏幕上「远排小近排大」根本不出现，与任务要求和原作观感直接冲突。
3. 用纵深轴后 sprite 宽 = 75·s = **55.7 / 72.2 / 88.7 px**（远/中/近），正好把原作的格宽 53..84.5 包在里面 ⇒ 兵的大小量级对上了。

## 2 投影模型：单点函数

文件：`game/src/view/projection.ts`（新建，331 行）。它**只** import `core/battle.ts` 的 `GRID_H/GRID_W/LANE_PX/ROW_PX`，**不** import `layout.ts`（避免与 layout 循环引用）；layout 反过来 import 它并转出 `FIELD_TOP/FIELD_H/FIELD_BOTTOM/FIELD_CENTER_Y` 四个常量，屏幕带只有**一个来源**。

### 2.1 行缩放与屏幕 y

```
r      = gx − camX                                  // 行偏移，负 = 远（敌侧）、正 = 近（我侧）
s(r)   = S0 · e^(k·r)                               // 该行的缩放系数
sy(r)  = 550 + ROW_PX·S0·(e^(k·r) − 1)/k            // 该行的屏幕 y
```

- `S0 = SCALE_CENTER = 0.9625`、`k = ROW_K = 0.03500`，由两端解出：`S0·e^(−k·7.434) = 0.742`（远边正好在 FEILD_TOP）、`S0·e^(+k·5.894) = 1.183`（近边正好在 FIELD_BOTTOM）。代码 `projection.ts:155-160, 210-212`。
- `[确认]` **单调**：`sy'(r) = ROW_PX·S0·e^(k·r) = rowPitch(r) > 0` 恒正 ⇒ 屏幕 y 是行号的严格增函数（测试 4 条里含一条扫 `[floor(farRow)−1, ceil(nearRow)+1]` 全区间、相邻 >40 px）。
- `[确认]` **中线不动**：`r = 0` 时 `sy = 550 = FIELD_TOP + FIELD_H/2 = FIELD_CENTER_Y`，镜头所在行永远在战场正中；`k → 0` 时 `sy → 550 + ROW_PX·r`，**逐字退化成改造前的常数投影** ⇒ 这是旧公式的连续推广，不是换了一套坐标系。
- 逐行格距 `rowPitch(r) = ROW_PX·s(r)`（`projection.ts:190`）：**53.00 / 68.75 / 84.50 px**（远边 / 镜头行 / 近边）——两端就是实测的那两个数。

### 2.2 反解（没有近似）

```
r      = ln(1 + k·(sy − 550)/(ROW_PX·S0)) / k
```

`rowOfScreenY()`（`projection.ts:182`）。测试里 `rowScreenY(rowOfScreenY(y)) === y` 到 1e-9。

### 2.3 横轴：无透视，但格宽随该行等比

```
lanePitch(r)  = LANE_PX · s(r) · LANE_SQUEEZE       // projection.ts:195
sx            = 375 + (gy − 6.5) · lanePitch(r)     // projection.ts:200
rowEdgeX(r,±1)= 375 ± 7.0 · lanePitch(r)            // projection.ts:205（含最外半格）
```

- `[确认]` 横轴保持**线性**（车道 0..13 等序、等距），只是该行的格宽乘上同一个 `s(r)` ⇒ 远排车道被「挤窄」，屏幕上车道线向上收敛成梯形（截图里看得很清楚）。
- `LANE_SQUEEZE = 750/(14·LANE_PX·SCALE_NEAR) = 0.8453`（`projection.ts:165`）：让**最近一排**的 14 条车道（含两侧半格）正好铺满 750，于是**任何一行都不会横向裁边**，同时最宽的一排也不留空边。
- 代价（`[确认]`，写在这里免得以后有人当成 bug）：镜头行的车道距从 53.57 变成 **43.59**（×0.8137），远边 33.60、近边 53.57。也就是说整块战场在横向上比改造前**窄**了约 19%，换来的是透视梯形 + 全列可见。

### 2.4 可见行数 + 自适应保险丝

- 远端可见行数 `ROWS_FAR = 7.434`、近端 `ROWS_NEAR = 5.894`、合计 `ROWS_VISIBLE = 13.327`（`projection.ts:210-212`）。
- 为什么不对称：`sy` 是指数，**近端同样多一行要更多像素**。固定「镜头行在正中（450 px 一半）」后，远半能塞 7.43 行、近半只能塞 5.89 行。这是指数透视 + 中心锚定的必然结果，不是参数没调好。
- 保险丝 `fitNearScale(sFar, sNear, ROWS_MIN=8, ROWS_MAX=14)`（`projection.ts:124`）：可见行数越界就二分 `sNear` 把它拉回 `[8,14]`。本次 `13.327 ∈ [8,14]`，**没触发**（`SCALE_NEAR_FITTED = false`）。
- `[确认]` 和改造前比：**12.60 → 13.33 行**（旧 = `FIELD_H/ROW_PX = 900/71.43`）。多出 0.73 行，视野比原来略大；但**近端从 6.30 行缩到 5.89 行**（少 0.41 行，即我方最后一排更容易掉出下沿），远端从 6.30 涨到 7.43 行。

## 4 命中测试与半径折算

- `[确认]` `hitTest` 走 `screenToUnit`，它是 `projectUnit` 的**精确反解**（不是近似）⇒ 「点到哪一格」与「那一格画在哪」严格互逆。测试 `hitTest 与 buildFrame 同源` + `round-trip`（4 个 camX × 可见行 × 14 车道，全部回到原格）。
- `[确认]` `screenToUnit` 的 `gy` 用 `Math.floor(worldY + 1e-6)`：车道中心点回代时会得到 5.9999999 这种值，不补 epsilon 会掉到上一条车道。
- `[确认]` 技能瞄准圈（`drawAim`）与特效兜底圈（`drawFx`）不再用常数 `r·LANE_PX / r·ROW_PX`，改成「按该点所在行，r 条车道 / r 行实际占多少像素」：
  - 水平半径 `= r · lanePitch(dr)`；
  - 垂直半径 `= (rowScreenY(dr + r) − rowScreenY(dr − r)) / 2`（即 r 行在屏幕上的真实半跨）；镜头行处 r=1 时 ≈ 43.6 × 68.8 px（旧值 53.6 × 71.4）。
- `[确认]` 单位本身**没有命中半径**（旧 `hitTest` 也只返回格），所以「命中半径怎么折算」这一条落到的就是上面两个圈 + 格反解。
