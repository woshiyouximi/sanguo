## 3. 数据流
```
data/*.json
   │  web: fetch + JSON.parse          cocos: resources.load(JsonAsset)
   ▼
GameData（types.ts：troops/formations/magics/wises/generals/terrains/items/scenarios）
   │  createWorld({data, seed, a, b, aiSides})     ← 唯一入口
   ▼
World（tick / units / sides / fx / rng / stats / over / settled）
   │  step(world) ×30/s；cast(world, side, seq, tx, ty)
   │  settle(world) 只由壳在 over 后调用一次
   ▼
视图读取 World
   ├─ Canvas2D：buildFrame(world, opts) → DrawCmd[] → render(ctx, …)
   └─ Cocos：BattleRoot.update() → Graphics.rect/line/circle + Label.string
```

关键边界：

- `data.ts` 用 `node:fs`，**只给 Node 测试/脚本用**。浏览器和 Cocos 各自加载 JSON，
  不 import `data.ts`。这不是重复，是两个运行时的 loader。
- `view/` 不 import `cc`，也不 import `data.ts`；它只认 `World` 和 `GameData` 的
  `magics` 表（技能名/MP）。这样同一份 `theme/layout` 能被 Cocos 直接复制。
- `World` 是唯一状态源：Canvas2D 不缓存单位位置，Cocos 也不缓存；两边每帧都从
  `world.units` 重新算。避免「视图状态与逻辑状态不同步」这一类最难查的 bug。

### 3.1 数据加载的差异
| 运行时 | 入口 | 路径 | 备注 |
| --- | --- | --- | --- |
| Node 测试 | `src/data.ts` | `node:fs` + `data/*.json` | 同步、无缓存 |
| 浏览器预览 | `web/main.js` | `fetch('../data/x.json')` | 8 张 core 表；`cache: 'no-cache'` |
| Cocos | `DataLoader.ts` | `resources.load('data/x', JsonAsset)` | 不带 `.json` 后缀；模块级 Promise 缓存 |

浏览器只加载 8 张（troops/formations/magics/wises/generals/terrains/items/scenarios），
`fonts/meta/sango_system/things/things_define` 留给图鉴/UI 按需加载。
Cocos 的 `resources/data/` 放了 13 张，`DataLoader.CORE_DATA_FILES` 仍只拉 8 张。

## 4. 坐标与投影：以 core 为准
### 4.1 逻辑坐标
- `worldX ∈ [0, 70]`：推进轴，71 格。A 方（我方）从大到小打，B 方（敌方）从小到大打。
- `worldY ∈ [0, 13]`：14 条车道，跨车道不镜像。
- 网格 71×14 是原作横屏口径，竖屏只做投影，**逻辑坐标一个都不改**
  （依据：project/02 §2.1、PROJECT_BRIEF §6）。

### 4.2 投影公式
core 的实现（`battle.ts` 的 `project`）：

```ts
sx = y * LANE_PX + LANE_PX / 2;          // LANE_PX = 750/14 ≈ 53.57
sy = 550 + (x - camX) * ROW_PX;          // ROW_PX = 96 * (750/1008) ≈ 71.43
```

`layout.project()` 只是包了一层，返回 `{x, y}`，不重新实现公式。

### 4.3 一个必须记录的口径冲突
`02_战斗重构设计.md` 的文字公式写的是：

```
screenY = 1000 - (worldX - camX) * s
```

这个公式假设「我方在 worldX≈0，敌方在 worldX≈70」，即 worldX 越大越靠画面上方。
但 core 的实际布阵是：

```ts
gx = side === 'A' ? GRID_W - 1 - … : …;   // A 在高位
```

配合 `sy = 550 + (x - camX) * ROW_PX`，得到 **worldX 越大 → sy 越大 → 越靠画面下**。
测试 `tests/battle.test.ts` 第 108 行也钉死了这一点：

```ts
assert.ok(far.sy > near.sy, 'worldX 越大越靠画面下');
```

结论：**视图层以 core 为准，A 侧恒在下、B 侧恒在上**；02 文档的文字公式当作
「意图描述」，不当作实现公式。不改 core、不改测试、不在视图层反向补偿。
（依据：project/02 §2.2 + core 实现；冲突处理为新设计）

### 4.4 可见范围与镜头
- 战场带 750×900，`FIELD_TOP=100`，`FIELD_BOTTOM=1000`，`FIELD_CENTER_Y=550`。
- 一屏可见 `900 / 71.43 ≈ 12.6` 行；14 条车道横向铺满 750。
- `camera(world)`：双方有兵时取 `(aMin + bMax)/2`，夹在 `[half, GRID_W-1-half]`，
  `half = 450 / ROW_PX ≈ 6.3`，所以 `camX ∈ [6.3, 63.7]`。
- 壳层对 `camX` 做 `lerp(5 * dt)`，避免镜头瞬移；逻辑推进不受影响。

## 6. 固定步长循环
逻辑 30Hz（`TICK_HZ=30`，依据：project/02 §6），渲染跟随 `requestAnimationFrame`（通常 60Hz）。
两者解耦，渲染帧率变化不改变战斗结果。

### 6.1 伪代码（web/main.js 与 BattleRoot.update 同构）
```text
acc = 0
last = now()

每帧(now):
  dt = clamp(now - last, 0, 0.08)     // 切后台/首帧防跳变
  last = now
  if mode == fighting:
    acc += dt
    steps = 0
    while acc >= 1/30 and steps < 5:
      step(world)                      // core 内部已包含 tickSkills
      tickFloaters()
      acc -= 1/30
      steps += 1
      if world.over: break
    if steps == 5: acc = 0            // 掉帧不追命：宁可慢放
    if world.over: endBattle()        // settle 只调一次（幂等）
  camX += (camera(world) - camX) * min(1, 5*dt)
  render/buildFrame
```

要点：

- **最多补 5 tick**（新设计）：100ms 的卡顿最多补 5 帧（166ms 逻辑），再多的积压直接丢弃。
  这保证低端机不会「越卡越补、越补越卡」。
- `step()` 内部已经调用 `tickSkills()`（气力回复、AI 放技、fx ttl--），壳层不要
  再调一次，否则气力/AI 会双倍推进。
- `settle()` 幂等：`world.settled` 存在就直接返回；壳层即使重复调用也不会重复
  加经验/战绩。
- 固定步长让「同 seed 同结果」在浏览器里也成立；`smoke.mjs` 用真数据跑过
  `render` 全链路，没有依赖真实时间。

### 6.2 时间轴
| 阶段 | 触发 | 逻辑 |
| --- | --- | --- |
| ready | 数据加载完，未开战 | 不 step；显示配置/开战遮罩 |
| fighting | 点「開戰」/空格 | 每帧固定步长；技能可点 |
| settled | `world.over` 后 | 调一次 `settle`；停 step；显示结算卡片 |
| restart | 点「再戰」/R | 用同一配置新建 World；`settle` 结果丢弃 |

## 7. 视图层 API（Canvas2D 参考实现）
### 7.1 DrawCmd
`buildFrame()` 不直接画，而是返回一个可序列化的指令数组（新设计），方便：

- 用 mock Canvas2D 在 Node 里做冒烟测试；
- 以后换 Cocos/WebGL 时，按指令翻译而不是重写布局；
- 统计指令数量，做性能预算。

指令联合：

| kind | 字段 | 用途 |
| --- | --- | --- |
| `rect` | x,y,w,h,fill,stroke,width,radius,alpha | 面板、血条、单位方块、按钮 |
| `line` | x1,y1,x2,y2,stroke,width,dash | 网格、分隔线 |
| `poly` | points,fill,stroke,width,close | 朝向缺口、将徽菱形、箭头 |
| `ellipse` | x,y,rx,ry,fill,stroke,width,dash | 技能环、AOE 范围 |
| `text` | x,y,text,size,color,align,baseline,stroke,maxWidth,bold | 所有文字 |

`render(ctx, world, opts)` 是唯一 Canvas2D 入口：清屏 → 按顺序执行指令 →
`save/restore` 包住每个 text/line/poly，避免状态泄漏。

### 7.2 ViewOptions
`ViewOptions` 包含 `camX/time/skills/selectedSkill/aim/floaters/message/mode/settlement/seed/aLabel/bLabel`，全部可选；`buildFrame()` 不修改 World 与 opts，`hitTest()` 只读。因此可以每帧重复调用，不会产生隐藏状态。

### 7.3 命中区
`hitTest(world, opts, sx, sy)` 返回：

- `start`：ready 遮罩的「開戰」按钮；
- `restart`：settled 遮罩的「再戰」；
- `skill`：控制台技能格（带 index）；
- `field`：战场内，带 `{gx, gy, worldX, worldY}`；
- `assault` / `retreat`：按钮（当前只提示未接）。

所有命中都用 `layout.ts` 的矩形，不在 `main.js` 里硬编码坐标。

### 7.4 单位与朝向
- 普通兵：18×26 的方块，顶部亮条；朝向缺口用三角形表示。
- 主将：30×38 的方块 + 金色菱形将徽 + 名字 + HP 条。
- A 方缺口朝上（屏幕上方是敌方），B 方朝下。这个方向由 `u.side` 决定，
  与 core 的 `gx` 布阵方向一致，不依赖 camera。
- 主将塞在 `world.units` 里，类型上是 `Unit & {isGeneral: true}`；`Unit.isGeneral`
  的声明是 `false`，所以视图层用
  `(u as unknown as {isGeneral?: boolean}).isGeneral === true` 判断。

### 7.5 飄字与技能环
- `pushFloater()` / `tickFloaters()` 是视图层的小型对象池替代：数组 + ttl，
  不进入 World，不参与逻辑。
- `drawFx()` 读 `world.fx`：非 heal 直接按 `(fx.x, fx.y)` 画椭圆；
  **heal 特判到主将位置**，因为 core 现在把 `x` 填成了 `g.hp`（见 §12）。
- 技能环（aim）只在 `selectedSkill !== null && aim !== null` 时画，
  半径按技能类型：单体 0.9 行、群体 2.2 行、治疗 0（直接放）。

  （依据：project/03 深色底 + 双阵营色）。

## 9. Cocos 实现
### 9.1 结构
`BattleRoot.ts` 是唯一挂载点：

- `onLoad()` 创建 5 个 `Graphics` 节点（base / A / B / general / fx）和 5 个 `Label`（A/B 兵力、计时、主将、状态）；
- `start()` 加载数据 → `createWorld` → 进入 fighting；
- `update(dt)` 按 §6 的固定步长推进，`world.over` 后调一次 `settle`；
- 每帧 `redraw()`：网格、单位、主将、FX、HUD 文字；
- 点击画面：结算后重开；未开战时开战。

### 9.2 为什么用 5 个 Graphics
Cocos 的 `Graphics` 是 immediate-mode 的路径 API。把「背景/网格」「A 方单位」
「B 方单位」「主将将徽」「FX」拆成 5 个组件（新设计），是为了：

- 每种颜色只 `fill()` 一次，减少路径状态切换；
- 单位层和 HUD 层天然分层，不用手工算 z；
- 以后把 A/B 方换成 `Sprite` 图集时，只替换 `drawUnits()` 的两个 Graphics 节点。

### 9.3 坐标翻转
`layout.ts` 是「左上原点、y 向下」；Cocos UI 是「中心原点、y 向上」。
`BattleRoot.fillScreenRect()` 统一做：

```ts
g.rect(x - 375, 667 - y - h, w, h);
```

新增绘制必须复用它，不要混用两套坐标。`project()` 返回的屏幕坐标也要先
`x-375 / 667-y` 再进 Graphics。

### 9.4 与 core 的同步
Cocos 里的 `assets/scripts/core/battle.ts` 是 `game/src/core/battle.ts` 的副本，
只改了两处 import 后缀（`.ts` → 无后缀，新设计）。同步流程：

1. 改 `game/src/core/battle.ts`（并跑 15 项测试）；
2. 复制到 `cocos/assets/scripts/core/battle.ts`；
3. 把 `from '../types.ts'` 改回 `from '../types'`；
4. 把 `layout.ts` 的 `'../core/battle.ts'` 改成 `'../core/battle'`。

没有第二套逻辑，也没有「Cocos 特供版」的规则分支。

## 10. 两套实现的差异表
| 维度 | Canvas2D 预览（web/） | Cocos（cocos/） |
| --- | --- | --- |
| 入口 | `main.js` + `render(ctx,…)` | `BattleRoot.update()` |
| 绘制 | Canvas2D 路径/文字 | `Graphics` 路径 + `Label` |
| 坐标 | 左上原点，y 向下 | 中心原点，y 向上（手动翻） |
| 文字 | `ctx.fillText` + 系统字体 | `Label` + `fontFamily` |
| 图集 | 无（纯矢量） | 预留 `Sprite`/`SpriteFrame` |
| Spine | 无 | 预留 `sp.Skeleton` |
| 数据 | `fetch` 8 JSON | `resources.load` 8 JSON |
| 固定步长 | `while(acc>=1/30)`，最多 5 | 同上 |
| 相机 | `camera()` + lerp | 同上 |
| 交互 | `hitTest` + 指针/键盘 | 全局 `input` 点击（骨架） |

### 12.5 这一轮踩的三个坑（都会让截图"看起来坏了"）
1. **`?sim` 没配 `?freeze`**：rAF 继续推进，截图时兵力已变，数字对不上。
2. **冻结时镜头不硬切**：`camX` 只在 `frame()` 里平滑跟随，`freeze` 跳过 `frame()` →
   镜头停在开局位置，单位全部被视锥裁掉，画面**全空**（曾误判为渲染崩了）。

3. **`?sim` 之外还要 `--virtual-time-budget`**：Edge headless 默认在首帧后立刻截图，

1. **heal fx 的坐标是 HP**：`cast()` 里 `fx.push({x: g.hp, y: 0, …})`，

2. **`Unit.isGeneral` 类型是 `false`**：主将实际以 `Unit & {isGeneral:true}` 塞入
   `units`，直接读 `u.isGeneral` 会被 TS 认为永远 false；两套视图都用
   `as unknown as {isGeneral?:boolean}` 判断。
3. **`cast()` 先判 MP 再判气力**：MP 不足时不会扣气力。视图的
   `castBlockReason()` 必须同序，否则按钮提示会与 core 结果不一致。
4. **`settle()` 对「未结束的世界」也会给结果**：强行 `endBattle()` 会得到

### 17.1 顺手修掉的一个真 bug（人数对不上）
`formationCells()` 只在 `fill` 里查 `"10"/"50"/"100"/"200"` 四档，查不到就**退回 100 人**，

### 19.2 AI 出兵规则

每月末（`推进一月` 或 `?adv=N` 的每一轮）跑一次 `rollAI()`：

| 项 | 规则 | 依据 |
| --- | --- | --- |
| 谁可以出兵 | 敌方城，且与至少一座我方城**相邻**（`adj` 图，77 条可走路径；39 条哨兵不算连通） | §15.3 |
| 打哪座 | 相邻我方城里**守军最少**的那座；同兵时按城名 `localeCompare`，保证 `?seed=` 可复现 | 本轮 |
| 兵力门槛 | `敌兵 ≥ 守军 + 30`，不够就完全不出兵（连掷骰都不掷） | 本轮 |
| 出兵概率 | `p = min(0.6, (敌 − 我) / 200)`；差 120 兵封顶 60%，只多 30 兵约 15% | 本轮 |
| 每月上限 | **1 次**：候选按 `p` 降序逐个 `Math.random() < p`，第一个成功的就是本月唯一进攻 | 本轮 |
| 随机源 | 正式流程 `Math.random`；`?seed=N` 换成 `mulberry32(N)`，用于截图/回归 | 本轮 |
| 敌城成长 | 每轮所有敌城 `troops = min(600, troops + 6)`（原有逻辑，勿删：它决定“第几个月开始有威胁”） | §15.3 |
| 记录 | `pushLog({t,s,k})` 写进 `save.log`，只保留最近 8 条 | 本轮 |

```text
aiCandidates():
  for 每座敌城 c:
    nb = adj[c] 里属于我方的城
    if nb 为空: 跳过
    to = nb 里守军最少的（并列按名字）
    if c.troops < troopsOf(to) + 30: 跳过
    p = min(0.6, (c.troops - troopsOf(to)) / 200)
  按 p 降序（并列比兵力差，再并列比城名）返回
rollAI(force): 按上面顺序逐个掷骰，命中即返回（force=1 时跳过掷骰）
```

**首月为什么没人来打**：三座开局城 `襄平 141 / 北平 145 / 代县 178` 兵，能摸到它们的敌城只有
`易京 110`（pop 0）和 `晋阳 145`。门槛是 `+30`、敌城每月 `+6`，于是：

| 月份 | 易京兵 | 够打北平（≥175） | 晋阳兵 | 够打代县（≥208） |
| --- | --- | --- | --- | --- |
| 第 5 月 | 140 | 否 | 175 | 否 |
| 第 10 月 | 170 | 否 | 205 | 否 |
| **第 11 月** | **176** | **是**（p = 15.5%） | **211** | **是**（p = 16.5%） |

也就是说**开局 10 个月是安全期**，第一次“敵軍來攻”最早出现在第 11～12 月。这是
`+30 门槛 + 每月 +6` 共同决定的节奏，改任一参数都会改变开局难度（见 §19.8）。

| `?sel=<城>` | 预选城池（截图用） |
| `defend=1&city=…`（`index.html`） | 守城战模式 |
| `?sim=N&freeze=1&end=1`（`index.html`） | 无头跑 N tick 后强制结算并冻结镜头（§12.5） |

`?seed=1` 是挑出来的可复现种子：第 11 个月第一次掷骰 0.627（晋阳错过）、第二次 0.003（易京命中），
所以 `campaign.html?adv=12&seed=1` 一定在 1 年 12 月出现一次“易京 → 北平”。

### 19.8 已知未做 / 已知问题

- **AI 没有行军过程**：相邻即出兵，没有部队在路上的概念，也就没有“半路拦截”。
- **AI 不记事**：同一座城可以每月来一次，不会因为上次被打退而收敛；也没有难度分级。
- **批量判定与真打不是同一套规则**：`resolveDefense()` 是近似式，只用于 `?adv=N` 长跑；
  真打的胜负完全由 core 决定。
- **敌军主将属性是代理值**：`bstr = 50 + DEFENSE/8`，不是城池实际驻将的武力；
  守城方 `gen` 用真实驻将，两边不对称。
- **平手按失守处理**：`settle()` 对未结束的世界也返回 `draw`（§12.2），此时无法判定城市归属，
  取保守解。
- **敌城线性成长**：每月 +6、上限 600，后期会把玩家压死（实测第 3 年即丢城），
  需要难度曲线时改这里（§19.2 的参数表）。
- **结算面板不加按钮**：`SETTLE_PANEL` 在 core 的 view 里是固定布局，本轮只在空档 `y=762` 加了一行横幅；
  要加“撤退/求和”按钮得改 `src/view/`（本轮禁止）。
