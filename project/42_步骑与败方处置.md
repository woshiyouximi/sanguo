## 一、R22 的"骑兵"到底是不是独立兵种：选 (a)

**结论：(a) 骑兵是独立的兵种池（同 13 类兵种属性的骑乘版），由升级从步兵转入；不是"马只是造型"。**

四条依据（互相独立）：
1. **两栏独立上限**：`general+0x42` 带兵上限 `min(level*5,100)`（`0x409FB6`）、`general+0x46` 骑兵上限
   `clamp((level-20)*5,0,100)`（`0x409FD8`）。造型不需要第二个上限，更不需要 20 级门槛。
2. **升级迁移文本**：`0x40F23C` 的升级提示分档——≤20 级「最大帶兵數增加5人」、21..40 级
   「**有5名士兵升為騎兵**」。有"迁移"就说明存在两个可加的池子。
3. **溢出转骑**：`if (rec->+0x44 > rec->+0x42) rec->+0x48 += rec->+0x44 - rec->+0x42;`
   步兵栏溢出会灌进骑兵栏，两个计数是同一批士兵的两种编制。
4. **独立美术物件**：`THINGS.INI` 里 13 个基准兵种全部有骑乘版（蓝军 140–152、红军 160–172，
   目录名「兵种·蓝军骑兵」），另有 12 个「戰馬」物件；`05b` 的兵种文件名 `{M|N}{兵种}{H=骑乘}{动作}{1}{帧}`
   也把 `H` 当骑乘标记。

否掉 (b) 的理由：美术层只能解释"看起来有马"，解释不了**独立计数**（+0x46）、**独立上限**、
**升级时的 5 人迁移**和**战功分 ×12 的权重**；`docs/04b` 里的争议按 §2.4 + §6.7 取上述解释。
（`docs/**` 本轮禁改，争议只在本文件记录，不改原文档。）

### 实现
- `Unit.kind?: 'infantry' | 'cavalry'`（battle.ts:113）。**只贴标签**：落位/移动/命中/伤害/仇恨一行没动，
  `kind` 只被"战功分"和"统计"读。测试 `stepcav.test.ts` 用同 seed 的两个世界（25 骑 vs 0 骑）
  逐单位比坐标、跑 300 tick 比 attacks/hits/blocks/aliveCount，全部逐位相同。
- `SideConfig.cavalry?`（缺省 `min(soldiers, cavalryCapOf(level))`）、`cavalryCapOf(level)`
  （battle.ts:462，`clamp((level-20)*5,0,100)`）；`createWorld` 把**最后 N 个**士兵单位标成骑兵
  （阵形格子顺序不变，所以坐标与改前完全一致）。
- `World.stats`：`killsInf/killsCav`（A 杀 B 的步/骑）+ `killsInfB/killsCavB`（B 杀 A），
  由 `recompute()` 数场上 `alive=false` 的兵（法术击杀也走同一路径），恒有
  `killsInf+killsCav === B.start-B.aliveCount`。
- `settle()`：`scW = 步兵击杀×6 + 骑兵击杀×12`，`scL` 用 B 侧同式（battle.ts:1054-1055）；
  四档加成原样保留（歼灭 ×51、击退 ×34、平手/大胜 ×17、大胜再 ×2），`SettleResult` 多带
  `killsInf/killsCav` 给面板。
- 面板 `battleView.ts:1343-1344`：`步兵擊殺 N 人 × 6` / `騎兵擊殺 N 人 × 12` 两行；10 行行距 34→30。

## 二、R54 败方全员逐个处置

`docs/04b2 §2.4` 的 `0x40452E(winner, loser, verbose)` 逐条映射到 `resolvePostBattle`：

| 原作 | 本实现 |
|---|---|
| `for (i<loser->count) if (status != 3) continue` | `for (const raw of roster)`，`alive === false` 的跳过（= 没被俘） |
| 君主被俘 → status 5 斩 | 未单独落地（见"只能近似"3） |
| `0x40ED3A` 逃脱掷骰 → status 7 | 未单独落地（并入被俘掷骰） |
| `0x404344` 成功 → status 6「投靠敵軍」 | `canRecruit`（含 R53 三条硬门）→ `captures`，`recruited=true` |
| 失败 `rand()%100 < 0x32` → status 5 斩 | `Math.floor(rng()*100) < 50` → `executed` |
| 否则 status 2 安全归来 | 否则 → `released` |
| 逐人弹菜单（`0x44E8FD`） | 一次算完，面板把三类各列 3 条 + 「另有 N 人」 |

- 名单 = 主将 + `SideConfig.officers`（副将**不上场**，只进战后处置）；`PostBattleSideView.officers`
  从 world 带进 capture。`officers` 的 `alive` 缺省归一化成 `true`。
- **rng 消耗顺序**（现有 `capture.test.ts` ④⑤ 依赖它）：每个将 = 被俘掷骰 → 招降掷骰（0/1/2 次，
  忠诚 >90/70/50 的硬门 0 次）→ 斩首掷骰；单人局（无 officers）与旧版逐字一致。
- `expBonus/meritBonus` 按人累加：归顺 `等级×16 / +15`，斩首 `等级×32 / +10`，释放 `0 / 0`。
- 面板：`招降 A、B、C 另有 N 人`（每人带忠诚值）、`斩首 N 人 · 名单`、`释放 N 人 · 名单`、`获得物品`。

## 三、格挡精确计数

- `World.stats.blocks`：只在"**未命中**（`roll >= power`）**且双方都是士兵**"时 +1（battle.ts:667）。
  主将互砍的闪避、以及将打兵/兵打将的未命中都不计——这正是 `attacks-hits` 代理多算的部分。
- `main.js` 只改一处判断：`statMark` 去掉 `attacksA/B`、加 `blocks`；`tickBattleSfx` 里
  `blocks = s.blocks - statMark.blocks`，`blocks > 0` 才播 `defense`。节流结构原样（每 tick ≤2 声、同名声 60ms）。
- 音频 HUD（`?sfxdbg=1`）显示的是**节流后实际播放次数**，所以 `defense×N ≤ blocks`；
  截图 `work/br_blocks.png` 里 blocks=206、defense×152、旧代理 attacks−hits=222。

## 四、只能近似的地方
1. **R59 的"带兵差"没做**：原作 `scW = (unitL->+0x14 − gL->+0x44)*6 + (unitL->+0x18 − gL->+0x48)*12`
   是"敌方开场带兵 − 敌将当前带兵栏"；本作武将与军队不共享带兵字段，改用**本场阵亡数**，
   语义近似（满编对满编时两者相等）。R59 仍记 🟡。
2. **骑兵不落库**：`general+0x46` 在本作没有对应字段，骑兵数每局按等级现算；
   升级提示「有5名士兵升為騎兵」的**迁移**未实现（升级不改骑兵栏，只影响下一局的开场编制）。
3. **R54 少了两道前置**：原作君主被俘直接斩（status 5）、`0x40ED3A` 另有逃脱掷骰；
   本作 `PostGeneral` 没有 `isKing`/逃脱字段，君主保护只体现在 `canRecruit`（挡招降、不挡被俘）。
4. **R54 不是逐人菜单**：原作玩家对每个被俘者选 招降/斩首/释放（`0x44E8FD` 循环），
   本作一次性判定后只做展示；想逐人交互要改 view 层（本轮禁改）。
5. **格挡的定义是近似**：原作 `$Defense` 的触发点未定位（37c 只追到 `THINGS.INI` 的 Defense 序列），
   本作以"兵对兵近战砍空"为格挡；本引擎没有远程弹道，因此不存在"射空"这一独立来源。
