### 1.2 字段偏移（引擎侧，引自 `project/133_原作数值真值.md` §3）

| 含义 | 指令 | 说明 |
|---|---|---|
| `BaseEXP` → `gen+0x2A` | `0x42D38B mov dword ptr [ecx+0x2a],eax` | 装载 TIMES 记录时写入 |
| 等级 = `level_of(gen->exp)` | `0x42D391 push edx ; call 0x409F73` | **就这一句决定等级** |
| 等级 → `gen+0x2E` | `0x42D39D mov word ptr [ecx+0x2e],ax` | 随后 `0x42D3A5 call 0x40A020` 用等级重算 HP |

```
0x409EE0(k):  k > 99 ? 0x98967F : ((k−1)×0x89 − 0x22) × k / 2 + 0x11     ; C 向零截断
           =  k > 99 ? 9999999  : ((k−1)×137 − 34) × k / 2 + 17
0x409F73(gen): for (i = 0; i < 99; i++) if (gen->exp[+0x2A] < 0x409EE0(i)) return i − 1;
               return 99;
```

⇒ **起始等级 = level_of(BaseEXP)**，与 STR/INT 无关，也与存档里的 `+0x2E` 缓存无关。
本仓 `game/src/core/battle.ts:2163 expToReach()` / `:2168 levelFromExp()` 与上面两式**逐字一致**，
本次校验脚本里又独立实现了一遍（`verify_table.mjs` 第 4.5 项：直接回读 `battle.ts` 原文用正则确认同式）。

## 2. 抽取方法

脚本：`F:\sanguo\work\scen_levels\extract.py`（Python，显式 `encoding='utf-8'`；`$env:PYTHONIOENCODING='utf-8'`）。

1. **逐剧本顺序解析原始 INI**：以 `[` 开头的行切段，遍历 401 个 `[GENERAL]` 段，取
   `NAME` / `BaseEXP` / `POS` / `CITY` / `Status`。`[SYSTEM]` 段取 `TIME` / `YEAR`。
2. **与项目数据对齐**：读 `game/data/scenarios.json`（5 条，`id` / `system.TIME` / `system.YEAR` / `file`），
   逐条断言剧本名一致（5/5 通过）。
3. **两路互证**：把原始 INI 的 `NAME + BaseEXP` 与 `extract/json/timesN.json` 的 `name + base_exp`
   逐将比对，**401/401 完全一致**（5 个文件都通过，否则脚本 `assert` 退出）。
4. **名字对齐 `generals.json`**：断言 `NAME` 集合相同 **且顺序相同**（与 `tools/import_legacy.py:311-330`
   按 `gi` 索引对齐 5 个剧本的既有假设一致）；不一致数 → 0 则继续。
5. **登场判定**：`Status != '未'` 为「该剧本登场」；脚本同时校验它等价于 `CITY != ''`，
   并校验 `POS` 的第 i 个槽位（POS 是 5 个剧本的城池槽位串，例如丁奉 `未 未 未 廬江 江夏`）
   与 `Status` 不矛盾——**5 个文件 × 401 行，矛盾数全部为 0**。
6. **算等级**：用原作 `0x409EE0` / `0x409F73` 实现（与 `battle.ts` 同式），并对每条断言
   「C 向零截断版」与「JS/TS 版」结果一致（不一致只允许 `baseExp == 0` 的边界，本次数据无此情况）。
7. **写出**：外壳 `indent=2`、**`levels` 里每个武将独占一行**（git diff 能按将看），写完后回读比对内存对象。

## 6. 表结构

```jsonc
{
  "schema": 1,
  "source": "TIMES",
  "sourceFiles": ["extract/pak/TIMES1.INI", ...],
  "expToLevel": "0x409EE0",         // 门槛表
  "levelFromExp": "0x409F73",       // 反推函数
  "loader": "0x42D38B (BaseEXP -> gen+0x2A) / 0x42D391 call 0x409F73 / 0x42D39D (level -> gen+0x2E)",
  "formula": "expToReach(k) = ... ; level = max{n | exp >= expToReach(n)}",
  "format": "……人话说明……",
  "generatedBy": "work/scen_levels/extract.py",
  "scenarios": [
    {
      "index": 0,                    // 0-based，等于 scenarios.json 的下标
      "id": 1,                       // scenarios.json 的 id（1..5）
      "name": "黃巾之亂",             // 与 scenarios.json 的 system.TIME 相同
      "year": 184,
      "file": "TIMES1.INI",
      "baseExpCommon": 200,          // 该剧本 400 将统一的 BaseEXP
      "defaultLevel": 2,             // 由 baseExpCommon 反推
      "counts": { "total": 401, "deployed": 142, "absent": 259, "missing": 0 },
      "levelHistogram": { "2": 142 },        // 只统计 deployed=true
      "absentLevelHistogram": { "2": 258, "12": 1 },
      "levels": {
        "盜賊": { "baseExp": 9999, "level": 12, "deployed": false },
        "丁奉": { "baseExp": 200, "level": 2, "deployed": false },
        "關羽": { "baseExp": 200, "level": 2, "deployed": true }
      }
    }
  ]
}
```

- `levels` 的 key 是**中文名，与 `game/data/generals.json` 的 `NAME` 逐字相同**，401 个名字都已核对。
- 每个剧本的 `levels` 都覆盖 **401 个将**（`counts.total = 401`），不是只覆盖登场的 142/189/…；
  这样消费方既能「按名查该剧本的起始等级」，也能「判断这个剧本里到底有没有这个人」。

- `missing: 0` 是显式字段：**没有任何一个剧本 × 武将是「抽不到数据」的**，因此表里没有 `null` 值。

## 7. 观察与推论

1. `[确认]` **原作根本没有「按 STR+INT 算起始等级」的东西**：`gen+0x2E` 的写入点全 `.text` 只有 3 条
   （升级 `0x40F281`、装载 TIMES `0x42D39D`、读档 `0x4330DA`），开局这条就是「`BaseEXP` → `0x409F73` → `0x2E`」。
2. `[确认]` **剧本级等级是数据集里的常量**：5 个文件各自只有一个非 9999 的 `BaseEXP` 值，
   所以 2/2/4/6/8 这五个数**不是**从 401 个样本统计出来的，而是「文件常量 + 门槛表」的确定结果。
   换句话说，本表的 2005 行在信息量上可以压缩成 5 行；保留逐将形式是为了让消费方按名 join，不必假设「同级」。
3. `[确认]` **盜賊 是五个剧本里唯一的 `Status=未` 之外的特例说明**：它 `BaseEXP=9999` → Lv12，
   但 `Status=未` + `CITY=''` **五个剧本都不登场**，等级 12 只在引擎里算出来、不会出现在地图上。
4. `[确认]` **「0 城势力」只有 盜賊 一个**，而且它就是 `[KING]` 列表的最后一项
   （TIMES1 的 15 个君主里 14 个有城，`盜賊` 0 城；TIMES2 的 19 个里 18 个有城，同理）。
   它的「武将行」就是 `[GENERAL]` 的第一条（`NAME=盜賊`, `TYPE=30`, 全属性 99）——表里已覆盖
   （`baseExp 9999 / level 12 / deployed:false`）。**不存在「有武将但一座城都没有」的君主**，
   所以没有「因 0 城而定位不到武将」的漏抽。另外各剧本有 27 / 33 / 24 / 25 / 19 座城的 `KING` 字段为空
   （无主城），但那些城里的武将 `CITY` 照样非空，判定不受影响。
5. `[推测]` `Status` 三值的语义：`登` = 仕官于该城势力、`野` = 在野（可招募）。
   依据是：`登` 的将 **100%** 落在有主之城里（79/114/154/179/192 全数），
   而 `野` 有一小部分落在无主城（22/25/10/14/4 座）。这是从数据分布反推的，
   **没有**去反汇编「登用/在野」相关代码，所以标 `[推测]`。
   对本表无影响：两者都算登场。
6. `[推测]` 数据小瑕疵：TIMES1 有 12 座城的 `KING` 字段写成裸数字 `1`..`12`（不是人名），
   疑为原作填表残留；与本表无关（本表不读 `KING`），仅记录于此。
7. `[确认]` `game/data/generals.json` 的 `pos_by_times` 是 import 时的缺陷（把整个 5 槽位 `POS` 串复制 5 份），
   **不可用于分剧本**；`city_by_times` / `status_by_times` 才是逐剧本真值，且与 5 个 TIMES 文件一致。
   本表**没有**用 `pos_by_times`。
