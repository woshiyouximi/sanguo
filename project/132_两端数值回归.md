# 132 · 两端数值一致性回归（web ↔ Cocos）

> 目标：同一存档 / 同一随机种子下，Cocos 版与 web 版跑出**完全相同**的数值。
> 用户定调「最后以 Cocos 验收」⇒ 只要两端数值有分歧，Cocos 验收就不成立。
>
> 本文件是**只读回归**的产物：没有改动 `game/web/**`、`game/src/**`、`game/tests/**`、`game/cocos/**`。
> 所有对拍脚本、编译产物、探针都落在 `work/parity_num/**`。

一条命令跑完四块：

```
node work/parity_num/run_all.mjs              # 正常对拍，有分歧 → 退出码 1
node work/parity_num/run_all.mjs --negative   # 四块阴性对照，四块全红才退出 0
node work/parity_num/run_all.mjs --verbose    # 附带四块完整输出
node work/parity_num/run_all.mjs --only=unit3 # 单块
```

**判决：Cocos 验收目前不成立。** 四块里两块（战斗内核、内政模型）两端跑不出相同数值；

- **AI 月动作 / 等级与带兵**：逐字段一致，可以放心按 Cocos 验收。

## 二、方法（可复现）

### 2.1 两端都是 TS，怎么让 node 跑起来

| 侧 | 编译 | 产物 | 装载 |
|---|---|---|---|
| Cocos | `tsc -p work/parity_num/tsconfig.cocos.json`（`module commonjs`） | `work/parity_num/_sim/cocos/**` | `createRequire` 原生 require（拿到的是 `module.exports` 本体） |
| web | `tsc -p work/parity_num/tsconfig.web.json`（**必须 `module ES2022` + `moduleResolution bundler`**） | `work/parity_num/_sim/web/**` | ESM `import()` |
| AI / 内政 | `tsconfig.ai.json` / `tsconfig.city.json` | `_sim/cocos_ai/` / `_sim/cocos_city/` | 同上 |

- web 侧**不能**编成 commonjs：`game/src/core/smartscript/runtime.ts:33`（cocos 对应 `smartscript/runtime.ts:51` 已被 K1 改掉）
  是 `const DATA_URL = new URL('../../../data/', import.meta.url);`，commonjs 目标下 tsc 原样保留 `import.meta`，
  node 装载直接 `SyntaxError: Cannot use 'import.meta' outside a module`。所以 web 走 ES2022 + `_sim/web/package.json = {"type":"module"}`。
- `_sim/package.json = {"type":"commonjs"}`：否则上层 `game/package.json` 的 `type: module` 会把 tsc 的 CJS 产物当 ESM 装。
- 任务书提到的 `game/tsconfig.check.json` **在仓库里不存在**，所以自建了上面 4 个 tsconfig（都在 `work/parity_num/`）。

### 2.2 阴性对照怎么做成「真的会变红」

tsc 把 `export const X` 的内部引用编译成 `exports.X`（实证 `_sim/cocos/core/battle.js:95/:98`），
所以 `createRequire` 拿到 `module.exports` 之后**直接改常量就真的改行为**。四块的扰动点：

| 单元 | 扰动 | 基线 → 扰动后 |
|---|---|---|
| unit1 | `COC_FIX.battle.ATTACK_COOLDOWN` 40 → 41 | 0 → 136596 |
| unit2 | `COC.TROOP_UNIT` 20 → 21（驱动环境变量 `PARITY_NEGATIVE=1`） | 0 → 32783（11.49%，5 剧本全红） |
| unit3 | `COC_FIX.DEV.COST` 400 → 401 | 8191 → 9918 |
| unit4 | `COC.TROOP_PER_LEVEL` 5 → 6 | 0 → 433 |

`node work/parity_num/run_all.mjs --negative` 实测：**四块全 RED，退出码 0**
（日志 `work/parity_num/_runall_neg.log`；正常模式退出码 1）。

### 2.3 数据源与确定性

- 四块**统一用 `game/data/`** 喂两端，隔离「代码差异」与「数据差异」。数据层差异单列在 §5。
- unit3 的确定性踩过坑：web `game/web/city_model.js:250-259` 的 `rngNext()` 走
  `globalThis.crypto.getRandomValues()`，`develop()` 里 `randBelow(DEV.POP)` 每次不同 ⇒ 同一存档两次结果不同。
  脚本里做了三件事把它钉死：`setRng(rngOf(seed ^ 0x9e3779b9))`、`save.searchNonce = 0x5eed1234`
  （`ensureExtras` 之后再 `setSearchNonce`）、**同脚本 web 连跑两遍 + diff**。
  自检结果：**30 组全部一致（字段 218292）**，之后不一致数稳定（两次独立运行都是 10726）。
  Cocos 侧没有 `setRng` / `setSearchNonce` —— 它的 `develop` 本来就不带随机，注入是单边的，这本身就是差异之一。
- unit3 的日志快照**必须当场深拷贝**（`push()` 里 `safeClone`）：`ensureCityState` 回的是存档内部 `st` 的活引用，
  `ensureExtras` 回的是 `save` 本身；不拷贝的话日志每条都退化成「跑完时的最终状态」，
  旧脚本 `work/cocos_city/parity.mjs` 就有这个毛病（它那条 `ensureExtras` 差异显示的其实是终态）。

## 八、[推测]

1. **[推测]** `ATTACK_COOLDOWN` 120→40 是 web 侧单方面按原作反汇编修的（web:62-77 有 R113 证据链），
   Cocos:63 的注释「R84 只把主将改到 40，士兵保 120，因为 `tests/battle.test.ts` 的单局时长区间是按 120 标定」
   说明当时的取舍是「保测试绿灯」，而不是「保原作一致」。⇒ 要两端一致，得同时改 Cocos 侧和那条测试的时长区间。
2. **[推测]** `capture.ts` 的掉落轮盘、`wises_effects.ts` 的十面埋伏、`smartscript/syscalls.ts` 的 `0x10d/0x129`，
   三者都属于「web 上某一轮 Rxx 先落地、Cocos 侧隔了一轮没跟上」的典型：它们的 web 注释里都有
   「R57 / R88 / 已定位」字样，而 Cocos 对应位置仍是旧口径/旧注释。⇒ 建议按「web 的 R 编号」逐轮对账，而不是靠人工 diff。
3. **[推测]** 内政那 8191 条残差里，`物品.ownedItemSeqs`(750) 与 `lock.clear`(485) 看似独立，实际是
   C3/C4 的下游：`develop` 随机增量改变了人口/金 → 徵兵/搜索的前置条件与抽签序号全变。
   我把 `物品.ownedItemSeqs`、`search` 单独在干净存档上探过（`_probe_city3.mjs`）：空存档两端**一致**，
   只有先跑过 `search` 之后才分叉。⇒ 不建议把它当独立 bug 追。
4. **[推测]** 数据层的 `generals.json` 用整串存 `WISESKILL/UseForce/Force/BattleArray`、`scenarios.cities.POS` 用 `"1108 90"`，
   是打包脚本（`extract` → bundle）的序列化策略不同造成的，不是数据本身不同（STR/INT/BaseEXP 0/401 不同）。
   若将来 Cocos 直接吃 bundle，凡是「按数组读这些字段」的代码都要有 K5 式兼容，否则会静默走空分支。
