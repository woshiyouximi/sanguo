# 152 补兵端口语义（0x113 / 0x119）

**结论**：`0x113` 是**纯格查询**（格 → 占用者句柄），`0x119` 是**在空格里新建一个兵**——不是复活尸体。
g13 的「参数是 (方向, 槽位)、要返回阵亡兵槽」被 24 + 12 个调用点的实参形态直接否证。
且端口里这 7 条技能**不是死在 syscalls.ts**：`MoreSoldier` 的「无兵可补就空放」判断在到达 `ProduceSoldier` 前就把补兵数算成了 0，真凶在 `vm.ts` 的比较/跳转极性（§5）。只改 syscalls **救不活**。

## 1. 语义 [确认]（字节级反汇编见 `work\re_port113\01_*.txt` / `03_*.txt`）

| 项 | 0x113 | 0x119 |
|---|---|---|
| 分派 | 表基址 `0x4A69B4`，4B/项按 id 索引 → `0x4A6E00` | 同表 → `0x4A6E18` |
| 宿主 | `0x4205C6` → `0x43AFAA(a,b)` | `0x42068C` → `0x43A971(a,b,c)` |
| 参数 | `x`∈[0,70] 列、`y`∈[0,13] 行（96×72 px 格） | `side` 0=A 方 / 非 0=B 方；`x`、`y` 同上 |
| 返回 | 占用者对象的 `[+4]`＝单位句柄；空格或越界 → **0** | 新兵对象的 `[+4]`；格被占/越界/兵满 → **0** |
| 越界 | `0x43AF54` 判 `x<0||x>=0x47||y<0||y>=0xE` → 0，不抛错 | 同左 → 0 |
| 副作用 | 无 | 占格(`0x4B3CA0`)＋7×7 权重(`0x4B4C54`)＋落像素(`x*0x60+0x30`,`y*0x48+0x24`)＋`side[+0x58]++` |

链路：`0x43AFAA` = `c=0x43AF7A(x,y)`（`*(u32*)(0x4B3CA0+y*0x11C+x*4)`）`? c->[0x44] : 0`；`0x43A971`：**格被占立即 return 0**（`0x43A9E9`），扫 `side[]` 找第一条 `[+0x2c]&0x2000`（`0x43B556` = 空闲位）的空记录复用，`slot==0xc8`（**每方 200 兵上限**）→ 0，再 `0x442A1A(x,y,tag,flags,rec)` 建对象。

## 2. 调用点归类 [确认]（逐点表：`work\re_port113\02_callsites.txt`）

- **0x113：24 处全是格坐标型，0 处槽位型**。4 处前置 `PUSHI 72; DIV`（DemonDancing 0x14F08/0x14F58/0x150A4/0x150F4）、1 处前置 `SYSCALL 0x109`（ArrowSupport 0xBB78，像素→行）、6 处 `±1` 邻格（SpoutKillEdge 四邻域、ThunderAttach 左右格）、12 处带 `70-x`/`13-y` 镜像或扫描（ProduceSoldier / XProduceSoldier / ProduceBackSoldier）。
- **0x119：12 处全部 `(side, x, y)`**，且永远紧跟同格的 0x113：探到空格才造兵。若 0x113 返回的是「阵亡兵槽」，0x119 就该复活那个槽，但它第一参是 side、后两参是格坐标，且 `0x43A971` 对「被占格」直接返回 0 —— 三条互证。

## 3. 补兵的真实机制 [确认]（`work\re_port113\03_magic_so_produce.txt`）

- `MoreSoldier`：`need = clamp(5*min(word[target+0x2E], 40) − 0x10C(side), 0, arg2)`；`need==0 → CastFail`（空放），否则 `ProduceSoldier(side, need)`；Magic9 传 `(arg1=0, arg2=17)`。
- `ProduceSoldier`：列 `loc1`=0..71 × 行（下半区 7→1，上半区 `13-loc2`），`side==1` 时把 `x` 按 `70-loc1` 镜像；每格 `0x113(x,y)` 探空 → 空则 `0x119(side,x,y)` ＋ `StepShow(新兵,10,0,0)`，补满 `need` 个才返回。
- ⇒ 原作补兵 = **两翼空格增派新兵**，与「阵亡兵槽」无关；士气/血量只决定**补几个**。

## 4. 可落地补丁（syscalls.ts 12 行 ＋ runtime.ts 11 行）

```ts
// game\src\core\smartscript\syscalls.ts —— 替换现有 :383-384 / :413-414
case 0x113: {                                   // 0x43AFAA(x,y)：格→占用者[+4]，空格/越界→0
  const gx = a(0) | 0, gy = a(1) | 0;
  if (gx < 0 || gx > 70 || gy < 0 || gy > 13) return r(0);   // 0x43AF54
  return r(ctx.unitAtPx(gx * 96 + 48, gy * 72 + 36));         // =0 表示空格
}
case 0x119: {                                   // 0x43A971(side,x,y)：在空格新建 1 个兵
  const side = a(0) | 0, gx = a(1) | 0, gy = a(2) | 0;
  if (gx < 0 || gx > 70 || gy < 0 || gy > 13) return r(0);
  return r(ctx.spawnSoldier(side, gx, gy));
}
// 接口（syscalls.ts:102 旁）加一行：spawnSoldier(side: number, x: number, y: number): number;

// ---- game\src\core\smartscript\runtime.ts —— 放 summon()（:947）旁；接口声明同款 ----
spawnSoldier(side0: number, gx: number, gy: number): number {     // 0x43A971
  if (this.unitAtPx(gx * 96 + 48, gy * 72 + 36) !== 0) return 0;  // 0x43AF7A 格被占
  const side: Side = side0 === 0 ? 'A' : 'B';                     // 0x43A971：0=A
  const live = this.world.units.filter((u) => u.side === side && u.alive && !u.isGeneral).length;
  if (live >= 200) return 0;                                      // side[+0x58]==0xc8
  const u: Unit = { side, x: gx, y: gy, prevX: gx, prevY: gy, alive: true, cd: 0 };
  const h = 5000 + this.nextSummonHandle++;
  this.byUnit.set(u, h); this.byHandle.set(h, u);
  this.unitList.push(u); this.world.units.push(u);
  return h;                                                       // 原作返回 obj[+4]
}
```

为什么这样写 `ProduceSoldier` 就能补出人：`0x113` 现在**只在真有单位时**返回非 0（沿用端口的「半格内最近活人」近似，语义等价），空格判为 0 → 走 `0x119` → `spawnSoldier` 在**该格**新建 1 个兵并返回句柄，`StepShow` 拿它播特效，`loc4++` 累计到 `need` 才停。**注意这不是「把阵亡兵拉回来」**：原作与本补丁都是「新增单位」。

## 5. 只改 syscalls 不够：真凶在 vm.ts（[推测·强]，字节码自洽；指令级证据 [未解]）

`docs\04d:473` 确认 EXE 无 opcode 分派表，拿不到解释器级证明；证据来自 8 处读点**同时**自洽：`ProduceSoldier` 的 `arg2==1`/`loc3==0`/`loc4>=arg1`/循环尾 `loc2>0`、`MoreSoldier` 四个 clamp、`InitializeBattle` 的 `loc1<60`、劍輪舞的 `loc27<280`，只有 `0x3C=非0跳 / 0x3D=为0跳`（或等价：比较为真时压 0）才全部成立。
端口相反（`vm.ts:572-577`：0x3C=JZ、0x3D=JNZ），且 `vm.ts:847` 的 binop 让「栈顶当左操作数」，于是 `loc7 = 5*loc6 − 0x10C` 被算成 `0x10C − 5*loc6 ≈ 1|2 − 200 ≈ −199` → `LT` 落空 → floor 赋 0 → 上限路过 → `need=0` → **inverted `NE` 不跳** → `ProduceSoldier(side,0)` 立刻 `loc4>=0` 成立 → 0 兵、不崩、会话走完。正好解释实测：`units.length` 不变 ＋ `skillMarks={miss:true}` ＋ `frames=59`。
**两个 bug 必须同修**（只改 SUB 顺序：`need=199→cap 17`，inverted `NE` 判「17!=0」为真 → 跳 CastFail，仍 0 效果）。最小改法二选一（都在 `vm.ts`，超出本报告改动范围，需 lead 决策）：① 交换 `0x3c`/`0x3d` 两 case 的极性；② 极性不动、把 6 个比较 op 的结果取反（真=0）。任一改法都要跑全量脚本回归（1000+ 处 JNZ 读点）。
## 6. 修好后的预期表现

| 项 | 修好前 | 修好后 |
|---|---|---|
| 7 条技能（seq 5/17/19/31/37/57/81） | 0 兵、`{miss:true}` | 每次补 `min(5*min(兵力,40) − 0x10C, 17)` 个，落在两翼空格 |
| `units.length` | 不变 | **增加**（每兵一条记录），每方上限 200 |

`battle.ts:2176` 用 `ownDead` 的减少量算 `summoned`，而「新增兵」不减少 `ownDead` ⇒ 即便补兵成功，端口仍会标 `miss`。修法（另一处）：「新兵数」改为 `after.selfAlive − before.selfAlive` 的正增量，或直接累计本次 `spawnSoldier` 的返回值。
