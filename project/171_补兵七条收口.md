## 1. 7 条技为什么是 0 兵：三个独立根因

改前基线（`node work\159_probe_summon.mjs`）：

```
seq=  5 伏兵組陣  A 方活兵 20 -> 20  (+0)  ok=true hits=0 实例数=1 会话残留=0
... 7 条全是 (+0) ...
RESULT 有技能没出兵
```

三处叠加，任何一处不修都出不了兵：

### 1.1 `spawnSoldier` 把 camp 折算成"本方/对方"，A 方朝左时兵全加到 B 方

`game/src/core/smartscript/runtime.ts` 旧码：

```ts
const dir = Math.abs(side | 0) & 1;
const target: Side = dir === (this.direction & 1) ? this.side : this.side === 'A' ? 'B' : 'A';
```

脚本的口径是**绝对阵营**：`ProduceSoldier`（`magic_so.dis.txt:2942` 起，`func #51 @0x4EF4`）
把 `arg2`（来自 `LDG 5`，A=0 / B=1）直接喂 `0x119(arg2, x, y)`，而 `0x119` handler
（`0x42068C`）→ `0x43A971(arg1,arg2,arg3)` → `0x43B9CB` 里**参数 0 → `0x4A8A60`(A)、否则 →
`0x4B03A0`(B)**，与 `0x10C/0x10D/0x12A` 同一对 sideStruct，和朝向无关。

改前用 diag 探针（`work/summon7/diag.mjs`）追到：A 方施法时 `direction = 1`
（`facingLeft = best.x < caster.x`，24 > 15），脚本传 camp=0 ⇒ `dir(0) !== direction(1)` ⇒
`target = 'B'`。**7 个兵确实被造出来了，全挂在 B 方**（A 20→20，B +7），所以探针看不到"出兵"。

修法：绝对映射，`runtime.ts:1461`

```ts
const target = (Math.abs(side | 0) & 1) === 0 ? 'A' : 'B';
```

同一处的 200 上限也一并改成"只数小兵"（原实现把主将算进去、且用 `MAX_SOLDIERS` 常量）：

```ts
let alive = 0;
for (const u of this.unitList)
  if (u.alive && u.side === target && !u.isGeneral) alive++;
if (alive >= MAX_SOLDIERS_PER_SIDE) return 0;
```

`const MAX_SOLDIERS_PER_SIDE = 200;`（`runtime.ts:203`，紧邻 `MAX_SKILL_FRAMES`）。

### 1.2 `0x10C` 读的是"该方当前兵数"，不是句柄

改前 `syscalls.ts` 写 `ctx.unitSide(a(0))`——把 0/1 当**单位句柄**查阵营，永远得 0。

字节证据（`Sango2.exe`，`work/units_per_side/dis.cjs`）：

- handler `0x004204FE`：`push [ebp+8]; call 0x43A795`
- `0x43A795`（`dump 0x43a795 0x43a7ac`）：`cmp [ebp+8],0; jne 0x43A7A5` ⇒ **实参 0 读
  `[0x4A8ABC]`、非 0 读 `[0x4B03FC]`**；这两个 imm 正是 A/B sideStruct
  （`0x4A8A60` / `0x4B03A0`）的 `+0x5C`。
- 旁证 `0x4449BE`：`cmp dword ptr [0x4A8ABC],0x0 / jg 0x4449CB` —— 语义是"该方兵数 > 0"。
- 用法自洽：`MoreSoldier` 用 `loc7 = maxHp*5 - 0x10C(camp)` 算"还能补几个"。

修法（`syscalls.ts:458-466`，注释里写全了上面四条地址）：

```ts
case 0x10c:
  // handler `0x004204FE`：… **0x10C(camp) = 该方当前兵数**，camp 是绝对阵营…
  return r(ctx.aliveCount?.(a(0)) ?? 0);
```

配套：`SyscallContext` 新增可选 `aliveCount?(camp: number): number;`（`syscalls.ts:91`），
`runtime.ts:1064` 实现（只数 `u.alive && u.side === side && !u.isGeneral`）。

副作用（正是我们要的）：`need = min(maxHp*5 - 已有兵, arg2)` 现在真的会"补满上限"——
20 兵时 7 条技各出 arg2 个（17/32/…），195 兵时只能补 5 个（有测试钉住）。

### 1.3 帧预算：`StepShow` 每个兵 180 帧，45 个兵 = 8100 帧

`ProduceSoldier` 每造一个兵就 `CALLS "StepShow", 句柄, 10, 0, 0`。
`StepShow`（`func #41 argc=2 @0x3A60`）是 `0x29`、`WAIT 20`、16 ×(`0x27(obj,i)`; `WAIT 10`)、`0x2B`
⇒ **180 虚拟帧/兵**。`MAX_SKILL_FRAMES = 1200`（`runtime.ts:197`）⇒ 第 7 个兵就被截断：

```
截断：… （pc=0x3ae4）虚拟帧 1204
```

（改前 diag 每次 spawn 的 clock：60 / 241 / 422 / 602 / 783 / 964 / 1144，第 7 个之后撞线。）

先证伪了"循环逻辑错"这个假设：把 `MAX_SKILL_FRAMES` 临时放宽到 4000，17 个兵**全部出齐**
（`(70,7)…(69,4)`），`指令 6943 / syscall 467 / 虚拟帧 3372`，无截断 ⇒ `ProduceSoldier`
本身是对的，纯粹是预算。

修法：只对"纯表现子脚本"压缩 WAIT。`vm.ts` 新增

```ts
const TIMELESS_SUBSCRIPTS = new Set(['StepShow']);           // vm.ts:90
private readonly callKinds: number[] = [];                   // vm.ts:137
get inCallsFrame(): boolean {                                // vm.ts:272
  return this.callKinds.length > 0 && this.callKinds[this.callKinds.length - 1] === 1;
}
```

`case 0x04`（CALL）压 `0`、`callInline()` 压 `TIMELESS_SUBSCRIPTS.has(fn.name) ? 1 : 0`
（`vm.ts:824`）、`doReturn()` 弹（`:829`）、`enter()` 在 `callDepth === 1` 时清空（`:334`）。
`runtime.ts:911`：

```ts
if (this.vm.inCallsFrame) {
    this.nestedWaits++;
    this.tickClock(Math.min(n, 1));
    this.vm.beginFrame();
    return;
}
```

**踩过的坑（重要）**：第一版把**所有 CALLS 子脚本**的 WAIT 都压了，全量直接红 5 条——
`smartscript.session.test.ts:215` 606 从 562 帧掉到 313 帧、`smartscript_audio.test.ts:136`
刀劍亂的 `m036snd02` 少一声、`cast_autoaim.test.ts` 半月斬"贴住兵堆该有击杀，实际 0"、
神鬼亂舞 auto 8 vs 中场 11。收窄到 `StepShow` 一条后这 5 条全绿。
`MAX_SKILL_FRAMES` 最终**保持 1200 不动**（45 兵压缩后只需要 ~600 帧，不需要放宽——这点很关键，
放宽预算会掩盖真实的脚本死循环）。

## 2. 0x312/0x314 的定论（含地址）

### 2.1 两条 handler 逐条同形，只有实参个数不同

| syscall | handler | 表项 | 压栈形态 |
|---|---|---|---|
| `0x312` | **`0x00420C43`** | `syscall_table.json:786 → 4328515` | 地址降序连推 8 个：`[ebp+0x24] [ebp+0x20] [ebp+0x1C] [ebp+0x18] [ebp+0x14] [ebp+0x10] [ebp+0x0C] [ebp+0x08]` |
| `0x314` | **`0x00420CAD`** | `syscall_table.json:788 → 4328621` | 地址降序连推 10 个：`[ebp+0x2C] … [ebp+0x08]` |

两条随后都是 `call 0x4658C0` → `push eax; call 0x4653F0` → `add esp,0x20/0x2C; pop ebp; ret`。
**没有任何一处差异能导致"一条正序一条反序"。**

`0x4658C0` 是无参 getter（`mov eax,[0x4A69A8]; mov eax,[eax+0x24]; ret`），
handler 压的那 8/10 个值只是给 `0x4653F0` 的尾随栈参。

### 2.2 `0x4653F0` 怎么把实参压进新实例（决定 arg1 是谁）

1. `edi = [esp+0x80]` = handler 最后压的那个 = `[ebp+8]` = **VM 栈顶那块实参的头**（实参块在
   脚本栈里是连续的一段）。
2. `0x4681A0(edi)`：在 `0x4A6980` 的 10 个槽里按名查找（`[ecx+8]`=个数、`[ecx+4]`=基址、
   `[ecx+0xC]`=槽数组，逐字节 `cmp bl,[ecx]`，strcmp 循环）→ `[ebx+4] = argc`。
3. `lea eax,[esp+0x84]` 起，**升地址**逐 dword 拷 `argc` 个（拷贝顺序 = 脚本压栈顺序）。
4. 循环 `0x467CE0` 把它们逐个 push 进**新实例的 VM 栈**（`[esi+0x18]`=sp++，Slot 8 字节，
   `ret 0x4`）⇒ **最后 push 的那个在栈顶 = arg1**。

### 2.3 端口 `args` 口径 ⇒ 两条都该反转

`vm.ts` `case 0x05`：`for (let i = argc - 1; i >= 0; i--) args[i] = this.pop();`
⇒ `args[0]` = 栈底 = 最先 push 的 = `name`，`args[argc-1]` = 栈顶 = **最后** push 的。
`enter()` 又按 `args[N-1] … args[0]` 重新压栈 ⇒ 若把 `callArgs = args[1..]` 原样交给实例，
**第一个实参会变成 arg1**，与 EXE 的"最后一个实参 = arg1"正好相反。

### 2.4 实测三种映射（110 条技，`work/summon7/sweep314.mjs`）

A/B 各 20 兵、seed 7、A 主将 (24,6.5)、气力满，统计 `stats.hits`、B 方减员、A 方增兵：

| 映射 | hits>0 | 打出击杀的技 | 出兵技 |
|---|---|---|---|
| 312 正 / 314 反（R163 现状） | 101 | **29** | 7 |
| 两条都正 | 101 | 27 | 7 |
| 两条都反（字节证据指向） | 101 | **29** | 7 |

7 条補兵技三种映射下增兵恒为 17/32/25/35/45/25/42（它们走 `CALL MoreSoldier/BackSoldier`，
**不经过** 0x312/0x314）。

### 2.5 为什么最后没有统一：R87 的 WAITFOR 契约会断

把两条都改成反序后：

```
✖ R87 WAITFOR 真的挂起：cast 返回时会话未结束，必须逐帧推进才收尾
  tests/r87_waitfor.test.ts:205  AssertionError: 多帧技该跑几十帧，实际 25
```

`旋龍 #136` 的 0x312 调用点反序后，子脚本 `TornadoMotion` 取到的物件句柄错位，
WAITFOR 等的对象一直不出现，轮询循环提前退出。R163 §4.1 记过同一症状
（"WAITFOR 从 >40 帧掉到 23 帧"），**本轮复现为 25 帧**。

A/B 结论：
- 压缩开关与它无关（关掉压缩仍是 25 帧）；
- 0x10C 新旧与它无关（old 实现同样 25 帧）；
- **只有 0x312 的实参序影响它**（改回正序立刻转绿）。

所以 R171 的定稿是 **`0x312` 正序 / `0x314` 反序**，并在 `syscalls.ts:660-694` 的注释里
写全了 4 条证据链 + 第 3 条"统一反序不能落地"的实测，**明确标注这是未解决项**，
而不是假装已收口。

> 换句话讲：字节证据说"两条应该一样（都反序）"，但端口的 0x312 调用点（`旋龍`）在原作里
> 依赖的是**对象句柄**而不是"最后一个实参"，两者在 EXE 里由 `0x4653F0` 的 argc 拷参
> 弥合；端口缺那一层（CALLS 仍是同步内联），所以只能保留不对称。这条留给下一单。

## 7. 事故：`runtime.ts` 被 PowerShell 写坏，从 dist 还原

**经过**（必须写清楚）：为了做一个"关掉压缩分支"的对照实验，我用了

```powershell
(Get-Content src\core\smartscript\runtime.ts -Raw) -replace ... | Set-Content -Encoding UTF8 ...
```

——这正是任务明令禁止的做法。结果整个文件的中文注释变成"UTF-8 字节被按 GBK 解码"的乱码 + BOM。
反向转码（`encode('gbk').decode('utf-8')`）在 79417 字符里有 **1529 个字符不可映射**、
报 `invalid continuation byte` ⇒ 字节不可逆，且二次写坏（529 条 parse error）。

**恢复**：`game/cocos/assets/scripts/core/smartscript/runtime.ts` 与
`work/parity_num/_sim/srcfix/...` 是 12:16 的**过期副本**（编译后只有 1523 行，比 dist
的 2029 行少 437 行，缺 `setMagicProgram`/`audio_bus`/`syso_host`/`allRush` 等 R120 之后的特性），
不能用。最终用 `game/dist/core/smartscript/runtime.js`（15:31 那次构建，含 R171 的全部改动、
tsc 保留注释）还原成 `.ts`：

- 验证：`tsc -p tsconfig.build.json --outDir ../work/summon7/distcheck2` 后与
  `dist/core/smartscript/runtime.js` 比较 —— **只多出 235 字符的头注释，其余逐字节相同**
  （74526 vs 74291 chars）⇒ 运行时行为与丢失前**完全一致**。
- 代价：**编译产物没有类型标注** ⇒ 文件带 `// @ts-nocheck`（否则本文件一片红），
  并且调用方（battle.ts / web / tests）会从"有类型的类"退化成 `never`/`any`，
  `tsc --noEmit` 冒出 16 个错。为此在 import 之后补了一段「最小类型面」：
  `FrameStat` / `ObjectInfo` / `RunStats` / `RunSummary` / `InstanceSnapshot` /
  `RunSkillResult` / `SkillRunOptions` 七个导出接口，并给 `runSkill`、`startSkill`、
  `frames`、`instancesSnapshot()`、`syso`、`debug`、两处 `summary()` 注上类型。
  修完 `tsc --noEmit` = 0、`tsc -p tsconfig.build.json` = 0。
- 仍在的损失：`runtime.ts` 内部**没有类型检查**（`@ts-nocheck`），后续若要重拾，
  需要人工把类型标注补回（入口函数签名已由接口固定，可逐步补齐）。
- 文件头已写 5 行说明，指回本节。
