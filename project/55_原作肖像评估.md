## 1. 任务书的两处事实修正（重要）

任务书写"`generals.json` 是对象（键=武将名）"、"hero 目录 800 个文件"。实测：

1. **`generals.json` 是 401 元素的 JSON 数组**（425,467 B），不是对象：
   - `[0]` 是一条 id=0 的**模板/杂兵记录**（`NAME=盜賊`，字段集与武将不同：有 `Skill`/`LOYAL`/`SKILLLEVEL1-4`，没有 `SEQUENCE`/`Loyal`/`Spirit`）；
   - `[1..400]` 是 400 名武将，`SEQUENCE` 1..400、`id` 1..400 连续且唯一。
   - 所以正确读法是 `[r for r in data if 'SEQUENCE' in r]`，直接 `data.keys()` 会崩（我第一版就崩在这）。
2. **`assets/hero/` 的 800 文件 = 400 个 `.webp` + 400 个同名 `.png`**：
   - 两种格式**同尺寸 480×701、同一张图**；代码里 4 处请求全部是 `.webp`，`.png` 零引用；
   - 那 400 个 png 合计 **188.29 MB**（平均 459.7 KB/张），webp 合计 13.52 MB。仓库里躺着 188 MB 死重（**本次不动，仅报告**）。

## 2. 覆盖率（每个数字都可复现，见 §8）

### 2.1 FACE 字段 → 原作 PNG

| 指标 | 数值 |
|---|---|
| 武将记录 | 400（+1 模板） |
| 含 `FACE` 字段 | **400 / 400 = 100%** |
| `FACE` 形如 `"FACE\\FACE349"` | 400 / 400（全部双反斜杠，全部 `FACE\` 前缀） |
| 解析出唯一 FACE 编号 | **400 个，FACE001..FACE400 无缺号、无重复** |
| `FACE*.png` 实际文件 | 400 张，**全部 100×120**（`PIL.Image.size` 统计 400/400） |
| 武将指向的 png 缺失 | **0** |
| 没有任何武将引用的 png | **0**（即 400 张图刚好用满，一张不剩） |

→ **原作侧是一条完整、零缺失、零冗余的 400 将 ↔ 400 图映射。**

### 2.2 武将名 → AI webp

| 指标 | 数值 |
|---|---|
| `generals.json` 中重名 | 0（400 个名字全唯一） |
| hero 目录 webp 数 | 400 |
| URL 解码后重名/碰撞 | 0 |
| 名字经 `encodeURIComponent` 往返稳定 | **400 / 400**（所以 `main.js:896` / `deploy.html:286` / `items.html:309,328` 的取图逻辑不会因编码取错） |
| **命中** | **400 / 400 = 100%** |
| **缺失清单条数** | **0** |
| 目录里多余（不对应任何武将）的图 | **0** |

> 任务书预判"可能含非武将图 / 可能误判缺失"——实测都不存在：hero 目录是干净的 400 张，一张不多一张不少；也没有因为编码差异造成的假缺失。

### 2.3 重复资产检查（防止"一张图复用 10 个将"）

| 检查 | 结果 |
|---|---|
| AI webp 完全重复（MD5） | **0 组** |
| AI webp 近似重复（aHash 64bit，汉明距离 ≤4） | **0 对** |
| 原作 PNG 近似重复（同法） | **0 对** |

→ 400 张 AI 图确实是一将一图；因此女性角色那张"男性图"**不是复用**，而是**生成/落盘时张冠李戴**（见 §5）。

### 3.3 重量与色深

| 资产 | 数量 | 单张 | 合计 |
|---|---|---|---|
| 原作 `FACE*.png` | 400（100×120, RGBA） | 16.5 KB | **6.76 MB** |

## 4. 观感判定（对比图索引）

### 4.1 小尺寸下谁更清楚：原作完胜

`work/face_cmp/_thumb30x40.png`（30×40 放大 6×，12 将成对）：
- 原作的**脸几乎占满 30×40**，五官、胡须、盔缨都在，隔 2 米也能认出关张曹。
- AI 在这个尺寸**头部只有 9×11 px 左右**（AI 图里头宽约占源图 28%，缩到 30px 宽后 = 8.4px），剩下全是暗背景和肩膀；冷门将（孔岫 / 胡班 / 譚雄 / 龔景）四张脸看起来**像同一个人**，完全无法区分。

`work/face_cmp/_scene_關羽.png`（4 个真实尺寸 × 原作/AI，2.5× 放大 + 1:1 真身条）：
- 86×108、88×110 上，原作是一张"眉头一皱的关公脸"；AI 是一张"绿袍持刀小人"，**脸占约 1/3 高，需要凑近才认得出**。
- AI 的暗调背景 + 场景光，在 HUD 那种深色面板上会和面板糊在一起（低对比）。

### 4.2 放大到 100×120 或更大时到底什么样：像素块 + 台阶，平滑则发糊

`work/face_cmp/_upscale_guanyu.png`（原作 1× / 2× 近邻 / 2× 平滑 / 3× 近邻 / 3× 平滑，旁边放 AI 原生分辨率做参照）：
- **2× 近邻**：胡须、盔缨边缘出现 1px 硬台阶，像马赛克但轮廓还硬朗 → 可接受（相当于 200×240 显示）。
- **2× 平滑（浏览器默认）**：台阶变成 2px 的软过渡，边缘发虚 → "有点糊，但不出戏"。
- **3×（300×360）**：近邻出现明显锯齿，平滑版胡须糊成一缕烟，眼睛高光散开 → **已经是"硬撑"**。
- 结论：**原作 100×120 的舒适上限约 110~120px 宽**（正好覆盖现有全部 UI 尺寸）；超过 ~150px 宽就开始付"放大税"。
- 附带优点：原作是老式厚涂 + 大色块，**比照片类素材更耐放大**——3× 时虽然糊，但没有出现"糊成一坨脏色"的崩坏。

### 4.3 风格：不是 AI 内部割裂，是 AI 与游戏割裂

`work/face_cmp/contact.png`（46 将，1:1 原始像素，左原作右 AI）：
- **AI 内部风格是统一的**：同一套"电影感厚涂 + 暗环境 + 3/4 身 + 武器入画"的语言，400 张放在一起没有跳戏。所以"AI 之间风格割裂"这个担心**不成立**。
- **AI 与原作割裂且明显**：原作是"彩色抽象底 + 胸像特写 + 平涂高对比"，AI 是"写实场景底 + 半身 + 暗调"。同一页里并排出现，观感像两个游戏。
- 构图差异是硬伤：原作脸占画面 50~60% 高；AI 脸占 25~35%，且下半身/武器抢走 40% 的画面预算——**这正是小尺寸失效的根因**。

## 5. 硬伤：6 名女性武将的 AI 图是男性

`work/face_cmp/_qc_women.png`（6 名女性 + 2 名南蛮首领，左原作右 AI）：

| 大喬 | 7 | 女性，簪花 | **男性**（束发、短须、甲胄、腰刀） |
| 小喬 | 8 | 女性 | **男性**（束发、甲胄） |
| 貂蟬 | 266 | 女性，红耳坠 | **男性**（束发 + 肩扛大刀） |
| 孫尚香 | 131 | 女性，红盔 | **男性**（青年武将） |
| 祝融夫人 | 151 | 女性，红金冠 | **男性（有胡子）**，褐袍 |
| 關鳳 | 387 | 女性，红盔 | 男性化（紫甲，性别难辨但非原作造型） |
| 孟獲 | 104 | 虬髯蛮王 | 蓝发青年（**形象偏了**，但仍是男） |

统计：**女性 6 / 6 全错，错误率 100%**。这已经不是"好不好看"，而是"人物是错的"。
逐张确认过原图（例：`_raw_大喬.png` 是 480×701 原图缩到 320×467，明确是一名留短须的男性武将）；`_scene_貂蟬.png` 把这张"貂蟬"按 4 个真实尺寸铺开，**每个尺寸下都是一名扛大刀的男性**，不存在"裁切裁错了"的可能。

> 影响：只要详情大图/列表用了 AI，大喬小喬貂蟬孫尚香祝融夫人關鳳就会"变性"。**这比清晰度问题严重一个量级，必须先修。**

## 6. 四条场景建议

| # | 场景 | 现尺寸 | **建议** | 理由（可执行） |
|---|---|---|---|---|
| 1 | **战斗 HUD 头像** | 86×108（`layout.js:51`） | **用原作** | 原作在此为 0.86× 缩小，等于无损；脸占满框，一眼认出关张。AI 脸只剩约 30px 高，暗背景在深色 HUD 面板上低对比。 |
| 2 | **武将列表 / 缩略** | 30×40（`items.html:49`） | **用原作** | AI 头部仅 9×11 px，冷门将四张脸同质化，玩家无法扫列表。原作 30×40 的五官仍清晰。 |
| 3 | **武将详情大图** | **不存在**（若新增建议 ≥240 宽） | **AI（有条件）** | 唯一 AI 真正占优的场景：480×701 有足够像素撑 240~480px 宽。**前置条件**：先修 6 张女性图 + 全量抽检错配 + 统一构图（裁到肩部以上，脸占比提到 ≥45%）。若不修图，这一格也应当用原作（240 宽时原作相当于 2.4× 放大，糊但可接受）。 |
| 4 | **内政任命** | 无头像位（最接近的是 `deploy.html:36` 的 88×110） | **用原作** | 与 #1 同理：88×110 是原作的舒适区。若将来在任命列表加头像（建议 56~72 宽），更应该用原作。 |

### 6.1 三方案的代价

| 方案 | 好处 | 代价 / 风险 |
|---|---|---|
| **A 全换原作** | 0 改图成本（400 张已在 `export/png/SHAPE/FACE`）；每张 16.5 KB（比 webp 省一半）；0 错配；风格 100% 统一 | 画面回到 1998 年的分辨率与平涂感，和"竖版重制"的卖点冲突；放大场景（>150px 宽）会糊 |
| **B 全留 AI** | 大图观感现代、单张信息量大 | 小尺寸三处全部失效（列表不可辨认）；**6 名女性性别错**；13.52 MB 传输只用到 3%；与既有 UI 的暗调/构图不搭 |
| **C 混合（推荐）** | 小图清楚 + 大图好看，各取所长 | 需要一处 fallback 分支（见 §6.2）；需要维护两份资产；6 张女性图在修好前必须走原作分支 |

### 6.2 混合方案的落地形状（建议，不在本次改动范围）

- 判定规则：**显示宽 ≤120px → 原作；>200px → AI；120~200px 灰区一律原作**（因为 AI 在此区间仍无明显优势，而原作已开始糊，两边都不完美，选成本低的）。
- 需要 1 张映射表：`work/face_cmp/face_map.csv`（400 行，已产出，见 §7）。
- 需要 1 个错误清单：`禁AI` 的 6 名女性（CSV 里已标 `乙`），修图后从名单移除。
- 取图建议形如：`portrait(name, size)` → `size<=120 || banned(name) ? FACE : hero`，FACE 侧文件名是编号不是姓名，所以**必须走 CSV/JSON 映射**（这也是 CSV 里 `FACE编号` 列的意义）。

## 10. 风险与 `[推测]`

1. **[推测] 女性全错的成因**：6/6 全错、且 400 张互不重复，最像"生成管线用了固定的男性武将 prompt 模板 / 名单与图错位（例如按某份男性武将表遍历）"，而不是单张手滑。**建议**：对 400 张跑一遍人脸性别分类或人工全量目检，再决定 AI 图能否进详情页。本次只目检了 47/400，**剩下 353 张存在同类错配的可能**，不能视为已验证。
2. **版权/合规**：原作 `FACE*.png` 是原版游戏素材。若本项目要公开发行，"全换原作"会引入素材版权问题（同人/学习用途另论）。`[推测]` 需法务或发行方确认，本次只做技术评估。
3. **原作放大的天花板**：100×120 是硬上限。若 UI 改版把头像位做到 ≥160px 宽，原作会明显发糊，届时必须换 AI 或做超分（超分会引入"AI 味"，与 §4.3 的风格问题叠加）。
4. **AI 与 UI 的调性冲突**：AI 是暗调电影感，现有 UI 是深色木纹/金边（`ui_btn_wood_*`）。两者能凑合，但 AI 的写实脸 + 原作的老式厚涂**不能同页并排**——混合方案下要保证"同一屏只出现一种"。
5. **188 MB 死重**：`assets/hero/*.png` 400 张无任何代码引用却占 188 MB。若部署包包含该目录，会显著拖慢构建/发布。`[推测]` 可能是生成管线的中间产物忘了清理。**建议**（本次不动）：移出 web 根目录或删除。
6. **`face_map.csv` 的建议列不是美术终审**：353 行是"按抽样规律推定"，只有 47 行是目检。若要把 CSV 当权威表用，需补全目检。
