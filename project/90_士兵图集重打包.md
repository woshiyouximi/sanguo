# 90 士兵图集重打包（`units.json` → 2048 上限内的一页）

> 目标：把原作 FORCE 版士兵图集（1 页 **1024×3973**）重打包成 ≤2048×2048 的页，web 与 Cocos 都能吃，**逐帧像素不许变**。
> 结果：**1 页 2048×1730**，572/572 帧 RGBA SHA256 与原图完全相同，web / Cocos 两侧同一份资产，**测试与 `main.js` 一个字没改**。

| 项 | 之前 | 现在 |
| --- | --- | --- |

**为什么是 1 页而不是 2 页**：原图集超限的根因是**宽度只有 1024**（13 帧/行 → 44 行 → 3973 高）。把页宽放到 2048 后每行能放 26 帧（26×77=2002≤2048），全部 572 帧只要 22 行 → 页高 1730，**一页就装下了**。一页方案让 `pages.length===1` / `pages[0].file==='units_00.png'` / `meta.page_size===[页宽,页高]` 全部继续成立，于是 `game/web/main.js`（不在我的授权清单里）、`game/src/view/unitFrames.ts`、`game/tests/*` **全部不用改**；web 侧 `battleView.ts` 的 `UnitFrameSet.img` 是**单张图**，多页在 web 上不可能不动 `battleView.ts` 就实现（该文件不在授权内）。详细权衡与 2 页方案的实测数据见 §1。

## 1. 为什么最后装成「1 页」，以及 2 页方案为什么没装

### 1.1 约束推导

- 微信小游戏纹理上限按 **2048** 算（保守），本地 web 无限制但为一致性同样切页。
- `game/src/view/battleView.ts:643` `pushSpriteFrames(out, set.img, units?.frames ?? {}, …)`，`:1510` `ctx.drawImage(c.img, c.sx, …)`：**一套帧集只配一张图**。所以「同一兵种（组）的所有帧必须落在同一页」——这是硬约束，只按行切页不行。
- 组内帧数：7 组 × 44 = 308 帧，6 组 × 44 = 264 帧（每组 back 12 + front 12 + attack 10 + attackEnemy 10 = 44）。
- 页宽 1024（13 帧/行）时 308 帧 = 24 行 ≈ 2280 > 2048 → **1024 宽无解**；页宽 2048（26 帧/行）时 308 帧 = 12 行 ≈ 1140、264 帧 = 11 行 ≈ 1045，两页都 ≤2048 → 2 页可行；而 572 帧整体 22 行 = 1730 → **1 页也可行**。

### 1.2 两页方案的实测（跑通并留证，但没装）

页 0 = 组 0..6（podao…manzu，308 帧，2048×967），页 1 = 组 7..12（tiechui…nvbing，264 帧，2048×843），合计 650,917 B，**572/572 等价、stray=0、overlaps=0**。产物在 `work\units_repack\_selftest\`（**未装机**，仅供将来切换时对照）。

装 2 页需要 lead 同时改 **4 处**（全部超出我的授权清单）：

1. `game/web/main.js:539-575`（写死 `j.pages[0]` + `img.src='anim/units_00.png'`）
2. `game/src/view/unitFrames.ts`（`UnitFrameRect` 加 `p`、`UnitsAtlas` 加 `imgs[]`）
3. `game/src/view/battleView.ts:1510`（按 `c.r.p` 选图）
4. `game/tests/soldiers.test.ts:249-261`（`pages.length===1`、PNG 尺寸断言）

而收益只有「单页更小一点」：2 页比 1 页只小 **9,280 B**（650,917 vs 660,197），代价是多一张贴图上传、多一次纹理切换、多 4 处跨模块改动。**结论：1 页 2048×1730 是「既满足 ≤2048，又零消费者改动」的唯一解**。脚本保留了 `--split-at`，真要切随时可切。

### 1.3 Cocos 侧仍然按「多页」实现

需求 3 要求 `ArtLayer.loadUnitAtlas()` 支持多页——**已实现**（§5）。今天资产是 1 页，走的是 i=0 分支（与改造前等价）；将来换成 2 页资产时 **Cocos 一行代码都不用再改**（`BattleRoot.ts` 也不用改）。

## 2. 重排方案（shelf packing，像素 1:1 整块搬）

**输入事实**（`work\units_repack\src\units.json`，即原图集归档）：572 帧、帧宽全 75（`meta.canvas_w`）、h 58..106、原排布 1024 宽 × 13 帧/行 × 44 行、padding 2、源 PNG 为 **P 模式**（256 色，`info.transparency=255`，alpha 只有 0/255）。

**排法**：

1. 每行能放 `PER_ROW = floor((pageMax + PAD) / PITCH) = floor((2048+2)/77) = 26` 帧（`PITCH = canvas_w + PAD = 75+2 = 77`，x = i×77，与源图的 2px 间隙一致）。
2. 帧按 **h 降序**（同高按源序）排——行高浪费最小；每行行高 = 该行 max(h) + 2。
3. 超页高就换页（`--split-at k` 时按组先切两段再各自排）。
4. 输出页高 = 末行 y + 末行行高（不补齐到 2048，省内存/省包体；宽度固定 2048=2 的幂）。

**实际落位（装机版，22 行 × 26 帧 = 572）**：

| # | y | 帧数 | 该行 max h | | # | y | 帧数 | 该行 max h |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0 | 26 | 106 | | 12 | 939 | 26 | 72 |
| 2 | 108 | 26 | 94 | | 13 | 1013 | 26 | 72 |
| 3 | 204 | 26 | 92 | | 14 | 1087 | 26 | 71 |
| 4 | 298 | 26 | 90 | | 15 | 1160 | 26 | 71 |
| 5 | 390 | 26 | 86 | | 16 | 1233 | 26 | 70 |
| 6 | 478 | 26 | 80 | | 17 | 1305 | 26 | 70 |
| 7 | 560 | 26 | 76 | | 18 | 1377 | 26 | 70 |
| 8 | 638 | 26 | 74 | | 19 | 1449 | 26 | 70 |
| 9 | 714 | 26 | 73 | | 20 | 1521 | 26 | 69 |
| 10 | 789 | 26 | 73 | | 21 | 1592 | 26 | 68 |
| 11 | 864 | 26 | 73 | | 22 | 1662 | 26 | 66 |

末行 1662+66 = 1728，加 2px 底边 → **页高 1730**。页面积利用率 = 帧矩形总面积 3,237,900 / (2048×1730 = 3,543,040) = **91.4%**（原来的 1024×3973 只有 79.6%），所以 PNG 反而缩小 163,206 B。

**像素搬运**（`work/units_repack/pixels.py`）：源是 P 模式 → 用 numpy 读**调色板下标矩阵**，按 `canvas[y:y+h, x:x+w] = src[sy:sy+h, sx:sx+w]` **整块下标拷贝**，输出 `Image.frombytes('P', …) + putpalette(源 palette)`，并沿用源的 `transparency`。全程**没有 RGBA 转换、没有缩放、没有重采样、没有任何 resample 参数**，帧外区域填源的透明下标（255）。

**JSON 结构**（只增不改）：

- `meta` 原字段全保留（`count:572`、`canvas_w:75`、`skirt:3`、`padding:2`、`scale:1`、`frame_raw_w:100`、`frame_scale_k:0.75`、`walk_frames:12`、`attack_frames:10`、`palette:256`、`source`），改/增：
  `page_size:[2048,1730]`、`packed_page_size:[2048,1730]`、**新增** `page_count:1`、`page_max:2048`、`page_sizes:[[2048,1730]]`、`packed_by:"work/units_repack/repack.mjs"`。
- `pages` 仍是数组（今天 1 条）：`{file:"units_00.png", w:2048, h:1730, sprites:[…572]}`。
- 每帧：`name/x/y/w/h` 全保留、**按源顺序输出**，**新增 `p`（页码，今天全 0）**——为将来多页留的字段；`main.js` 只读 `sp.x/y/w/h`，测试只读已知字段，都不受影响。
- `groups`（13 组 × back/front/attack/attackEnemy/hold/troop/letter/name）**一字未动**。

## 3. 逐帧等价证据（真跑，不是看代码觉得对）

```
$ node work\units_repack\repack.mjs
[pixels] mode=P frames=572 equal=572 indexEqual=572 stray=0 overlaps=0
[pixels] units_00.png 2048x1730 frames=572 bytes=660197 opaque=882064 sha256=27f4b98d5216
```

校验口径（`work/units_repack/pixels.py`，**重新读盘**后再比，不信任内存里的数组）：

1. 对每一帧，在**源 PNG** 与**落盘后的新 PNG** 上分别裁 `(x,y,w,h)` → 转 RGBA → 算 SHA256，逐帧比对 → **572/572 相同**。
2. 源是 P 模式，额外比一次**调色板下标原始字节**（`src[sy:sy+h, sx:sx+w]` vs `dst[y:y+h, x:x+w]`）→ **572/572 逐字节相同**（比 RGBA 更强）。
3. `strayPixels = 0`：新页「帧矩形之外」**没有任何不透明像素** → 没搬歪、没漏搬、没把邻帧蹭过来。
4. `overlaps = 0`：572 个矩形两两不重叠 → 测试里「按矩形反查帧名」不会串名。
5. 交叉校验：新页不透明像素总数 **882,064** = 源页 `1024×3973 − 3,186,288(透明) = 882,064`，完全相等。

证据文件：

- `work\units_repack\out\frames.sha256.csv` —— 573 行（表头 + 572），列 `name,page,x,y,w,h,src_sha256,dst_sha256,equal`，**`equal` 列 572 行为 `1`**。
- `work\units_repack\out\verify.json` —— `{frames:572, equal:572, indexEqual:572, mismatches:[], strayPixels:0, overlaps:0, pages:[{file,w,h,frames,bytes,sha256,opaquePixels,strayPixels,overlaps}], pageMax:2048}`。
- `work\units_repack\src\` —— 原图归档（`units.json` 43,991 B / `units_00.png` 823,403 B，sha 见 §4），随时可比对/重跑。

## 5. Cocos 侧多页改造（`ArtLayer.loadUnitAtlas`）

**改造前**：先 `loadFrame(imagePath)` 再读 json，只取 `pages[0]` → 多页资产第 1 页起根本不会被加载。

**改造后**（`game\cocos\assets\scripts\ArtLayer.ts:323`）：

```
读 json → pages = doc.pages.filter(p => p && Array.isArray(p.sprites))
       → left = pages.length，逐页 loadFrame：
           i=0      : path = imagePath（调用方原样路径，不猜）
           i>=1     : path = unitPageImagePath(i, page, imagePath, jsonPath)
                      = dir(jsonPath) + "/" + page.file 去掉 .png   → 如 anim/units_01
                        （page.file 缺失时把 imagePath 结尾 _00 换成 _0i）
           每页 → buildAtlasFrames(page, 该页自己的 texture) → 合并进同一个 Map
                 （跨页重名只 console.warn 一次并保留先出现的页）
       → left==0 → cb(frames, pages[0], groups)   // 签名/语义不变
       → 任意一页失败 → failed=true; cb(null, null, groups)  // 与原降级口径一致
```

要点：

- **回调签名一个字没变**：`(frames: Map<string,SpriteFrame>|null, page: AtlasPage|null, groups: Record<string,unknown>|null)`；`page` 传 `pages[0]`（`BattleRoot.ts:417` 只拿它判 null）。→ **`BattleRoot.ts` 一行没改**，`this.forceAtlas = { groups, frames }` 照旧；每个 `SpriteFrame` 自带自己的 `texture`，画的时候不需要知道页码。
- **多页路径的贴图尺寸纠偏仍是 per-page**：`buildAtlasFrames` 里 `texW/page.w`、`texH/page.h` 用的就是该页自己的声明尺寸（`ArtLayer.ts:298`）。
- **今天 1 页 = 与改造前等价**：`pages.length===1`，只走 i=0，`path===imagePath`，帧表由同一个 `buildAtlasFrames(pages[0], texture)` 产出；差别只有「先读 json 再读图」的顺序（失败降级点与 warn 文案都保留）。
- 顺手修掉一个隐性坑：以前 `loadFrame` 失败时 `cb(null,null,null)` 会把**已知的 groups** 丢掉；现在失败也带上 `groups`（`BattleRoot` 判 `!frames` 先行返回，行为不变，但信息更全）。
