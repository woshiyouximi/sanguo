## 0 裁决摘要

1. **「1 格 = 多少屏幕 px」不是常数，是屏幕纵坐标 y 的函数。** 同一排两个相邻单位（= 两个相邻格）的间距实测：y≈94 → 53 px、y≈124 → 57.6 px、y≈136 → 64 px、y≈170 → 81 px。battle B 三点拟合 `pitch(y) = 9170/(283−y)`（三点残差 2.5%）；battle A 同比 **×1.092** 缩放。
   ⇒ 在 y=94 处 **1 格 ≈ 53 ± 5 px**，在 y=164.5（主将所在排）**1 格 ≈ 84.5 ± 8.5 px**。
2. **主将 5.558 px/视频帧 = 166.8 px/s = 1.97 格/秒 = 每格约 15.2 视频帧 = 0.507 s。**
3. **不被堵士兵（前方空格、零位移帧 0）2.934 px/视频帧 = 88.0 px/s = 1.66 格/秒 = 每格约 18.1 视频帧 = 0.602 s。**
4. **结论一句话**：`[确认]` 反汇编里没有「主将更快」的任何机制，闸门确实共用；录像的 1.89× 像素比 = 1.59×（透视：同一把尺下 84.5/53）+ 1.19×（士兵约 1/5 的行动没走成）。扣掉透视后两者格/秒之比 1.19，而这个 1.19 小于 px/格 与 tick 率各自的误差带（均 ±10%），因此它**不构成「主将步进更快」的证据**；**1.89× 不是速度比。**
5. **m1 与 176 为什么都对**：`+0x34` 是以**引擎 tick** 计数的（`0x4A79C4` 全局 tick 计数器，本节 §6 给字节），不是以视频帧计。176 把 30 fps 当成 30 tick/s 用了，于是「40 tick/格」算出 2.4 世界 px/帧 → 对不上 5.59；按录像反推 tick 率约 **66–79 Hz**（见 §5.4），一切就对齐了。

## 1 方法：为什么必须放弃「全局 96 或 128 px/格」

- 画面满幅无黑边（左右两侧是「待机兵列」装饰贴图），**不存在 4:3→16:9 的 pillarbox 或拉伸**（`work\speed_arb\z_f190_top.png` 等目视；188 §0 的「96 或 128」两选一前提不成立）。

## 3 格尺：同一排相邻单位间距

### 3.1 判据：屏幕上「1 个兵」≠「1 格」

每侧只有 **8 个单位槽**（主将 slot0 + 小队 slot1..7；出自 `0x44497F` 只写槽 0、`0x4448B2` 只写槽 1..7）。battle B 07:48.667 的蓝方展开方阵里可数出 **约 16 个蓝甲贴片、8 个队中心**（与「7 队 + 1 主将」吻合）⇒ **1 队 ≈ 2 个贴片**，贴片对内部偏移只有 (Δx 17–21, Δy 10–14)；**队中心之间才是格距**。所以「相邻士兵间距」直方图里同时存在 19 px（队内）和 57–83 px（队间）两族，必须按 Δy≈0 且 >40 px 筛。
（另：斜向那串 Δ=(+19,−19)、(+21,+26) 的连线是**队内摆位**，不是格矢；同 y 的水平连线才是 x 轴方向。）

### 3.2 实测（全部为「同屏 y 的两个队中心」）

| 屏 y | px/格 | 来源（同排实测原值） |
|---|---|---|
| 94 | **53 ± 5** | battle A 敌弓兵散兵线：47 / 53 / 54 / 54 / 55 / 56 / 57（7 个相邻差，n=7） |
| 123.6 | **57.6** | battle B 展开方阵第 1 排 |
| 135.8 | **64.0** | battle B 展开方阵第 2 排 |
| 170.5 | **81**（80–83） | battle B 展开方阵第 3–4 排 |

拟合（battle B 三点，`k=9170, p=283`）：**`pitch_B(y) = 9170/(283 − y)`**，三点残差 57.67/62.4/81.2 vs 实测 57.6/64/81 → **≤2.5%**。
battle A 缩放：把 y=94 的 53 px 代回 battle B 曲线得 48.5 px ⇒ **battle A 的镜头比 battle B 大约 ×1.09**（同一深度在 battle A 里更「放大」），跨场比较必须带这个系数。

### 3.3 自洽性检验（替代失效的「相机纹理位移」交叉验证）

- 同一把尺下：**主将 / 弓兵 = pitch(164.5)/pitch(94) = 84.5/53 = 1.59**，而实测像素速度比 = **5.558/2.934 = 1.89**。
- 残差 **1.89/1.59 = 1.19**，只可能来自「单位时间内实际挪动的格数」——即士兵有约 1/5 次行动没走成（被堵/让位失败/出手帧），这与 m1 §「能打就不走」「让位失败原地不动」的代码路径一致。
- 该 1.19 与 §5.4 的 tick 率自洽性检验同向（见下）。

## 4 换算：格/秒 与「多少帧走一格」

| 对象 | 屏 y | px/帧 | px/秒 | px/格 | **格/秒** | **视频帧/格** | **秒/格** | 若 40 tick/格 ⇒ tick 率 |
|---|---|---|---|---|---|---|---|---|
| 主将赵云 | 164.5 | 5.558 | 166.8 | 84.5 ± 8.5 | **1.97** | **15.2** | 0.507 | **79 Hz** |
| 不被堵弓兵 | 94 | 2.934 | 88.0 | 53 ± 5 | **1.66** | **18.1** | 0.602 | **66 Hz** |

- 两者格/秒之比 **1.19**（像素比 1.89）。
- **为什么 176 会算不通**：176 隐含「30 fps = 30 tick/s」，于是 40 tick = 1.33 s = 40 个视频帧；主将 5.558 px/帧 × 40 = **222 px/次行动**。而本次实测主将所在排 1 格只有 **84.5 px** ⇒ 「一次行动走一格」在 176 的口径下差 222/84.5 = **2.6×**，只能靠「每步 2.33 格」或「格宽 222 px」自圆，两者都被同排实测否掉。**矛盾全部来自 tick 率假设，不是来自实测像素。**

### 4.1 tick 率独立校验（倒计时）

p3 实测倒计时：战斗 B **0.571 单位/秒**（1.75 s/单位）、战斗 A **0.656 单位/秒**（1.53 s/单位）。若倒计时每 **N tick** 减 1：
- N=120 ⇒ 68.6 Hz（B）/ 78.4 Hz（A）
- N=100 ⇒ 57 Hz（B）/ 65 Hz（A）

⇒ **战斗 A 的 tick 率比战斗 B 高 14%**，与「引擎逻辑由 tick 计数器驱动、帧率随机器/负载浮动」一致（§5.4 给机制）。这与上表 79/66 Hz 同带。**tick 率不是引擎常数**，这也是 173/176 两方各自算式看似都对、结论却差 1.9× 的根因。

## 5 反汇编复核（判据 3：主将真 <40 tick/格吗 / 若不是，为什么）

### 5.1 `0x43E964` 主将帧整段逐条读完的结论

`dis_range.py 0x43E964 0x2A0`（文件 0x43E964–0x43EC46）整段已读，**没有任何「更小闸门 / 2 格步进 / 中途被新行动覆盖」的字节**：

- 入口 `mov ecx,[eax+0x84]` ⇒ unit = obj→+0x84；`[ebp-4] = unit→+0x40`（子状态）。
- `call 0x43B67F(unit)`（**m1 未提**）：非 0 → `[ebp-4]→+0x4C -= 0x32`，跳 0x43E9ED；否则 `[ebp-4]→+0x4C += 0x43E72E(st)`，`cmp [+0x4c],0x1d4c0` 夹取，`call 0x43E847(st)`。这是个毫秒级累加器，**不参与走位时机**。
- 死亡/离场状态机：`0x43E9F1` 判 `0x42233D(obj)==0x20`；`0x43EAA4` 判 `0x43B50D(unit)&0x8000` ⇒ 都走 `0x43CD48 / 0x43BE32 / obj→+0x90--` 收尾分支，与速度无关。
- **正常分支 0x43EB4C：`0x43EB50 call 0x43B574`——与士兵帧 `0x43D24B` 完全同一个闸门函数**（`0x43B574` 全 EXE 只有这两个调用点）。
- 非 0 之后：记上一格 `unit→+0x10/+0x14 = +0x8/+0xc`（`0043EB66 8b4208` / `0043EB69 894110`、`0043EB72 8b420c` / `0043EB75 894114`）→ `0x43EB7C call 0x43BCA7`（探邻敌）→ 有敌则 `0x43EBA7 u+0x38=1` + `0x43CCE3` + `0x43C1E7` + `0x43D0F1(u,dir,0)`（攻击消息）→ 无敌/被背对则 `0x43EBE6 call 0x43AF1A` 取 cmd → `0x43EBFD call 0x43CF07(unit,cmd)` 走位。
- 帧尾 `0x43EC22 call 0x468720`（**= 读全局 tick 计数器，见 5.4**）与 `obj→+0x88` 比较，不等则 `0x43E55C(obj,2,0)`。

⇒ 主将帧与士兵帧是同构的两份代码，**批次、落位、滑行时长全部共用**；`0x43BF5F push 0x28`（滑行 40 tick）是写死的，不区分主将/小队。

### 5.3 主将帧的调用点（排除"多跑一遍"）

`p12_xref.py` 全 `.text` 线性扫描（166150 条指令；capstone 必须 `md.skipdata=True`，否则第一个非法字节就静默停）：
- `0x43E964` ← **只有 `0x43EFC5`**（事件派发器 `[ebp-0x18]==2` 分支）
- `0x43D125` ← **只有 `0x43DE5E`**（`[ebp-0x14]-0x10001` 跳表 0x43E193 分支）
⇒ 两个帧函数各只被调用一次，**没有「主将额外多跑一遍」**。

### 5.4 【本次新增】`+0x34` 是「引擎 tick」单位，不是视频帧、也不是毫秒

这是解开 173↔176 矛盾的钥匙，m1 把它当成「全军统一平移计时器」略过了：

```
00468710 c705c4794a0000000000  mov dword [0x4a79c4], 0      ; tick 计数器清零
00468720 a1c4794a00            mov eax,[0x4a79c4]           ; ★getTick()   （被 0x43AC7F/0x43EC22 调用）
00468725 c3                    ret
00468730 a1c4794a00            mov eax,[0x4a79c4]           ; ★incTick()
00468735 40                    inc eax
00468736 a3c4794a00            mov [0x4a79c4],eax
0046873B c3                    ret
```
追帧器（m1 的"全军统一平移计时器"，入口 `0x43AC79`）：
```
0043AC79 55 8bec 83ec14        push ebp; mov ebp,esp; sub esp,0x14
0043AC7F e89cda0200            call 0x468720                ; ★now = getTick()
0043AC89 f02b05147b4b00        lock sub eax,[0x4b7b14]      ; ★dt = now − 上一次
0043AC90 8945f4                mov  [ebp-0xc],eax           ; dt 单位 = tick
...
0043ACCD e883080000            call 0x43b556                 ; if (unit→+0x2c & 0x2000) 跳过
0043ACDD 8b4234                mov  eax,[edx+0x34]
0043ACE0 0345f4                add  eax,[ebp-0xc]           ; gate += dt          ← tick 补偿
0043ACE6 8b513c                mov  edx,[ecx+0x3c]
0043ACE9 8d8410f1d8ffff        lea  eax,[eax+edx-0x270f]    ; + (+0x3c − 9999)
0043ACF3 894134                mov  [ecx+0x34],eax
0043ACF9 c7423c00000000        mov  dword [edx+0x3c],0
0043AC4C c7403c0f270000        mov  dword [eax+0x3c],0x270f  ; 0x270F=9999 是"无补偿"哨兵
```
⇒ 门的单位 = **tick 计数**；引擎另有全局 tick 计数器与追帧补偿。**因此「40」是 40 个逻辑 tick，落到秒上取决于运行机器的 tick 率（本次录像实测 66–79 Hz，§4.1 倒计时校验同带）。** 176 用「30 fps = 30 tick/s」把 40 tick 折成 1.33 s，才推出 2.4 世界 px/帧 与 5.59 实测对不上。

其它反向证据（同批）：
- `timeSetEvent` 的唯一调用点 `0x47C6CC` 所在的多媒体定时器封装（`0x47C67E SetTimer(this,uDelay,uResolution,fn,user)`）**既无 `call` 调用点、也无任何 4 字节指针引用**（`p30_hunt.py` 搜 0x47C67E / 0x47C65D / 0x47C645 各 0 命中；`tools\xref_call.py 0x47C67E` = 0 caller）⇒ 是链接进来的死代码，引擎**不用**多媒体定时器，这也解释了为什么 tick 率会随机器浮动。
- `0x4686ED` 那段 `mov ecx,[ecx*4+0x4d2820]; sub ecx,eax; mov eax,0x7400; idiv ecx` 是「帧预算/等待时间」计算（0x7400=29696），**与逻辑 tick 解耦**，进一步支持"渲染帧率 ≠ 逻辑 tick 率"。

## 8 仍然不知道 / 未解

1. **引擎 tick 率的常数**：没找到硬锁（不用多媒体定时器、无 Sleep 常量证据），只能从录像反推 66–79 Hz。若原作在不同机器上跑出不同速度，这一点本身需要写进移植说明（原作速度非严格实时）。
2. **px/格 的绝对锚**：`pitch(y)=9170/(283−y)` 是**同一场战斗的屏幕函数**，不是世界函数。世界格 96×72 与屏幕 pitch 的对应关系仍缺一个独立锚（需要找到视口投影矩阵/相机常数，`project\02_战斗重构设计.md:895` 也登记「EXE 的视口缩放/裁剪未定位」）。因此我给的是 px/格 **±10%**，不是精确值。
3. **battle A / battle B 的相机缩放差 1.092** 只由 y=94 单点标定，样本薄（7 个间距，47–57 px）。理想做法是在两场战斗的同一 y 上各量一排。
4. **士兵行动失败率**没有直接数出来（1.19× 是残差反推）；要直接数需在混战里逐队判「本格滑行是否为 0」，本轮被遮挡/死亡打断，未做。
5. **敌方主将（曹豹）速度**仍无法量（全程不入画，176/188 已登记）。
6. 方阵里「1 队 = 2 贴片」是从 16 人 / 8 槽推出的，没有从动画集直接确认小队成员数（`project\48` 的装配表可交叉验证，本轮未做）。
