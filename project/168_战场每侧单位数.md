## 0. 一句话结论

**原作每侧战场只有 1 个将领单位**；士兵不是「将领自带的兵」而是**该侧 unit 自己的士兵记录数组**（上限 200 条）。
部队（Obj3）里可以挂任意多个武将，**上场的永远只有 1 个**：默认是主将（`部队+0x0C`，建表时被 swap 到名册 `entry[0]`），
但**出陣画面里可以改选名册中的任意一个**（名册下标 `army+0x04` 被列表 UI 写入：`0x4496D1`(B) / `0x449853`(A)），
选中的那一个才会被实例化成战场单位（`0x448690` → `0x43A1C4`）。
**「5 个武将槽、前 3 上阵」在原作里不存在**：`project/162` 读到的 `+0x010` 是**军师指针**、`+0x01C` 是**武将链头**，被当成了槽位；
而「5」的真实出处是**出陣名册列表每页 5 行**（`0x44883D: mov dword ptr [msg+0x28], 5`，`0x44888B` 的翻页映射按 5 算）——
它是 UI 分页常量，不是队列长度，也不是上场数。

## 1. 结论

### 1.1 每侧将领单位数 = 1（1 个主将 + N 个士兵）——`[确认]`

五条独立证据互相闭合：

1. **战场 unit 结构只有两个固定全局**：A `0x4A8A60`、B `0x4B03A0`，间距 `0x7940`。
   `0x4A8B00`–`0x4B0399` 这段区间在全 `.text` 里**没有任何绝对地址引用**，即不存在「单位数组」。
2. **「对手」是写死的另一个全局**，不是搜索出来的：
   `0x43B9E2(unit) = (unit == 0x4A8A60) ? 0x4B03A0 : 0x4A8A60`（字节见 §2）。
    因此任何单位想找「对面」，只能拿到那唯一的一侧。
3. **单位实例化每侧只发生一次**：唯一入口 `0x448690`，
   `entryA = 0x446F45([0x4A668C])` → `0x43A1C4(entryA, entryB)`；
   `0x43A1C4`（单位初始化）在全 `.text` 只有 `0x44873F` 一个调用点，`0x448690` 只有 `0x448DE9` 一个调用点。
4. **名册的「当前条目」下标 `army+0x04` 只有一个消费者**：`0x446F45(army) = &entries[army+0x04]`，
   全程序只有 2 个调用点，都在 `0x448690`（唯一建单位的地方）。初值由 `0x446D00`（A）/`0x446EFD`（B）写 0，
   建表时又把主将 swap 到 `entry[0]`，所以**默认就是主将上场**。
   但这个下标**并非恒定**：出陣画面的名册列表会写它 —— `0x4496C8`（B：`[ecx+0x04] = edx`，`ecx=[0x4A6690]`）
   与 `0x44984B`（A：`[eax+0x04] = ecx`，`eax=[0x4A668C]`），下标 = `[0x49108C] + [msg+0x20]`（A 侧基数 `0x49102C`）。
   ⇒ **玩家可以在出陣前改「这一仗由谁上场」**，但**不会**因此多出第 2 个将领单位（见 §1.5）。
5. 反证尝试：若存在「第 2/第 3 个将领单位」，`G2/G3` 就不该是「双方各一个对象句柄」。
   实际 `0x43BA59(unit)` 里 `[ebp-4] = unit+0x44`（本方主将对象）、`[ebp-0xC] = 0x43B9E2(unit)`（对方 unit）、
   `[ebp-8] = 对方+0x44` —— 只有两个槽，且各自唯一。与 `project/154` 的 G2/G3 结论一致。

### 1.2 上限：将领单位上限 = 1（结构性）；士兵上限 = 200 条/侧 ——`[确认]`

* **将领单位的上限是「结构」而不是「计数」**：引擎里没有「单位数组」，只有两个固定全局
  （A `0x4A8A60` / B `0x4B03A0`），建单位函数 `0x448690` 每侧只写一个全局（`[0x4A8A24]` / `[0x4A8A20]`），
  「对面」由 `0x43B9E2` 直接返回另一个全局。所以**没有任何数字能把它变成 2**；`[0x4A8A24]`、`[0x4A8A20]`
  这两个指针全程序只写不读（各 3 处引用，全是写），也不存在「第二支部队/援军」的入口。
* 士兵槽分配 `0x43A971(side, x, y, …)`：
  `0x43AA44: cmp dword ptr [ebp-0x0C], 0x0C8` / `jne` / `xor eax,eax`（返回 0 = 满）⇒ **每侧最多 0xC8 = 200 条士兵记录**。
  这个 200 不是拍脑袋：原文「兵」上限 100 + 「骑」上限 100 = 200（见 §1.4 的计数公式）。
* **名册条目数没有显式上限检查**：`0x446B52` / `0x446D4E` 的循环沿武将链一路写 `army[0x1C + i*0x48]`，
  既不判 `i < 5` 也不判结构边界。结构上 `army` 只有 0x460 字节，
  条目区 `0x1C`–`0x453` 共 `0x438` = **正好 15 条**（`0x1C + 15*0x48 = 0x454`，`0x454` 就是「军师」字段）——
  所以实际安全上限是 **15 条**，第 16 条会踩掉军师字段。`[推测]`（无显式检查，属结构容量推断）。
* 唯一被**显示**出来的「上限」是**城池**的武将上限：`0x417A15: movsx edx, word [城+0x44]` 与 `[城+0x30]`（武将数）
  一起送进 `0x489298 "武將數   %d/%d"`。部队面板（`0x4189A2`）只有 `0x4894DC "武將數 %d"`，**没有分母** ⇒ 部队层无 5 人上限。

### 1.3 出陣队列：原作没有「5 槽」，也没有「前 N 个上阵」——`[确认]`

* 部队（Obj3）是**定长 0x6C × 128** 的池：`0x43884C(i) = i<0x80 ? [0x4A662C] + i*0x6C : 0`，
  `0x3600 / 0x6C = 0x80`（整除）。字段（用两个面板逐字段实证）：
  | 偏移 | 含义 | 证据 |
  |---|---|---|
  | `+0x00` | 状态（2 = 空闲，池初始化时写 2） | `0x4385AA` |
  | `+0x04` | 自身 id（`0x438810` 用它校验） | `0x4385C0` |
  | `+0x08` | 军名 → 面板 `"%s軍"`（`0x4894A4`） | `0x4189xx` |
  | **`+0x0C`** | **主將 general\***（面板 `"主將   %s"`，`0x4894AC`） | `0x418A07` |
  | **`+0x10`** | **軍師 general\***（面板 `"軍師   %s"`，`0x4894B8`） | `0x418A44` |
  | `+0x1C` | **武将链头**（头插，链节 = `general+0xDF`） | `0x438948` / `0x446D5E` |
  | `+0x40` | 目的地城（面板 `"目的地 %s"`，`0x4894C4`） | `0x418A86` |
  | `+0x68` | 空闲链 next（池初始化按 `i+1` 串联） | `0x4385E0` |
  ⇒ `project/162` / `docs/07b §6` 记的「`+0x010/+0x014/+0x018/+0x01C/+0x020` = 5 个武将槽」**是把 `+0x10`(军师) 和 `+0x1C`(链头) 当成了槽**。
* 一个部队确实可以带**多个**武将：`0x411F8F`–`0x411F99` 是
  `for (i = 0; i < arg+0x14; i++) 0x406E11(部队, list[i])`，`0x406E11` 内部又调 `0x438948` 头插进 `部队+0x1C`。
  但这条链**只喂两个消费者**：出陣面板计数（`0x446F73` 数条目 / `0x446FBE` 累加兵力）与战后处置。
* 上场的**只有 1 个条目**：单位从 `army->+0x04` 取一条（`0x446F45`，全程序只有 2 个调用点，都在 `0x448690` 里）。
  该下标默认 0 = 主将（`0x446D00`/`0x446EFD` 写 0；`0x446D4E` 里 `cmp [side+0x0C], g` 命中就 swap 到 `entry[0]`），
  **但出陣画面可以让玩家把它改成别的条目**（见 §1.5）。
* 其余名册条目去哪了：**战后结算**。
  * `0x447410`：`mov dword ptr [edx+ecx+0x20], 0x7`（status = 7，被俘后逃脱）；
  * `0x4490AB`：`mov dword ptr [eax+edx+0x20], 0x3`（status = 3，全体被俘 —— 退兵分支）；
  * `0x44D065`/`0x44D08F`/`0x44EBFC`/`0x44ECD3`/`0x44EDC5`：status 5 / 2 / 6 / 5 / 2（军师技的 67 个 case 里）。
  * `0x447037` 战后循环 `for (i < army->+0x00)` 只处理 `[army + i*0x48 + 0x20] == 3` 的条目：
    逐个打 `0x491290 "我們俘虜了敵方武將%s"` 或 `0x4912B0 "我們俘虜了敵方君主，但被逃了"`，然后置 7。
* 因此「出陣队列怎么消费」的准确答案是：
  1. **原作没有「队列」，只有名册**：名册 = 该侧武将链的全部在职武将（野战=部队链 `+0x1C`／`+0xDF`；
     攻城守方=城武将链 `+0x24`／`+0xE3`），长度无 5 上限；
  2. 名册在出陣画面以**每页 5 行**的列表展示（`0x44883D` 写 `msg+0x28 = 5`；`0x44888B` 用 `i<5 / i<0xA / else` 算滚动位置）；
  3. 玩家选中哪一行，哪一行的下标就被写进 `army+0x04`（`0x4496C8`/`0x44984B`）；
  4. **只有这一行会变成战场单位**（`0x448690`），其余条目留在名册里，
     作为面板数字（`0x446F73` 武將數 / `0x446FBE` 兵數）与战后被俘/逃脱的候选（`0x447037`/`0x447410`）。
  ⇒ **5 不会都上场，也不是「前 3 个」上场：永远是 1 个**。`[确认]`

### 1.4 士兵与将领的关系：士兵归属「军团 unit」，不是将领个人 ——`[确认]`

* 士兵记录数组在 unit 内部：`unit+0xB4 + i*0x48`，记录数 `unit+0x58`，
  记录 `+0x40` = 所属 unit（`0x43A780: cmp [ecx+0x40], 0x4B03A0` 判侧）、`+0x1C` = 兵种 id（`general+0x8B`）、
  `+0x44` = 兵的图形对象（`[obj+0x84]` 反指记录）。
* **数量来自「一个」将领**（主将）：B 侧 `0x442EFA` 里
  `0x44304F movsx ecx, word [eax+0x44]`（带兵数）、`0x443063 movsx edx, word [ecx+0x42]`（带兵上限）→
  `[ebp-0x10] = min(带兵数, 带兵上限)`；`0x443087/0x44309B` 同理得 `[ebp-0x34] = min(+0x48 骑兵, +0x46 骑兵上限)`；
  然后 `0x443118 mov [edx+0x58], ecx` = **步 + 骑**，`0x443124 mov [eax+0x5C], edx` 复制到「士兵总数」。
  A 侧 `0x443498` 有一段完全同构的代码（`0x4435ED` / `0x443601` / `0x443625` / `0x443639` / `0x4436B6` / `0x4436C2`）。
* 铺兵由阵形几何驱动、按全局写指针顺序填槽，**不按将领循环**：
  `0x442D38` 用 `idx = [0x4B0380]`、`rec = unit + 0xB4 + idx*0x48`；`0x442CB6` 算落点
  （`pos = base + (0xC8 - n)/0x19`，再按 `arg` 修正）。生成期全局 `0x4B0380` / `0x4B7B18` 只在两个孪生生成器里出现
  （`0x442DE2`/`0x443768`、`0x442E56`/`0x443758`）。
* 结论：**不存在「每个副将带自己的兵上场」的机制**。副将的兵只体现在出陣面板的 `兵數` 总数里（`0x446FBE` 累加所有条目），
  不进入战场。

### 1.5 补充（本轮新发现）：出陣画面可以「选谁上场」——`[确认]` 机制 / `[推测]` 玩家语义

这条不改变「每侧 1 个将领单位」的结论，但推翻了本文早前写法里的「`army+0x04` 恒为 0」。

* **列表容器 handler `0x4487BB`**（`code` 取 `1`(init) / `0x800`(update) / `0x80000`）：
  - init（`0x4487EA`）：`cmp dword ptr [[0x4A6690]], 0x5`（army 条目数与 5 比较，决定 `msg+0x40`）；
    `0x448819`：`[msg+0x34] = army->+0x00`（总行数）；`msg+0x30 = 0`、`msg+0x2C = 0`（滚动）、
    **`msg+0x28 = 5`**（`0x44883D: c7 41 28 05 00 00 00`，每页 5 行）、`msg+0x24 = 0`、`msg+0x38 = 0`。
  - update（`0x44885D`）：`[msg+0x38] = army->+0x04`（选中项）；若它在视窗外则按 `i<5 → 0` / `i<0xA → 5` / `else → 10`（`0x44888B`/`0x4488A8`）重算滚动。
  ⇒ **「5」是这份名册列表的每页行数**（容器 1 份 + 5 个行描述符 `0x4906E0/0x490718/0x490750/0x490788/0x4907C0`，
  几何 `x=0x22, y=0x54+k*0x4E, w=0x8C, h=0x4C`，handler 都指向 `0x44960B`）。
* **每一行的 handler `0x44960B(msg, ?, code)`**：`code` 取 `1` / `2`(update) / `4`(confirm) / `0x200`。
  - update（`0x44964E`）：`idx = [0x49108C] + [msg+0x20]`；`idx < [0x491094]` 时调 `0x4491E9(msg, idx, sel?, 1)` 画那一行。
  - **confirm（`0x4496A2`）**：`if ([0x4A79C8] & 1) { idx = [0x49108C] + [msg+0x20]; if (idx < [0x491094]) { ecx = [0x4A6690]; [ecx+0x04] = idx; 0x41CAB5(0x491060, 0x800); } }`
    —— 字节 `8b 0d 90 66 4a 00 8b 55 fc 89 51 04`（**这就是 `army B+0x04` 的唯一非 0 写点**）。
    A 侧镜像在 `0x44984B`：`a1 8c 66 4a 00 8b 4d fc 89 48 04`（写 `army A+0x04`）。
* **每行怎么画** `0x4491E9(msg, index, ?, ?)`：`entry = [0x4A668C] + index*0x48 + 0x1C`（`0x44922C imul eax,eax,0x48`）；
  行首面板图 `0x491470 = "MENU\\WARPREP04"`（**WARPREP = 出陣准备画面**）；`entry+0x04 != 0` 时用 `0x455E4A(8)` 画「不在场」标记；
  名字 `0x46B910(0x9DDD, 0x9EB8, 0x400, general+0x0C, …)`；兵种 `0x449169(general+0x8B)`；
  再 `0x468A10(0x491480="%8s", 0x8410, 0xFFFF, …, general)`。
* **结论**：`army+0x04` 是「本场由谁上场」的选择位；它的两个非 0 写点都在出陣画面的名册列表 confirm 分支里，
  而 `0x448690` 就按它建单位。`[确认]`（写点与消费者都有字节证据）
* `[推测]` 玩家语义：列表在出陣画面（`WARPREP04`）里为双方各有一份，所以**玩家所属阵营那一份等价于「这一仗派谁上」**。
  不确定处：写入门控 `[0x4A79C8] & 1` 的语义未定（同一全局在 `0x4115D6` 用 `& 2` 决定是否跳过战斗请求、
  在 `0x448DFE` 用 `& 0x100` 决定出戰对话框倒计时），所以「敌方那份列表是否也可点」没有确认；
  但**无论点哪一行，场上都只有 1 个将领单位**，这一点不受影响。

### 1.6 命令层同样只有 1 个将领槽 ——`[确认]`

* 「武將出擊」`0x445491` 的两个分支都走 `0x444BA6`：
  - 查询（`arg==1`）：`[0x4A8AE0] & 4` 为真则不可用；否则取 `unit A` 的 `+0x08/+0x0C`（主将战场坐标），
    `0x43AF7A(x-1, y)` 探一格，若命中「自己的、`+0x24==0` 的对象」则返回 0，否则 1。
  - 执行（`arg!=1`）：`0x43ADED(0x4A8A60, 0, 1)` —— 字节 `6a 01 6a 00 68 60 8a 4a 00 e8 dd 61 ff ff`（`0x444C02`–`0x444C10`），
    即**只给命令槽 0 写 1**；随后 `[0x4A8AE0] |= 2`、`&= ~0x10`。
* `0x43ADED(army, which, cmd)`：`which == 0x100` 时 `for (i<8) army->[0x94 + i*4] = cmd`（全 8 槽）；
  `which == 0x101` 走另一分支。⇒ **命令槽数组 = `unit+0x94..0xB3`，共 8 个 dword**，
  第 0 槽是主将（「武將出擊」只动它），第 1–7 槽是士兵编组（前/後/左/右/中軍 × 前進/後退/集中/分散…）。
  没有「第 2 个将领」的槽位。

## 4. 与本作现状的差异表

**原作结论**：每侧 1 个将领单位；名册可以很多将，上场的只有 1 个（默认主将，出陣前可改选）；士兵属于军团、上限 200；没有 5 槽 / 前 3 上阵。

| 项 | 原作（EXE 事实） | 本作（当前实现） | 差异影响（玩家能感觉到什么） |
|---|---|---|---|
| 每侧将领单位数 | **1**（`0x43B9E2`、`0x448690`、`0x43A1C4`） | **1**（`game/src/core/battle.ts:845-858` push 一个 `isGeneral: true` 的单位，每侧恰一个） | **无差异**。这一层本来就对，不需要改 |
| 将领单位的选择 | 名册下标 `army+0x04`：默认 0（主将），**出陣列表可改**（`0x4496D1`/`0x449853`） | `SideConfig.general` 单一主将，进战斗前不可换 | 「这一仗派谁上」原作可以挑，本作不能。**玩家能感觉到**：守城/多将部队时不能换一个更合适的人上场 |
| 出陣槽数 | **无槽**；部队武将链无 5 上限（`0x438948`；结构上限 15 `[推测]`） | `deploy_queue.ts:29` `DEPLOY_SLOTS = 5` | 编成页强制 5 格。玩家看到「只能编 5 个」这个原作不存在的限制（原作的「5」只是名册列表每页行数，`0x44883D`） |
| 「前 N 上阵」 | **不存在**；只有 1 个上场（可选的） | `deploy_queue.ts:32` `DEPLOY_FIELD_SLOTS = 3`；`deploy.html:547` 前 3 格标「上陣」，第 4/5 格标「預備」 | 玩家会以为「预备槽的将会在某个时机顶上来」。原作没有这个机制 → **预期被误导**。实际战斗里 3 个上阵槽的后 2 个也不上场 |
| 副将的角色 | 名册条目：只进出陣面板数字 + 战后被俘/逃脱结算（`0x447037`、`0x447410`） | `officers: PostGeneral[]`（`battle.ts:329/699`）只参加战后处置（`capture.ts:388-405`）+ 战功经验（`battle.ts:2903-2907`） | **语义已经基本对**。差一点：原作把**主将自己也算在名册**里统一结算，本作 `officers` 不含主将（`ourCount = 1 + officers.length` 补上了） |
| 士兵归属 | unit 级数组（`unit+0xB4`，stride 0x48） | `world.units` 里每兵一个 `Unit`（`battle.ts:808-819`） | 表现一致（都是一兵一单位），内部模型不同 |
| 士兵数量 | `min(g+0x44,g+0x42) + min(g+0x48,g+0x46)`，上限 200/侧（`0x443118`、`0x43AA44`） | `soldiers = cfg.soldiers`（≤100）+ `cavalry = min(soldiers, cavalryCapOf(level))`（≤100） | 上限同为 200，但公式不同：本作 `cavalry` 是 `soldiers` 的**子集**，原作是**步 + 骑两栏相加**。等级低时本作骑兵=0（`cavalryCapOf`），原作骑兵上限独立 |
| 命令下发对象 | 8 个命令槽（`unit+0x94..0xB3`，`0x43ADED`）：槽0 主将（「武將出擊」只写它，`0x444C02`）、槽1..7 士兵编组 | `army_cmd.ts` 的编组命令 | 概念一致 |
| 战后处置 | 遍历名册所有 `status==3` 条目，逐个判定被俘/逃脱（`0x447037`/`0x447410`） | `capture.ts` 按 officers 顺序逐个 | 一致；但原作被俘名单可以包含**同部队的全部武将**，本作只含 `officers` |
| 「武將出擊」 | `0x445491`，对单个 unit 下命令 | 有对应按钮 | 无差异 |

## 6. 反证尝试与未解项（如实记录）

**做过的反证尝试（都失败 ⇒ 支持「每侧 1 将」）**

1. 找「第 2/第 3 个将领单位」：`G2/G3` 只有两个句柄槽（`0x43BA59`）；`0x43B9E2` 把「对面」写死成另一个全局；`0x4A8B00`–`0x4B0399` 零引用。
2. 找「战斗中换将」：`army+0x04` 的非 0 写点只有出陣名册列表的 2 处（`0x4496C8`/`0x44984B`，都在**建单位之前**的
   出陣画面）；开战后没有任何写点，主将死亡后 `0x448DBF` 仍 `call 0x448690` 用**同一个下标**重建，不会顶上一个新的将。
3. 找 MAGIC.INI 的「主將2/主將3」实现：`0x42F2B9` 解析成 0x30/0x40 写进技记录 `+0x0E`；但全 `.text` **没有** `test`/`and` 用 0x30 掩码，战场也没有第 2/第 3 个将可指。⇒ 只是数据表标签。
4. 找「援军/第二战场」：`0x4A8A20`/`0x4A8A24`（`docs/04b` 称援军指针）**只写不读**；EXE 无「援軍」字符串。⇒ `docs/04b` 第 20 行说法错误。
5. 找「5 个将领槽」：部队 `+0x10` = 军师（面板 `"軍師   %s"` 实证）、`+0x1C` = 武将链头（`0x438948` 头插）。⇒ `project/162` 的 5 槽表是误读。
6. 找「士兵按将领分配」：士兵记录 `+0x40` 只指 unit（A/B 二选一），`+0x1C` 只存兵种；数量只由主将一个 general 的 `+0x42/+0x44/+0x46/+0x48` 决定。

**未解 / 没找到**

1. `[推测]` 的「名册结构上限 15」没有显式代码检查（`0x446B52` 无边界判断），是从 `army` 定长 0x460 与 `+0x454` 军师字段推的。
2. 出陣菜单「武將位置」（`0x448F23` → 面板 `0x490F30`）的具体内容没查（面板数据在资源/脚本侧，不在 `.text` 里）。它**不影响**本文结论（单位生成只有一处），但「玩家能不能手动指定主将站位」这一点没确认。
3. 部队层「谁能当主将」的规则没查：`部队+0x0C` 的写入点未定位（只确认了读法：`0x418A07` 面板 + `0x446E6D` 名册 swap）。
4. `0x4A8144` 战场阶段变量（取值 1/2/4/8）的确切语义没查全，只知道 `0x447D8C`/`0x44904B` 置 4、`0x446B37`/`0x44787F` 置 2、`0x448644` 置 8。

6. 出陣列表写入门控 `[0x4A79C8] & 1` 的语义没定：同一全局在 `0x4115D6` 用 `& 2`（决定是否跳过战斗请求）、
   在 `0x448DFE` 用 `& 0x100`（出戰对话框倒计时门控）。所以「敌方那份名册列表能不能点」**没找到答案**；
   但写入门控只影响「能不能改选」，不影响「场上只有 1 个将领单位」。
7. `0x43B7D0`（`for i<8` 读 `p[i+0x54]` 判 `0x10`/`0x40` 位）的实参 `p` 没能确定：
   它由 `0x4035D6` 传入，而 `0x4035D6` 所在函数反汇编错位，`p` 来源未定位。
   命令槽数组本身已由 `0x43ADED` 确认为 `unit+0x94..0xB3`（8 个 dword），所以「8 槽 = 1 将 + 7 组」的结论不依赖 7。
