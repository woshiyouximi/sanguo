## 0. 一句话结论

**真机（MuMu 模拟器）已复现并确证根因：`MainActivity.boot()` 在 `setContentView()` 之前调用 `goFullscreen()`，API 30+ 的 `getWindow().getInsetsController()` 此时会抛 `NullPointerException`（抛点在 `PhoneWindow` 内部，`getWindow()` 不为 null，所以普通判空拦不住），异常冲出 `onCreate` → 闪退 / 点了没反应。** 1.0 和 1.1 都是这么死的；1.2 已修（挪位置 + try/catch + 回落旧式全屏），详见 §0.5 与 §2.0。

**装不上/必崩的常见原因（缺 INTERNET、缺 `exported`、明文被拦、签名、dex 引用不存在的 API、`goFullscreen` 缺 `SDK_INT` 保护）在产物里逐条都不成立**——我用 `aapt2 dump badging`、`aapt2 dump xmltree`、`apksigner verify`、`dexdump` 逐项验过（见 §3），真机也确实把 Activity 拉起来了（`Activity.performCreate` → `onCreate`），只是死在 onCreate 里。

崩点修掉之后还剩一个**未证伪的第二可能**：`campaign.html` 是 302 KB、5,371 行的内联 `<script type="module">`，含 **143 处 `?.`、22 处 `??`**，整仓还用到了顶层 await → 要求 **WebView 内核 ≥ Chromium 89**；API 30 的 AOSP 镜像只有 83。**这一页在老内核上解析期就 SyntaxError：一行 JS 不执行、Java 无异常、页面无 error 事件 → 壳起来了也是黑框。**（§2.1，待 smoke 包打出版本号定论。）

1.0 的壳对这两类失败**都是零防御**：不探测内核版本、不显示 `onReceivedError`、不写崩溃日志、崩溃也不兜——这才是「点了图标没反应，怎么查都查不出来」的真正机制。1.1 补上诊断（这次就是它自己把栈打出来的），1.2 再修掉崩点。**sanguo-smoke.apk** 则是把「壳坏了」和「内核太旧」一刀切开的探针：一页 ES5，直接把内核版本 / `?.` / `??` / ESM / 200 / 206 / 404 全打出来。

## 0.6 第二个 bug（1.3 修）：mimeType 带了 charset → 整页被当纯文本渲染

用户装上 1.2 后发来第二张截图（`F:\sanguo\work\apk206\07-device-rawhtml-1.2.png`，768×1352，31 万字节，原图 sha256 `8b9ce79661d570f06b426fcb0df12d74194d6be70c83191de7051d5b51285ae2`）：

- 壳**起来了**（说明 1.2 的 `goFullscreen` 修复有效），`campaign.html` 也**加载了**；
- 但屏幕上显示的是**等宽字体的 HTML/CSS 源码**：首行 `< !doctype html>`，往下能读到 `:root{--bg:#0E1116;…}`、`#list{flex:1 1 auto;…}`；
- 底部一条红色横幅 `子资源加载失败 404：/favicon.ico` —— 这是 1.1 加的 `banner` 在正常工作（探针也证明拦截层在用）。

**根因**：`AssetHandler` 把 `HttpUtil.mimeOf()` 的**完整值**（`text/html; charset=utf-8`）当成 `WebResourceResponse` 的 `mimeType` 传了进去。这个字段会被原样写进 Chromium 的 `net::HttpResponseInfo.mime_type`，而 Blink 判断「这是不是 HTML」用的是**字符串全等**（`IsHTMLMimeType()` 只认 `text/html`）→ 认不出来 → 整页按纯文本渲染。`Content-Type` 响应头带参数是对的，**只有 `WebResourceResponse` 的 mimeType 这个字段不能带**；charset 必须走构造函数的 `encoding` 参数。

**修法（1.3）**：

| 位置 | 改动 |
|---|---|
| `F:\sanguo\apk\java\com\sanguo\webview\HttpUtil.java` | 新增 `public static String mimeTypeOf(String full)`（取 `;` 前的裸类型，null→`application/octet-stream`）与 `public static String charsetOf(String full)`（有 `charset=` 取其值；没有则 `text/*`、`application/json`、`+json`、`application/xml`、`+xml`、`image/svg+xml` 给 `utf-8`，二进制给 `null`） |
| `F:\sanguo\apk\java\com\sanguo\webview\AssetHandler.java` | 5 处 `new WebResourceResponse(...)` 全部改成「裸类型 + encoding」；`baseHeaders()` 仍发完整 `Content-Type`（含 charset），HTTP 语义不变 |
| `F:\sanguo\apk\java\com\sanguo\webview\MainActivity.java` | `onLoadError()` 对 `/favicon.ico` 的 404 **静默忽略**（Chromium 自己来要的，assets 里没有），否则每次进游戏底部都会弹一条红条，让人以为又坏了 |
| `F:\sanguo\apk\test\java\com\sanguo\webview\AssetPathTest.java` | 新增 `③b 裸 mimeType（真机黑屏回归）`：10 个代表路径断言裸类型不含 `;`、html/js 给 `utf-8`、mp3/webp 为 `null`，再对全部扩展名扫一遍 |

单元测试因此从 42 条涨到 **68 条**（烟雾包 36 → 62），构建脚本 `[4c/10]` 每次都会跑 —— 这条 bug 不可能再悄悄回归。

## 2. 根因判定（按可能性排序）

### 2.0 【已确证 · 真机复现】`goFullscreen()` 在 decor view 还没建时就摸 `getInsetsController()` → `NullPointerException` → onCreate 直接死

这是**唯一的已确证根因**。MuMu 模拟器（Android 12 / API 31+ 分支，见 §0.5 截图）装 1.1 后立刻复现：

```
启动失败：java.lang.NullPointerException：Attempt to invoke virtual method
'android.view.WindowInsetsController com.android.internal.policy.DecorView.getWindowInsetsController()'
on a null object reference

at com.android.internal.policy.PhoneWindow.getInsetsController(PhoneWindow.java:3931)
at com.sanguo.webview.MainActivity.goFullscreen(MainActivity.java:691)
at com.sanguo.webview.MainActivity.boot(MainActivity.java:131)
at com.sanguo.webview.MainActivity.onCreate(MainActivity.java:122)
```

机制：`boot()` 第一件事就是 `goFullscreen()`，那时 `setContentView()` 还没调，window 尚未 attach、decor 未创建；API 30+ 的 `PhoneWindow.getInsetsController()` 内部要取 decor，`mDecor == null` 就抛 NPE。**注意抛点在 `PhoneWindow` 内部，外面 `getWindow()` 并不为 null，所以 `if (c != null)` 这种判空拦不住**——1.0 和 1.1 都是这么死的。1.0 的 `onCreate` 又只在建 `AssetServer` 那段有 try/catch，于是异常直接冲出 → 无任何界面的闪退/黑屏。

1.2 的修法（§4.2、§0.5）：①`boot()` 里把 `goFullscreen()` 挪到 `setContentView(root)` 之后；②`goFullscreen()` 整体 try/catch，任何失败都回落到旧式 `setSystemUiVisibility`，全屏失败绝不影响启动。

一条旁证：1.0 的失败形态「有时闪过一下就没了」正是未捕获异常；而「点图标没反应」是因为崩溃发生得太早，连一帧都没画。

### 2.1 【次可能 · 尚未证伪，1.2 已加门控告警】WebView 内核 < Chromium 89，campaign.html 解析期 SyntaxError

**证据 A · 页面要求的语法门槛**

`F:\sanguo\game\web\campaign.html`：302,404 B，其中内联 `<script type="module">` 占 **216,172 字符 / 5,371 行**。

### 2.2 【与 §2.0 是同一处代码 · 1.0 的版本】`goFullscreen()` 对 `getInsetsController()` 没有兜底

1.0 的 `MainActivity.goFullscreen()`：

```java
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.R) {
    WindowInsetsController c = getWindow().getInsetsController();   // 可能返回 null
    c.hide(WindowInsets.Type.statusBars() | WindowInsets.Type.navigationBars());  // ← NPE
    ...
}
```

`onCreate` 只在「创建 AssetServer」那一段有 try/catch，`goFullscreen()` 在它之前、无保护。某些模拟器/ROM 上 `getInsetsController()` 确实返回 null → **onCreate 里 NPE → 直接闪退（连黑屏都看不到）**。这一条我在 1.1 里做了判空（`MainActivity.java:689` 起）。

> 注：任务里怀疑的「`WindowInsetsController` 没有 SDK_INT 保护」**不成立**——1.0 的源码有 `SDK_INT >= R` 分支，dex 字节码也证实了（§3.4）。真正的缺陷是**没判空**，不是没分版本。

### 2.3 【并存】1.0 的 socket 方案本身有三个先天问题

1. **随机端口 ⇒ 每次启动换 origin**：`AssetServer.start()` 用 `new ServerSocket(0, ...)`，页面地址是 `http://127.0.0.1:<随机端口>`。WebView 的 `localStorage` 按 origin 隔离，而 `game\web\main.js:913` 读 `localStorage['sanguo_campaign_v1']`、`:996/:1003/:1013` 写它 → **每次冷启动存档都读不到**（玩家视角：「进去是空的/像没启动」）。
2. **`assets.openFd().getLength()` 可能是 `UNKNOWN_LENGTH = -1`**，回落分支又拿 `src.available()` 当 `Content-Length` → 长度错 → 页面静默半死。
3. **`Connection: close` + 8 线程固定池**：首屏要 1,678 个请求，落在这套手写 HTTP 上，慢和截断都正常。

### 2.4 【放大器，不是根因】1.0 的壳对页面失败**完全没有可见性**

无内核探测、无 `onReceivedError` 展示、无 `onReceivedHttpError`、无 crash.log、TAG 还是随意的 `MainActivity`。所以上面任何一条发生时，用户只能看到黑屏——这也是「多次测试无法定位」的直接原因。

## 8. 仍未验证的部分（必须说清楚）

**已经确证、不再是推断的**：§2.0 的 `goFullscreen` NPE —— 用户在 MuMu 模拟器上装 1.1 后一次复现，栈打到屏幕上（§0.5）。1.2 修的就是它；同时也证明了「安装 / 签名 / manifest / INTERNET / exported / Activity 被系统拉起」这几环全是通的（`Activity.performCreate` → `onCreate` 都走到了）。

**仍未验证的**：

1. **1.2 本身还没有设备实测**：本机 `adb devices` 为空，SDK 里没有 emulator 二进制、没有 system-images、没有 AVD。修复逻辑（挪到 `setContentView` 之后 + try/catch + 回落旧式全屏）是确定性的，但「装上去能起」需要用户那台模拟器点头——这一次的崩溃也正是这么被抓出来的。
2. **崩点修掉之后，页面能不能真的跑起来**：1.1 死得太早，从来没走到 `loadUrl`；1.2 才是第一次真正加载 `campaign.html`。这台 MuMu 的 WebView 版本未知，若 < Chromium 89 就会停在「WebView 内核太旧」说明页（§2.1），**需要装一次 smoke 把版本号打出来才能定论**。
3. **`available()` 语义**：`AssetHandler` 用 `AssetInputStream.available()` 当 `Content-Length`（注释里写了推导：STORED asset → `Asset::getRemainingLength()`）。桌面 JVM 测不到 Android 的 `AssetInputStream`。→ smoke 页会把 `Content-Length` 打出来，**等于 5571 才算这条假设成立**。
4. **`appassets.androidplatform.net` 的 localStorage 持久性**：origin 固定是设计目标，但「WebView 对拦截应答是否允许 localStorage/IndexedDB」在不同内核版本上要实测（`chrome://inspect` 里 `localStorage.getItem('sanguo_campaign_v1')` 一看便知）。这就是把 origin 从随机端口换掉的理由，但没跑过真机不敢说 100%。
5. **Range 在 `<audio>` 上的实际拖动**：协议层面 206 / `Content-Range` / `Accept-Ranges` 已经对齐（桌面单测 42/42、HTTP 语义已查），但「拖动进度条真的能续播」只能在设备上听。
