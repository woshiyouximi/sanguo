## 1. mp3 编码参数与前后体积

### 1.1 源文件不是统一码率（这是 80k 方案翻车的原因）

实测 `dist\audio-cdn\audio\bgm`：只有 `04/05/06` 是 **128 kbps stereo 44.1 kHz**，其余 7 档早就是
**64 kbps mono 44.1 kHz**。按父任务给的 80k 统一转，mono 档会被**反向放大到 125.1%**，BGM 反而
从 13.38 MB 变成 12.66 MB 只降 5%，总包会冲到 ~32.4 MB 超限。

另：MP3 合法码率只有 32/40/48/56/64/80/96/112/128…，先试的 `-BgmKbps 54` 被 lame **就近吞回 56k**
（10 档字节与 56k 完全一致）。脚本头已写明这一点。

### 1.2 最终参数（按源声道分档，只降不升）

```
ffmpeg -hide_banner -loglevel error -nostdin -y -i <src> -codec:a libmp3lame -b:a <rate> -f mp3 <tmp>
```

- stereo 源（128k）→ **56 kbps**；mono 源（64k）→ **48 kbps**；`-ar` 不动（44.1 kHz）；
- SFX 99 档 **原样字节复制**（96 kbps mono 22.05 kHz，不走 ffmpeg）。

## 2. bundle 选择：复用 res 分包的 `audio\` 子目录，不新建 bundle

读现状后选**现有 `res` 分包**，理由：

1. **路径约定已经指向这里**：`AudioBus.audioPath()`（`game\cocos\assets\scripts\AudioBus.ts:127`）返回
   `audio/bgm/<NN>` / `audio/sfx/<名>`，`AudioHost.loadBundleClip()` 通过 `getResBundle()` 载入，
   manifest 的 key 也用同一套逻辑名（`audio/sfx/hit01`）。音频放 `res/audio/` 是零改动对接。
2. **res 本来就是上传用分包**：`-Mode upload` 下 `work\pack_subpackage.mjs` 把 `assets/res` 整体挪到
   `subpackages/res`，`res` bundle 的 `config.*.json` 自动登记新增的 109 个 AudioClip + 1 个 JsonAsset
   （本次实测 `paths=2915`，类型表含 `cc.AudioClip`）。
3. **新 bundle 接不进现有构建**：`tools\build_wechat.ps1` 调 Cocos CLI 只传
   `platform/debug/md5Cache/buildPath/startScene`（脚本头注释 4 已说明不能传 bundleConfigs），
   新建 `audio` bundle 要另外改构建参数 + 加载器 + 分包声明，收益为零。
4. `game\cocos\assets\bundles\` 现状只有 `res`（`res.meta` 之外无别的 bundle），不引入第二套目录约定。

加载链行为（实现后）：

1. `loadClip()` → `remoteBase`：配置传 `''` 强制本地；传 URL 强制远端；不传则读包内 `audio-remote`（源码 base 为空 → 本地）。
2. 本地：`ensureLocalManifest()` 载 `audio-manifest`（JsonAsset）→ `bundle.load(<去扩展名路径>, AudioClip)`。
3. 远端：`base` 非空时先 `audio-manifest.json` + `assetManager.loadRemote`；任何一步失败 → 回落 `loadBundleClip`，不抛。
4. 缺档：清单里没有 → 静默 null（`stats.missing` 由上层播放失败计数）；清单里有但 bundle 载不到 → `warnOnce` 一条，战斗继续。

`tsc -p tsconfig.json --noEmit`（Cocos 自带 TS）过滤后 AudioHost.ts **无报错**（其余报错是 `DataLoader.ts` 的
`fromEntries` 等既有 lib-target 噪声）。

## 7. 仍缺什么 / 风险

1. **首次播放延迟**：本地读盘已不是瓶颈（Resource-Timing 13/10/29/7 ms，含 HTTP 开销），但 mp3 **解码**
   到可播的耗时没打点；本次只观察到 `loadScene('Battle')` 后 6 s 内 BGM `playing=true`。要量化首帧可听时间，
   需在 `playBgm`/首帧处加 `performance.mark` 或真机录屏。
2. **内存**：mp3 解码后 PCM 常驻（stereo 44.1 kHz ≈176.4 KB/s）。10 档 BGM 若全解 ~200 MB 量级，
   实际只会驻留当前用到的（本场 2 档 ≈ 3.5 MB）。微信小游戏 AudioContext/buffer 上限未真机验证；
   长时间切歌是否有泄漏看 `stats`/`clips` 已可观测。
3. **真机未测**：CDP 只覆盖 web-mobile。微信开发者工具/真机的音频策略（iOS 静音键、WebAudio 不可用回退
   `InnerAudioContext`、分包首次加载时机）仍需一次真机验证；本报告只证明 web 构建产物内音频路径正确。
4. **30 MB 计量口径**：官方文档只写 "30M"，没有字节口径。本包按 MiB 余 2.24 MiB，按十进制余 0.89 MB；
   再往包里加约 0.8 MB 内容就会在十进制口径越线，加资源前先看 `pkg_numbers.txt` 的算法。
5. **回退 CDN 的注意点**：源码 `res\audio` 已被替换成 56k/48k；再跑 `-Audio cdn` 时 `Write-AudioCdn` 会从
   源码重拷，**会把 `dist\audio-cdn` 覆盖成压缩版**。原始母带仍在 `game\web\assets\audio\`（未动，web 版路径不变），
   需要原始码率时用 `tools\pack_audio_local.ps1 -Source F:\sanguo\game\web\assets\audio` 重转，或先备份
   `dist\audio-cdn`。

## R199b · 真机 20MB 上限逼出的二次压缩（[确认]）

### 关键事实：这个账号的总包上限是 **20MB**，不是 30MB

`cli.bat preview --project dist\wechat-upload`（27.76 MiB 包）报：

```
错误码：80051, source size 23388KB exceed max limit 20MB
```

官方文档写的是「总包不超过 30M」，但**该 AppID 实际按 20MB 卡**（可能受虚拟支付未开通影响）。CLI 上传同一份 27.76 MiB 包也是这个错，所以与 GUI 缓存无关。

### 代价（必须说清）

- BGM 由 128k stereo / 64k mono 统一降到 **32k mono 32kHz**，音质明显下降（1998 年配乐素材本来简单，但仍听得出变闷）。
- SFX 从 96k mono 降到 32k mono 22.05kHz，刀剑/弓弦的瞬态会糊一点。
- 想要原音质 + 全本地，只能：①开虚拟支付把上限抬到 30MB；②把大图转 WebP 腾 3–4MB；③音乐回到 CDN（需真 base）。
