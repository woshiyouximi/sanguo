## 0. 先纠一个前提：旧的"52 条"和"42 条"两个数都不可信

这一步很关键，否则整个分诊会建在噪声上。

**A. 旧探针的判定公式漏了 `killed`/`dmgA`，却把战斗噪声当成了技能效果**

`work\skillwait\probe_all_magics2.mjs:70` 的公式是

```js
row.effect = markDmg>0||markKills>0||markHeal>0||markSummon>0||dmgB>0||dStatus||dMorale||dTire||dMp||dCount
```

其中 `dmgB`（B 方主将掉血）、`dmgA`、`killed` 全部是**普通近战自己就会产生**的量。控制组实测（`work\skillwait\control.mjs`，同 seed 同场景**不放技能**跑 400 tick）：

```
{"dmgB":0,"dmgA":3,"killed":11,"marks":0}
```

⇒ 不放技能，400 tick 内也会打死 11 个 B 兵、打掉 A 主将 3 血。所以 **`killed>0`/`dmgA>0`/`dmgB>0` 一律不能当技能生效证据**；旧公式里 `dMp` 更糟——施法本身扣主将 mp，那一项**恒真**。

**B. 两个口径给出的清单互相矛盾**

| 探针 | 条件 | 无效果数 | 清单 |
|---|---|---|---|
| `probe_all_magics.mjs`（8:58，用户引用的 final2） | 窄口径（只 伤害/击杀/治疗/召唤） | **52** | 见任务书 |
| `probe_all_magics2.mjs`（宽口径，本次复跑 `base2.json`） | + `u.status`/士气/疲劳/主将 mp/单位数 | **42** | 3,4,8,9,12,14,15,18,22,24,25,26,27,28,30,32,39,40,42,44,47,53,54,55,61,64,66,67,69,70,74,77,80,84,89,90,92,98,102,103,108,110 |

两者交集 40，用户独有 12（5,17,19,31,37,48,57,58,75,81,91,105），宽口径独有 2（**seq 4 火箭 / seq 30 火箭天襲** —— 这两条在 final2 里"有效"，宽口径里"无效"，即新增坏技）。取**并集 54 条**作为工作集，两个口径的差异逐条在 §1 里给结论。

**C. 真正可信的判据只有"技能自己记账"**

引擎里唯一由技能会话自己写的账是 `world.skillMarks`（`battle.ts:2113 recordEffect()`）与会话统计 `session.hits/killed/healed`（`battle.ts:2143 finishSummary`）。所以 `probe_all_magics3.mjs` 的净口径是：

```js
hits>0 || killed>0 || healed>0 || castHits>0 || castHealed>0 || castKilled>0
|| markDmg>0 || markKills>0 || markHeal>0 || markSummon>0
|| dCount!==0 || dStatus || dMorale || dTire || dFoeMp>0
```

**不含**施法者自己的 mp/qi（那是施法成本，不是效果）。

## 2. §2 修了什么

### 2.1 决定性修复：逐帧命中链补"落点兜底"（`runtime.ts`）

**证据链**：同一段 MAGIC.SO 字节码，走同步模型 `runSkill()` 有伤害、走逐帧 `settleFrame()` 却 0 命中。原因在 `runtime.ts` 两个分支不一致：

- 同步：`runtime.ts:1117` 有兜底
  ```ts
  pts.push({ x: this.targetPoint.x / 96, y: this.targetPoint.y / 72, r: 1.4 });
  ```
  原注释：「脚本没有产出可判定的特效物件…按目标格做一次小范围判定，避免技能完全没有效果」。
- 逐帧：`resolveFrameHits()` 里**没有**这一支，`pts` 为空就直接 `return this.unhitUnits([])` ⇒ 整发 0 命中。

**改动**（`F:\sanguo\game\src\core\smartscript\runtime.ts:1170-1176`，`resolveFrameHits()` 末尾、`return this.unhitUnits(pts)` 之前）：

```ts
// 同一发技能走 `runSkill()` 有伤害、走逐帧 `settleFrame()` 却 0 命中（R145 的 89 条"实测无效果"）。
// 与 execute() 的同款兜底保持一致：脚本没产出可判定物件时，按目标格做一次小范围判定。
if (pts.length === 0 && !this.isHeal && !this.isSummon) {
  pts.push({ x: this.targetPoint.x / 96, y: this.targetPoint.y / 72, r: 1.4 });
}
```

**实测**：`v3a`（改前）110 条里只有 **21 条**有命中；`v3e`（改后）**101 条**。47 条 C1 全靠这一处（见 §1 的 `hits 0→60/72`）。

为什么不是"特效物件坐标没写对"：`objdiag.mjs` 实测 seq 8 火雷的 13 个物件 resource `44005/44007-44011` 全在 `(0.0,0.0)`、angle 已设（`0x15` 生效）、会话 `frames=35 done=true reason="技能虚拟帧超过 1200…脚本被截断"`；seq 3 地泉衝 22 个物件、**没有一个**落在 `1000..90000` 的资源带内。也就是说原作的落点是由 C 侧引擎按 target 摆放的，本模型没有对应端口 —— 逐帧路径必须自带兜底，这与 `execute()` 里既有的设计意图一致。

> 文件权限说明：任务书允许改 `runtime.ts` 的 `callScript` 分派与 opcode 实现；这处改动属于 **VM→World 的命中绑定（opcode/端口层）**，不涉及 session 调度，因此就地改并在此备案。

## 4. §4 剩余 7 条与原因（全部 `[阻塞]`）

**7 条**：seq 5 伏兵組陣 / 17 伏兵排陣 / 19 後伏連兵 / 31 後伏兵陣 / 37 後伏軍陣 / 57 伏兵班陣 / 81 伏兵連陣。属性全是 `補兵`。

**调用链**（逐层反汇编）：

1. `MAGIC.SO` 的 `Magic9`（`magic_so.dis.txt` 03AC00 起）只有 4 条指令：
   `PUSHI 17; PUSHI 0; CALL MoreSoldier; RET 0`
2. `MoreSoldier`（argc=2，145 条指令，`dis1.mjs MoreSoldier`）关键段：
   ```
   0054DC  LDSL loc3 ; SYSCALL 0x116, 1   -> loc6
   0054F8  loc6 > 40 ? loc6 = 40
   005524  loc6*5 ; SYSCALL 0x10C(loc3) ; SUB -> loc7
   0055B0  loc7 != 0 ? 继续 : JMP CastFail
   0055CC  PUSHS "ProduceSoldier" ; loc3 ; loc7 ; 0 ; 0 ; CALLS
   ```
3. `ProduceSoldier`（func #51，168 条指令）：
   ```
   004F1C  SYSCALL 0x12D -> loc6
   004F30  SYSCALL 0x12E -> loc7 ; loc2 = loc7/2
   004F8C  SYSCALL 0x113(loc1, loc2) -> loc3
   004FE4  loc3 == 0 ? JMP CastFail : SYSCALL 0x119(loc1, loc2) // summon
   ```

**断点（两处，都需要原作语义才能继续）**：

- **`0x113`**：现实现是 `ctx.unitAtPx(a(0)*96+48, a(1)*72+36)`（`syscalls.ts:383`）—— 把两个参数当**格坐标**、只找**存活**单位。但 MAGIC.SO 里 24 个调用点两种用法并存：一部分前面紧跟 `PUSHI 72; DIV`（`magic_so.dis.txt` 014EFC/014F4C/015098/0150E8 —— 确实是把像素 y 转成格行），另一部分（`ProduceSoldier`/`MoreSoldier`）传的是 `(方向, 槽位号)` 这种小整数，且需要返回**已阵亡**的兵槽（補兵的全部意义就是复活死兵）。两种语义无法用同一实现兼容。
  `[阻塞]` 需要：`0x43AFAA` 的函数体（不在 export 里）；或至少一份原作里"阵亡兵槽是否仍占位"的行为证据。
- **`0x10C`**：现实现 `return r(ctx.unitSide(a(0)))`（0/1）。但 `MoreSoldier` 用 `loc6*5 - 0x10C(loc3)` 算补兵数，把它当"该方存活兵数"用。若按 0/1 解释，`loc7` 会恒等于 `loc6*5-0/1`（≈200）然后被 `arg2` 夹到 17 —— 数值上恰好不致命，所以这条不是唯一断点；真正让它 `CastFail` 的是 `0x113` 返回 0。
