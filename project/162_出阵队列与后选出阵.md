## §1 数据结构与语义

### 1.1 对照原作 Obj3 部队池的 5 个武将槽

`docs/07b_存档字段详解.md` §6：Obj3 部队池 = `128 × 0x70`（记录 `0x6C` + 4 字节长度），池指针 `[0x4A662C] = malloc(0x3600)`，取址 `0x43884C(i) = i < 0x80 ? [0x4A662C] + i*0x6C : 0`。一支部队 = 所属君主 + **5 个武将槽** + 4 个城池引用 + 路径下标 + next/prev，即地图上移动的军团：

| 原作偏移 | 含义 | 本作字段 |
|---|---|---|
| `+0x00C` | 所属君主 `King` | 存档既有 `king`/`force`（未改） |
| `+0x010` | 武将槽 1（`u32 Idx(General*)`） | `deployQueue[0].general`（主将） |
| `+0x014` | 武将槽 2 | `deployQueue[1].general` |
| `+0x018` | 武将槽 3 | `deployQueue[2].general` |
| `+0x01C` | 武将槽 4 | `deployQueue[3].general` |
| `+0x020` | 武将槽 5 | `deployQueue[4].general` |

**槽位顺序 = 出阵顺序**。原作没有单独的「兵种表」，兵种挂在武将/部队上，本作把它落在每槽的 `troop` 上；`troops` 是该槽带兵数（原作的兵数在部队/武将侧，本作沿用编成页既有的 1..100 口径）。

### 1.2 类型（`game/src/core/deploy_queue.ts:29-56`）

```ts
export const DEPLOY_SLOTS = 5;        // Obj3 每队 5 个武将槽
export const DEPLOY_FIELD_SLOTS = 3;  // 战斗上阵 3 个单位（seq 3 放开重排的就是这 3 槽）
export const DEFAULT_TROOP = '刀';
export const DEFAULT_TROOPS = 100;

export interface DeploySlot { general: string; troop: string; troops: number }
export type DeployQueue = DeploySlot[];
export interface DeployQueueSave { deployQueue?: unknown }
export interface AfterFoePlan { foe: DeployQueue; mine: DeployQueue; fieldSlots: number; reorderable: number[] }
```

- `general` 存**武将名**（`generals.json` 的 `NAME`）：存档里武将在各表用名字索引（`generalLevel`/`learned`/`loyal` 都是 name→值），存名字比存下标抗剧本差异。
- `troop` 存**单字兵种**（刀/槍/弓/鍊/飛/武/蠻/鐵/籐/賊/弩/女）：web 与 Cocos 读同一个字段，不能一边存「朴刀」一边存「刀」。
- `troops` 夹在 `1..100`（与编成页滑桿、`troopCapOf` 上限同一口径；上限在 UI 侧再按等级夹一次）。

**为什么 `moveSlot` 带 `limit`**：编成页平时 5 槽都能调；军师技 seq 3 的语义是「开战前重排**上阵的 3 槽**」，预备的 2 槽不参战，所以界面按 `DEPLOY_FIELD_SLOTS` 限制 ▲▼ 的可点范围（`deploy.html:552-553`、`DeployRoot.ts:1343`）。

### 1.4 语义落点

1. **战前**：`wises.ts` `SPECS[3] = { kind:'deploy', op:'choose_after_foe', value: DEPLOY_FIELD_SLOTS }`；`applyWise` 走 `applySpec` 的 `case 'choose_after_foe'` 把 `world.army[side].chooseAfterFoe = true`（不碰任何数值）。
2. **战中派发**：`strategy.ts` 的 `case 'reserve'` 仍然只发 `afterfoe` + `note` 两个 op（原作 `0x44DE44` 只有一条成功日志 `0x491900`、零状态写入，照抄）；`applyOp` 的 `case 'afterfoe'` 也是立旗，不改数值。
3. **编成页消费**：`deploy.html` 在 `applyWise` 之后（同一存档）读 `save.deployQueue`，把前 3 槽做成可调序；`chooseAfterFoe()` 只是把这条规则表达成纯函数，实际 UI 用 `moveSlot(..., DEPLOY_FIELD_SLOTS)`。
4. **战斗内核不读 5 槽**：`battle.ts` 本轮禁改，仍只取主将上阵；队列目前影响的是「谁排在前 3 / 谁预备」与存档，不改变战场单位数（见 §5）。

## §4 旧档兼容性

**结论：旧档能读，零迁移；`deployQueue` 是 v3 的可选字段，不进 `SNAPSHOT_REQUIRED`、不开 v4。**

1. **读**：`saves.js` 容器本来就不做字段白名单，snapshot 是整份深拷贝；`upgradeSnapshot` / `ensureSnapshotShape` / `normalizeStore` 都不删未知键。`deployQueueOf(snapshot, fallback)` 在没有字段时按 fallback 生成，`queueOf` 同样，**两者都只读不写**，所以「打开一次旧档」不会伪造出队列。
2. **写**：`setDeployQueue` 只碰 `snapshot.deployQueue`；空队列会 `delete`，不留空数组。`normalizeCampaign`（`campaign.html:4334` 注释）「未知键一律原样留着」，当前 v3 的 `upgradeSnapshot` 返回同一对象，所以字段能活过 `normalizeCampaign`。
3. **战后续存**：`main.js` 的 `writeBackCampaign()` 是 `JSON.parse` 整份 legacy 对象→改若干字段→`JSON.stringify` 写回同一对象，未知字段不会被丢；Cocos `GameState.normalize` 也保留未知顶层键（`GameState.ts:319-324`）。
4. **版本升级**：v2→v3 的 `upgradeSnapshot` 逐跳补字段，不动 `deployQueue`。实测（`work/deployq/saves_helper_check.mjs`）：

```
missing -> [{"general":"A","troop":"刀","troops":100},...]     ← 缺字段按 fallback 生成
has(missing) -> false
roundtrip -> [{"general":"張飛","troop":"槍","troops":80},{"general":"關羽","troop":"刀","troops":100}]
upgrade keeps -> 同上  | from 3 to 3 changed true
v2->v3 keeps -> 同上  | steps ["v2→v3"]
empty deletes -> false                                          ← 空队列会删字段
```

5. **槽快照**：`deploy.html` 的 `persistQueue()` 同时写 legacy 键与「当前自动存档槽的 snapshot」，所以从大地图读槽（而不是等 legacy 新鲜度判定）也能看到队列；`campaign.html` 出征时再 `saveQueue(save, queueOf(...))` 兜一次，保证进 `deploy.html` 前存档已有 5 槽。

**还差的（旧档角度）**：旧档第一次进编成页时，队列是按「本城候选 5 将」自动生成的，顺序=候选排序（太守→STR+INT），不一定等于玩家当年心里的出阵序——这是没有历史数据可依，只能让玩家调一次；调完即落盘。

## §5 没做到 / 仍存疑（标 `[推测]`）

1. **原作 `0x44DE44` 零状态写入 vs 本作立旗**：原作分支只打一条日志（`0x491900`），「让使用方在敌方之后选将/兵种」是从 `ATTRIB=1`、`docs/03a:297` 与 Obj3 5 槽结构推出来的语义（`project/109` §5.3）。本作把它落成「战前立 `chooseAfterFoe` + 编成页可重排前 3 槽」，**没有原作直接的状态位可对**——`[推测]` 这是原作把选择交给 UI 流程、分支本身无事可做的合理解释。
2. **「3 槽」的依据**：`DEPLOY_FIELD_SLOTS = 3` 取的是本作战斗上阵单位数（战场同时 3 个单位），不是原作 Obj3 的字段。原作 Obj3 只有 5 个武将槽，没有「前 3 上阵」的显式字段——`[推测]` 5 槽里前若干槽参战、其余预备。
3. **战斗内核尚未消费 5 槽**：`battle.ts`（任务书禁改，且另一 agent 正在改）仍只取主将上场；队列目前只影响编成页/存档与「谁算主将」。真要让第 2、3 槽变成战场上的友军单位，需要改 `battle.ts` 的 `createWorld`/上阵逻辑——**超出本单允许范围**，未做。
4. **兵种字表**：web `TROOP_CHARS` 是 12 个去重单字（`TROOP_BY_CHAR` 去掉「關」），Cocos `TROOP_CHARS` 是 13 个下標（0 朴刀与 2 大刀都映射「刀」）。跨端只存单字，所以 0/2 会合并显示为「刀」——`[推测]` 原作兵种表里这两种本来就是同一类刀兵，UI 上的区分只在编成页的下标层。
