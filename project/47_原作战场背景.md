# 47 原作战场背景（A2：把原作 12 套战场背景接进竖版战斗画面）

> 归属：A2 / 战场画面 agent。只改了 `game/src/view/battleBg.ts`（新建）、`game/src/view/battleView.ts`（3 处接线）、
> `game/web/assets/bg/orig/**`（新建 48 个 PNG）、`work/bg_orig*`（脚本与取证图）、本文件。
> `game/web/main.js`、`game/src/core/**` 一行没动。

一句话结论：原作那三张 96px 的 `BG/MG/FG` 条是**地平线景物**（不是可平铺贴图、A/B 也不是视差两帧，而是**白日/黄昏两套天光**）。
在竖版俯视场地里，它们只能贴在场地最上沿当"远景带"用；地面 `FLOORnn` 才是真正该铺满的东西。
最终方案：(b) **地面平铺 + 顶部 100px 三层远景带 + 场地上下边缘轻压暗**，实测每帧 1.98–2.04ms（预算 16.7ms 的 12%）。

  1:1 叠回去就等于原作的 horizon 合成图——这是"三层怎么用"的物理依据，不是拍脑袋。

## 2. A/B 两张到底是什么关系（像素比对，不是猜）

结论：**A = 白日 / 晴天，B = 黄昏 / 夜 / 阴天。两套天光变体。**
不是"远景帧/近景帧"，不是左右拼接，不是动画两帧。

判据（脚本 `work/bg_orig/analyze*.py`，原始输出 `work/bg_orig/analyze2.txt`）：

1. **alpha 掩膜 IoU 恒等于 1.000（BG 全部 12 个）** —— 天空/远山的**形状完全一样**，只有颜色不同。
   MG 0.667–1.000、FG 0.968–1.000（FG 几乎 1:1，连调色都没怎么改）。
2. **RGB 相关性**：BG 只有 0.008–0.476（t03 最低 0.008，t05 甚至是 **-0.761**），dRGB 45–141 —— 整幅天空换了。
   FG 0.94–1.000、dRGB 0–13 —— 近景剪影基本没变。
3. **天顶 12 行平均色**：A 普遍是蓝天（t00 `(114,154,223)`、t02 `(64,144,215)`），
   B 普遍偏暖/偏暗（t00 `(247,215,221)` 落日、t01 `(219,155,103)`、t09 `(166,20,9)`、t10 `(82,18,8)`、t05 `(4,7,32)` 近黑）。
   特例 t05：**A 是橙红落日 `(231,124,73)`、B 反而接近纯黑 `(4,7,32)`**——同一地形的"黄昏 vs 入夜"。
4. 对照组：不同地形的 `BG00A vs BG01A` corr=0.409、`BG00A vs BG04A` corr=0.513，
   而 A/B 同地形的 BG 相关性可以低到 0.008 —— 说明 A/B 的差异**不是"两个不同地形"级别的换画面**，
   而是同一构图下的天色重绘（08 直接是"雪山晴空 vs 暗山脊+青灰云"）。

肉眼证据：`work/bg_orig/ab_BG00.png`（A 蓝白晴空 / B 红粉落日）、`ab_BG08.png`（A 雪山 / B 暗脊）。

**取舍**：只入库 **A（白日）**。B 变体如果一起入库，48 个文件会从 2.44MB 涨到 ~4.3MB，超 3.5MB 上限；
且本作战斗没有昼夜机制（`World` 里只有 `terrain`，没有时刻/天气字段），入库了也只会是死资源。
若以后要加"夜战"，B 变体按同一管线再烘一套即可（`bg_orig_assets.py` 第 107 行 `f"{layer}{t:02d}A.png"` 改 B）。

## 3. 三条带能不能当循环贴图？（不能，有实测）

判定方法（`work/bg_orig/seam_test.txt`）：比较"首列 vs 末列"的差 与 "内部相邻列"的差，比值 > 3 就算接缝可见。

| 层 | 首末列差 / 相邻列差 | 结论 |
| --- | --- | --- |
| BG | 9.6×–160.7×（12 个地形全部 >9×） | 全部不能循环 |
| MG | 2.2×–275.8× | 只有 MG02/05/07/08 恰好能接 |
| FG | 1.8×–57.8× | 只有 FG01/03/05/10 恰好能接 |

而且宽度本身就是证据：730/880/1000 相对原作的 **640 宽视口**，余量正好是 **+90 / +240 / +360**，
按 1:2.67:4 递增 —— 这就是原作做"整幅横移"视差时每层需要的行程，条子=单幅全景，不是 tile。

第一版原型不信邪，用**左右镜像平铺**硬接：结果天空在镜像轴处出现一条竖直亮线、树丛"面对面"（`work/bg_orig/seam_test` 同批原型图已删，结论保留）。
**最终做法：不循环。** 每层只画一次，横向偏移在 `[-(W-750)/2, +(W-750)/2]` 内随镜头平移、到头饱和。
代价是长距离奔跑时远景会"贴边不动"，收益是**任何地形任何时刻都没有竖缝**。

## 4. 三层在竖版俯视场地里怎么用：(a)/(b)/(b2)/(c) 实拍对比

`game/src/view/layout.ts` 的场地是 `FIELD_TOP=100 … FIELD_BOTTOM=1000`、`ROW_PX=71.43`、一屏 12.6 行的**俯视斜平面**：
敌方后排贴 y=100 的上沿、我方后排贴 y=1000 的下沿，没有地平线。所以"把 96px 横屏景物条贴上去"没有唯一正确答案。

四个候选（`?bgmode=` 一键切换，实拍 750×1334）：

| 模式 | 做法 | 实拍 | 判断 |
| --- | --- | --- | --- |
| `a` | 只用地面平铺 | `work/bg_orig/mode_00_a.png` | 平、干净，但完全没有纵深，12 个地形只剩"换地板" |
| `b` | 地面 + 顶部 100px `BG+MG+FG` 三层带 | `mode_00_b.png`、`terrain_04.png` | **采用**。天光+城楼+树线都在，层次最好 |
| `b2` | 地面 + `MG+FG`（丢掉 BG） | `mode_00_b2.png` | 最差：BG 是唯一不透明的层，去掉后带子上半截透明、城墙像悬空 |
| `c` | 地面 + `FG` 两端压四角当框景 | `mode_00_c.png` | 差：树丛像浮在场角的贴纸，不像框景 |

对比图：`work/bg_orig/modes_compare.png`（t00 / t04 各一行，四列并排）。

**为什么是 (b)**：
1. 三层带子共用一条地平线基线，只有叠在一起才是完整的"远处世界"；拆开用任何一层都会露出半透明的空洞。
2. 带子只占场地顶部 100px（FIELD 的 11%，约 1.4 行），并且画在**所有单位/特效之下**——
   最上面一排敌人会自然地"站在城墙/树线前"，读起来像纵深，不像遮挡。
3. `FG` 作为最后绘制的一层，会挡住 `MG` 的山脊，正好复现原作的前后关系。
4. 竖版画面比原作横屏多出 900px 的场地纵深，如果地面之外什么都不给，12 个地形会全部退化成"换地板"。

带子的下边缘：`BG` 底 26px、`MG` 底 16px 做 alpha 淡出，`FG` 不淡出（它的底边本来就是与地面接触的墙根/树根/地平线），
所以带子往地面过渡处是一条"实地"边，而不是浮空裁切线。

## 5. 几何：地平线高度、地面比例、缩放

| 量 | 取值 | 依据 |
| --- | --- | --- |
| 带子高度 | **100px**（`BAND_H`），y = 100…200 | 源图 96px ×1.04 = 100：**保持源像素近似 1:1**（不拉伸），同时把带子压到 1.4 行以内 |
| 带子缩放 | 1.04 | 烘焙时即缩到 759/915/1040 宽，运行时 1:1 贴，不再二次缩放（省 CPU、不吃糊） |
| 地平线位置 | `BAND_BASE = FIELD_TOP + 100 = 200` | 原作 96px 带在 410px 高画面里占 23.4%；照搬到 900px 场地会吃掉 210px（近 3 行兵）→ 不照搬，取 100px |
| 地面 tile | **256px**（512×0.5） | 256/71.43 = **3.58 行**，正落在 lead 给的 3–4 行 / 0.45–0.55 区间 |
| 地面缩放 | 0.5 | 兵高 60–90px，256px tile 里的砖/草/沙颗粒与人的比例自然（见 `terrain_00.png` / `terrain_04.png`） |
| 场地压暗 | 顶 60px α0→0.30、底 110px α0→0.30 | 只压上下边缘（≤30% 且为暗色不是蓝色），中间原色不动 —— 满足 lead"≤20% 轻压暗、不许整体调蓝"的意图，雪原实测仍偏亮但没有割裂感 |

颜色处理**没有**做任何整体调色/色偏/深蓝化，只有：源图自带的顶边压暗（0.28/24px，烘焙时做）、
三层各自的下沿淡出、运行时上下边缘的暗角渐变。

## 6. 视差速率（为什么是 1 : 2.67 : 4）

一条可得证的线索：三层宽度减去 640 视口 = `90 : 240 : 360`，这正是原作各层需要的横移行程比。
把它按 `1 : 2.67 : 4` 归一后乘公共系数 **0.05**，得到

```
RATE_BG = 0.05    RATE_MG = 0.1333   RATE_FG = 0.2      // px / 镜头 px
```

即镜头走光一屏（12.6 行 ≈ 900px），FG 横移 180px、MG 120px、BG 45px —— **近景最快、远景最慢**，
且都不超过各自的可用余量（360/240/90 的一半，`layerX()` 里 `clamp` 到 `±slack/2`，到头饱和，永不露边）。
0.05 这个公共系数是为了让"整场战斗（镜头走 3–6 行）"的横移落在 8–90px 区间：既看得出视差，又不至于侧滑到让人晕。
`[推测]` 0.05 没有原作代码可对照，是按观感定的（见 `terrain_*.png` 里同一帧的带子位置）。

**方向**：地面沿**屏幕 y** 滚动（俯视平面里镜头沿 worldX 前进，投影到屏幕就是 y），带子沿**屏幕 x** 平移。
brief 里写"地面按 camera 的 x 平铺"，这里取"用 camera 位置驱动"的语义、把位移落到屏幕 y 上——
否则前进时地面横向侧滑，看着像在横移而不是推进。

| 模式 | 画什么 | 用途 |
| --- | --- | --- |
| `b`（**默认**） | 地面平铺 + BG + MG + FG 三层远景带 + 上下暗角 | 正式效果，12 张截图用的就是它 |

### 7.2 坑：`drawField()` 的纯色底必须让位给贴图

背景是在 `render()` 里、**指令列表执行之前**画的：

```ts
ctx.clearRect(0, 0, DESIGN_W, DESIGN_H);
ctx.fillStyle = COLORS.bg; ctx.fillRect(0, 0, DESIGN_W, DESIGN_H);
drawBattleBg(ctx, terrain, camX);   // ← 背景先落地
for (const c of cmds) execute(ctx, c);   // ← 这里再执行 buildFrame() 生成的指令
```

而 `buildFrame()` 的第一条指令就是 `drawField()` 里的 `R(out, FIELD.x, FIELD.y, FIELD.w, FIELD.h, COLORS.field)` ——
一条**不透明的深蓝矩形**，覆盖整个场地。它后画，所以把刚画好的背景整个盖掉，画面看起来跟改造前一模一样（贴图其实一直在画，只是被埋了）。

修法是让 `drawField` 知道"背景已经画过了"：

```ts
// battleView.ts:488
drawField(out, camX, opts.time ?? 0, bgReady(world.terrain ?? 0));
// battleView.ts:504
function drawField(out: DrawCmd[], camX: number, time: number, bgPainted = false): void {
// battleView.ts:507
  if (!bgPainted) R(out, FIELD.x, FIELD.y, FIELD.w, FIELD.h, COLORS.field);
```

`bgReady(terrain)` 只在**贴图解码完成且没被 `?bgmode=off` 关掉**时返回 true；没就绪的那几帧仍然铺纯色底，
所以加载期间不会闪白/闪黑，出问题时也自动退回旧样子。**这个坑值得记住**：在这个渲染器里，"先画的东西在下面"，
任何全屏铺底矩形都会无声地埋掉它之前画的一切。

## 8. 性能（实测，非估算）

`?bgbench=1` → 在离屏 750×1334 canvas 上预热 20 帧，再跑 300 帧 `drawBattleBg`，
末尾 `getImageData(0,0,1,1)` 强制 flush 光栅化（不 flush 只能量到"提交指令"的 0.005ms，是假数字）。

| 地形 | 300 帧墙钟 | 每帧 | 提交指令 | 占 60fps 预算 |
| --- | --- | --- | --- | --- |
| terrain 00（砖地+城墙） | 571.0 ms | **1.903 ms** | 0.005 ms | **11.4%** |
| terrain 08（雪原，最亮/最高频） | 600.7 ms | **2.002 ms** | 0.006 ms | **12.0%** |

（同在 03:50 那版跑过一轮：592.9 ms / 1.976 ms / 11.9% 与 613.2 ms / 2.044 ms / 12.3%，两轮差 3–4%，属软件光栅的抖动。）

取证：`work/bg_orig/raw/bench_00.png`、`raw/bench_08.png`（数字直接画在场地左上角）。
环境：Edge headless `--disable-gpu`（**软件光栅**）、dpr=1、内容 750×1334。
真机有 GPU 合成只会更快；反过来 dpr=2 时像素多 4 倍，可粗算 ~8ms/帧 —— 这是**整个画面**（含 HUD/单位/特效）都有的性质，不是背景独有。

每帧背景的绘制调用总数是 **6 次**（1 fillRect 地面 + 3 drawImage + 2 fillRect 暗角）+ 1 次 clip，
没有 per-tile 循环、没有每帧 `createPattern`、没有每帧 `createLinearGradient`（都缓存在 `WeakMap`/`TerrainBg` 里）。

### 9.1 拍图的正确姿势（踩过的两个坑）

1. **不要用 `freeze=1` 拍带背景的图**：`?freeze=1` 会在 `?sim=` 跑完之后**只 `draw()` 一次**就停住，
   而那一刻背景 PNG 往往还没 decode 完 → 拍到的是纯色底（我第一次拍点击验收就是这么翻车的）。
   正确做法：`?sim=250&terrain=N` **不冻结**，让 rAF 一直画；`Page.navigate` 之后**再等 1.6 s 以上**（我用 4.8 s）让贴图解码 + 至少一帧画上去。
2. **判定一张图是不是"背景接线后"拍的，别看文件名看方差**：纯色底场地的 `field_sd ≈ 10`、`field_mean ≈ 25`；
   有贴图的 `field_sd ≈ 23–82`、`field_mean ≈ 48–191`。`work/bg_orig/check_shots.py` 就是干这个的（对 12 张逐一统计 band/field 的标准差）。

## 10. 与原作的偏差 / 没做到的部分

1. **远景带不循环**（brief 写"各按自身宽度循环"）。实测三条带 9.6×–275.8× 的接缝比，硬平铺必有竖缝，
   镜像平铺会出现对称伪影。改成"整幅平移 + 余量饱和"。**近景最快**这条要求满足了（1:2.67:4）。
2. **地面沿屏幕 y 滚动**，不是 x。俯视场里镜头前进=屏幕 y 位移，横向滚动会看成侧滑。
3. **A/B 只入库 A**。B 变体超体积预算，且当前 `World` 没有昼夜字段可驱动。
4. **地面 tile 的重复节律可见**：砖地/黄土这类规则纹理，每 256px 能看出一次重复（`terrain_00.png` 的砖缝）。
   要彻底消掉需要四象限镜像或双 tile 混合，会牺牲体积和清晰度，当前判定不值得。
5. **类型检查**：`tsc -p game/tsconfig.build.json` = **exit 0**；`tsc --noEmit` = **exit 0**（`view/` 零错误）。
   中途 `tests/city_rules.test.ts` 曾报 20 条（另一个 agent 在写，后加 `// @ts-nocheck` 收掉），与本次改动无关。
6. **雪原地形的既有文字对比度**：「敵 方 · 前 線」/「我 方 · 本 陣」这行是 `battleView.ts` 既有元素（深灰小字），
   在 t08 雪地上偏淡。按 brief 不属于我的改动范围，没碰；如果要改，建议给这行加半透明底。
7. **带子上沿与 HUD 的过渡**：靠烘焙时的 0.28/24px 压暗 + 运行时顶部 60px 暗角，
   在 t08 这种亮天光地形上仍能看到 HUD 与天空的色差（可接受，见 `terrain_08.png`）。
8. **`?bgmode=` / `?bgbench=` 是调试开关**，默认值 `b`/关，不影响正常玩法；`bgmode=off` 保留"改造前"纯色底用于对照。

### 12.1 接口语义坑：`world.status` 不是状态机字符串

第一次点「撤 退」**毫无反应**，根因不在按钮也不在 core，而在 `game/web/main.js` 的点击分支：

```js
// 错（旧代码）
if (!state.world || state.world.status !== 'fighting') { state.message = '戰鬥已結束。'; return; }
```

`world.status` 的真实类型是 `Record<Side, 0|2|3>`（战果状态码：0 未分 / 2 撤退 / 3 被俘，见 `game/src/core/battle.ts:272`），
它**永远是对象**，`!== 'fighting'` 恒为真 → 每个撤退点击都被判成"已结束"直接 return。
正确写法（lead 已改）是只判 `world.over`，因为 `requestRetreat()` 内部已经判过 `over || fled[side]`：

```js
if (!state.world || state.world.over) { state.message = '戰鬥已結束。'; }
else if (requestRetreat(state.world, 'A')) { state.message = '全軍撤退。'; }
```

教训：**判断"战局是否结束"只认 `world.over` + `world.endReason`**；`status` 是给结算/存档用的战果码，别拿它当状态机。
结算面板同理——`state.settlement` 现在给 `record`（R63 累计战绩）/`score`（战功）/`status`（`{A,B}` 战果码），
`endReason` 从 `world.endReason` 取，view 不要自己再算一遍。

## 13. 事故与恢复：PowerShell 把 `battleView.ts` 的中文写坏了

**事故**：为了把主将名字往上挪 40px，我执行了

```powershell
(Get-Content 'game\src\view\battleView.ts' -Raw) -replace '...', '...' | Set-Content -NoNewline -Encoding utf8 'game\src\view\battleView.ts'
```

PowerShell 5.1 的 `Get-Content -Raw` 用系统 ANSI(cp936) 解码 UTF-8 文件 → 整篇中文变乱码；
`Set-Content -Encoding utf8` 又写回**带 BOM** 的 UTF-8。结果：66081 B / 1722 行，**代码 ASCII 全对、中文全毁**（`战斗视图层` → `鎴樻枟瑙嗗浘灞傦細`）。

**为什么难修**：cp936 用「前导字节 + 任意 0x40–0xFE」成对解码，3 字节 UTF-8 汉字被吃成 1 个字（1.5× 膨胀），
**紧跟其后的 ASCII（反引号/括号/空格）会被吞进同一个乱码字**，无法解码的字节退化成 ASCII `?`（全文 586 个 `?`，且合法三元也长这样）。
所以反解是个**有歧义的 DFS**：`?` 位置正确字节只能落在 0x80–0xBF，选错就得到形近字（`撤`→`撁`、`。`→`、`）。

**怎么最终定案**：坏文件的 ASCII 骨架是完好的，而 `dist/view/battleView.js`（出事前最后一次成功编译）**注释齐全、中文正确**，
是天然的文本 oracle。用"行内 equal 块 + 中文只在两侧都有非 ASCII 时才替换"的规则逐行回填，比反解编码稳得多。
（`work/bg_orig/` 下留了 `cp936_table.json`、`restore.py`、`repair*.py` 一串过程脚本，供复盘。）

**禁令（我踩过，写进报告）**：仓库里带中文的文件，**永远不要**用 PowerShell 的 `Set-Content`/`Out-File`/`>`/`Add-Content` 写；
改 `.ts` 只用 `edit`/`write` 工具；脚本必须显式 `encoding='utf-8'`（Python）或 `[IO.File]::WriteAllText($p,$s,(New-Object Text.UTF8Encoding $false))`（.NET）。

**代价**：这个文件被别的 agent 同时改过（士兵图集 `pickUnitFrames`/`pushSpriteFrames`、结算面板 `s.report/s.learned/s.post` 扩展），
恢复必须保住它们的改动 —— 这也是最后改成"以损坏文件为基座只修中文"、而不是"回退到更旧的合法副本"的原因（那份 18:37 的副本缺这两块）。
