## 2. 竖屏投影：方案 A（战场转 90°）

> 一句话：逻辑网格一个字不改（71 列 × 14 行、格 96×72 px、世界 6816×1008），只把**呈现**转 90°——横向的 14 条车道放到屏幕左右，前进的 71 列放到屏幕上下，**我方在下、敌方在上、向上推进**（依据：PROJECT_BRIEF §6）。

### 2.1 为什么是 A（用户 m01722 拍板）

两案都算得出来。把数字摆在一起后，A 唯一输的是美术，赢的是**可见纵深**和**手势**：

| 维度 | A：转 90°（**选定**） | B：保持横向 + 横向镜头 | 差 |
|---|---|---|---|
| 可见推进纵深 | 12.6 / 71 行 = **17.8%** | 8.75 / 71 列 = 12.3% | A ×1.44 |
| 可见横向 | 14 / 14 车道 = **100%** | 14 / 14 行 = 100% | 平 |
| 一屏格数 | **176 格** | 122.5 格 | A ×1.44 |
| 拇指手势 | 战场纵向铺满，单指上下推（一维） | 战场铺在 750 宽里，横拖 5976 px 镜头 | A 省手势 |
| 单位朝向 | 背视 / 正视 / 侧视 三套（§6.2） | 只要原作侧视一套 | B 省美术 |
| 地面特效 | 约 55% 需重做（§7.4） | 全复用 | B 省美术 |
| 玩家决策 | 两翼全见、纵深 17.8% | 两翼出屏、纵深 12.3% | 平 |
| 用户决策 | m01722：「A，我说只换皮，包含视角转换带来的换皮」 | 已否决 | — |

结论：**选 A**。信息量比 B 大 44%、手势天然适合竖屏；代价 100% 集中在美术（三套视角 + 一半特效重做），而用户已把"视角转换带来的美术重做"明确算进"换皮"预算（依据：PROJECT_BRIEF §2 视角行、§6.2）。

### 2.2 投影公式与全部常量

| 常量 | 值 | 推导 |
|---|---|---|
| 世界坐标 | `worldX = gx*96 + 48`（0..6816，前进轴）、`worldY = gy*72 + 36`（0..1008，车道轴） | docs/04b1 §1 |
| 战场带 | 750 × 900 px，`screenY ∈ [100, 1000]` | PROJECT_BRIEF §6.1 |
| 缩放 `s` | **0.7440** | `750 / 1008`（14 车道 × 72 px） |
| 屏上格 | **53.6 × 71.4 px**（横 × 纵） | `72s × 96s` |
| 可见 | **14 车道全宽 × 12.6 行** | `900 / (96s) = 12.6` |
| 推进轴可见比 | **17.8%** | `12.6 / 71` |
| `camX` 范围 | **[0, 5606]** | `6816 − 900/s = 6816 − 1210` |
| `camY` | **恒 0** | `14 × 72 × s = 750.0`，恰好铺满 |
| 单位朝向 | 我方背视 / 敌方正视 | PROJECT_BRIEF §6.1 |

```ts
// 唯一的投影函数：逻辑层不知道屏幕存在，只有渲染层调它
const S = 0.744;                                  // = 750 / 1008
function project(u, camX) {
  return {
    x: u.worldY * S,                              // 车道横轴 → 屏幕 x
    y: 1000 - (u.worldX - camX) * S,              // 推进轴 → 屏幕 y（我方在下）
  };
}
// 定点实现（整数，1 px 精度）：
//   screenY = 1000 - idiv((worldX - camX) * 744, 1000)
```

- **Y 翻转是唯一的实质差别**：`screenY = 1000 − …`，`worldX = 0` 落屏幕下沿，`worldX = 70 格` 落屏幕上方。
- 以格为单位更直观：`screenCol = 格Y`、`screenRow(自下) = 格X`，即 `screenY = 70 − 格X`（再乘 `s` 加带偏移）。这就是"原 X → 新 Y、原 Y → 新 X"。
- **不裁剪**：投影无分支；带外单位由渲染层 cull（`screenY ∈ [−64, 1064]` 留余量），逻辑照跑。

### 2.3 三档缩放与一屏可见

| 档 | `s` | 屏上格（横×纵） | 可见车道 | 可见行 | `camY` | 用途 |
|---|---|---|---|---|---|---|
| 近景 `Z_NEAR` | 1.34 | 96.5 × 128.6 px | 7.8（需裁切） | **7.0** | 需，`∈[0,448]` | 主将相遇、技能瞄准、战后特写 |
| 标准 `Z_STD` | **0.744** | **53.6 × 71.4 px** | **14（全见）** | **12.6** | 恒 0 | 进军、混战（默认） |
| 全景 `Z_WIDE` | 0.67 | 48.2 × 64.3 px | 14（675 px，两侧黑边 37.5） | 14.0 | 恒 0 | 开战看全阵、长按战况条看全局 |

- `Z_NEAR` 是唯一需要第二自由度的档：`750 / (72×1.34) = 7.8` 车道 < 14，必须横向裁；`camY ∈ [0, 1008 − 750/1.34] = [0, 448]`。
- `Z_WIDE` 两侧各 37.5 px 黑边**不放任何可点元素**，只压暗，避免误触。
- 士兵屏高：**世界高度 86 px**（= 0.90 个格深）→ `86 × 0.744 = **64 px**`（标准）/ `86 × 1.34 = 115 px`（近景）/ `86 × 0.67 = 58 px`（全景）。**64 px 是 v1 的可读性基线**（§6.3；`03 §3.4` 用 13 兵种两两辨认测得 64 px 命中 93%、56 px 降到 78%）。

### 2.4 摄像机：一维纵向跟随便够

横向 14 车道恒定铺满，所以 `camY` 恒 0，镜头只有 `camX` 一个自由度：

```ts
const heroX  = ourGeneral.worldX;                    // 我方主将
const frontX = maxWorldX(ourLivingSoldiers);         // 我方最前兵
const focusX = 0.55 * heroX + 0.45 * frontX;         // 关注点
let   target = focusX - 544;                         // 544 = (1000-595)/0.744
target = clamp(target, 0, 5606);                     // 5606 = 6816 - 900/0.744
if (abs(target - camX) > 144) camX = approach(camX, target, 8);   // 死区 ±144，每帧 ≤8
```

- **544 的来历**：把关注点放在屏高 595（战场带下 45%），`(1000 − 595) / 0.744 = 544`。
- **为什么 0.55 / 0.45**：主将会冲（原作 `cmd 3 武將出擊`，依据：docs/04b3 §4），只跟主将看不见兵墙；只跟前锋主将会跑出屏。加权后主将最多偏出屏心 2.2 行，仍在 12.6 行视野内。
- **死区 ±144 世界 px**（= ±1.5 格 = ±107 屏 px），避免主将微动导致镜头呼吸。
- **每帧 ≤8 世界 px** = 240 px/s，快于步兵 1.45 格/s（139 px/s）——镜头永远追得上，不会出现"单位跑到镜头外"。

| 机位 | 触发 | `camX` 目标 | `s` | `camY` |
|---|---|---|---|---|
| `CAM_FOLLOW` | 默认 | 上式 | 0.744 | 0 |
| `CAM_DUEL` | 两主将同格/相邻（距离 ≤1），或隔格追击（原作 `0x43D76C` 的特例） | `(heroX_our + heroX_foe)/2 − 302` | 1.34 | `clamp(midY − 280, 0, 448)` |
| `CAM_SKILL` | 技能包围盒 > ½ 屏（§7.4） | 技能中心 `− 544` | 0.744 或 1.34 | 0 或上式 |
| `CAM_ROUT` | `0x4000` 全军撤退 / 主将亡 | 我方主将 | 0.744 | 0 |
| `CAM_SETTLE` | `[0x4A8144] == 8` | 战场中段 | 0.67 | 0 |

- `302 = (1000−595)/1.34`、`280 = 375/1.34`：都是"把某点放到屏心偏下 45%"的同一套算术，只是换了 `s`。
- **机位切换不改逻辑**：`camX/s/camY` 全是渲染状态，逻辑帧仍按 §5 跑；0.25 s ease，卡顿时直接跳变（宁跳不抖）。

### 2.6 点选：把触点反投影回格子

```ts
function touchToCell(sx: number, sy: number) {        // 屏幕 → 格
  if (sy < 100 || sy > 1000) return null;             // 战场带外不响应
  const worldY = sx / 0.744;                          // 横轴 = 车道
  const worldX = camX + (1000 - sy) / 0.744;          // 纵轴 = 推进
  return { gx: Math.floor((worldX - 48) / 96), gy: Math.floor((worldY - 36) / 72) };
}
```

| 轴 | 屏上 1 格 | 44 px 指腹覆盖 | 对策 |
|---|---|---|---|
| 推进轴（纵） | 71.4 px | 0.62 格 | 精度足够，直接按格取 |
| 车道轴（横） | 53.6 px | 0.82 格 | 目标先**吸附到最近车道中心**（±26.8 px 容差），再取该车道内最靠前者 |
| 近景档 | 128.6 / 96.5 px | 0.34 / 0.46 格 | 更准；`CAM_DUEL` 时不改交互 |

- 三型技能指向照旧（§7.2）：点将走顶部头像条（不受战场带限制）、点地面走上面的车道吸附、自身走长按。**拇指热区（`y > 1000`）永不进战场**，点地技的按下点先抬到 `y = 960` 再反投影。
- 点选优先级：武将 > 小队旗 > 士兵；同层取"离手指最近的世界格"，不取"最靠前"（避免误选屏外）。

### 2.7 深度排序与像素对齐

- **排序键**：`worldX` 降序（远者先画），同 `worldX` 按 `worldY` 升序，同格按槽索引（`unit+0xB4` 的 idx）稳定排序。A 下"越靠上越远"——这是转置带来的唯一一处渲染差异。
- **像素对齐**：`camX` 取整；`screenX/screenY` 四舍五入到整数；精灵锚点 `(0.5, 0.12)` 脚底贴格心，避免浮空。
- **不按 1:1 世界像素出图**：世界 1 px 只占屏上 0.744 px，按 1:1 出图会白涨 1.8 倍带宽与内存。精灵按**标准档屏上尺寸**出图（士兵 64 px 高、宽 36–44；主将 120 px，见 `03 §3.4`），近景档只给**主将**另出 1.34× 一套；士兵近景直接放大 1.8×（模糊可接受，`CAM_DUEL` 只持续数秒）。

### 2.8 视野变化的规则性影响与补偿

| 轴 | 竖屏 A | 原作 640×480 | 变化 |
|---|---|---|---|
| 车道（横） | 14 / 14 = **100%** | 640/96 = 6.67 / 14 = **47.6%** | 两翼第一次全见 |
| 推进（纵） | 12.6 / 71 = **17.8%** | 480/72 = 6.67 / 71 = **9.4%** | ×1.9 |
| 一屏格数 | **176** | 44 | ×4.0 |

两个结论：

1. **"敌方后阵永远在屏外"不是新问题，与原作同构**。原作只看得见 9.4% 的推进轴，玩家一辈子看不到敌方本阵；竖屏 17.8%，同样看不到。"要靠猜敌人还剩多少"的手感被完整保留，这也是 §2.1 里 A 胜过 B 的地方（B 只有 12.3%）。
2. **两翼全见是新变量**。原作看不全左右，包抄只能靠想象；A 把 14 车道全铺上，玩家第一次能看见"绕后"。这是**纯表现层变化**，不改任何 AI 权重；但看得见就会改变玩家操作，属于"规则性影响"——只描述、不补偿（遮住两翼只会更糟）。

## 3. 原作布阵数组的原样使用

### 3.1 33 组数组与取值公式（一字不改）

| 项 | 原作事实 | 依据 |
|---|---|---|
| 网格 | 71 列（x 0..70）× 14 行（y 0..13），格 96×72 px | docs/04b1 §1 |
| 表结构 | 33 行 × 5 个分区（mode1..5）指针表 `0x485B10`，坐标数组元素 `{int16 x, int16 y}`，容量 = 该区权重 w | docs/04b1 §2 |
| 权重 | `0x485DA8`，33 行 × 6 int16（w1..w5 + anchorX），**Σw ≡ 200** | docs/04b1 §2.3 |
| 取值 | `格X = 表X + anchorX + (200 − N)/25`，`格Y = 表Y`（Y 锚点恒 0） | docs/04b1 §3.2 |
| 分区人数 | `k_m = w_m × N / 200`（步/骑各算一遍，mode1 吃余数） | docs/04b1 §3.1 |
| 循环顺序 | `m = 1,3,4,5,2`；区内骑兵占低位 slot | docs/04b1 §3.1 |
| A 侧 | 整表镜像 `X = 0x47 − X`（71 − 格X） | docs/04b1 §3.2 |
| 占位冲突 | 该格已占则沿 X 微调 1 格，`cmp X, 0x36`(54) 决定方向"远离列 54" | docs/04b1 §3.3 |
| 主将 | 行固定 6（`0x6A8 = 6 × 0x11C`），列由 `0x442CB6` 算 | docs/04b1 §3.4 |

**这 9 条是 v1 的"不许动清单"**：任何重排、重映射、坐标压缩（例如把 71 列压成 60 行）都算改规则，v1 不做。

### 3.2 数据落地：`formations.bin`（60 KB，逐项校验）

33 组数组共约 3 万个 `{int16 x, int16 y}`（每组容量 = 该区 w，Σw = 200/行 × 33 行 ≈ 6600 项/侧 × 2 侧），JSON 存会膨胀到 1 MB+，故烘焙成二进制：

```
formations.bin
  header: magic "FM01" | u16 count(33) | u16 version
  index : count × { u16 offset, u16 nSlots[5], i16 anchorX, u16 w[5] }
  payload: 每组每区 nSlots 个 { i8 x, i8 y }      // 表内坐标范围 -12..31，int8 足够
```

- 体积：6600 × 2 B ≈ 13 KB × ... 实测量级 **≈60 KB**（含 33 组 × 5 区）。
- 校验：`tools/bake_formations.py` 解出的每组每区前 N 项必须与 EXE 反汇编数组**逐项相等**；A 侧镜像由 `71 − x` 现算，不重复存。
- 与 JSON 的分工：`formations.json` 只存**可读元数据**（阵形名、权重、anchorX、分区覆盖范围），坐标一律走 `.bin`。策划想看坐标用工具导出 CSV，不在运行时读。

### 3.3 绘制流程（格坐标 → 竖屏）

```ts
// 布阵完成时算一次，之后每帧只做投影
for (const u of units) {
  const gx = slotX + anchorX + idiv(200 - N, 25);   // 原作公式，原样
  const gy = slotY;
  u.worldX = gx * 96 + 48;                          // 原作 px = x*0x60 + 0x30
  u.worldY = gy * 72 + 36;
}
// 每渲染帧：转 90°（X/Y 互换 + Y 翻转）
sprite.setPosition(
  Math.round(u.worldY * S),                             // 车道 → 屏幕横轴
  Math.round(1000 - (u.worldX - camX) * S),             // 推进轴 → 屏幕纵轴
);
```

- **以格为单位就是一句话**：`screenCol = 格Y`、`screenRow(自下) = 格X`，等价于 `screenY = 70 − 格X`；乘 `s` 加带偏移即成像素式。这就是"原 X → 新 Y、原 Y → 新 X"。
- 单位**不在布阵时转成屏幕坐标**：世界坐标是唯一真值，缩放/镜头只影响绘制，符合"逻辑与表现分离"，也让 §5.7 的差分测试能在无渲染环境跑。
- 精灵按**屏上尺寸**出图（士兵 43×64、主将 64×82），标准档 `setScale(1)`，1:1 无额外采样；切档时整体乘 `s/0.744`，不产生第二套资源（主将近景另出 1.34× 一套，见 §2.7）。
- 世界坐标 → 屏幕的 `Math.round` 只出现在渲染层；逻辑层的小数由定点（1/256 格）承担，屏幕取整不回写逻辑（避免"画在哪"影响"走到哪"）。

### 3.4 占位冲突与叠格（原样）

- 原作每格 1 个对象指针（`0x4B3CA0`，行 stride `0x11C`），冲突时沿 X 微调（依据：docs/04b1 §3.3）。v1 **照搬单槽**，不做双槽。
- 若满编方陣在某格真的产生 2 个兵（原作靠 `cmp X,0x36` 微调应当避免），表现层允许**同格两兵**：绘制时沿 +x 偏 24 px、深度按 y 排序，读作"人挤人"——这是原作 100 兵在 96 px 格里的真实观感，不需要额外机制。
- **"叠格"问题在 71 行原网格下不存在**：早前一版曾把 71 列压缩成 60 行（`row = 59 − floor(gx*60/71)`），压缩后不同 `gx` 撞到同一 `row`，才出现"方形 10 例、錐形 8 例"的叠格。v1 回到原作 71 列，逐兵占独立格。按原作格坐标复算：方形 N=100 落格 `x10..20 × y2..11` = 110 格 ≥ 100 兵，10 个空位就是冲突微调的余量，**不需要任何妥协**。
- 验收：`formations.bin` 解出的 33 组数组落格后，与 EXE 布阵结果逐单位比对（§10 第 2 条），同时断言"每格 ≤ 1 兵"（除原作微调允许的极端情况）。

### 3.5 主将与 A 侧镜像（原样）

- 主将行固定 6 → `worldY = 6×72 + 36 = 468` → `screenX = 468 × 0.744 = 348`，落在屏幕水平中线（375）偏左 27 px。**主将天然在屏幕中间**，所以 A 的镜头只需要一维纵向跟随（§2.4），不必为主将做横向补偿。
- A 侧镜像 `X = 71 − X`（依据：docs/04b1 §3.2）在布阵时算，表现层不再二次处理。敌方阵落在 `worldX` 大的一端 → 屏幕上方；镜像后两军正面相对，玩家永远看到敌方**正面**——这正是 §6.2"敌方用正视"的前提。
- 后果：两军同一 `格Y` 映射到同一 `screenX`，左右对称，玩家的"左/右"概念与原作一致（不会因为转置而左右颠倒）。

## 5. 数值基线：全部原样，作为回归对照

> 本节的作用不是"设计数值"，而是**把 v1 必须逐位复现的公式钉死**，供 §5.7 的差分测试对照。所有条目 `处置` 列都是"原样保留"。

### 5.1 战力五段（`unit+0x70`）

```
power = 150                              // base 为推断值，见 §13-2
      + TROOP_COUNTER[攻兵种][守兵种]     // 13×13 @0x48CD88，-68..+68，对角 0
      + TERRAIN_MOD[地形][攻兵种]         // 12×13 @0x48D030，约 -25..+25
      + FORMATION_COUNTER[攻阵][守阵]     // 11×11 @0x48D2A0，-25..+25 零和
      + idiv(全局 + 50, 100)              // 通常 -1..+1
      + idiv(士气 - 50, 5)                // -10..+10
```

五段**直接相加、不乘系数**（依据：docs/04b §2）。值域 21..279，中性 150 → 命中 50%。

### 5.2 命中（两套口径，不可互换）

```ts
// 士兵/箭矢 0x43D400
p = power;
if (目标是将) p = 150 - 目标武力 * 20 / 100;
if (目标在移动) p = p * 2 / 3;
hit = rand() % 300 < p;
if (!hit && 攻方骑兵) hit = rand() % 300 < p * 2 / 3;    // 二段判定

// 武将 0x43D4CB
p = 目标是將 ? 150 + (攻武 - 守武) / 2
  : 目标是骑兵 ? 150 + 攻武 / 3
  :             150 + 攻武 / 2;
if (增益位 & 0x200) p += 增益值;
if (目标在移动) p = p * 2 / 3;
hit = rand() % 300 < p;
```

依据：docs/04b4 §3、docs/04b3 §2。士兵打武将的 `150 − 武力×20/100` 与武将打武将的 `150 + 差值/2` 是**两套完全不同**的公式。

### 5.3 伤害（无防御/减伤项）

```ts
if (攻方是将) { h = 武力; half = idiv(h,2); d = idiv(half + rand() % (h - half), 10); }
```

### 6.2 单位朝向与动画映射（方案 A 的核心代价）

转 90° 后"推进轴"竖到了屏幕上，于是同一个单位在不同运动方向下要用**不同视角**：

| 世界运动方向 | 屏上方向 | 看到的是 | 视角 | 谁在用 |
|---|---|---|---|---|
| `+x`（推进） | 向上 | 后脑、披风、背甲 | **背视** | 我方（多数时间） |
| `−x`（迎击 / 后退） | 向下 | 脸、胸甲、正手兵器 | **正视** | 敌方（多数时间） |
| `±y`（横移 / 包抄） | 向左 / 向右 | 3/4 侧脸、侧身 | **侧视** | 双方横移时 |

- 原作只有**一套 3/4 侧视朝右 + 水平镜像**，8 个动作码是"动作"不是"朝向"（依据：PROJECT_BRIEF §6.2 对 `MAJOR\BODY` 的实测）。所以：侧视沿用原作口径，**背视 / 正视是方案 A 的净新增**。

| 原作码 | 语义 | 目标动作 | 背视 | 正视 | 侧视 |
|---|---|---|---|---|---|
| `A` | Attack 攻击 | 攻击 | ✅ | ✅ | ✅ |
| `D` | Death 死亡 | 死亡（沿用当前视角，倒地姿势与视角无关） | ✅ | ✅ | — |
| `F` | First 登场 | 登场（开战 1 次） | ✅ | ✅ | — |
| `H` | Hit 受击（PAIN） | 受击 | ✅ | ✅ | ✅ |
| `L` | 8 码里唯一无独立动画组 | 并入待机，不单独出图 | — | — | — |
| `R` | Rest 待机 | 待机 | ✅ | ✅ | ✅ |
| `S` | Shot 射击 | 射击（弓 / 弩 / 飞刀） | ✅ | ✅ | — |
| `W` | Walk 走 | 移动 | ✅ | ✅ | ✅ |

- **帧数账（以 `03 §3.13.6` 为准）**：近战 `W4+A6+R5+S6+H2+F3 = 21` 帧背视 + `W4+A7+R6+S6+H2+F3 = 25` 帧正视 = **46 帧/兵种**；远程（弓 `F`/弩 `B`）背 26 + 正 31 = **57 帧/兵种**。13 兵种合计 **620 帧**（单视角 325 帧的 1.91 倍），图集 9 页 × 328 KB = **2,952 KB**。侧视**不新画**，横移时沿用原作口径的侧视帧（M1 可先复用背视+镜像，记 §11）。
- **视角不跟"朝向角"，跟最近一次移动的世界主轴**：`|dx| ≥ |dy|` 时 `dx>0` → 背视、`dx<0` → 正视；否则侧视 + 水平镜像。这个判定**只影响画哪一帧**，不影响 `dir8`、不影响走位（原作 `0x43C4C0` 照跑，§6.4）。
- 主将用 **Spine 骨骼**（不是序列帧，同屏 ≤6 具），只需多出 **24 个背视部件**（`03 §3.13.5`：80 → 104 部件，12 条动画不变），图集 5 页 × 328 KB = 1,640 KB。额外收益：敌方主将**正视**让玩家在战场上直接认出"来的是谁"（原作只有侧脸）——这是 A 换来的真实手感增益，配 §4.3 的将战条使用。

**结论：不能"一套背视 + 镜像 + 换色"冒充敌方正视，必须两套。** 三条理由：

1. **几何上不可逆**。背视是"略俯视背面"（看得见头顶、肩背、脚后的地面）；正视是"平视/略仰视正面"（看得见脸、胸口，地面在脚前）。垂直翻转得到的是"脚朝上、头朝下"的倒立人；水平翻转只是左右镜像，仍然是背视。
2. **第一识别信号不同**。屏上士兵高 64 px、宽 36–44 px，脸占 4–6 px，但"有没有脸"是玩家一秒内分辨敌我的最强信号（我方全是后脑、敌方全是脸）。换色能改阵营色，改不了"有没有脸"。
3. **攻击的遮挡顺序相反**。背视攻击是"向远处刺/劈"（武器在躯干后，前臂被身体挡掉一部分）；正视攻击是"朝镜头砍来"（武器在最前层，躯干在后）。镜像与换色都改不了这一层关系。

**但同一视角内部可以省**：水平镜像覆盖"横移向左/向右"（侧视只画朝右 + 镜像）；换色板覆盖"敌我同兵种不同阵营色"（双方都有的兵种不必画两遍）。这两项省的是"左右与配色"，省不了"视角"。

### 6.4 远程弹道与寻路：判定不变，只加表现

- 原作箭矢是 Process 9/12，**到达目标格才结算**，用的是同一 `0x43D400` 判定，无远程命中率修正（依据：docs/04b4 §6）。v1 判定完全不动。
- 表现层加视觉抛物线（抬 0.35 格）：`screenY = 100 + (worldY - sin(π t/T) * 0.35 * 72) * s`。**这是纯视觉**，落点仍按世界格结算，所以"眼睛看到的角度"不影响命中。
- 落空特效（原作角度偏转 ±0xB0、`rand(0x60)` 步、`rand(3)+2` 步、停留 `0x18` 帧）保留原参数，只按 `s` 缩放。
- 寻路：通用走位器 `0x43C4C0` 用 8 组格偏移逐格试走（依据：docs/04b3 §4），v1 **照搬**，不引入 A* 或流场——引入任何新寻路都会改变单位到达时间，进而改变接敌序列（差分测试会立刻失败）。表现层只做两件事：① 移动时按 `dir4` 播 WALK；② 卡住 >0.5 s 时播一次"踏步"动画（不改变移动逻辑）。

## 8. 性能预算

### 8.1 目标机与帧率基线

### 8.2 DrawCall

|---|---|---|
| 地面 + 视差（4 层） | 4 | 4 层各 1 张，按 512² 平铺 |

| 项 | 上限 | 依据 |

### 8.6 降级阶梯

| 级 | 触发（连续 3 s） | 动作 | 代价 |
|---|---|---|---|
| L0 | 基准 | 全开 | — |
| L1 | 帧时长 > 28 ms | 特效层 6→4、粒子 300→180、飘字 40→20 | 观感略钝 |
| L2 | 仍 > 28 ms | 阴影/底环合并、士兵 4 兵种图集 → 2、视差 4 层 → 2 | 场景变平 |
| L3 | 仍 > 28 ms | 锁 30 fps、士兵改"静态图 + 2 帧踏步"、关闭受击特效 | 明显掉档 |
| L4（兜底） | 仍 > 28 ms | 纵深视野缩到 8 行（`camX` 窗口 1210→765 px，同屏兵数降 15%）、关闭小地图刷新 | 可玩性受损 |

**三条不可降红线**：① 士兵数 100（不能少画，否则等于改规则）；② 逻辑 30 Hz（不能降，否则 `rand()` 序列与原作不再对齐）；③ 相克/战力判定（不能省，省了就不是这个游戏）。降到 L4 仍不达标 → 记入 §13，不在 v1 内解决。

## 9. 数据表：原作 1:1 导出

### 9.1 原则

1. **字段名 = INI 原名**（`POWER/ATTACK/ATTRIB/ACTIVE/SCRIPT`），只加一个 `id`（= 原表序号），方便与 `03a` 的表逐行对照。
2. **不做单位换算、不做默认值补全**：INI 里没有的字段，JSON 里也不出现（缺失即缺失，由代码兜底）。
3. 导出脚本 = 校验脚本：`tools/export_ini.py` 导出后立刻回读比对，差异为 0 才允许提交。
4. 二进制大表（阵形坐标）单独 `.bin`，JSON 只存元数据（§3.2）。

### 9.2 `magic.json`（110 + 67）

```json
{
  "meta": { "source": "MAGIC.INI", "count": 110, "magicianCount": 67 },
  "skills": [
    { "id": 1, "SEQUENCE": 1, "NAME": "半月斬", "TITLE": "",
      "POWER": 100, "Attack": 12, "Script": 503, "Attrib": 0, "Active": 1, "TARGET": 3 }
  ],
  "strategies": [
    { "id": 8, "SEQUENCE": 8, "NAME": "保留氣力", "TITLE": "",
      "POWER": 100, "Attack": 0, "Script": 561, "Attrib": 0, "Active": 1, "TARGET": 1 }
  ]
}
```

| INI 列 | JSON 字段 | 语义（不变） | 备注 |
|---|---|---|---|
| 序号 | `id` | 表内序号 | 唯一新增字段 |
| 名稱 | `NAME` | 技能名 | 竖屏 UI 直接显示 |
| — | `TITLE` | 官衔/级别要求 | INI 原文保留 |
| 威力 | `POWER` | 恒 100 | 用于气力消耗（§7.1） |
| 攻 | `Attack` | 0..60 真实威力 | 特效强度也读它 |
| 脚本 | `Script` | 501..610 | → `Magic{num−500}` |
| 屬性 | `Attrib` | 属性/元素 | — |
| 目標 | `TARGET` | 指向类型（自身/点地/武将） | §7.2 三型的依据 |

### 9.3 `things.json`（`THINGS.INI` → 兵种 + 物件）

| INI 列 | JSON | 语义 |
|---|---|---|
| 序号 | `id` | — |
| 名稱 | `NAME` | 朴刀兵/長槍兵/… |
| `Process` | `PROCESS` | **3=士兵 / 4=主将 / 6=法术波 / 9=法术箭 / 12=箭矢**，决定走哪个 tick |
| 圖形 | `SHAPE` | 序列帧目录 |
| 攻擊/防禦/… | 原样 | 兵种相克表的行索引 |

`PROCESS` 是**行为分派**字段，v1 必须按原值重放：`3` 走士兵 tick（`0x43DDBF`）、`4` 走主将 tick（`0x43EF64`）、`12` 走箭矢 tick。改它就是改规则。

## 13. 开放问题

1. **原作一屏到底多少格？** 按 96×72 格与 640×480 视口推算约 6.7 列 × 6.7 行，但 EXE 的视口缩放/裁剪未定位。若原作实际显示更多，§2.8 的"可见纵深 1.9 倍、横向 2.1 倍"要重算（方向不变，量级会变）；不影响 `s = 0.744` 与一维镜头。
2. **`basePower = 150` 是推断值。** `unit+0x70` 的初值在 EXE 里未定位，150 来自"战力值域 21..279、`rand()%300` 的 50% 中性点"。若初值是别的数（如 100 或 200），整个命中率分布平移，§5.7 的差分测试需换成实测初值。
3. **`0x43A14D` 的调用点未定位。** 公式已知（`m>50 ? −1 : clamp(m,4,50)×6`），但它什么时候被调用（每次命中？每个行动周期？）没有确认，v1 先按"每次行动周期一次"实现，需拿原作录像比对。
4. **气力上限 60000（docs/04b）vs 120000（docs/04b3）。** `docs/00 §9` 的仲裁表只覆盖字段偏移，未仲裁此条；v1 按 `docs/04b` 取 60000。若仲裁结果反过来，只需改 `battle_params.json` 的 `qiMax`。
5. **地形是否参与战力第 2 段。** `PROJECT_BRIEF §3` 记"地形不参与数值、只是场景选择器"，而 `docs/04b §2` 的五段公式里明确有 `TerrainMod` 且有一张 12×13 修正表；`docs/00 §9` 未仲裁此条。v1 按 `docs/04b` 实现（参与），表可一键关，等仲裁。
