**盘出来的真缺口**（就是本轮补的东西）：

1. ACT 九项没有「一 ACT 一函数」的可枚举形态（`ACT_IMPL`），也没法逐项单测；
2. 产出物没有统一 Action 形状（`kind`/`reason`/`troops`/`generals`/`gold`），月报与调试只能看 `act` 数字；
3. `planForceMonth` 不纯（`planRecruit` 就地改兵/金），没法在 UI 里「先预览再执行」，也没法确定性测试；
4. 内政三命令（開發/搜索/徵兵）在 ACT 表里没有，但 R73 的「多路 AI」要求有 —— 完全没有；
5. ACT=3 只有「把 1 个将挪到 0 将城」，没有「前线缺兵时调将带兵增援」（`0x40C34D` 的运输语义）；
6. 每势力固定 1 条，没有「多路」放开的旋钮；玩家 vs AI 的 Rate 优先级只能靠 `argMaxRate` 黑盒。

## 4. `planMonth` 决策树

```
planMonth(save, cities, ctx)                                  ai_model.js:2102
│
├─ ① prepareMonth(save, cities, ctx)                          :1544（纯：只新建 world）
│    · save.cities 优先（troops/money/pop/owner/officers），剧本行兜底（DEFENSE/FLAGS/RATE/MAJOR）
│    · 随机源：ctx.rand > ctx.rng > seedRng(ctx.seed ?? save.seed ?? 0)   ← 绝不退回 Math.random
│    · ctx 透传：adj / paths / forces / capOf / limitOf / distanceOf / neighborsOf / rules / talentPool
│
├─ ② for forceId of forceOrder(world)                          :2108
│    · 跳过玩家势力（world.playerId）；跳过 0 城势力（已灭亡）
│    · ctx.forces 可限定跑哪几家；ctx.kinds 可白名单 kind（见 §4.3）
│
├─ ③ planForceActions(world, forceId, ctx)                     :2044
│    12 个生成函数依次跑（顺序不影响结果，最终靠全序排序）：
│      actAttackPlayer(4) → actAttackAI(5) → actJoin(7) → actOccupyEmpty(8)
│      → actFlee(2) → actSupplyGold(1) → actMoveGeneral(3)
│      → actRecruit / actDevelop / actSearch（act=0 + kind）→ actCheat(6) → actNop(0)
│    每个函数产出 Action[]，`rate > 0` 才收
│
├─ ④ sort(compareAction)                                      :2077
│    ① Rate 降序（200 攻玩家/聯合打玩家 > 100 攻AI > 50 聯合打AI > 40 占空城
│                 > 35 逃跑 > 33..35 徵兵 > 26..32 開墾 > 24..28 增援 > 22..30 補金
│                 > 18..24 搜索 > 15 cheat）
│    ② 同 Rate → act 编号降序（聯合 7 压过单城攻 4 —— 等价于 argMaxRate 的「并列取后出现」）
│    ③ 同 act → score 降序    ④ 同 score → from/to/joinCity/kind/generals 升序（保证确定性）
│
└─ ⑤ 取前 maxPerForce 条（默认 MONTH_ACTION_MAX=1），写 rank=1,2,…     :2118
```

**Action 形状**（任务书要求 + 额外调试字段）：

```js
{ force:'曹操', act:7, actName:'聯合', kind:'attack', sub:'join',
  from:'許昌', to:'江夏', joinCity:'陳留', rate:200, score:412, rank:1,
  troops:100,                     // 出兵人数（单位×20）；徵兵/增援也带
  generals:['曹操','夏侯惇'],      // 参与武将
  gold:0,                         // 補金/徵兵/開墾/搜索的钱数
  reason:'聯合：許昌（40 兵）＋ 陳留（30 兵）→ 江夏（玩家，守 10 兵／城防 120），各出 60／40 兵；本勢力 …；Rate 200',
  cand:{ act:7, actName:'聯合', from:'許昌', to:'江夏', a:2, b:3, rate:200, joinCity:'陳留', kind:'attack', reason:same } }
```

`cand` 是给 `executeCandidate` / `describeCandidate` / c1 既有循环吃的**原作量纲**候选（a/b 是 1..5 的「单位」）。

### 4.1 确定性

- 同一 `(save, cities, ctx)` → 逐字段相同的 `Action[]`（`tests\ai_act.test.ts:118` 断言两次结果深度相等）；
- 随机只走 `ctx.rand` / `ctx.rng` / `seedRng(ctx.seed)`，**任何路径都不退回 `Math.random`**；
- `planMonth` 不改 `save`、不改 `cities`（:106 用 JSON 快照前后对比断言）。

### 4.2 每势力条数 N

`N = 1`，有据：`0x40D751`（AI 势力回合）→ `0x40CC10` ArgMaxRate → `0x40D52F` 执行，**每势力每月只执行一个动作**（候选表可多条，只取 Rate 最大一条）。
`ctx.maxPerForce` 可放开多条（[新设计]，给「一月多动作」的实验用），默认严格 1。

### 4.3 真实剧本上的分布（诚实数据）

用 `game\data\scenarios.json` 的 5 个剧本、每城兵=DEFENSE、金=MONEY、将=MAJOR 造一份快照，跑一次 `planMonth`：

| 调用 | 总条数 | 分布 |
|---|---|---|
| 默认（忠实原作 Rate） | 53 | `攻擊ai` 32、`佔領空城` 21 |
| `ctx.kinds = ['recruit','develop','search','supply','defend','reinforce']` | 35 | `徵兵` 12、`開墾` 23 |

**这张表就是 R73 的真问题**：只要有一座邻城是别人家，`攻擊ai = 100` 就永远压过内政的 18..35，
所以補金/逃跑/聯合/移動武將/開發/搜索在实数据里**一条都胜不出**（与 b2 报告 §7 的 400+ 次观察一致）。
R73 的「多路」在原作的 Rate 机制下本来就只在**没有邻敌**时才轮得到内政 —— 这是原作的形状，不是 bug。
要让 AI 真的经营，c1 有两个口子（都写进 §5）：`maxPerForce`、`kinds`。

## 6. `[推测]` 清单（无原作证据的部分）

1. **ACT=1 補金的 Rate 公式** `22 + 缺口/200` 夹 22..30，以及「需要额 = max(3×将, 500)」。
2. **ACT=2 逃跑的全部条件**（0 兵 / 邻敌 ≥30 / 搬金到最安全城）—— 原作只有「逃跑」两字，Rate 35 也是推的。
3. **ACT=3 的 ② 带兵增援**：从后方调 1 将 + 带 `min(5,ceil(缺口/20))` 单位兵（原作 ACT 3 只写「移動武將」）。
4. **ACT=6 cheat 的触发分支**（0x40BFCE 内未定位）与 Rate 15。
5. **ACT=8 的距离口径**：跳数（相邻=1，上限 9），所以相邻空城 Rate = 40。
