## 1. 设计立场

### 1.1 竖屏不是"横屏裁一刀"

原作 640×480 横屏靠**横向并列**组织信息：一屏能摆 3 列（左列表 + 中内容 + 右命令），因为 640 px 宽正好够。竖屏只有 686 px 内容宽，压成 3 列后每列 220 px，24 px 字只能放 9 个字——比原作的单行还短。

因此三条硬规则：

1. **单列优先**：主结构永远是"纵向一列"，只有平板（可视宽 ≥900）才出现侧栏。（新设计）
2. **一屏一个主面板**：第二块信息只能是页签或折叠区，不能是并列面板。（依据：PROJECT_BRIEF §5）
3. **层级换密度**：宁可两次点击进二级页，也不在一屏塞 20 行属性。（依据：PROJECT_BRIEF §5）

### 1.2 砍的三条判据

| 判据 | 定义 | 例 |
|---|---|---|
| **频率** | 一局看 >50 次 → 必显；<5 次 → 二级页 | 年月/金/兵数常显；`CONSTANCY` 义理收进"更多" |
| **决策相关** | 影响"打不打/怎么打" → 提到一屏 | 兵力/士气/兵种相克常显 |
| **可推算** | 能由别的字段算出的，不显示原始值 | 骑兵上限 `clamp((等级−20)×5,0,100)` 不显示，只显示当前骑兵数（依据：docs/04c §3.2） |

### 1.3 与"复刻"的关系

v1 的目标是把原作完整搬到竖屏（依据：PROJECT_BRIEF §1）：**玩法数据一条不减**（40 将、110 武将技、67 军师技、13 兵种、9 阵形全部进表），减的只是**同一时刻屏幕上的字段数**——折叠 ≠ 删除。

## 2. 信息架构

### 2.1 主界面清单

| # | 界面 | 职责 | 吞掉的原作界面 | 主要出口 |
|---|---|---|---|---|
| **P0–P3** | 启动层（标题/选剧本/选君主/读档） | 一次性流程，≤4 屏 | `TITLEBG`、`MAIN01-04`、`COMPANY`、`C3_*`、`C4` | M1 |
| **M1** | **大地图** | 全局唯一 hub：态势、点城、行军、推月 | `MAP\CHINAMAP`、`D12A` | M2/M3/M5/M6 |
| **M2** | **城池**（概览/内政/守将） | 城池数据 + 内政命令 + 驻将三合一 | `D1_35`、`D1_2A`/`D1_31–34`、`D1_6A/6B` | M3/M5 |
| **M3** | **出征编成**（选将/布阵/军师） | 出征前全部决策 | `WARPREP01-07`、`D12C`、`D12D` | M4 |
| **M4** | **战斗** | 100 人实时兵战 + HUD | `WAR0D`、`WARINFO01-05`、`WAR01-0C` | M6 |
| **M5** | **武将详情**（属性/技能/战功） | 单将全部数据 | `D3_1A–1G`、`D3_2A–2H`、`D3_3–7` | M3 |
| **M6** | **战报与招降** | 战后结算、俘虏处置、月报 | `D4_3`、`D7_A`、`D8_*`、`E1_*`、`POLICY\YIELD` | M1 |

> 原作没有独立"设置"界面（选项在启动器里）——M7 是**新增**（新设计）。微信小游戏若找不到"关音乐/清缓存"，玩家会直接投诉到平台。

**屏数**：上表 7 个是**导航一级**。加上 5 个启动屏、11 个 L2 全屏页、8 个 L3 浮层，v1 实际共 **31 屏**——逐项对应原作的哪个界面，见 §5.5 功能覆盖矩阵（v1 不删功能）。

### 2.3 四条主流程

```
① 一回合闭环（最高频）
 M1 →[点城]→ 浮卡 →[进入]→ M2 →[内政]→ 命令宫格 →[开发]→ 结果弹窗
    →[关闭]→ M2 →[返回]→ M1 →[长按 结束本月]→ 月报 → M1

② 一场仗
 M1 →[点目标城]→ 浮卡 →[出征]→ M3 选将→布阵→军师 →[出征▶]
    → 行军动画（沿 PATH.Point 插值）→ 遭遇 → M4 → M6 → 招降 → M1

③ 养一个将
 M1 →[底部 武将]→ L2 列表 →[点将]→ M5 →[技能页签]→ 看解锁等级 → 返回 → 返回

④ 看局势
 M1 →[顶部 ⚑]→ L2 势力图 →[点势力]→ 该势力城列表 → 返回 → 返回
```

**热区** `x≥480 且 y≥900`：主操作、技能、加速、结束本月。**温区** `x≥480 且 640≤y<900`：页签、次级操作。**冷区** `x<480 或 y<640`：返回、设置、标题、纯只读信息。**死角**：左缘 0–24 宽条 + 四角 24×24，不放可点元素（系统手势区）。

## 6. 交互规范

### 6.1 手势分工

| 手势 | 用在哪 | 不用在哪（原因） |
|---|---|---|
| 单击 | 一切选择与确认 | — |
| 长按 500 ms | ① 词条解释气泡（"城防 425 是什么"）② 列表进多选 ③ 兵种克制的详情 | 不做长按删除（误触成本高） |
| 长按 300 ms 松手 | "结束本月"（唯一不可逆主操作） | 只此一处，保持稀缺 |
| 双击 | ① 地图镜头回中 ② 地图放大一级 ③ 列表行进详情 | 战斗内禁用（与技能连点混淆） |
| 拖拽 | ① 地图平移 ② 列表/战报滚动 ③ 布阵拖将 ④ 技能槽排序 | 不做"拖拽松手即确认"（与滚动同源） |
| 捏合 | 仅大地图 0.6–1.6× | 战斗/列表禁用（与滚动打架） |
| 横滑 | 筛选条、技能横滑 | 不做整页横滑（与系统右滑返回冲突，§6.4） |

**无 hover 态**（依据：PROJECT_BRIEF §4）。按钮只有 4 态，定义见 03 §5.3（常态/按下/禁用/冷却）；补充一条界面侧规则：**按下反馈必须在 `TOUCH_START` 立刻给**，不等 `TOUCH_END`——竖屏手指遮住按钮，玩家靠"按下就缩"确认点中（新设计）。

### 6.2 地图移动：点选寻路，不做拖拽部队

**决策：单击城池 → 浮卡 → 出征/移动 → 高亮整条路径 → 确认。**（新设计）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A 拖部队到目标 | 直觉 | 拖距常跨 1 屏；与地图平移同手势；松手精度差 | ✗ |
| **B 点城自动寻路** | 一次点击、可预览路程、单手可完成 | 多一层"选中态" | **✓ 采用** |
| C 长按径向菜单 | 快 | 竖屏径向菜单遮挡严重 | ✗ |

| 规则 | 内容 |
|---|---|
| 图 | 60 城 / 116 条路径，实际可通行 77 条（依据：docs/08 §3.4） |
| 代价 | `PATH.Length`，这就是原作的行军代价，无独立"移动力"字段（依据：docs/04c §5.3） |
| 算法 | Dijkstra（节点 ≤60、边 ≤77，单次 <1 ms，不需要 A*） |
| 表现 | 高亮整条 `PATH.Point` 折线；浮卡显示"N 段 · 约 M 月" |
| 关卡 | `FLAGS==1` 的关卡城不可穿越（依据：docs/04c §5.3）→ 寻路时当路障，浮卡提示"须先取关" |

### 6.3 拇指热区五条规则

1. 每屏**最多 1 个**热区主操作，其余靠左或靠上。
2. 热区内元素**纵向不叠 3 层**，否则拇指要换姿势。
3. 危险操作（斩首/解散/覆盖存档）**不放热区**，放冷区 + 二次确认——用"离手远"代替"多一次弹窗"。
4. 战斗技能图标 ≥96（03 图标按钮档），相邻间距 ≥12（连点不误触）。
5. 底部 88 安全区**不放可点元素**（home 条上滑会抢触摸）。

### 6.4 返回键与右滑冲突

| 场景 | 处理 |
|---|---|
| 界面内返回 | 状态栏左上 `◀`，点击区 96×96，**每屏固定位置** |
| 左缘 0–24 宽条 | **死区**，不响应自研手势（地图平移从 x>24 起），留给系统 |
| 整页横滑返回 | **不做**；页签用点击，横滑只留给"明确有横向内容"的筛选条 |
| 安卓实体返回键 | 小游戏侧**没有可靠的"拦截返回并弹确认"**（`wx.enableAlertBeforeUnload` 属小程序 API）→ 不假设能拦，改为"随时可恢复"：进战斗前自动存档 + `wx.onHide` 立即落盘 |
| 战斗中被系统打断 | `onHide` 暂停并写战斗快照；`onShow` 弹"继续 / 认输"，认输按撤退处理 |
| L3 弹窗 | 点遮罩 = 关闭；但已生效动作（招降/斩首/释放）的弹窗点遮罩无效 |

### 6.5 防误触

**二次确认**只给斩首/解散/覆盖存档/退出战斗；**长按 300 ms** 只给"结束本月"；**撤销 Toast** 给释放俘虏与卖装备（480×72 带 `[撤销]`，3 s 有效）；**滚动锁定**：速度 >200 px/s 时点击只停滚动、不触发子项；**点击去抖**：同一按钮 250 ms 内只响应一次。

## 7. 信息密度取舍

### 7.1 四档定义

**A 一屏必显**（影响当前决策，主视图固定区，**≤8 项/屏**）· **B 折叠**（偶尔要看，一行摘要 + `▾`，展开限高 2 屏，≤12 项）· **C 二级页**（低频、成组、需横向比较，走页签，不限）· **D 删除**（玩家无意义或纯实现细节）。

> **校验声明（因 v1 不删功能，密度取舍必须可逆）**：D 档只允许放"玩家据此做不了任何决策"的内容——造型号 `TYPE`、纯坐标 `POS/FLAGPOS`、几乎全空的 `FLAGS`、随机种子之类；**凡是原作界面上显示过、且参与数值的，一律不得进 D 档，最低进 C 档**。C 档的定义就是"在二级页里完整可见"，所以"折叠"不等于"看不到"。
>
> 验收方法：拿原作界面截图逐屏对照，截图里出现过的每一个数字，在竖屏版里都必须能在 A/B/C 中某一档查到；查不到即 bug。这张走查与 §5.5.2 的功能走查**同一次验收做**，一次录屏走完 31 屏。

## 8. 战斗 HUD 详解

> 战场口径全部来自 `02_战斗重构设计.md`：14 列 × 60 行、格 52×46 px、战场 728×2760 px、视口 900 px（1.0× 显示 19 行）、我方在下。本节只定义"屏幕上叠什么"，不重定义战场。

### 8.1 为什么上下拆

原作 `WAR0D` 是 640×136 的**一条**：左端我方头像 100×120、右端敌方头像、中间两条白条相向、正中一个按钮槽。横屏 3 列并排成立；竖屏照搬则每个头像只剩 100 px、每条血条 200 px，字全掉到 24 以下。

因此**敌方在上、我方在下**：顶条 100 px 放敌方与我方总兵力，底栏放我方主将细节，正好配合"我方在下"的战场方向（新设计）。这也与 02 §1.4 的 100/900/334 三带一一对应，UI 不侵占视口。

### 8.3 技能区：3 常驻 + 1 状态 + 1 抽屉

| 槽 | 内容 | 为什么 |
|---|---|---|
| ① ② ③ | 玩家自选的 3 个武将技（默认按"已习得 + 耗技力低"自动排） | 拇指横向舒适区 ≈ 3 个 96 px 钮（02 §1.6） |

## 9. 适配

### 9.1 缩放策略

**决策**：基准 750×1334，`scale = min(W/750, H/1334)`，多出的空间按 §9.2 分配，不足方向用背景延展，**不裁切、不黑边**。

|---|---|---|---:|---|---|
| iPhone SE/8 | 750×1334 | 9:16 | 1.000 | 750×1334 | 基准 |
| iPhone 14 Pro | 1179×2556 | 19.5:9 | 1.572 | **750×1626** | +292 高 |
| 主流安卓 | 1080×2400 | 20:9 | 1.440 | **750×1667** | +333 高 |
| iPad | 1536×2048 | 3:4 | 1.535 | **1000×1334** | +250 宽 |
| 折叠展开 | 1768×2208 | 4:5 | 1.655 | **1068×1334** | +318 宽 |

### 9.2 多出来的空间给谁

| 富余方向 | 分配 |
|---|---|
| 纵向（常规页） | 100% 给主视图（列表多 1–3 行）；**操作区 347 恒定不拉伸** |
| 纵向（战斗页） | 视口吃 60%、指挥区吃 40%（技能钮 96 不变，空隙变大） |
| 横向（平板） | 左右各留白 `(可视宽−750)/2`，背景延展；可视宽 ≥900 才启用双栏（右侧竖排按钮柱） |

### 9.3 安全区

| 项 | 规则 |
|---|---|
| 取值 | `wx.getWindowInfo()` 的 `safeArea` + `screenHeight`：`top = safeArea.top`、`bottom = screenHeight − safeArea.bottom`，再按 scale 折算 |
| 排版 | 设计按 88 排；实际 = `max(88, inset)`，只向下推状态栏，不动操作区 |
| 刘海 | 顶部 88 内只放背景 |
| home 条 | 底部 88 内不放可点元素（上滑抢触摸） |
| 横屏 | 锁竖屏（`"deviceOrientation": "portrait"`），不做横屏布局 |

### 9.4 可读性

字号下限已见 §3.4：全部可读文本 ≥24（@750），22 只给版权/版本号；19.5:9 上 scale 1.572 → 24 px 实渲染 37.7 物理 px ≈ 12.6 pt，可读；**不做平板专属字号档**（一套版式，避免双份维护）。（依据：03 §5.5）

## 开放问题

1. **16:9 以下的老机器怎么保底？** 现方案把 88 安全区当硬值；若实测到 16:9（750×1333 附近）以下且系统栏更高，状态栏 160 是否要压到 144？需要真机清单（含 720×1280 机型）后再定，可能要在 §3.1 加一档"紧凑模式"。
2. **战斗中切后台判负吗？** 单机对 AI 可"暂停 + `onShow` 继续"，但 100 人实时战斗的暂停会被用来规避败局。需与 `02_战斗重构设计.md` 补一条：切后台 >30 s 是否按撤退处理（本文 §6.4 暂按"继续/认输"二选一）。
3. **5 将 × 100 兵时 HUD 还成立吗？** 现 HUD 假设"1 个主将在视野"。多将同屏（原作最多 5 人，依据 docs/08 §4）时，底栏我将卡是**切换制**还是**并列 5 格**？前者省空间、后者要重算 §8.2 的高度。
4. **`+0x9F`/`+0xA1` 到底是什么？** 若证实是"战绩胜败"，按 §7.2 归 B 档折叠；若是别的（如"上次出阵月份"），可能直接进 D 档。等 `docs/07b` 的存档字段定名。
5. **平板要不要真做双栏？** §9.2 规定可视宽 ≥900 才启用，iPad 只有 1000（刚好过线），折叠屏 1068 也过线——即 v1 会真的触发双栏，但没有设计稿。是否 v1 先等比放大、双栏留给 v1.1。
