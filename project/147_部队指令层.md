## 1. 两层结构与核心结论

- 第一层 6 按钮（描述符表 `0x48F2A8`，stride `0x38`）：
  `保護主將`(0x4451C3) / 部队指令子菜单(0x4450AE) / `武 將 技`(0x4453C2) /
  `武將出擊`(0x445491) / `主將待機`|`主將後退`(0x445282) / `全軍撤退`(0x44554A)。
- 第二层：串区 `0x48F94C–0x490294` = **33 组 × 6 条**（组步长 `0x48`，`索引 = 组号×6 + 槽号`），
  指针表 `@0x48EB60`、执行表 `@0x48EE78`。组号 = 双方单位 `+0xc` 的阵形 id `0..32`。
- **第 5/6 条 198 项无一例外 = `全軍待機` / `全軍突擊`**，前 4 条随阵形变。
- 每条命令的执行都是同一个写入口 `0x43ADED(army, which, value)`：把命令字 `value` 写进
  `army+0x94 + idx*4` 的 8 个槽。`which` 语义：`0x100` 全体 8 槽 / `0x101` 除主将 7 槽 /
  `0..7` 单槽。槽位：`0 主将 / 1 前軍 / 2 後軍 / 3 左軍 / 4 右軍 / 5 中軍 / 6-7 备用`。
- 命令字（`docs/04b3` 表 + 18 入口交叉验证）：
  `0 待機 / 1 前進 / 2 後退 / 3 上移 / 4 下移 / 5 分散 / 6 集中 / 7 突擊 / 8 撤退`。

## 3. 18 个执行入口的语义归并

所有入口同构：`if (mode==1) return ((flags & mask)==0) && [0x4a8abc] > 0; else { 执行; return 1; }`。

| 入口 | 写入 `(which, value)` | 可用 mask | label（33 组里的出现） |
| --- | --- | --- | --- |
| 0x4449A9 | (1, 1) | 0xd | 前軍前進 / 全軍前進 |
| 0x4449EA | (1, 2) + 清 `[0x4a8ac4]` | 0xd | 前軍後退（组 0-8 等） |
| 0x444F58 | (1, 2) | 0xd | 前軍後退（组 9/20/31） |

| 0x444A80 | (1, 6) + 清 `[0x4a8ac4]` | 0xd | 中央集中 / 前軍集中 |
| 0x444ACB | (0x101, 0) | 0xd | 全軍待機 |
| 0x444B0F → 0x4448B2 | `AllRush` + (0x101, 7) + `army+0x80 |= 1` | 0x5 | 全軍突擊 |
| 0x444CCF | (3, 1) | 0x5 | 左軍前進 |
| 0x444D10 | (4, 1) | 0x5 | 右軍前進 |
| 0x444D51 | (5, 1) | 0x5 | 中軍前進 |

| 0x44501B | (2, 1) | 0xd | 伏軍攻擊 |
| 0x44505C | (1,3)(1,4) | 0xd | 左右前進 |

- `[0x4a8abc]` = **本方兵力数**（`0x43A795`：side 0 → `0x4a8abc`，否则 `0x4b03fc`）。
  所以"查可用"第二项就是**本方还有兵**（主将不算）。
- `[0x4a8ae0]` 是战场状态字：bit `0x2` 武將出擊、bit `0x4` 撤退中、bit `0x10` 主將待機/後退
  都是 `[确认]` 的置位点；bit `0x1` 在每个 mask 里，但**置位点没定位**（见 §4）。
- 全軍撤退（0x444B4C → 0x4447B7）是唯一**双判**入口：`([0x4a8ae0]&4)==0 && ([0x4a8ae4]&4)==0`，
  即双方都不能已在撤退。
- 18 个地址里有 1 对完全同签名（`0x4449EA` 与 `0x444F58` 都是「前軍後退 = (1,2), mask 0xd」，
  差别只在是否清 `[0x4a8ac4]`），所以 label 级去重是 **17 种** `(命令字, 目标槽, mask)` 签名
  ——测试 `label 级去重后 17 组…` 钉住这个数，防止后续改表时悄悄少一条。

## 4. `[推测]` 清单（拿不到原作常量的地方）

| # | 项 | 本作取值 | 依据 / 为什么只能推测 |
| --- | --- | --- | --- |
| 1 | 状态字 bit `0x1` 的语义 | 解释为「全局锁」：`world.over \|\| world.settled` 时置位 | `0x1` 出现在**每一个** mask 里 ⇒ 一定是"不可下令"的总闸；但置位点未定位。把它当"战斗结束/结算"最保守：不会误放行 |
| 2 | `主將待機/後退` 的 bit `0x10` | 开关：置位=待機（显示 `0x490420`），再按=待機（命令字 0）并清 bit | `0x445282` 的 `mode4` 置位 + label 二选一读 bit 是 `[确认]`；"再按一次走 0x444C94 命令字 0"来自 `0x444C37` 邻近分支，未在 198 表内闭环 |
| 3 | 保護主將的减伤系数 | `army.takenMul = min(现値, 0.75)` | `army+0x84 |= 0x10`（`guardGeneral`）是 `[确认]`；0.75 沿用 `strategy.ts:791` 的既有消费口径（R 系列早前实装），本轮不另立数字 |
| 4 | 五军怎么落到"每个士兵是独立 Unit" | 按位置切：以本方士兵 x 中位数分前/後（靠敌=前），y 中线 `6.5` 分左/右，`|y-6.5| ≤ 13/6` 兼中軍 | 原作 8 槽是"主将 + 7 支部队"，本作没有部队编制，只能按几何聚类；一支兵可同时属于"前+中"（原作槽位也允许一条指令写多槽） |
| 5 | 後退/分散/集中/上移/下移的**速度** | 全部 `1.0 × MOVE_PER_TICK = 0.09 格/tick` | 原作只写命令字，位移由阵形/移动子程序按槽位自己算，常量未定位 |
| 6 | `全軍待機` 是否连主将也停 | 只停士兵（`which=0x101` 除主将） | `[确认]` 的 which 语义直接推出；实机观感待验证 |
| 7 | `伏軍攻擊` 的效果 | 後軍前進（写 (2,1)） | `0x44501B` 就是 `(2,1)`；但"伏軍"是否另有伏兵状态位，未在 18 入口里看到第二处写 |
| 8 | `左右前進` 的两连写顺序 | `codes=[3,4]` 依次写前軍槽（上移再下移） | `0x44505C` 两次 `0x43ADED` 顺序 `[确认]`，但两次写同槽后一次覆盖前一次 ⇒ 净效果可能是"先上移一帧再下移"，暂按"先 3 后 4"记录 |
| 9 | `stepWithArmyOrders` 把位移放在 `step()` **之后** | 先跑完整 step，再用快照回写 | 约束禁止改 `battle.ts`；快照回写的语义 = 「本 tick 的位移被指令改写」，与内联钩子（§6 diff）逐位一致 |

## 5. 状态放在哪（为什么不加 `world.armyOrder`）

硬约束禁止改 `battle.ts` / `strategy.ts`，所以一侧的指令状态放在本文件自己的
`WeakMap<World, Record<Side, ArmyOrderState>>` 里，`armyOrderOf(world, side)` 取用：

```ts
interface ArmyOrderState {
  slots: (ArmyCmdDef | null)[];  // 6 条子菜单
  cmds: number[];                // 8 个命令槽（army+0x94 的镜像）
  active: ArmyCmdDef | null;     // 唯一持续影响位移的一条
  last: ArmyCmdKind | null;
  at: number;                    // world.tick
  buttons: number;               // ARMY_BTN
  broken: number;                // [0x4a8ac4] 镜像
}
```

`applyArmyCmd()` 只写这个结构（外加 `army.flags/takenMul` 这两个 battle.ts 本来就在读的字段），
**绝不直接改士兵数/位置/血量**——测试 `applyArmyCmd 只写状态：调用瞬间任何单位的位置都不变` 钉住。

WeakMap 的代价：`world` 被序列化/克隆后状态丢失（存档/回放）。当前战场不是存档对象，可接受；
若以后要进存档，改成 `world.armyOrder` 字段即可（§6 diff 里 World 接口那两行就是预留位）。
