## 2. opcode 覆盖 90/90

`so.ts` 的 `OPCODES` 是 0x00–0x59 的 90 项表；`vm.ts` 每个 opcode 都有 `case`，未命中即抛
`SmartScript: 未知 opcode 0x.. @0x..（0x00–0x59 之外）`，**不会静默跳过**。

| 类别 | opcode |
|---|---|
| 栈/常量 | `0x00` NOP、`0x03` PUSHN、`0x06` PUSHI、`0x07` PUSHS、`0x0E` POP |
| 变量 | `0x08/0x0B` LDSL/STL、`0x09/0x0C` LDSG/STG、`0x0A` LDG、`0x0D` STE、`0x1D/0x20` INCL/DECL、`0x1E/0x21` INCG/DECG、`0x1F/0x22` INCE/DECE |
| 数组 | `0x4E/0x4F` LDSLS/LDSGS、`0x50` LDGIDX、`0x51/0x52/0x53` STLIDX/STGIDX/STEIDX、`0x54–0x59` INCLIDX/INCGIDX/INCEIDX/DECLIDX/DECGIDX/DECEIDX |
| 算术 | `0x0F/0x12/0x14/0x16/0x18` ADD/SUB/MUL/DIV/MOD、`0x10/0x13/0x15/0x17` 浮点四则、`0x1A/0x1B` NEG/FNEG、`0x3E/0x3F` SHL/SHR |
| 比较/逻辑 | `0x23–0x25` AND/OR/XOR、`0x26–0x37` EQ/NE/GT/GE/LT/LE 及 STR*/F* 变体、`0x38–0x3A` LNOT/LAND/LOR |
| 跳转/调用 | `0x3B/0x3C/0x3D` JMP/JZ/JNZ、`0x40` CASE、`0x04` CALL、`0x47` CALLS、`0x01/0x02` RETV/RET |
| 系统 | `0x05` SYSCALL、`0x42` WAIT、`0x45` WAITFOR、`0x48–0x4B` I2F/I2S/F2I/F2S |
| 推测实现 | `0x11/0x19/0x46/0x4C/0x4D`（MAGIC.SO 中 0 次出现，语义仅由 handler 推断） |

MAGIC.SO 实际用到其中 **58 个**；未出现的 32 个按 `docs/04` 的 handler 语义实现，测试只保证"有分支 + 未知 opcode 会抛"。

**调用约定（踩过坑，写死在这里）**：CALL 前实参从右往左压，**最后压的是 arg1**（`frame-2`）；CALLS 的 name 压在最底下，其余同样"最后压 = arg1"。
比较与减法采用**栈顶为左操作数**（`a = pop(); b = pop(); fn(a, b)`）；这是让 `ProduceArrowSoldier` 等循环正常退出的关键，反过来会让 110 技能只剩 71 个通过。

## 4. `runSkill` API

```ts
export function runSkill(
  world: World,
  side: Side,
  scriptNum: number,     // magics.json 的 SCRIPT（501–610），不是 SEQUENCE
  tx: number, ty: number, // 目标格
  opts?: { budget?: number; ttl?: number; trace?: (s: string) => void; onInstruction?: (ins: Instruction) => void },
): { ok: boolean; log: string[]; stats: RunStats; objects: SkillObjectSummary[] };
```

- 脚本号→函数：按名字 `Magic${scriptNum-500}` 查（**不要用 num 查**：MAGIC.SO 里另有 `F9999` 这类自带 id 的函数会撞车）。
- 引擎全局：`g2`=施法者句柄、`g3`=目标句柄、`g4`=数值（治疗=`20+ATTACK`，攻击=`ATTACK`）、`g5`=方向（0 右 / 1 左）或治疗目标句柄。
- 句柄：单位 = `1000 + 下标`，物件 = 1..，召唤单位从 5000 起 —— 统一空间后 `0x105/0x106/0x12` 对单位与物件都成立。
- 结算：治疗走 `0x117/0x118`（直接改 `general.hp`）；伤害按脚本物件轨迹做几何判定（见 §7），击杀统计进 `stats.killed`；fx 一律 push 进 `world.fx`。
- 预算：单帧 > 200,000 条指令抛 `SmartScript: 疑似死循环…`；虚拟帧 > 1200 抛"截断"（`ok` 仍为 true，已产生的效果照常结算）。
  **"单帧"的边界是 `WAIT`**：`vm.beginFrame()` 在每个 `WAIT` 之后重置计数器，所以一个合法的长技能（大量 `WAIT 1` 的循环）不会因为总量大而被误判；真正的死循环（`JMP` 自环、没有 `WAIT`）仍会在 20 万条时报同一个错。

## 4b. 逐帧驱动：`startSkill()` / `SkillSession`

`cast()` 不再"一次跑完"，只**启动**脚本；`step()` 每 tick 推一帧，`WAIT n` 真的挂起 n 帧。

```ts
export function startSkill(world, side, scriptNum, tx, ty, opts?): SkillSession;

class SkillSession {
  readonly frames: SkillFrameStat[];   // { frame, instructions, syscalls, hits, killed, healed }
  frame: number;        // 已经跑完的帧数
  pendingFrames: number;// 当前 WAIT 还剩几 tick
  done: boolean; ok: boolean; reason: string;
  killed: number; healed: number; hits: number;
  advance(): SkillFrameStat | undefined; // 推 1 tick；还在挂起时返回 undefined
  drain(): void;                         // 一口气跑完（只给瞬发技能用）
}
```

- `start()` 跑第 0 帧就返回，所以 `cast()` 返回时 `world.fx` 里已经有本次特效、`killed/healed` 也回填的是第 0 帧的数字（`game/web/main.js` 直接读这两个值播命中音效 / 弹 `+N`，接口不变）。
- `World.sessions` 存所有在播会话；`step() → tickSkills() → advanceSessions()` 每 tick 推进一次，会话结束时把 `killed/healed` 汇总进 `world.stats.spellKills* / spellHealed*`，`settle()` 的 `spellKills` 就取这个数（结算面板能看到"法术击杀"）。
- **WAIT 语义**：`vm.requestWait(n)` 先把 `suspended` 标志置位再抛 `VmSuspend`，`invoke()` 的 `finally` 看到标志就**不**恢复栈/帧，于是 VM 停在 `WAIT` 的下一条指令上；session 每 tick 减 `pendingFrames`，减到 0 才 `vm.resume()`。VM 主体（decode/step/doReturn）没有重写，只在 `vm.ts` 外面加了一层 `pump/resume`。
- **嵌套调用的 WAIT 也必须能挂起**：`0x47 CALLS` 原来是 `invokeByName()` 递归进宿主栈（callDepth=2），里面的 `WAIT` 只能同步推虚拟帧。现在改成 `callInline()`——按 `fn.argc` 压参、压返回地址、置 `pc`，在**同一个 exec 循环**里跑，callDepth 恒为 1。这是 606 能逐帧播完的关键（见 §7.7）。
- **命中按帧结算**：`settleFrame()` 用物件**这一帧**扫过的线段判定，`hitUnits` 去重保证"每个单位整场只吃一次伤害"——于是帧数只改变节奏、不改变一个技能的总量。
- **補血類是瞬发**：`cast()` 里 `session.isHealSkill` 为真时直接 `drain()` 跑完。原作里 命療術/補血 扣完技力血就回来，没有"等 N 帧才回血"的玩法；而 web 端是同步读 `result.healed` 弹数字的，所以这类技能保持同步语义。攻击/召唤類一律逐帧。

## 7. 已知偏差（离"像素级还原"还差什么）

1. **帧时序（已修）**：`WAIT` 现在真的挂起 VM（`skip` 见 §4b），`cast()` 只启动、`step()` 逐帧推进，所以"第 N 帧改变战局"的技能节奏与原作一致，也能表现"打到一半被中断"（会话留在 `world.sessions` 里，随时可以丢弃）。**遗留**：1 tick 固定 = 1 虚拟帧（30 Hz），原作的实际帧率没有逐帧校对；`補血類` 仍是同步跑完（见 §4b）。
2. **物件寿命**：原作由动画资源帧数决定；这里用 `DEFAULT_OBJECT_FRAMES=96`（`0x18` 会用脚本给的真实帧数覆盖）。`0x12` 的语义是"物件是否已结束"（0=还在播，非 0=已结束），靠这个寿命收敛。
3. **伤害判定是几何近似**：原作由 C 侧逐帧碰撞回调 `Hurt`；这里收集脚本物件（资源号 1000–90000）的轨迹点做圆判定（单点 r=1.25 格、飞行按方向采样到 `speed*frames/96` 格）。`Hurt` 里"直接改单位字段"的部分通过 `0x125` 落到真实单位上。
4. **随机数序列不同**：`0x303` 用 `world.rng`（mulberry32），与原作 CRT `rand()` 不是同一序列；同 seed 可复现，但逐帧轨迹与原版不会一致。
5. **20 个视觉 syscall 是占位**：震屏/闪白/镜头锁定/亮度渐变只记录不表现（`0x12F/0x131` 记了状态，渲染层尚未消费）。
6. **`0x12A` 的返回值**：脚本拿它当"对象数量"做循环上界，原实现返回句柄会让循环次数等于句柄值；这里固定返回 1（`F9999`-类函数的真实语义仍待用 IDA 核对）。**它和 606 的死循环无关**——606 的调用链里一个 `0x12A` 都没有（探针 `work/probe_606b.ts` 反汇编确认）。另外 `work/probe_args.ts` 顺带发现 vm 的 binop 是 `a=pop(); b=pop(); fn(a,b)`，所以 `LDSL x; PUSHI n; LT` 算的是 `n < x`，循环实际跑 `n+1` 次——全文件统一差 1，不影响总量，暂不改（改了要重测全部 110 个技能）。
7. **劍輪舞(95)（已修）**：不是死循环，是**一个 280 圈 ×4 象限的有限循环**（`CreateTwisterSwordAttack @0x304AC..0x30820`：`0x3067c PUSHI 0 / STL 27`，`0x3068c LDSL 27 / PUSHI 280 / LT / JNZ 0x307c0`，每圈末尾 `0x307a4 PUSHI 1; 0x307ac WAIT; 0x307b0 INCL 27`）。整条链 528,078 条指令、18,872 次 syscall，只是**单次 20 万预算**装不下。两处修复：① 预算按 `WAIT` 分段（`vm.beginFrame()`），每帧约 1,886 条；② `0x47 CALLS` 改 trampoline（`callInline()`），让嵌套调用里的 `WAIT` 也能挂起。修完：同步 `runSkill` = **528,078 条 / clock 1201 / ok**（旧版 200,000 条就抛 `pc=0x3076c`）；逐帧会话 = **1,132 帧 / 1,133,298 条 / kills 分摊在第 43 帧**。
8. **未实现 opcode 语义的 5 个**（`0x11 0x19 0x46 0x4C 0x4D`）在 MAGIC.SO 中出现 0 次，实现是推断值；换别的 `.SO`（SYSTEM.SO 等）前需要按 `docs/04` 再核对。

## 9. 未解 / 已知贴边

1. **`MAX_SKILL_FRAMES = 1200` 贴边**：606 逐帧跑完恰好 1,201 虚拟帧，再慢一帧就会被截断（`ok` 仍为 true，只是尾部 `DownBrightness/0x110` 不执行）。如果以后要提高帧率（1 tick ≠ 1 帧）或改 `WAIT` 的折算，**先动这个常量**。
2. **`0x12A` 的真实语义**仍未核对（§7.6）。它不影响 606，但影响所有"取物件数量做上界"的脚本——目前全 110 个技能里没有因此跑飞的。
3. **20 个占位 syscall** 的视觉表现（震屏/闪白/镜头）仍未落地（§7.5）。
4. **`補血類` 的同步跑完**是接口妥协（web 端同步读 `healed`），不是原作语义；哪天 `cast()` 改成异步/回调，应该也把补血改成逐帧。
5. **`0x47 CALLS` 的 trampoline 只覆盖脚本内 CALL**；`callScript()`（`syscall 0x310–0x314`）仍走 `vm.invokeByName()`，若被调函数里有 `WAIT`，还是退化成同步推帧（`SkillRun.nestedWaits` 会计数，目前 606 全程为 0）。
