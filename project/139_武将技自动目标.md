# 139 武将技自动目标：还原「点技能格直接放」

> 用户报的差异（原文）：「释放武将技和原版貌似也不同，原版我记得是不需要选目标的。」
> 本作改前：点技能格 → 进瞄准态 → 点战场某格 → `cast(gx, gy)`。
> 本作改后：点技能格 → **立即** `cast(world, 'A', seq)`，落点由内核 `defaultAim()` 自动算。

---

## 0. 一句话结论

**原作「不需要选目标」既不是「引擎随便给个默认落点」，也不是「脚本完全自治」，而是：**
**引擎按 `MagicDef+0x10` 的 ACTIVE 目标类型解析出目标句柄 `g3`，落点只用来选这个 `g3`；
110 条 MAGIC.SO 脚本每条都自己写 `SYSCALL 0x100` 覆盖特效锚点，伤害范围由脚本自己算。**

所以玩家点哪一格，**不进伤害公式**；点格的唯一作用是决定「最近的敌人是谁」= `g3`。
而 `g3` 该是谁，可以由 ACTIVE 掩码（敵方主將 / 敵方士兵 / 敵方全軍 / 純己方）唯一确定 —
这就是原作不需要玩家点目标的机制。

## 1. 考古：落点到底被谁读走

### 1.1 引擎侧：落点的唯一作用 = 选 g3

`game/src/core/smartscript/runtime.ts`（本作内核，逐字对应原作 `0x41xxxx` 派发逻辑）：

```ts
// runtime.ts:318-329
// 目标：离 (tx,ty) 最近的敌单位
for (const u of world.units) {
  if (!u.alive || u.side === side) continue;
  const d = (u.x - tx) ** 2 + (u.y - ty) ** 2;
  ...
}
this.targetHandle = best ? (this.byUnit.get(best) ?? 0) : 0;

// runtime.ts:343-346
this.targetPoint = { x: best ? best.x * 96 : tx * 96, y: best ? best.y * 72 : ty * 72 };
```

即：**落点 → 最近的敌人 → g3，然后 targetPoint 直接改成那个敌人的像素位置**。
落点本身在 `best` 存在的分支里**被彻底丢掉**。

引擎槽位（`runtime.ts:351-355`）：`g2 = 施法者`、`g3 = targetHandle`、`g4 = ATTACK 威力`、
`g5 = 方向（治疗技 = 被治疗者句柄）`。

### 1.2 脚本侧：110/110 条自己写锚点；读锚点的只有相机

`export/script/magic_so.dis.txt` 全库统计（`work/autoaim/analyze_dis.mjs` → `work/autoaim/dis_stats.txt`）：

| 指标 | 数值 |
|---|---|
| 函数总数 / 指令总数 | 463 / 30,720 |
| `SYSCALL 0x100`（setTargetPx，写引擎全局 `0x4AC368/0x4AC370`） | 54 个函数、65 次 |
| **110 条武将技里写 `0x100` 的** | **110 条全部（s100 ≥ 1）** |
| `SYSCALL 0x111`（取 targetPx.x）/ `0x112`（取 targetPx.y） | 12 / 4 次，**只在 7 个相机函数里**（MoveCamera / LockCameraSimple / LockCameraSimple2 / LockCameraLine / LockCameraLineDelay / LockCamera / LockCamera2） |
| `LDG 3`（读 g3 目标句柄） | 93 个函数、142 次 |
| `0x113`（unitAtPx 扫场）/ `0x10d`/`0x129`（按阵营遍历单位） | 24 / 24 / 31 次 |

结论 1：**伤害判定一次都没读 targetPx**（`0x111/0x112` 的 12 个调用点全部落在 dis:786…1372 的相机族函数里）。
脚本写 `0x100` 是为了「镜头/光柱/弹丸该出现在哪」，不是为了「打谁」。

逐函数取证（行号均指 `export/script/magic_so.dis.txt`）：

| 技能 | 脚本函数 | 锚点怎么来 | 证据行 |
|---|---|---|---|
| 1 命療術 | `Heal` func#167 | `LDG 2`（施法者）→ `0x105/0x106` 取自己坐标 → `PUSHI 120; SUB` → `SYSCALL 0x100`。**完全不读 g3** | dis:13721 函数头；13732-13745 |
| 2 落月弓 | `ShootObject` func#60 | `LDG 2`→loc1、`LDG 3`→loc2、`LDG 5`→loc3；**全段无 `LDSL loc2`**（g3 死读）；弹丸起点 = 施法者 ± 180px | dis:3901 函数头；3912-3917 三次 LDG；3950-3966 |
| 50 半月斬 | `HalfMoon` func#50 | 同上：`LDG 3`→loc2 后无回读（死读）；自写 `SYSCALL 0x100` | dis:2679 函数头；2690-2695；2769 |
| 62 地茅刺 | `Spear` | `LDG 3`→loc3 → `0x105/0x106` → **`CALL MoveCamera`**：g3 只决定镜头看哪 | dis:26181-26183；26211-26223 |
| 105 神鬼亂舞 | `DemonDancing` | `0x113` 扫施法者周围的格子 → `LDG 3` + `EQ` 比对 → 走不同分支 | dis:12034/12046（扫场）；12050-12051（`LDG 3` + `EQ`）；12106-12110（第二处） |

### 1.3 g3 的真实用途分类（逐技，`work/autoaim/report_g3.mjs` → `work/autoaim/g3_classes.md`）

判定规则：`LDG 3` 之后若存进 `STL locN` 且在该槽被覆盖前没有 `LDSL locN` = **读了丢掉**；
直接作为比较/`SYSCALL` 操作数，或存进去后被回读 = **真消费**。

| 类别 | 条数 | 含义 |
|---|---|---|
| 真消费 g3 | 65 | 落点经 g3 影响脚本行为 |
| 读了立刻丢掉 | 11 | 落点对这些技**完全无影响**（含 2 落月弓、50 半月斬） |
| 完全不读 g3 | 34 | 落点只当特效锚点（含 1 命療術、110 鬼哭神號） |

65 条「真消费」里还要再分两类（抽查）：

- **只拿 g3 的坐标做镜头/特效锚**：如 `Spear` dis:26223 `CALL MoveCamera`。这类落点改的是「镜头往哪摇」。
- **把 g3 灌进伤害分支**：如 `DemonDancing` dis:12050-12051（`LDG 3` + `EQ`）→ 不同的 `0x314` 伤害区。
  这才是「落点会改战果」的技 — 与实测吻合（见 §2）。

### 1.4 回答用户指定的三个问题

1. **脚本从引擎全局 target 句柄取目标，还是自己扫场？**
   —— **两者都有**：`LDG 3` 读引擎给的句柄（142 次 / 93 个函数）；同时 `0x113`（24 次）、`0x10d`（24 次）、
   `0x129`（31 次）自己扫场。`DemonDancing` 是典型：先扫场（0x113），再和 g3 比对。
2. **`targetPoint` 被哪些 opcode 读？** —— 只有 `0x111`（取 X）/`0x112`（取 Y），
   而且只出现在相机函数里。`0x10e` 在 MAGIC.SO 里**一次都不存在**（0 个匹配），`0x12a` 是「生成对象」不是读目标。
3. **原作「不需要选目标」是「引擎默认落点」还是「脚本完全自治」？**
   —— 都不是，见 §0：**引擎按 ACTIVE 目标类型解析 g3，脚本自己算伤害范围**。
   引擎确实需要一个落点（用来选 g3），但这个落点对玩家不可见、也不需要玩家提供 ——
   它可以由目标类型唯一推出来。

## 2. 实测：落点到底改不改战果

### 2.1 用户已跑的表（本报告直接引用，未重复跑）

同 seed(777)、同对手，`cast()` 到 4 个落点 `[4,6] / [24,6] / [62,6] / [66,2]`，400 tick 后：

| seq | 四点结果 |
|---|---|
| 1 命療術 | 完全相同（敌将 −33、敌兵 −134） |
| 2 落月弓 | 完全相同（−62、−130） |
| 50 半月斬 | 完全相同（−62、−130） |
| 61 地茅刺 | 完全相同（−45、−142） |
| 104 神鬼亂舞 | **不同**：−89 / −29 / −29 / −81 |

### 2.2 我这一轮的独立复现（`work/autoaim/probe_aim.mjs`、`probe_default.mjs`）

只统计法术增量（`stats.spellKillsA / spellDamageA / spellHealedA` 的前后差），把普攻肉搏隔离掉：

| seq | 5 个落点（敌将 / 敌前排 / 我主将 / 敌后 / 中场）的结果 |
|---|---|
| 1 | 五个点完全一致：治疗 **49**、0 tick（瞬发） |
| 104 | 敌将 → 将伤 **38**；敌前排 → 击杀 **9**；我主将 → 击杀 **11**；敌后 → 击杀 **2**；中场 → 击杀 **11** |

⇒ 与用户的表同向：**绝大多数技的落点是无效输入，只有少数（104 这类）会变**。
`[推测]` 用户表里 seq 2/50/61 在四个点上都打出了伤害，是因为跑到 400 tick 时两军已接战；
我这一轮的 probe 在 PRE=120/SOL=200 下这三个技打出 0（射程/站位不同），所以「不变」在我的场景里被「没打中」掩盖了 —
但「104 敏感」这一点两边一致。

### 2.3 关键推论

落点 → `g3` = 「离落点最近的敌单位」（runtime.ts:318-329）。
所以只要默认落点落在**ACTIVE 指定的那类目标**上，选出来的 `g3` 与玩家手点它**完全等价**。
这就是 `defaultAim()` 的设计依据。

| ACTIVE 掩码 | 选点 | 例 |
|---|---|---|

```ts
// battle.ts:2201-2204（现状）

  tx === undefined || ty === undefined
    ? defaultAim(world, side, seq)
```

`[推测]` 标注：`MagicDef+0x10` 指向的子表 `0x4868A8` 内容至今没定位到

## 8. `[推测]` 与未解问题

1. `[推测]` **`0x4868A8` 子表内容未知**：`MagicDef+0x10` 的 ACTIVE 位如何映射到「具体哪个单位」，
   原作有张子表，至今没人定位（`docs/04-脚本引擎SmartScript.md:1008` 说「写入者未定位」）。
   本报告的映射表是**按 ACTIVE 位的中文语义直译**。若将来定位到子表，`defaultAimForMask()` 是唯一要改的地方。
2. `[推测]` **原作引擎侧真正算落点的代码没定位**（应该在 `0x41xxxx` 的技能调度里），
   所以「引擎是否也做质心/最近单位」是推断 —— 但结论不依赖它：脚本自己写 `0x100`，
   落点只影响 g3，而 g3 由目标类型唯一决定。
3. `[推测]` **65 条「真消费 g3」里到底哪些会改战果**：只逐条看过 `Spear`（只摇镜头）、
   `DemonDancing`（真进伤害分支）两条；其余是按「g3 是否流进 `0x125/0x314/0x118`」粗判，未全测。
4. **未解**：`SYSCALL 0x100` 的引擎侧唯一写入者仍未定位（脚本侧 65 次写入已确认）。
5. **未解**：用户表里 seq 2/50/61 四点不变，但这两条脚本的 g3 一个是死读（2、50），
   一个只喂镜头（61）—— 三个都在「落点无效」这一侧，与表一致；本轮 probe 因射程没打出伤害，无法二次确认。
