# 01 · Sango2.PAK 包格式与解包

> **一句话结论**：`Sango2.PAK` 是 Odin Soft 自制的**无压缩、无加密**资源包，11110 个文件首尾相接存放在 0x18 起始的数据区，末尾跟一张定长 64 字节/项的索引表。格式简单到可以直接用 30 行代码读写。
> 证据：`Sango2.PAK` 全量解析 + 逐个文件 offset/size 自洽校验（末文件结束于 117,028,039，索引表起始 117,028,049）。

## 1. 文件总体布局

```
+0x00  ┌───────────────────────────┐
       │ Header (24 B)             │
+0x18  ├───────────────────────────┤
       │ Data area                 │  文件内容连续存放，无对齐填充
       │  file#0, file#1, ...      │
+...   ├───────────────────────────┤
index  │ Index table (64 B × N)    │  N = 11110
EOF    └───────────────────────────┘
```

## 2. 头部（24 字节）

| 偏移 | 类型 | 实测值 | 含义 |
|---|---|---|---|
| +0x00 | char[4] | `"PAKS"` | 魔数 |
| +0x04 | u16 | `0x662B`（字符 `'f'`,`'+'`） | 版本/版权标记。官方原版可能不同（本作为 1.05+ 重打包版） |
| +0x06 | u16 | 0 | 未用 |
| +0x08 | u32 | `0x06F9B4D1` = 117,028,049 | **索引表起始偏移**（= 文件末尾 − 64×N） |
| +0x0C | u32 | `0x403F` = 16447 | **名义条目数——不可信**（实际 11110）。原版可能预留过更多条目 |
| +0x10 | u32 | 0 | 保留 |
| +0x14 | u32 | 0 | 保留 |

> ⚠️ 坑点：`+0x0C` 的计数比实际条目多 5337，按它遍历会读到越界垃圾。**必须用 `index_off` 反算 `N = (filesize − index_off) / 64`，或按 offset 链顺推**。

## 3. 索引项（64 字节 / 项）

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0x00 | u32 | **size**，文件字节数 |
| +0x04 | u32 | **offset**，数据区绝对偏移（从文件开头算） |
| +0x08 | u8[24] | 保留（全 0） |
| +0x20 | char[40] | **文件名**，NUL 结尾，含相对路径，反斜杠分隔，**大写** |

> ⚠️ 坑点 2：名字字段是 **40 字节**，不是 16 字节。按 16 字节读会把 `FACE001.SHP` 截成 `FACE0` 之类的假名字，并制造出成百上千个"重复文件"。

## 4. 解包实现（最小可用版本）

```python
import struct, os
data = open('Sango2.PAK', 'rb').read()
magic, ver, index_off, count = struct.unpack_from('<4sHII', data, 0)
n = (len(data) - index_off) // 64
for i in range(n):
    p = index_off + i * 64
    size, off = struct.unpack_from('<II', data, p)
    raw = data[p + 0x20: p + 0x40]
    name = raw.split(b'\x00')[0].decode('ascii').replace('\\', os.sep)  # 名字全是大写 ASCII
    os.makedirs(os.path.dirname(name) or '.', exist_ok=True)
    open(name, 'wb').write(data[off: off + size])
```

现成工具：`F:\sanguo\tools\pak_extract2.py`（输出到 `F:\sanguo\extract\pak\`，并生成 `_manifest.json`）。

## 6. 重打包（给新项目参考）

原版/1.05+ 用社区工具 `odin_pak_packer` 重打包，规则与本格式一致（头 + 连续数据 + 64B 索引）。若新游戏沿用此格式，建议改进：

1. 索引里加 **u32 CRC32**（现在是 24 字节全零的保留区，正好够用）。
2. 计数改成真实条目数。
3. 名字扩到 64 字节或改用 UTF-8 并支持长路径。
4. 大文件（CHINAMAP）考虑分块，避免一次性读入。

> 设计参考价值：这套"**定长索引 + 无压缩直读 + 内存映射式访问**"是 1999 年 CD 游戏的标准做法（读盘快、实现简单）。现代项目可用 ZIP/自研包，但要保留"**整包热更新 + 单文件直读**"两个特性。
