# 05b · 动画与造型目录（THINGS.INI / COMBINE.INI 逆向）

> **一句话结论**：`THINGS.INI` 的 620 个 `[OBJECT]` 段合起来是一张"**造型 + 动画序列**总表"：每段用 `Directory` 指定 `SHAPE\` 下的资源子目录、用 21 个动作字段（`Wait/Walk/Attack…`）列出该造型的逐帧序列，`#N` 是**帧停留 tick 数而不是帧数**；文件名末尾的数字是**帧号（4 位）**，主将/武器类在帧号前还多一位"武器/招式位"（`L1A10002`），兵种类多一位固定 `1`（`MAW10001`）或骑兵标记 `H`（`MAHA0002`），师团/旗/死马另有 6 位写法（`FLAG0101`、`SH010001`）。武将的战斗画面并非单张图，而是 `MAJOR\BODY`（身体）+ `MAJOR\WEAPON`（武器）+ `MAJOR\HORSE`（马，仅骑乘时）三层按各自 `offsetX/offsetY` 锚点叠出来的；`COMBINE.INI` 则是另一件事——一个"把 N 张 SHP 按 (x,y) 拼成一张"的**测试配置**（实测只有 4 条，不是 8 条）。
>
> 证据：`F:\sanguo\extract\pak\THINGS.INI`（600317 B / 9083 行 / **cp950**）、`F:\sanguo\extract\pak\COMBINE.INI`（27534 B / 8 行 / ascii）、`F:\sanguo\extract\pak\TIMES1-5.INI`、`F:\sanguo\extract\pak\SANGO.INI`、`F:\sanguo\extract\json\xls_群英2.json`、`SHAPE\` 下 10969 个 `.SHP` 的文件名与 SHP 头。
> 中间产物：`F:\sanguo\work\things_probe.py`（结构探针）、`F:\sanguo\work\things_analyze.py`（逐帧解析器）、`F:\sanguo\work\things_parsed.json`（620 对象 × 4025 条动作 × 35301 帧，含每帧解析到的真实文件路径）。

## 0. 方法论与两个硬坑

| 项 | 结论 | 证据 |
|---|---|---|
| 编码 | **cp950 / Big5（繁体）**，不是 GBK | 用 gbk 在偏移 57 处 `UnicodeDecodeError`；`A9 52 C0 F8 B3 4E` → `命療術` |
| 路径大小写 | `\magic\000` 与 `\MAGIC\000` 在同一个文件里混用，**加载器必须大小写不敏感** | THINGS.INI 里 `\magic\000`（#273）与 `\MAGIC\000`（#275）并存 |
| 标志分隔符 | `Flags` 值里 `,` 和 `+` 混用（`OF_MAN+OF_TRIGGERMAN`、`OF_MAN, OF_BIGSHAPE`） | #0 与 #31 段 |
| 全大写键 | 31 个对象用 `FLAGS=`（全大写）代替 `Flags=`，两者语义相同 | 字段名统计 |
| 动作名 | 21 个动作字段 + `Life`/`Lose`；**没有 `Sprite` 字段** | 620 对象字段计数（见 §1.2） |

解析器要点（`F:\sanguo\tools\parse_ini.py` 已具备）：按段名重复保留**有序列表**、只在第一个 `=` 处切分、保留每个字段的 `lineno`。

## 2. 动作行语法：`#N` 是延时，不是帧数

### 2.1 token 表

动作字段的值是**逗号分隔的 token 流**，例如：

```
Attack = '#3, L1A10002, L1A10003, L1A10004, L1A10005, L1A10006, L1A10007, @%OM_ATTACK, L1A10008, L1A10009, L1A10010, L1A10011, SCROVER'
```

| token 形态 | 数量（全表） | 含义 | 证据 |
|---|---:|---|---|
| `#N` | — | **该帧停留 N 个 tick**（不是"重复 N 次"、也不是"第 N 帧"） | ① `Win='#6, Sol0WIN1…WIN4'` 只有 4 张图却写 `#6`；② `Wait='L1W10001, #16, L1W10002, #8, …'` 呈"图, 延时, 图, 延时"**后置**写法；③ 行首 `#N` 是该动作所有帧的**默认延时**（`Attack` 216 个对象里 214 个都是 `#3`） |
| 文件名 | 35301 | 帧图 → `<Directory>\<name>.SHP` | 解析后只有 32 个 token 找不到文件，且全部是注释模板段与 `!` 音效号（见 §2.4） |
| `@%OM_xxx` | 1109 个 token（分布在 688 条动作里） | **在该帧触发操作码**（命中判定、死亡停帧、移除等） | `@%OM_ATTACK`（攻击判定帧）、`@%OM_DEATHSTOP`、`@%OM_REMOVE` |
| `$xxx` | 263 个 token | **具名引用**（引用另一个动作序列或音效） | `$Defense` 120、`$Hit01` 120、`$Horse01` 8、`$m005snd02` 4…；具体语义**未证实** |
| `!NNNNN` | 少数 | 推测：数字化的音效/特效号 | `!99`、`!7003`、`!33002`、`!18002` |
| `SCROVER` | 3000+ 行尾 | **序列结束哨兵** | 几乎所有动作以它收尾 |
| `NULSHAPE` | `First` 全用 | 空图（"起始圖檔"= 不显示） | `First = '#1, NULSHAPE'` |
| `#9999` | 173 个 `Wait` | **无限停帧**（图静止不动） | `Wait='#9999, m000hit01'` |
| `#-1` | 少量 | 特殊值（雨天对象的死亡行） | `#-1, Rain001, !99, NULSHAPE, SCROVER` |
| 纯数字（如 `1200`） | 16 | `Life` 字段的 tick 数 | `Life` 字段 |

### 2.4 "起始帧"到底怎么算

```
文件名 = <前缀><5 位数字>   e.g.  L1A10002
                              │││└──── 帧号 0002（4 位，动作内从 0001/0002 起递增）
                              ││└───── 武器/招式位（1–4 = 剑/枪/矛/刀；5=半月斬 6=後攻擊…）
                              │└────── 动作码（W/R/A/L/S/D/H/F/FS）
                              └─────── 阵营/造型（L=藍 R=紅，或 A–D 武器类）
```

- **起始帧 = 该动作字段里第一个文件名**，没有单独的"起始帧字段"。
- 帧号是**动作各自独立编号**的，不是全文件全局编号：`Walk` 从 `0001` 起（9 或 12 帧）、`Wait` 从 `0001` 起（4 帧）、`Attack` 系**从 `0002` 起**（10 帧，`0001` 留给了待机起手帧，被 `Wait`/`First` 复用）、`Death` 从 `0001` 起（10 帧）、`Win` 用单独的 `FS` 前缀从 `0001` 起。
- `Attack4` 是**跨动作码拼接**，所以它没有单一"起始帧"规律（`L1A30002` 起，中途跳到 `L1A20004`、`L1A50004`）。
- 特殊动作的"帧"不是图片：`Spell1/2` 1 帧、`Defense` 1 帧（`#8, L1D10002, $Defense`）、`First` 用 `NULSHAPE`。

**注释模板段**（段序 99、`L1324`、`Name='主將L1 (主體)'`）是官方自带的字段说明——它的动作值不是文件名而是繁体中文，等于把 21 个动作的含义写死了：

| 字段 | 官方注释 | 字段 | 官方注释 |
|---|---|---|---|
| `First` | 起始圖檔 | `Defense` | 防禦 |

## 5. `COMBINE.INI` 与"一帧画面怎么叠出来"

### 5.1 文件实况（**只有 4 条，不是 8 条**）

| 行 | 内容 | 说明 |
|---:|---|---|
| L1 | `[SHAPE]` | 唯一段 |
| L2 | `NAME=TestCombineShape` | 名字直说"测试用拼合造型" |
| L3–L6 | `SHAPE=-96,-96,FACE\FACE001`<br>`SHAPE=0,-96,FACE\FACE002`<br>`SHAPE=-96,0,FACE\FACE003`<br>`SHAPE=0,0,FACE\FACE004` | **4 条**，格式 `x,y,<SHAPE 内相对路径>` |
| L7 | （空） | — |
| L8 | 27388 字节纯空格（占全文 99.47%） | 把文件撑到 27534 B（**推测**：PAK 打包的定长块/对齐残留） |

`combine.json` 的解析结论与实测一致：`shape_entry_count=4`、`grid.unique_x=[-96,0]`、`unique_y=[-96,0]`、`step_x=step_y=96`、`bbox=192×192`、4 个 `FACE001-004` 各 25236 B 且都存在。

### 5.2 拼合示意

```
        x=-96        x=0
y=-96  ┌────────┐ ┌────────┐
       │FACE001 │ │FACE002 │      每格 96×96 步长，
       └────────┘ └────────┘      子图实际 100×120（会互相压边）
y=0    ┌────────┐ ┌────────┐
       │FACE003 │ │FACE004 │      合成画布 bbox 192×192
       └────────┘ └────────┘
```

坐标是**每张子图左上角相对拼合原点的像素偏移**，负值表示向左/上 → 原点落在 2×2 网格中心。`step=96` 是由相邻坐标差反推的（不是从 SHP 头读的），与头像实际 100×120 不等 → **推测**这张 `TestCombineShape` 只是验证"多图叠加"机制的样例（4 张头像拼成 2×2 通讯录样式），并未在正式界面中使用。

### 5.3 主将一帧的图层装配（真正用到的叠法）

`THINGS.INI` 用 **3 个独立对象 + 3 套 Process** 描述主将，各自有 `Directory` 与 `offsetX/offsetY`，按**同一锚点**叠放：

| 图层 | 代表文件 | 尺寸 | `offsetX/offsetY` | 触发条件 |
|---|---|---:|---|---|
| 身体 | `MAJOR\BODY\L1W10001` | 72×102 | (37, 141) | 恒有 |
| 武器 | `MAJOR\WEAPON\A1W10001` | 33×67 | **(−10, 170)** | 恒有（空手类仍有基础武器） |
| 坐骑 | `MAJOR\HORSE\HAW10001` | 140×123 | (77, 117) | 仅骑乘（`OF_CAVALRY`/骑乘状态） |
| 头像 | `FACE\FACE001` | 100×120 | (0, 0) | 仅 UI（对话/血条/单挑），不进战场叠加 |

```
   ┌─ 绘制顺序（推测：先后景后前景）
   │   HORSE  (140×123, 锚点≈底部中心)
   │   BODY   ( 72×102, 锚点≈脚底)
   │   WEAPON ( 33×67 , 锚点≈握持点，offx 可为负 → 武器可伸到身体左侧)
   └─ 三层用同一个"角色锚点"，各自加上自身 offx/offy 后落到屏幕坐标
```

**未解**：`offx/offy` 的精确语义。三种解释都能自圆其说——"图左上角相对锚点"、"锚点在图内位置"、"含负值的手持点偏移"；`A1W10001` 的 `offx=−10` 与身体 `offy=141 > h=102` 说明不能简单当成"图内锚点"。本文只确认**三层共用一套锚点坐标、必须各自加偏移才能对齐**，具体公式留给加载器实现时用像素比对确定。
