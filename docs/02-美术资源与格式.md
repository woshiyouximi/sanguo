## 2. SHP 精灵格式（核心）

### 2.1 结构

文件 = **0x24 字节头** + **行偏移表** + **逐行段数据**。全部整数小端。

| 偏移 | 类型 | 含义 | 实测 |
|---|---|---|---|
| +0x00 | char[4] | 魔数 `"TLHS"` | 10969/10969 |
| +0x04 | u32 | — | 恒 0 |
| +0x08 | u32 | 像素格式 | 恒 2（16bpp RGB565） |
| +0x0C | u32 | — | 恒 0 |
| +0x10 | u32 | **透明色键**（RGB565） | 见上表分布 |
| +0x14 | u32 | 画布宽 W | 1–2000 |
| +0x18 | u32 | 行数 = 高 H，也是偏移表长度 | 3–2711 |
| +0x1C | i32 | 热点 offsetX（可为负） | -137…197 |
| +0x20 | i32 | 热点 offsetY（可为负） | -168…572 |
| +0x24 | u32[H] | 每行数据在文件内的绝对偏移 | 恒有 `offset[0] == 0x24 + 4*H` |

每一行（y = 行号，自上而下）是一串"段"，段格式：

```
u16 x            ; 段起始列
u16 n            ; 段内像素个数
u16 color[n]     ; RGB565 像素
... 重复 ...
u16 0xFFFF       ; 终止符（x 或 n 位置为 0xFFFF 即视为结束）
```

空行 = 单独 2 字节 `FF FF`。同一行内未覆盖的像素 = 透明。

### 2.2 解码要点（踩过的坑）

1. **行内是稀疏的**：一行只有若干个水平段，不是整行像素。必须按段填，未覆盖处 alpha=0。
2. **色键不是 alpha**：像素值等于 `+0x10` 色键时视为透明；其余全部不透明。所以本格式**没有半透明**（游戏里所有半透明都是运行时光栅运算，不是资源自带）。
3. **offsetX/offsetY 只是热点**，与像素解码无关。但 `tools/sango_shp.py` 的注释指出：原版加载器（`Sango2.exe` VA `0x46B3D0`）会把每段的两个 u16 交换成 `[n][x]`、x 减去 offsetX，并"重写 RGB565 通道"。这点对应 §3 里 .TEX 的通道差异。
4. **RGB565 展开**：`r5→r8 = (r5<<3)|(r5>>2)`，`g6→g8 = (g6<<2)|(g6>>4)`，`b5→b8 = (b5<<3)|(b5>>2)`。
5. 结构自校验：**10969 个文件全部满足** `offset[0] == 0x24 + 4*H`，无一例外；解码耗时全库 23 秒（1280×960 的大地图单张 0.35 秒）。

### 2.3 导出约定

`export/png/SHAPE/<与原目录同构>/<原名>.png`，RGBA，透明区域 alpha=0（不是填色键绿）。
例：`SHAPE/MAJOR/BODY/L5S10007.SHP → export/png/SHAPE/MAJOR/BODY/L5S10007.png`。

## 3. `.TEX`：其实是标准 TGA

**结论：7 个 `.TEX` 全部是标准 Targa（TGA 2.0）文件，Pillow `Image.open()` 直接可读。** 不需要自写解码；`tools/sango_tex.py` 自带独立解析器（与 Pillow 结果逐像素一致，最大差 1，仅来自 5→8 位展开的取整）。

### 3.1 字节级结构

18 字节 TGA 头（`POLICY\PALAIS01.TEX` 实测 `00 00 02 00 00 00 00 00 00 00 00 00 80 02 E0 01 10 00`）：

| 偏移 | 类型 | 字段 | 实测值 |
|---|---|---|---|
| +0x00 | u8 | idLength | 0 |
| +0x01 | u8 | colorMapType | 0（无调色板） |
| +0x02 | u8 | imageType | **2 = 未压缩真彩** |
| +0x03 | u16 | cmapFirst | 0 |
| +0x05 | u16 | cmapLength | 0 |
| +0x07 | u8 | cmapDepth | 0 |
| +0x08 | u16 | xOrigin | 0 |
| +0x0A | u16 | yOrigin | 0 |
| +0x0C | u16 | width | **640** |
| +0x0E | u16 | height | **480** |
| +0x10 | u8 | pixelDepth | **16** |
| +0x11 | u8 | descriptor | `0x00`（POLICY）/`0x01`（TEXTURE，声明 1 bit alpha） |

* descriptor bit5 = 0 → **行序自下而上**（TGA 默认，Pillow 会自动翻正）。
* +0x12 起是 640×480×2 = 614,400 字节像素，**RGB555**：bit14-10 = R5，bit9-5 = G5，bit0-4 = B5，bit15 未用（全 0）。

文件长度对账：

| 文件 | 字节 | 构成 |
|---|---:|---|
| `POLICY\PALAIS01-05.TEX`、`POLICY\YIELD.TEX` | 614,420 | 18 头 + 614,400 像素 + **2 字节尾巴**（PALAIS01 尾 `CA 14`，YIELD 尾 `11 11`，引擎不读） |
| `MAP\TEXTURE.TEX` | 614,444 | 18 头 + 614,400 像素 + **26 字节 TGA 2.0 页脚** `TRUEVISION-XFILE.\0` |

### 3.2 引擎怎么用它（反汇编证据）

`Sango2.exe` VA `0x41D2D4`（由 `0x41AAF8` 处 `push "SHAPE\MAP\TEXTURE.TEX"` 调用）：
`fread 头 0x12=18 字节` → `fread 0x96000=614400 字节像素` → `call 0x46B2D0(surface, 640, 480)`。
`0x46B2D0` 的像素循环是 `ax=word[ecx]; edi=(ax&0xFFE0)<<1; eax=ax&0x1F; word[ecx-2]=edi|eax` —— 即 **RGB555 → RGB565 的就地转换**（G5 左移一位变 G6，R/B 位不动）。

这解释了 .TEX 与同名 .SHP 的差异：同名 .SHP 是同一幅画的 565 版本（红通道满 5 位），而 .TEX 的红通道实测最大只有 15（4 位有效），所以**同名 .SHP 比 .TEX 亮一档**。对上像素时，`r5(tex) == r5(shp) >> 1` 在 307200 像素中 100% 成立——两者是同一套美术的两种色深版本，不是两张不同的画（曾一度误判，用错基准算误差导致）。

> 结论：**需要"亮版"就取 .SHP；要"引擎内实际显示效果"就取 .TEX。** 两者都保留在导出里。

## 4. `.TGA` 地面贴图（12 张）

`SHAPE\BG\FLOOR00-11.TGA`：标准 TGA 2.0，**512×512**、16bpp RGB555、`descriptor=0x01`、文件长 524,332 = 18 + 524,288 + 26（页脚）。
Pillow 直读即得正确结果（平均色如 FLOOR04 = (33,95,8) 自然草地绿）。它们是**无缝平铺的地面材质**，不是整屏战场背景——战场背景由 `BG\BG00A/BG00B`（远景）+ `MG*`（中景）+ `FG*`（近景）三层 SHP 叠加而成。

12 张的实际内容（肉眼核对）：FLOOR00 砖地、01 黄土、02 碎石路、03 木纹、04 草地、05 泥地/杂土、06 沙土、07 苔草、08 冰雪、09 沙丘、10 沙地、11 石板路。

![12 张地面贴图（Terrain 材质）](../export/sheets/sheet_tga.png)

## 5. `.MSK` 地形遮罩（4 个）

### 5.1 结论先说

`.MSK` 是**战略地图的"逐像素地形类型图"**，不是势力图、不是战争迷雾。语义由反汇编坐实：取值函数 `0x44FD1B` 的调用点 `0x40DF43` 后面紧跟着
`push eax; push "%s Terrain=%d"; call 0x450260`（格式串在 VA `0x488b8c`）——一次坐标查询地形值并打印。`SANGO.INI` 里也正好有 12 个 `[TERRAIN]` 段（Name = 城/平原/山/森林/…），与调色板 12 个有效色一一对应。

### 5.2 字节级结构

| 偏移 | 类型 | 含义 | CHINAMAP1 实测 |
|---|---|---|---|
| +0x00 | u8×4 | 版本/标志 | `0A 05 01 08`（4 个独立 u8，**不是 u32**） |
| +0x04 | u16 | left | 0 |
| +0x06 | u16 | top | 0 |
| +0x08 | u16 | right | 639 |
| +0x0A | u16 | bottom | 479 |
| +0x0C | u16 | width | 640 |
| +0x0E | u16 | height | 480 |
| +0x10 | RGB[16] | 16 色调色板（每色 3 字节，末 4 色全 0） | 见下表 |
| +0x40 | 64 B | 保留（实测仅 `00 01 80 02` 即 256/640 有值，含义未定） | |
| +0x80 | … | **PCX 式 RLE 像素数据** | 解码 307,200 像素，消费 51,306 字节 |

调色板（索引 0–11，RGB）：

| # | 色 | # | 色 |
|---|---|---|---|
| 0 | (0,0,0) 黑 | 6 | (131,103,71) 褐 |
| 1 | (255,0,0) 红 | 7 | (175,191,0) 黄绿 |
| 2 | (203,183,255) 淡紫 | 8 | (187,183,183) 灰 |
| 3 | (0,0,255) 蓝 | 9 | (255,191,0) 琥珀 |
| 4 | (0,171,0) 绿 | 10 | (0,195,251) 青 |
| 5 | (255,135,0) 橙 | 11 | (255,0,255) 品红 |

12–15 号为黑色。像素值直方图（CHINAMAP1）：`255` 占 79%（= 无地形/空地），其余按 6、4、7、5、3、2、8、11、10、0、9、1 递减——**255 是"空"，0–11 才是地形类**。

### 5.3 RLE 解码（PCX 式，来自反汇编）

函数 `0x44FD1B` 签名 `get_terrain(int x, int y, void* buf)`：

```
w = u16[buf+8] - u16[buf+4] + 1;      // right-left+1
h = u16[buf+0xA] - u16[buf+6] + 1;    // bottom-top+1
if (x >= w) return -1;  if (y >= h) return -1;
edi = y*w + x;  esi = buf + 0x80;              // ★ 数据从 +0x80 起
loop:
  al = *esi++;
  if (al & 0xC0) { edi -= (al & 0x3F); bl = *esi++; }   // 低 6 位 = 重复次数，下一字节 = 值
  else           { edi -= 1;           bl = al; }       // 否则该字节本身是一个像素
  if (edi >= 0) goto loop;
return bl;
```

即标准 PCX RLE：**高位两 bit 非零 → 低 6 位是重复计数，紧随的 1 字节是像素值；否则该字节直接是一个像素**。这是"随机访问第 N 个像素"的写法（从前往后跳，直到覆盖目标下标），等价于顺序解码整个位图。

### 5.4 尾部 769 字节是死数据

`0xC86A` 起：`u32 0x0000000C`（=12）+ 12×RGB（调色板 1–12 的副本）+ 大量 `0x00` 填充 + 文件最后 3 字节 `FF FF FF`。
引擎只按 `y*w+x` 索引、不做二次读取，所以这段**从不被读取**（应为导出工具残留）。已排除"第二张图/调色板覆盖"假设。

### 5.5 与大地图的关系

`CHINAMAP.SHP` 是 **1280×960**，`.MSK` 是 **640×480**，正好 1:2。把 MSK 放大 2 倍叠到大地图上，道路/河流分段完全重合（下图）；左上角逐个地形类别的图例色点也来自这张 MSK 自身的像素。

4 张都是 640×480 的同一张中国地图，但逐像素比对显示它们不是同一份数据：`MSK1` vs `MSK2` 差 11,147 像素、vs `MSK3` 差 5,545、vs `MSK4` 差 23,391（总计 307,200 像素）。差异集中在 4/5/6/8 号类（绿/橙/褐/灰）——即草地与道路/河流的类型被重新标注。合理推断是**同一张地图的 4 套地形配置**（对应不同剧本/时期或不同季节），运行时由 `0x4A6448` 这个索引选择加载哪一张（见 §5.2 的 `0x41AAEB/0x41AB38` 引用）。尚未确认索引与剧本的对应关系。

## 6. 字体

### 6.1 中文点阵：`SANGO.20` / `SANGO.15`

| 文件 | 字节 | 单元 | 单元数 | 宽×高 | 每行字节 | 说明 |
|---|---:|---:|---:|---|---:|---|
| `SANGO.20` | 832,020 | 60 B | **13,867** | 20×20 | 3 | 1bpp，每行用前 20 bit（24 bit 中低 4 bit 补 0） |
| `SANGO.15` | 416,010 | 30 B | **13,867** | 16×15 | 2 | 1bpp，每行 16 bit 全用 |

**没有文件头**：832020/60 = 416010/30 = 13867 整除。第 0 个单元就是「一」（其前半部分本来就是空白行，曾误判成 20 字节文件头）。位序 MSB first，1 = 亮点。
单元大小公式与 `SANGO.INI` 的 `ChineseBytes = ChinesePerLineBytes × ChineseHeight` 完全吻合（20 宽 → 3×20 = 60；16 宽 → 2×15 = 30）。

### 6.2 `SANGO.IDX`：Big5 码 → 字形槽号

* 38,000 字节 = **19,000 项 u16**，值 = 字形槽号（**1-based，实际槽号 = 值 − 1**），0 = 无字形。
* 码位 → 表项下标的公式（实测 13,708/13,865 命中）：

```
pos = (lead - 0x81) * 157 + compact(trail) + 1
compact(trail) = trail - 0x40            (0x40..0x7E)
               = 63 + (trail - 0xA1)     (0xA1..0xFE)
```

* 槽号在 Big5 码序上被切成 4 段重排（`0xA4` 起常用字在 1..5401，`0xA1-0xA3` 符号区在 13094..13500，等等），仅 2 处回退，所以**必须走 IDX**，不能按码序直接算槽号。
* 字形本体按 Big5 码序存放（从 `0xA440`「一」开始，跳过 Big5 未定义码位），首 100 槽依次是 一乙丁七乃九了二人儿入八几刀刁力匕十卜又三下丈上…，与标准 Big5 完全一致。

### 6.3 英文字模与 SHAPE 字模

* `MINGASC.20` 10,240 B = **256 个 40 字节单元**（10×20，每行 2 字节，MSB first）→ ASCII 0–255。
* `OLDASC.15` 3,840 B = **256 个 15 字节单元**（8×15，每行 1 字节）→ ASCII 0–255。
  两者都已渲染验证：`ABCDEFGHIJKLMNOPQRSTUVWXYZ[\]^_` 可读。
* `SHAPE\FONTS\` 53 个 SHAPE 字模，命名 = 前缀 + 三位 **ASCII 码**：`CNUM048-057`（0–9 装饰数字）、`TNUM048-058`（0–9 与大数字，含 058 = ':'）、`WB047-057`、`WP048-057`、`WS047-057`（047 = '/'，其后 0–9）。
* `SANGO.INI` 的 7 组字体配置（`[FONTS01]`…`[FONTS07]`）给出权威规格：

| 组 | 中文字体 | 宽×高 | ChineseBytes / PerLine | 英文字体 | 类型 |
|---|---|---|---:|---|---|
| 01 | Sango.20 + Sango.idx | 20×20 | 60 / 3 | Mingasc.20 | BITMASK 10×20 |
| 02 | — | — | — | WP | SHAPE 8×10 |
| 03 | — | — | — | MNUM（实际文件名 `CNUM*`） | SHAPE 10×15 |
| 04 | Sango.15 + Sango.idx | 16×15 | 30 / 2 | OldAsc.15 | BITMASK 8×15 |
| 05 | — | — | — | TNUM | SHAPE 19×19 |

> 顺带一个强约束：**游戏文本编码是 Big5（cp950 繁体）**，不是 GB2312。所有 INI/MESSAGE 用 cp950 才能正确解码，简体字在字库里也查不到槽号。新项目复用这套字库必须按 Big5 索引。

渲染验证（`F:\sanguo\export\png\font\sample_text.png`，用 `SANGO.20` + `SANGO.IDX` 直接渲染）：

![SANGO.20 点阵字体渲染样张](../export/png/font/sample_text.png)

## 7. COMBINE.INI：多张 SHP 的拼合

文件 27,534 字节，但**只有 6 行有内容，其余 27,396 字节全是空格填充**（写文件工具按固定块补齐留下的）。有效内容就是唯一一个演示定义：

```ini
[SHAPE]
NAME=TestCombineShape
SHAPE=-96,-96,FACE\FACE001
SHAPE=  0,-96,FACE\FACE002
SHAPE=-96,  0,FACE\FACE003
SHAPE=  0,  0,FACE\FACE004
```

机制：一个 `NAME` 段 + 若干 `SHAPE=x,y,<相对路径不带扩展名>`；运行时按 (x,y) 把多张 SHP 依次画到同一画布上（这里 4 张 100×120 头像拼成 2×2，每张的落点是负偏移，因为头像热点在脸中心）。

![COMBINE.INI 唯一方案的复现：4 张头像 2×2 拼合](../export/png/face/combine_FACE001_004.png)

出厂资源里只有这一个拼合定义（`TestCombineShape`），说明该机制是给"组合大图/拼接怪物"预留的通用工具，实际游戏里没有大规模使用。新项目若要用，只需按 `x,y,路径` 追加即可，不需要改代码。

## 8. SHP 命名规律（重点）

### 8.1 `MAJOR\BODY`（3601）

`[L|R][造型号][动作字母][动作变体][4 位帧号]`，例 `L5S10007` = L · 5 · S · 1 · 0007。

* **造型号**：`0-9` + `A-E` 共 **15 种**（十六进制风格，跳过 F），每种恰好 240 个文件（= 2 阵营 × 120）。
* **动作字母**（语义直接由 `THINGS.INI` 里同名字段的引用坐实）：

| 字母 | 含义 | 证据（`THINGS.INI` 引用处） | 每造型文件数 |
|---|---|---|---:|
| `W` | Wait 待机 | `Wait = L1W10001, #16, L1W10002, #8, …` | 480 |
| `R` | Walk 行走循环 | `Walk = #4, L1R10001 … L1R10009` | 270 |
| `A` | Attack 攻击（6 种变体） | `Attack = L1A10002…`, `Attack2 = L1A6…`, `Attack3 = L1A5…` | 1800 |
| `S` | Shot 射箭 | `Shot1 = #3, L1S10002 … L1S10011` | 300 |
| `D` | Defense 防御 | `Defense = #8, L1D10002, $Defense` | 30 |
| `H` | Pain 受击 | `Pain = #4, L1H10002, $Hit01` | 30 |
| `F` | Death 阵亡 | `Death = #5, L1F10001 …` | 300 |
| `FS` | Win 胜利动作 | `Win = #5, L1FS0001 …` | 300 |
| `L` | Spell 施法 | `Spell1 = #64, L1L10001`, `Spell2 = L1L10002` | 90 |

* **动作变体的数字**对 `W`/`A` 是**武器适配**：`THINGS.INI` 里同一造型有 4 个对象 "主將L1 (主體) - 劍 / 槍 / 矛 / 刀"，分别用 `L1W1xxx / L1W2xxx / L1W3xxx / L1W4xxx`，即 **1=劍 2=槍 3=矛 4=刀**；`A` 的 1–4 同理，5、6 是额外两套攻击（`Attack5/Attack6`）。
* 帧号：`A` 类 0002–0011（10 帧）、`W` 0001–0004、`R` 0001–0009、`S`/`F`/`FS` 0001–0011、`D`/`H`/`L` 只有 1–2 帧。

### 8.2 `MAJOR\WEAPON`（2585）

`[兵器大类 A-D][兵器编号 1-9][动作][武器变体][帧]`，例 `A1A10002`、`C1A20002`。
`THINGS.INI` 的 34 个武器对象直接给了名字：`A1`=直劍、`A2`=吳鉤劍、`A3`=青銅劍、`A4`=弧月刀、`A6`=流星鎚……
大类推断（结合渲染样张）：**A = 剑/刀类短兵**（836 个）、**B = 枪/矛类长兵**（608）、**C = 戟/钺类**（532）、**D = 奇门兵器**（608）。动作字母同 BODY，但只有 `A/W/R/L/F/D/H`（没有射箭与胜利），因为胜利动作由 BODY 演。

### 8.3 `MAJOR\HORSE`（185）

`H[马种 A-H][动作][帧]`，例 `HAA10002`。`THINGS.INI` 8 个对象 "主將1 (馬)…主將8 (馬)" 对应 `HA…HH`。动作只有 `A`(Attack/嘶鸣)、`W`(Wait)、`R`(Walk)。

### 8.4 `FORCE`（2845）：士兵

`[M|N][兵种字母][动作][变体][帧]`，例 `MAA10002`（朴刀兵）。`THINGS.INI` 69 个 `Directory = \Force\` 对象给出兵种名（朴刀兵、長槍兵、弓箭兵、弩兵、…，含 "(紅軍)" 版本）。
动作字母（`FORCE` 与 `MAJOR` 语义不同！）：`W`=Wait、`R`=Walk、`A1`=Attack、`A2`=Win、`D`=Defense、`F`=Death、`FS`=Pain（受击）。
`M` = 我方配色、`N` = 红军（敌方）配色，两者文件成对、动作帧完全对应。另有 `SH*`(108 个) 与 `SHOR*`(9 个) 是**影子**贴图。

### 8.5 其他

* `FACE001-400`：武将头像，**全部 100×120**、色键白 `0xFFFF`、非空像素率 0.999（整块不透明）。编号与武将表对应。
* `TROOP\FLAG0101-FLAG2704`：108 面部队旗 = 27 组 × 4 帧，约 18×19 px；`SOL0/SOL1/SOL2` 各含 `0001-0006`（行军）+ `LOS1-4`（败退）+ `WIN1-4`（胜利），是 3 种小兵（`SOL0/1/2`）的界面用小人。
* `JEWEL`：`BOOK01-10` 书籍、`JEWEL1-5` 珍宝、`WEAPONA/B/C/D*` 武器图标、`HORSEHA-HH` 坐骑图标，全部 56×56。
* `MENU`：`BUTTON01-10A/B/C`（按钮三态）、`MAIN01-04A/B`（主菜单）、`D1_*/D3_*/D12*`（内政/外交窗口分块）、`SB_H*/SB_V*`（滚动条与边框）、`TITLEBG/TITLEBG2`（640×480 标题）、`STAFF`（542×2711 长条制作名单）、`WAR*`/`WARPREP*`（战前准备）。
* `MAGIC\000-041`：41 个数字子目录 = 41 个武将技/法术特效对象（`THINGS.INI` 里 `Directory = \magic\038` 等可直接对上），同名音效 `SOUND\M0xxSND0y.WAV`。
* `MAP\CHINAMAP.SHP` 1280×960 大地图、`CITY01-04` 城池标记、`POINT.SHP` 光标。

### 8.6 `L`/`R` 与 `M`/`N`：阵营配色，不是朝向

这是最容易猜错的一条。实测证据：

1. 随机抽 40 对 BODY（`L5S10002` vs `R5S10002` 等），**40/40 的 alpha 通道逐像素完全相同**，只有 RGB 不同，平均通道差仅 4.94；而把它们镜像后再比，差 25.3。
2. 典型例子：`L5S10002` 蓝甲、`R5S10002` 红甲，姿势、轮廓、弓的位置一模一样。
3. `THINGS.INI` 里只定义了 `主將L0 … 主將L14`（没有 `主將R*`），说明 R 不是单独的"造型"，而是同一造型的敌方配色，由程序按阵营选。

![同一帧的 L/R 两版：蓝甲 / 红甲，轮廓完全相同](../export/png/SHAPE/MAJOR/lr_compare.png)

所以：**L = 我方（蓝），R = 敌方（红）；M = 我方，N = 敌方**。这带来一个很实用的结论——**美术量减半**：一套动作两种配色，是 1999 年省磁盘的经典做法。新项目若用同一思路，只需给"阵营可换色区域"单独出一张色表（palette swap），不必画两套。

## 11. 未解问题与下一步线索

1. **`MAJOR\BODY` 造型号 0–14 的具体含义**：只知道是 15 种造型、各有 4 种武器适配；具体"哪种造型对应哪类武将（文官/武官/君主/异族）"需要读武将数据表，超出美术范围。
2. **`L`/`R` 阵营色是否由引擎 palette swap 生成**：文件是实体存在的两套（不是运行时改色），但 `THINGS.INI` 只定义 L 侧。R 侧的选取逻辑在 EXE 里，未追。
3. **`MSK` 头 `+0x00` 的 4 个字节 `0A 05 01 08` 与 `+0x40` 的 `00 01 80 02`**：不参与解码，含义未定（疑似版本号 + 256/640 两个常量）。
4. **`SANGO.20` 里 159 个未被 IDX 引用的槽**：是预留位还是别的字集（如造字区），未核。
5. **`SANGO.INI` 的 `MNUM` 字体缺失**：`SHAPE\FONTS` 下无同名文件，疑似就是 `CNUM*`（10×15），未证实。
6. **`FORCE` 的 `M`/`N` 双份是否全部内容重复**：抽样看是配色差异，但没有逐像素核完 2845 个文件。
7. **`TEXTURE.TEX` 的用途**：是战斗地面的程序化纹理（青绿 + 暗裂纹噪声），但同一目录下的 `FLOOR00-11.TGA` 已经是地面材质，两者关系（是否用于地图边缘/水面/远景模糊）未定。
