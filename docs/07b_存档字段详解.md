# 《三国群英传2》存档字段详解（07b）

> 本文是 `07_存档格式.md` 的续篇：07 只给出了七段的骨架（stride / 条数 / 偏移），本文把**每条记录里的每个字段**逐个命名。
>
> 对象：`Sango2.exe`（PE32, MSVC6, ImageBase 0x400000, 682,496 B）
> 文件偏移换算：`文件偏移 = VA − 0x400000 − 0x1000 + 0x400`
> 全部代号与 04b（GENERAL 结构）、04c（CITY 结构）一致。

---

## 0. 一句话结论

存档 = **0x1D0 字节定长头 + 七段紧接的定长记录数组**，七段分别是
**① 势力（King，32×0x352）② 城池（City，64×0xB2）③ 部队（Obj3，128×0x70）④ 武将（General，512×0x11F）⑤ 路径（Path，n×0x18）⑥ 路径点（PathPoint，m×8）⑦ 128 字节全局标志表**；
每条记录第 0 个 dword 是自己的长度（= 段 stride），对象字段从 +4 开始；**文件内没有任何段头、块长度、校验和或版本分支**，段边界完全由头部 7 组 `(count, offset)` 描述符决定，整个缓冲一次性写出（`0x455AB2`），读出时只校验 `长度=0x1D0`、`magic="SSAV"`、`version=0x20000` 三项（`0x433D9B..0x433DBA`）。

字段命名覆盖率：

| 段 | 身份 | 记录数 | 已命名字段 / 可辨字段 | 覆盖率 |
|---|---|---|---|---|
| 1 | 势力 King | 32 | 18 / 21 | ~85%（两块定长块内容未知） |
| 2 | 城池 City | 64 | 某 26 / 29 | ~90% |
| 3 | 部队 Obj3 | 128 | 结构 100%，语义名 ~50%（4 dword + 4 u16 未定名） |
| 4 | 武将 General | 512 | 58 / 66 | ~88% |
| 5 | 路径 Path | 118 | 5 / 5 | 100% |
| 6 | 路径点 PathPoint | ≤2048 | 2 / 2 | 100% |
| 7 | 标志位 | 128 | 0 / 1 | 0%（源表语义未定位） |

## 1. 方法与证据等级

| 证据类型 | 说明 | 本文标注 |
|---|---|---|
| 写档指令 | 段函数里 `mov [rec+disp], …` / `memcpy(rec+disp, …)` 的实际 disp，以及同屏 `mov reg,[obj+disp]` 的源偏移 | 【写】= 直接读出的指令 |
| 读档指令 | `0x4323CF` 起的回填代码，`obj+X ← rec+4+X` | 【读】 |
| Xform 除法 | `0x409430`/`0x406A4A`/`0x43884C` 里的 `div 0x34A` / `div 0xF7` / `*0x6C` 决定对象池基址与节点大小 | 【池】 |
| 交叉 | 与 04b / 04c 已确认的字段名对齐 | [确认] / [存疑] |

置信度：**高** = 写档与读档两侧都能对上，或与 04b/04c 已证字段一致；**中** = 只有写档侧单侧证据；**低** = 推断。

### 1.1 三条对象池事实（本次新逆出，是全文的地基）

| 助手 | 公式 | 结论 |
|---|---|---|
| `0x409430(p)` | `p==0 ? -1 : (p − [0x4A6190]) / 0x34A` | **King 池基址 `0x4A6190`，节点 `0x34A`** |
| `0x406A4A(p)` | `p==0 ? -1 : (p − [0x4A6180]) / 0xF7` | **General 池基址 `0x4A6180`，节点 `0xF7`** |
| `0x43884C(i)` | `i < 0x80 ? [0x4A662C] + i*0x6C : 0` | **Obj3 池指针 `0x4A662C`，节点 `0x6C`，上限 128** |

Obj3 池初始化在 `0x438530`：`if(![0x4A662C]) [0x4A662C]=malloc(0x3600); memset(…,0,0x3600)`，而 **0x3600 = 128 × 0x6C**，闭合。

> 这三个助手在存档里被大量使用：**所有指针都不存原值，而存"池内下标"**（p==0 存 -1）。本文把这种"指针→下标"的转换记作 `Idx(...)`（07 里叫 Xform）。

### 1.2 通用记录格式

```
+0x00  u32  记录长度（= 段 stride，写档时 mov dword ptr [rec+i*stride], stride）
+0x04  …    对象体（object[0] 落在 rec+4）
```
读档侧 `0x4323CF` 反向证实：`memcpy(king, rec+4, 0xC)`、`king+0xC = Idx⁻¹(rec+0x10)`……

## 2. 文件整体布局

```
0x00000  头部 0x1D0
0x001D0  段1 势力    count1 × 0x352
         段2 城池    count2 × 0xB2
         段3 部队    count3 × 0x70
         段4 武将    count4 × 0x11F
         段5 路径    count5 × 0x18
         段6 路径点  count6 × 0x8
         段7 标志    count7(固定 0x80) × 1
```
理论最大 = 0x1D0 + 32×0x352 + 64×0xB2 + 128×0x70 + 512×0x11F + 256×0x18 + 2048×8 + 0x80 = **0x35A20（219,680 B）**。
写档缓冲 `malloc(0x36710)`（`0x43207C` 开头）留了余量。

### 2.1 七段描述符总表

| 段 | 身份 | 段函数 | 函数大小 | 上限 | stride | count 在头部 | 段体在头部 | 段基址全局 |
|---|---|---|---|---|---|---|---|---|
| 1 | 势力 King | `0x4308B0` | 770 B | 0x20 = 32 | 0x352 | +0x68 | +0x6C | `0x4BD218` |
| 2 | 城池 City | `0x430BB2` | 1310 B | 0x40 = 64 | 0xB2 | +0x7C | +0x80 | `0x4BD270` |
| 3 | 部队 Obj3 | `0x4310D0` | 902 B | 0x80 = 128 | 0x70 | +0x190 | +0x194 | `0x4BD26C` |
| 4 | 武将 General | `0x431456` | 2517 B | 0x200 = 512 | 0x11F | +0x1A4 | +0x1A8 | `0x4BD214` |
| 5 | 路径 Path | `0x431E2B` | 287 B | 0x100 = 256 | 0x18 | +0x1B8 | +0x1BC | `0x4BD220` |
| 6 | 路径点 PathPoint | `0x431F4A` | 182 B | 0x800 = 2048 | 8 | +0x1C0 | +0x1C4 | `0x4BD21C` |
| 7 | 标志位 Flag128 | `0x432000` | 124 B | 0x80 = 128 | 1 | +0x1C8（常量 0x80） | +0x1CC | 无（局部） |

**规律（七段全成立，已逐段验证）**：`count_field = base_field − 4`。
段5/段6 的条数是动态的（= `[0x4A64AC]` / `[0x4A64B0]` 当前值），段7 的 "count" 字段写的是常量 `0x80`（即字节数，不是条数）。

## 5. 段2：城池表（City）64 × 0xB2

**两处存疑，必须记录**：

1. **[存疑] 记录内位移不是恒定的 4**。头部区（城名、太守指针等）是 `rec+X ← city+X−4`（shift 4，读档 `memcpy(rec, city+4, 0xC)` 双证）；但尾部区是 `rec+X ← city+X−8`（shift 8，双证：`mov cx,[city+0x70]` → `[rec+0x78]`（`0x430E9F`）、`[city+0x9A]` → `[rec+0xA2]`（`0x43102F`））。⇒ 中间某处**被省略了 4 字节**（候选：City+0x0C 的运行期缓存指针，写档时不保存）。本文表格的"源偏移"列是**逐字段实测**的，不受此影响。
2. **[存疑]** `4 + 0xAA = 0xAE`，而 stride = 0xB2，差 4 字节。结合 shift 8 的事实，尾部最后两个字段（链 next）实际落在 `+0xA6/+0xAA`，记录正好用满 0xB2 —— 即**没有附加字段**，而是中间省略 4 字节后整体下移。两种解释在数值上等价，采用后者。

## 6. 段3：部队表（Obj3）128 × 0x70

写档 `0x4310D0`（902 B），循环上限 `[ebp-8] = 0x80`，取对象 `0x43884C(i)`。
Obj3 节点 = **0x6C**，池 `[0x4A662C] = malloc(0x3600)` = 128 × 0x6C（`0x438530` 初始化）。

### 7.1 与 04b 的冲突（重要！）

| 04b 的标注 | 段4 实测 | 结论 |
|---|---|---|
| `gen+0xBF` = LOYAL 忠诚 | 以 `Idx(King*)` **指针**形式序列化 | **[存疑] 冲突**：`0x409430` 做 `(p−base)/0x34A` 除法，若 0xBF 是 0..100 的忠诚值则得到巨大负数，游戏会崩。故 `gen+0xBF` 是**对象指针**，04b 的 LOYAL 偏移标注错位 |
| `gen+0xC3` = BLOOD 血统 | 以 `Idx(General*)` **指针**形式序列化 | **[存疑] 冲突**：同上，`gen+0xC3` 是 General 指针 |
| `gen+0xC7` = CONSTANCY 节操 | 以 u16 序列化（`+0xEF`） | [确认] 与"小整数"一致 |

⇒ **建议**：`LOYAL` / `BLOOD` 的真实偏移**未定**（可能在 `gen+0xB5..0xBD` 这段未被段4 单独列出的区间里，被整体当作 `+0xC7..0xCD` 之外的字段）；`gen+0xBF`/`0xC3` 应改标为"君主指针 / 上级武将指针"。本文不修改 04b，仅在此记录冲突。

## 10. 段7：128 字节全局标志表

写档 `0x432000`（124 B）：循环 128 次，`mov al, 0x408EC3(i)` → `mov byte ptr [rec+i], al`。

```c
// 0x408EC3(i)
if (i >= 0x80) return 0;
return (i16)[0x4C3A80 + i*0x56];     // 取 i16，存盘时只取低字节
```

- 源表：**`0x4C3A74`**，**128 项 × 0x56（86）字节**；`0x4C3A80 = 0x4C3A74 + 0xC`，即取每项的第 +0x0C 处 i16。
- 全 EXE 只有 3 处引用该表：`0x408703`、`0x408722`、`0x408F10`，**全部只读**。
- **语义未定位**。候选：事件标志、关卡/城池解锁标志、剧本进度。0x56 的 stride 与 128 项的组合在其它表里没有对应物。
- 段7 的头部 "count" 字段写的是常量 `0x80`（字节数），因此**这一段的长度与条数不可由头部区分**，只能按 0x80 固定处理。

## 11. 写档 / 读档流程（无校验和）

### 11.1 写档（`0x43207C` 起，851 B）

```
buf = malloc(0x36710); memset(buf, 0, 0x36710);   // [0x4BD224] = buf, [0x4BD268] = buf
填头部（见 §3）

call 0x4308B0   // 段1 势力
call 0x430BB2   // 段2 城池

```
**关键**：`0x455AB2` 只被调用 **1 次**，长度 = 游标 = `0x1D0 + Σ(count × stride)`。
⇒ **文件里没有段头、块长度、校验和、EOF 标记**。

### 11.2 读档校验（`0x433D60` 起）

```c
h = open(name);
n = read(h, hdr, 0x1D0);
ok = (n == 0x1D0)                                   // 0x433D9B
  && (*(u32*)(hdr+0x00) == 0x56415353)              // "SSAV"，0x433DA4
  && (*(u32*)(hdr+0x04) == 0x20000);                // 版本严格 2.0，0x433DB0
if (!ok) { printf(0x48D88C /* 空槽/无效 */); return 0; }
strcpy(0x48D5C7 + slot*0x40, 槽名);                 // 槽描述缓冲，stride 0x40
[0x4BD240 + slot*4] = 1;                            // 槽有效位表
```
- **没有向后兼容分支**：`version` 必须恰好 `0x20000`，其它值一律判无效（与 `MAGIC.SO` 的 `0x100` 版本分派不是一回事）。
- magic 在整个 EXE 里只出现 2 次：写 `0x4320C1`、读 `0x433DAA`。
- 槽位描述：`0x48D5C7` 起每 0x40 字节一段；有效位表 `0x4BD240`。槽标签格式串 `0x48D840 "%-6s 城數%02d 武將%03d 時間%3d年"`（`0x43212A`）。

### 11.3 读档回填（段1 为例，`0x4323CF`）

```c
    king = 0x40945B(i);                              // KingAt
    memcpy(king, base + i*0x352 + 4, 0xC);           // 头 12 字节
    king->[0x0C] = IdxInv(base + i*0x352 + 0x10);    // 0x406A75 = 下标→指针
    king->[0x10] = 0;                                // 两个运行期字段清 0
    king->[0x14] = 0;
    king->[0x18] = IdxInv(base + i*0x352 + 0x1C);
    king->[0x1C] = base + i*0x352 + 0x20;
    king->[0x20] = base + i*0x352 + 0x24;
    king->[0x24] = base + i*0x352 + 0x28;
    king->[0x28] = base + i*0x352 + 0x2C;
}
```
⇒ `record[4+X] = 对象[X]` **在读档侧再次得到证实**（偏移 0xC/0x1C/0x20/0x24/0x28 一一对应）。

## 15. 仍未定位（诚实清单）

1. **段1 的 0x100 与 0x200 定长块**内容。0x200 = 512 与 `TotalGeneral=512` 同数，疑为"每武将 1 字节"的归属/状态位图，但无直接证据。
2. **段1 `+0x34E`、段2 `+0xAE` 类"超出对象体"的 4 字节**：本文字段表已按"中间省略 4 字节后整体下移"解释（§5 存疑 2），但省略点具体在哪个字段之前未定。
3. **段2 记录中位移从 4 变 8 的确切分界**：只有两点实测（`+0x78` 与 `+0xA2`）。
4. **段7 源表 `0x4C3A74`（128 × 0x56）的语义**：全 EXE 仅 3 处只读引用，无写入点、无字符串线索。
5. **段4 `+0x011..0x02F`、`+0x0DF`、`+0x0E0..0x0E6`** 三处空洞的字段名（写档代码无显式赋值）。
6. **段3 的 4 个 dword（`+0x024..+0x030`）与 4 个 u16（`+0x034..+0x03A`）**的具体含义：部队的兵数/士气/粮草（本作无粮草）/移动进度，四者之一。
7. **头部 `+0x060`/`+0x064`（`[0x4C30D8]`/`[0x4C30DC]`）** 与九个"统计量"字段（`+0x070..0x078`、`+0x084..0x08C`、`+0x198..0x1A0`、`+0x1AC..0x1B4`）的含义：都是 `Idx(无参函数())`，即"某个池里某个对象的序号"，但对应函数体未读。
8. **LOYAL / BLOOD 的真实偏移**：§7.1 证明 04b 的 `+0xBF/+0xC3` 是对象指针而非数值。
