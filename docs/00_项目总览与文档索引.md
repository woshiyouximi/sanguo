# 00 · 三国群英传2（修正版 1.05+）完整拆解 —— 项目总览与文档索引

> **这份文档是什么**：对一个 1999 年的商业游戏《三国群英传2》（Sango2.exe + Sango2.PAK）做的**全量拆解记录**——文件包格式、美术资源格式、全部数据表、可执行文件逻辑、脚本引擎、存档结构，以及"如果要照着它做一个新游戏，哪些该抄、哪些该改"。所有结论都尽量给出**可复现的验证方式**（地址、偏移、脚本、样本文件）与**实测数字**，而不是"大概是这样"。
>
> **给谁看**：你的新项目的策划（看 08、03 系列）、程序（看 01/02/04 系列）、美术（看 02、05b、`export\png`）。

## 1. 一句话结论

**这不是一个"靠代码硬写内容"的游戏，而是一个"把内容全外置成数据 + 脚本"的引擎**：

```
684 KB 的 EXE（逻辑）  +  117 MB 的 PAK（内容）  +  2 个 .SO 脚本文件（技能效果）
```

- **逻辑**：C++ + Win32 + DirectDraw/DirectSound，固定 640×480×16bpp，行为几乎全部由"读表 + 状态机"驱动；
- **内容**：11,110 个文件全在一个**无压缩、无加密**的 PAK 里（64 字节定长索引），改个 INI 就能改数值、换张 SHP 就能换头像——这就是它被社区 MOD 了 20 年的原因；
- **技能**：`MAGIC.INI` 只存元数据（耗蓝/攻击力/属性），真正的效果在 `MAGIC.SO` 的字节码里（`SYSCALL` 调引擎内置函数）。

## 7. 还没解开的（如实记录）

第一轮交付后，原先"证据不足"的 8 项里有 6 项已经做完（阵形站位、招降斩首掉落、单挑、MAGIC 映射、存档字段、普攻伤害），结论分别落在 `04b1`/`04b2`/`04b3`/`05c`/`07b`/`04b4`。**留下来的**是这些（都是"再往下走性价比骤降"或"需要动态调试"的）：

1. **对话/事件脚本里的两个记号**：`$xxx`（263 处）与 `!NNNN`（15 处）的确切语义仍未证实；`#N` 已确认是"停帧 tick 数"。
2. **`SANGO.INI` 的 `TotalTimes=6` 但只有 5 个剧本文件**：第 6 个是废弃剧本还是 MOD 预留位，无证据。
3. **`04b1` 的阵形变体族**：`unit+0x68`（X 变体开关）与 `unit+0x10` 的写入者全 `.text` 搜不到，推断本版恒 0，即 11–19 / 22–32 两族数据**实战中未被启用**；变形族的语义只有数据形态推断。
4. **`04b3` 的 `cmd 8` + `0x4000` 语义**：唯一写它的是 `0x4447B7`（"全軍撤退"按钮与主将阵亡都调它），现象上又像"前线接敌"——需要动态调试才能定案是撤退还是出击。
5. **`04b4` 的战后兵力回写路径**：战场减员只动 `unit+0x5C`，而 `general+0x42` 在全 `.text` 里只有升级函数 `0x40F294` 一处写入 → 回写要么在别处（未找到），要么由"势力刷新时重算"，与 `04b2` 的"补兵发生在势力刷新"部分吻合但仍未闭环。
6. **存档字段的 3 处空洞**：段 3 有 4 个 dword + 4 个 u16 未定名，段 7（128 字节全局标志表）语义 0% 定名，段 1 的 0x100/0x200 两块定长块内容未知。
7. **`04b3` 的 `0x43C4C0` 方向语义**、`0x43E55C` 派发器、`general+0x40`/`+0x8F` 等零散字段。
8. **存档没有真实样本**：`SAVES\` 是空的，`07`/`07b` 全部是静态逆向；`save_layout.py` 已带自测，但没在真存档上跑过。

## 9. 跨文档一致性修正（**以本节为准**）

六路并行子任务各自独立反汇编，出现了几处**互相冲突的字段偏移**。我用人物属性面板 `0x429634`（全 EXE 唯一一处把字段"打印给玩家看"的地方）做了仲裁：

| 偏移 | 类型 | 含义 | 面板证据 |
|---|---|---|---|
| `+0x10` / `+0x12` | i16 | 體力 一对（当前/上限） | `0x4299E7` 读 `+0x10`、`0x4299F1` 读 `+0x12` → `0x48B5C0 "體力   %d/%d"`；**扣血落点确定是 `+0x12`**（`0x43F3CF` 减、`0x43F3DA` 写回、`jle` 归零进死亡流程）。**哪个是"当前"仍有冲突，见下方说明** |
| `+0x14` / `+0x16` | i16 | 技力 一对（当前/上限） | `0x429A28` / `0x429A32` → `0x48B5D0 "技力   %d/%d"` |
| `+0x2A` | u32 | 經驗值 | `0x4299B1` → `0x48B5B0 "經驗值 %d/%d"`（分母 `0x409F5B(level)`） |
| `+0x2E` | i16 | 等級 | `0x429814` → `0x48B55C "等級   %d"` |
| `+0x34` / `+0x36` | i16 | 武力 / 智力（面板显示的就是这两个，`04b` 记作"基础值"；`+0x30/+0x32` 疑为"当前值"） | `0x4298FC` / `0x429933` → `0x48B58C` / `0x48B598` |
| `+0x38` | i16 | 士氣（初值 80） | `0x42996A` → `0x48B5A4 "士氣   %d"` |
| `+0x3A` | i16 | **疲勞度** | `0x4298C7` → `0x48B580 "疲勞度 %d"` |
| `+0x3C` | i16 | **忠誠度** | `0x429892` → `0x48B574 "忠誠度 %d"`（`0x48B568 "忠誠度 ---"` 是"未招降"占位） |
| `+0x42` / `+0x44` | i16 | 帶兵數 上限 / 当前 | `0x429A69`/`0x429A7F` → `0x48B5E0 "帶兵數 %d/%d"`；升级 `+0x42 := 0x409FB6()`（`0x40F294`）、`+0x44 := max(+0x44,+0x42)`（`0x40F311`） |
| `+0x46` / `+0x48` | i16 | 騎兵數 上限 / 当前 | `0x40F2A7` / `0x40F344`，同上一套逻辑 |
| `+0x9F` / `+0xA1` | i16 | 戰績 勝 / 敗 | `0x429794`/`0x4297A1` → `0x48B53C "戰績   %d勝 %d敗"` |

**说明：体力 `+0x10`/`+0x12` 的"当前/上限"仍有冲突，两边证据都记在这**——

- 支持 **`+0x12` = 当前**：面板 `%d/%d` 的压栈顺序使第一个 `%d` 取 `+0x12`（先显示的数通常是当前值）；战斗扣血明确落在 `+0x12`。
- 支持 **`+0x10` = 当前**：升级函数 `0x40F35A` 只写 `+0x10`，值是 `0x40A020(gen) + (旧当前−旧上限)`——这正好等于"新当前 = 新上限 + 剩余差额"，也就是 `04c` 已记录的升级规则。
- **概率最高的解释**：战场上的受击对象是**战斗副本**（`unit+0x40` → `+0x48` 取到的结构），不是 GENERAL 节点本身；两者布局差一格，所以 `+0x12` 在副本里是当前体力、在节点里是上限。
- **对做新游戏没有影响**：只要知道"扣血扣的是玩家看到的那条当前体力"即可。若要在旧 EXE 上打内存补丁改体力，必须先确认你拿到的是节点还是战斗副本。

**据此要更正的旧说法**：

1. `04b_战斗系统.md` §2.1 的"`+0x3A` 功勳、`+0x3C` 疲勞度"**两处都错**：正确是 `+0x3A` 疲勞、`+0x3C` 忠誠。EXE 里根本不存在「功勳 / 功績」这两个字符串（cp950 全表搜索为空）；`04b` 记的"功勋上限 100、`0x4108xx` 累加"实为**单场战功的计算结果**（`0x410989` 的返回值），不是持久字段。
2. `04b` 的"`+0x10` 当前 / `+0x12` 上限"与 `04b4`/`04b3` 的"扣 `+0x12`"并不矛盾——见上面的副本解释；两处都在文档里标了 [未定]。
3. `04b4` 的"`general+0x42` 只有升级处一处写入"与 `04b2` 的"补兵发生在势力刷新"**不矛盾**：战斗中减员只动战场单位 `unit+0x5C`，`general+0x42` 由势力刷新时从城池预备兵（`city+0x86`）补回。
