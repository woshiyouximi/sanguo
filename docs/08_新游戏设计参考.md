# 08 · 新游戏设计参考（拆解结论 → 设计决策）

> 这份文档不是"游戏介绍"，而是**把一个 1999 年的成品拆成可复用的设计零件**，并对"如果今天重做一个同类型游戏"给出取舍建议。
> 所有数字都来自本仓库解包出的真实数据（`F:\sanguo\extract\`）与逆向结果（见 01/02/03/04 系列文档），不是回忆或传闻。

---

## 1. 它到底是什么类型的游戏

**一句话**：一个"**战略地图 + 回合制内政 + 实时小队战斗**"的混合体，核心驱动是**武将收集与养成**。

一局游戏的时间结构：

```
剧本开局（选君主，5 个历史时期之一）
   │
   ├─ 战略层（大地图，按"月"推进）
   │    ├─ 内政：开发/征兵/训练/搜索/巡查（每城每月 1 次指令）
   │    ├─ 人事：登用/离间/赏赐/结义
   │    ├─ 军事：移动/出征/守城
   │    └─ AI 势力同时行动
   │
   ├─ 战斗层（进入战斗后切成实时）
   │    ├─ 布阵（9 种阵形 + 兵种搭配）
   │    ├─ 军师技（开战前的全局 buff/debuff）
   │    ├─ 兵战（士兵自动交战，武将可移动/攻击/放技）
   │    └─ 结算（俘虏/斩将/缴获/经验）
   │
   └─ 成长层（贯穿全局）
        ├─ 武将：等级 1→99（修正版），武力/智力成长，技能按等级解锁
        ├─ 兵种/阵形：随等级解锁
        └─ 装备：武器/马/宝物（唯一物品）
```

**设计上的关键取舍**（这是它区别于《三国志》系列的地方）：

| 维度 | 三国群英传2 的选择 | 后果 |
|---|---|---|
| 战略层深度 | **刻意做浅**：内政只有几条指令，没有复杂的官僚/税收系统 | 玩家 80% 时间在打仗和养成，节奏快 |
| 战斗表现 | **实时小队制**：几十个士兵 + 武将同屏，能看清每个人的动作 | 有"带兵打仗"的临场感，是系列招牌 |
| 武将数量 | **400 人**，每人有独立头像、7 个必杀技、8 个军师技 | 收集欲极强，是长线动力 |
| 数值复杂度 | 双轴（武力/智力）+ 相克矩阵，**没有复杂的兵种科技树** | 易懂难精，老玩家能背出相克表 |
| 叙事 | 极弱（只有开场和事件文本） | 靠历史知识补足，重玩价值来自"换君主/换剧本" |

> **给新项目的第一个决策点**：你要继承的是"**快节奏 + 收集养成 + 可见的士兵战斗**"这三件事，而不是它的内政深度。它的内政是**为了让打仗更频繁而故意做薄的**。

## 3. 数值骨架：它为什么"耐玩"

### 3.1 武将：双轴 + 技能等级门槛

- 每人两个主轴：**武力**（近战伤害/单挑）、**智力**（军师技/技力上限/武将技伤害）。
- 400 人里"双高"（武力≥90 且智力≥90）**只有 1 人：姜维（93/96）**——这不是巧合，是刻意的稀缺性设计：武力与智力的相关系数为 **-0.39（负相关）**，即"越能打越不聪明"，全能型只能靠极少数特例制造收集目标（诸葛亮 68/100、吕布 100/42、关羽 99/85、赵云 98/88 都是明确的偏科）。
- 分布实测：武力 30~100（均值 66.6、中位 70），智力 25~100（均值 64.3、中位 66）；武力≥80 有 91 人、智力≥80 有 95 人，双≥80 只有 16 人。
- 技能按等级解锁：必杀技从 1 级起、在 1~41 级之间零散分布（每人 8 个格子，数据表里最高解锁等级 41），军师技按"初/中/高"三档对应不同智力门槛。
- 修正版把等级上限提到 **99**、体力/技力上限破解到 **32767**——说明原版的成长曲线在后期会"封顶"，玩家需求推动了这项修改（原版上限具体数值未在代码中定位到，别照抄 20 这个数）。

> **可复用**：双轴 + 阈值解锁是**低成本、高感知**的成长设计。新项目可以保留"双轴"，但建议把"技能解锁"从"等级门槛"改成"条件解锁"（如"武力≥80 且 单挑胜 10 场"），增加叙事感。

### 3.2 兵种相克：13×13 的显式矩阵

`xls_兵种.json` 是一张 **13×13 的整数矩阵**（13 个兵种，单位是"点数"），例如：

- 朴刀 → 长枪 = **-42**（朴刀被长枪克）
- 长枪 → 朴刀 = **+42**（对称）
- 大刀 → 弓箭 = **+66**（大刀克弓箭，幅度最大之一）
- 弓箭 → 大刀 = **-66**

特征（全部实测，不是估算）：
1. **严格反对称**：`|A + Aᵀ| = 0`、对角全 0、取值域 **-68 ~ +68**、**非对角元素 `|均值| = 37.36`**——实现上只需存上三角。
2. 幅度集中在 **±40 ~ ±70**（≥40 的"强克制"共 **36 格**），即"克制"大约等于 **40-70 点攻防差**——足以影响战局但不至于一击必杀。
3. **存在"万能兵种"**：按行和排名，**大刀 +139、长枪 +129、弩兵 +119** 系统性占优；**黄巾 -176、蛮族 -151、女兵 -143** 系统性吃亏。原版平衡并不完美——这是老版本"出兵只出大刀/长枪"的根源。

阵形同理：**社区表是 9×9**（方形/圆形/锥形/雁形/玄襄/鱼丽/钩形/冲锋/箭矢），同样严格反对称，幅度只有 **-25 ~ +25**、`|均值| = 13.4`，且**所有行和都是 0±2**——**阵形几乎是完美的零和"软修正"**，与兵种的硬克制形成两级分工：兵种决定"打不打得过"，阵形决定"打得顺不顺"。（引擎里实际是 **11×11**，多出的第 10 号是 `亂陣`：对所有阵 **−25**，等于"没布阵就挨打"的惩罚项。）

> **可复用**：两级相克（兵种硬 + 阵形软）是很好的结构。矩阵化 + 反对称让"查表"成为可能，玩家能记住。
> **要改的**：绝对对称矩阵意味着"没有真正的剪刀石头布三角"，容易出现支配策略。新项目建议做**非对称三角**（每兵种只强克 2 个、被 2 个克），配合地形修正。

### 3.3 技能：110 武将技 + 67 军师技

`xls_武将技.json` 的字段是：`序号/名称/消耗技力/能量（气）/攻击力/调用代码/属性/官衔/注释,级别/目标`。

- **消耗技力**（MP）+ **能量（气）**（另一条资源）双资源——这是它战斗节奏的核心：技力决定"能放几个技"，气决定"什么时候能放必杀"。
- **调用代码**是脚本段号（110 个值互不重复，构成 501–610 的一个**排列**——不能靠"500+序号"去推），运行时定位到 `MAGIC.SO` 的函数目录（第 N 个技 = `0x1D4+N`）。
- **属性/目标** 是位域：`ACTIVE` 是"我兵/我将/敌兵/敌将"四位掩码，决定打谁。
- **`POWER` 恒等于 100**（全表无变化，没有信息量），真正的"威力"是 `ATTACK`（0–60，均值 10.5）；而 `POWER` 被用来算**气力消耗**（`气力 = POWER×1200`，满条 60000 → 一个技固定烧 2% 气条）。

`xls_军师技.json`：`序号/执行代码/军师技等级/名称/属性/等级/目标`，**执行代码 1/4/9/12/34…** 是另一套编号（军师技是"开战前一次性效果"，所以只需要"执行代码"）。

> **可复用**：**"元数据表 + 脚本入口号"** 这个结构比"把技能逻辑硬编码进 C++"好一万倍。110+67 条技能如果硬编码，会变成不可维护的 switch。
> **要改的**：双资源（技力+气）容易让玩家困惑，新项目建议**只保留一条资源**（或把"气"改成"连击/蓄力槽"，只影响表现不影响数值）。

### 3.4 城池与地图：60 城 / 116 路（实际可通行 77 条）

- 城池坐标是 **1280×960** 地图空间（例：襄平 `1108,90`）。
- 每条路径存**路点串**（`1108,90 1066,66 1038,64 …`）——**移动是沿折线插值，不是直线**。这是"行军动画有地形感"的原因。
- 路径长度（`长度` 列：260/78/112…）直接决定**行军时间**。
- **地图是"36 座城 + 12 座关 + 12 座不可通行占位"的混合图**（实测：60 城里 12 座关的 `等级=0`、人口与金钱都是 0、防御恒 100；116 条 `PATH` 里有 **39 条是 `Length=30000` 的哨兵值**，只表示"地图上画了线但走不通"，真正可通行的只有 77 条，平均度 2.57，图直径 **2084**（云南↔襄平最远））。
- **没有"超级枢纽"**：每个城的连接数都不高 → 行军必须一站一站走，这正是"补给线"感的来源（虽然它没有粮草系统）。

> **可复用**：**图结构 + 折线路点 + 长度权重 + 关隘卡口**，是最省事又最有表现力的战略地图方案（比六边形格子便宜得多）。
> **要改的**：60 城、77 条可通行边，图很稀疏——新项目若城多，需要"自动寻路 + 路点生成"工具链；`Length=30000` 这种"用魔法数表示不可通行"的做法建议改成显式 `blocked=true` 字段。

### 3.5 内政与 AI：极简到"只有 4 个数"，但节奏很稳

这套游戏的内政经常被诟病"太薄"，但它的**薄是有意的**，细节见 `04c_世界与内政.md` / `04d_AI与脚本引擎.md`：

- **时间是回合制的隐含骨架**：一回合 = **一个月**，靠一个倒计时全局（`[0x4C30E0]`）推进；12 个月后年 +1。没有"季节性事件"，也没有粮草。
- **没有粮草/后勤**：全表搜 `糧`/`徵糧`/`訓練`/`治水` **0 命中**。开发一次同时加人口与防御，没有单独的农业/商业/治安分支。
- **城池规模不会变**：`Rate` 字段只读不写 → **一座城从开局到终局就是那个等级**，玩家不能"养成"城市。
- **武将成长只长两样东西**：`最大带兵数 = min(等级×5, 100)`（20 级封顶）、`骑兵数 = clamp((等级−20)×5, 0, 100)`（40 级封顶）；**40 级以后带兵结构不再变化**，只剩体力/技力在涨。体力上限 = `BaseHP + 等级×2×武力/100`。没有统率/政治，只有一个派生的"综合值" `武力>智力 ? (武力+智力)/2 : 智力`。
  > 这条"两条 5 人/级的阶梯"是它兵种构成演变的全部——**玩家不需要造骑兵，20 级后自动转**。修正版把等级上限提到 99、体力/技力上限破解到 32767（原版后期会明显封顶）。
- **AI 每个势力每月只执行 1 个动作**，动作由 4 个规划器打分后 argmax 选一个；权重是硬编码常量：

  | 动作 | 评分 |
  |---|---:|
  | 攻打**玩家**的城 | **200** |
  | 攻打**其他 AI** 的城 | 100 |
  | 占空城 | `50 / (距离+1)` |
  | 联合（多城同月合击）玩家 / AI | 200 / 50 |

  出兵数 = `min(目标城兵力 + rand(3)+1, 上限, 5, 源城兵力−1)`。

> **设计上的三个可借鉴点**：
> 1. **"每月一个动作"制造了可预测的节奏**——玩家能从"这个月谁动了"推断局势，比每帧都在算计的 AI 更可读、更省 CPU。
> 2. **"打玩家 200 / 打 AI 100"是软性 rubber-band**：AI 会优先咬玩家，但不会明着作弊。想做难度曲线，改这一个常量比写复杂 AI 便宜。
> 3. **砍掉后勤是刻意的取舍**：没有粮草 → 玩家 90% 的决策都落在"武将搭配 + 兵种相克 + 技能时机"上，这正是它的核心乐趣所在。**新项目如果加后勤，必须同时砍掉别的东西，否则会把核心乐趣稀释。**

## 4. 战斗系统（结构，细节见 04b）

战斗是这套游戏的招牌，结构大致是：

```
出征 → 选择武将（最多 5 人）→ 布阵（选阵形/兵种/站位）
   → 军师技阶段（双方军师依次施加全局效果）
   → 实时战斗
        ├─ 士兵：按阵形站位，自动接敌，按兵种相克结算
        ├─ 武将：可移动、普攻、放武将技（耗技力）、集气放必杀
        └─ 单挑：武将接近可触发单挑（1v1，胜负影响士气）
   → 结算：胜负、经验、俘虏、缴获、城池归属
```

### 4.0 它其实只有"一条公式"（`04b` 已完整还原）

这一节是全套文档里对**做数值的人**最有用的部分：整个战斗的胜负判定收敛成一条命中判定，没有"攻防公式"。

```c
int 战力 = 兵种相克[我兵][敌兵]      // -68 .. +68
         + 地形修正[地形][我兵]       // -25 .. +25（只有少数兵种吃地形）
         + 阵形相克[我阵][敌阵]       // -25 .. +25
         + (全局加成 + 50) / 100      // 武将/技能给的百分比加成折算成点
         + (士气 - 50) / 5;           // -10 .. +10

int p = 战力;
if (目标是武将) p = 150 - 武力×20/100;   // 打武将走另一套（武将更难被打中）
if (状态不符)   p = p×2/3;               // 被眩晕/诅咒之类
命中 = (rand() % 300) < p;               // ← 全部战斗的最终裁决
```

- **四项加算、不乘系数**：这是关键设计——玩家能"心算"出这场能不能打（兵种 +40、阵形 +10、士气 +8 ≈ +58 → 命中率从 1/3 涨到近 1/5 的失败率）。
- **命中之后不在这里扣血**：只广播一个 `OM_PAIN` 消息，真正扣血分散在 20 个"物件 Process"的消息处理器里（`THINGS.INI` 的 `Process=1..21`）。**这是数据驱动带来的代价**：可扩展性极好（加个新兵种只要加 Process），但**伤害公式不可读**——想做平衡表，得去每个 Process 里翻。
- **经验阈值**：`f(n) = ((n−1)×137 − 34)×n/2 + 17`（`f(2)=120`、`f(5)=1302`、`f(20)=25707`），升级后 `新当前 = 新上限 + (旧当前 − 旧上限)`——**升级即回满，且不浪费溢出**。
- **战功/功勋**：`战功 = 步兵×6 + 骑兵×12 + 敌将等级×{51 歼灭/34 击退/17 平手/34 大胜}`；`功勋 = 15 + 战斗秒数/10`（≤100）。
- **士气惩罚**：`士气>50 → −1/回合；否则 clamp(士气,4,50)×6`——**士气低会雪崩**，这是它"一崩到底"手感的来源。

> **可复用的取舍**：把"多因子攻防"压成"一条命中率"，是**低代码、高可读**的经典做法；代价是**数值调试只能靠模拟跑量**（因为没有可读的伤害公式）。新项目如果要做"可计算的战斗"，建议保留"加算式战力"，但**把伤害结算收敛到一处**，别学它分散进 20 个 Process。

**为什么"能看清小兵"很重要**：士兵是**独立实体**（有 HP、有朝向、有动作帧），不是数字。这带来两个设计后果：

1. **性能预算**：同屏几十个士兵 × 每个 20+ 动作帧 —— 所以它用 16bpp 直接写显存 + 精灵缓存，而不是 3D。
2. **战术可读性**：玩家能"看出"阵形被冲散、侧翼被包抄——这是纯数值战斗给不了的。

> **给新项目的建议**：如果做 2D，**保留独立士兵实体**（哪怕只有 20-30 个），这是"群英传味"的核心；如果做 3D，至少要保留"士兵是实体"这一点，否则会变成《三国志》式的数值对撞。

### 4.1 战场只有 12 种，但每一张都是"4 层视差"

`SANGO.INI` 的 12 个 `[TERRAIN]` 段，每段的构成完全一样：

```
FLOORnn.TGA          512×512 无缝平铺地面贴图（按滚动坐标循环取样）
  + BG\BGnnA/B.SHP   远景两层（A/B 交替，做视差/云/远山）
  + BG\MGnnA/B.SHP   中景两层（树/房屋/旗帜）
  + BG\FGnnA/B.SHP   近景两层（前景草/栅栏，压在士兵之上）
  + SoundTrack=4/5/6 该地形的 BGM（12 种地形只用 3 首曲子轮流）
```

![12 种战场地面贴图](img/terrains_12.png)

*（上图为 `SHAPE\BG\FLOOR00-11.TGA` 的实际解码结果：砖墙 / 土墙 / 石板街 / 船甲板 / 草地 / 泥地 / 山地 / 苔草 / 雪原 / 沙丘 / 沙地 / 城墙砖。全是 512×512 可无缝平铺的材质，不是"一张张画好的战场背景"。）*

两点值得学：

1. **12 种地形 × 4 组图层 = 48 张图的组合，做出"到处都不一样"的错觉**——但美术只画了 12 套底图。这是 1999 年在 640×480 / CD-ROM 容量下的必然选择，现代项目用"程序化地表 + 少量装饰物"可以做到同样效果而更省。
2. **地形只影响"打哪张背景"和一张很小的兵种修正表，不影响移动**：`[TERRAIN]` 段本身只有 `Floor/Foreground/Midground/SoundTrack` 四项，**没有攻击/防御/移动修正**；但战斗里另有一张硬编码的 **地形×兵种 12×13 表**（`0x48D030`，`04b` 已定位），只给特定兵种加减点：**森林（行 3）里弓箭 +25、蠻族 −24**，行 0/1/2 三个"城"完全同值，等价于平地。大地图上每 2×2 像素的地形色号（`CHINAMAP1-4.MSK`，取值 0-11）同时决定"这一仗的地形号"。
   > 这是它被低估的一个设计取舍：**地形修正极窄（只有少数兵种吃地形），所以战斗公式仍然可读**（主体是兵种 × 阵形 × 属性），玩家不会因为踩到不利地形而输掉，失败总能归因到自己的编队。**新项目如果要做宽地形加成，务必同时把 UI 做得足够清楚**，否则玩家会把"地形惩罚"当成随机性。

> 反例警示：`TotalTimes=6` 但只有 5 个剧本文件——**别用"计数"驱动遍历**，用了就要写容错；这也是新项目做 MOD 支持时第一个会被踩的坑。

## 5. 架构启示：这套引擎最值得抄的三件事

### 5.1 全内容外置 + 一个 PAK

11110 个文件、112 MB 全部在一个 `.PAK` 里，索引 64 B/项、名字 40 B、**无压缩无加密**。好处：

- 加载快（一次 seek 读整块）
- 改 Mod 容易（`odin_pak_packer` 重打包即可，社区就是这么改出 1.05+ 的）
- **坏处**：任何资源都能被直接提取（本文档就是证据）

> 新项目建议：**用 PAK 的思路（单包 + 索引）但加一层轻压缩 + 版本号 + 哈希校验**。别加密（防不住，还拖慢加载）。

### 5.2 数据表 + 脚本双轨

- **声明式**：INI 表（武将/城池/技能/物品/剧本）——策划可直接改
- **命令式**：`.SO` 字节码（技能演出、特殊效果）——程序写一次，策划配 N 次

这套结构在 1999 年是超前的。`04-脚本引擎SmartScript.md` 已把它的虚拟机完整还原：**90 个 opcode（0x00–0x59）**、**124 个注册 syscall（脚本实际用到 102 个）**、每脚本 121 个全局槽、栈元素 8 字节 `{value,type}`、字符串对象带引用计数。`MAGIC.SO` 里 463 个函数 / 30,720 条指令，对应 110 个武将技——**平均一个技能不到 70 条指令**，这就是"技能是脚本，不是代码"的量化证据。

> 今天等价物就是 **"ScriptableObject/JSON 数据 + 可视化脚本（或 Lua/C# 热更脚本）"**——但要记住它是**自己写了个 VM**（~1800 行 C），今天直接用 Lua/Wren 就行，别重复造轮子。
> 新项目建议：技能/事件/剧情全部走"数据 + 脚本"，**不要把任何一条技能写成 hardcode**。110 条技能硬编码的维护成本，会在第 3 个资料片时爆炸。
> **反面教材**：它的 syscall 是硬编码注册表（`0x420D52` 里 124 个 if/else），没有反射、没有类型检查——**改版作者想读个内存，要靠 `0x213–0x219` 这种"任意地址读写"后门**。新项目的脚本 API 必须**带类型和沙箱**。

### 5.3 定长节点池 + 整池存档

对象是定长节点（GENERAL 247 B）+ 自由链表，存档直接整池落盘。今天看来很"土"，但它带来一个好处：**存档格式极其稳定**，加字段只要改 record size。

> 新项目建议：**别学这个**。用 ECS 或普通对象 + 序列化框架（JSON/MessagePack/Protobuf），但要**保留"数据版本号 + 迁移函数"**——老游戏最痛的就是存档不兼容。

### 5.4 旁证：社区 20 年改出来的"可改面"，就是这套架构的验收报告

用户下载的这个包里自带 `可选补丁\` 目录，它恰好列出了**玩家实际能改什么**（每一项都不需要改 EXE）：

| 补丁 | 改的文件 | 说明什么 |
|---|---|---|
| 技能耗蓝上调 | `MAGIC.INI` | 技能数值全在表里：伏兵组阵 21→25、大地狂啸 48→90、天地无用 50→70、鬼哭神号 50→100（13 条技能） |
| 去兵符阵法 | `SANGO.INI` | `[SYSTEM]` 里有"能否搜索到兵符/阵法书"的开关；关掉后所有武将只能用默认兵种/阵法 |
| 智力书籍 13-15-17-18-20 | `SANGO.INI` | 书籍加成是**配置值**，不是硬编码 |
| 4 套头像包 | `SHAPE\FACE\*.SHP` | 美术可整批替换（甚至引入 FACE401-414 这类超出 400 人的编号） |
| 繁体字体包 | `SANGO.15 / SANGO.20` | 字体是独立资源，且**点阵按 Big5 码位**排（与 INI 的 cp950 编码一致） |

> **这正是数据驱动架构的价值证明**：一个 1999 年的商业游戏，靠"改 INI/换 SHP"就能被社区持续迭代 20 年。
> **给新项目的硬指标**：如果一个策划改数值需要程序改代码，这套架构就是失败的。**新项目的"可改面"应当不少于这张表**。

## 6. 美术资源的组织方式（对美术管线最有用）

这套游戏的资源组织有一个非常聪明的设计：**部件化 + 拼合**。

```
武将的一帧画面 =
    BODY（身体，按造型编号 + 动作 + 帧号）
  + WEAPON（武器，按类型 + 动作 + 帧号）
  + HORSE（马，仅骑马时）
  + FACE（头像，仅界面用）
       ↑ 三层按各自的 offsetX/offsetY 锚点直接叠（引擎硬编码的装配层）
       ↑ 注意：COMBINE.INI 不是干这个的——它只有 4 条 SHAPE 记录，
         是"把 4 张头像按 2×2 拼成一张图"的测试配置（详见 05b）
```

- `SHAPE\MAJOR\BODY` 3,601 个文件、`WEAPON` 2,585 个、`HORSE` 185 个——**不是 400 个武将各画一套**，而是"造型 × 武器 × 动作 × 帧"的组合爆炸。
- 命名规则（`05b` 已完全解码）：`{L|R}{造型号}{动作码}{武器位 1-4}{4 位帧号}`，如 `L1A10002`；`L`=蓝军、`R`=红军（实测像素均色 R−B 分别为 +16 / +50）。武器 `{A|B|C|D}{序号}{动作码}{类别}{帧}`，兵种 `{M|N}{兵种 A-M}{H=骑乘}{动作码}{1}{帧}`。
- 动作是**离散帧序列**，动作名就是引擎常量：`WAIT/WALK/ATTACK/DEFENSE/PAIN/DEATH/FIRST/ATTACK2..8/SPELL1..2/SHOT1..3/CURSOR/STAFF/END1..3/HIT01/SCROVER`，序列里 `#N` 是**该帧停留的 tick 数**（`#9999` = 无限停帧），不是帧数。

> **可复用度：极高**。这套"部件拼合 + 动作状态名"的思路，今天直接对应 **2D 骨骼/换装系统**（Spine/DragonBones 的 skin + attachment）。
> **给新项目**：如果做 2D，**第一天就把"武将 = 身体 + 武器 + 坐骑 + 特效"的装配层设计出来**，不要按"每个武将一套图"生产——那是 400×N 的产能灾难。
> **另一个可学的**：修正版社区能整包替换 `SHAPE\FACE\*.SHP`，说明**美术资源与逻辑彻底解耦**（换图不用改代码）。新项目的资源清单必须"可整包替换 + 编号连续"。

## 7. "手感"清单（复刻时最容易被忽略的部分）

这些是玩家能感觉到、但文档里通常不写的：

1. **行动点/回合的节奏**：每月只能做 1 件事，逼玩家做取舍。
2. **战斗可以加速**（`S#` 调速度）——老玩家几乎全程加速。
3. **单挑的仪式感**：喊话 → 冲锋 → 交手 → 胜负特写。
4. **技能演出必须短**（1-2 秒），110 条技能如果每条 5 秒，战斗会变成看动画。
5. **数字反馈要大**：伤害数字、兵力条、士气条同屏可见。
6. **"名将脸"**：400 张 100×120 头像，是收集欲的视觉载体——**不要用程序生成的头像**。
7. **音乐是 MP3 外挂的**（修正版），原版是 CD 音轨——说明"音乐质量"在当年就是卖点。

## 8. 新项目的取舍建议

### 8.1 建议继承

| 继承项 | 理由 |
|---|---|
| 双轴武将 + 阈值解锁技能 | 低成本高感知，玩家能理解 |
| 兵种硬克制 + 阵形软修正（两级） | 易懂、可背、有深度 |
| 独立士兵实体 + 可见战斗 | 系列招牌，替代不了 |
| 数据表 + 脚本双轨 | 内容量 > 代码量的唯一解 |
| 部件化造型 + 动作状态名 | 美术产能的关键 |
| 图结构战略地图 + 折线路点 | 便宜且有效 |

### 8.2 建议重做

| 重做项 | 原因 | 建议方案 |
|---|---|---|
| 内政深度 | 原版太薄，现代玩家会觉得"没事干" | 加"城池建筑 + 政策"两条浅层系统，但**每回合操作数不超过 3 次** |
| 相克矩阵 | 绝对对称 → 支配策略 | 非对称三角 + 地形修正 + 兵种熟练度 |
| 双资源（技力+气） | 认知负担 | 单资源 + "蓄力槽"（只影响表现） |
| 存档 | 定长池整池落盘 | 版本化 JSON/MessagePack + 迁移 |
| UI | 1999 年的 640×480 界面 | 现代分辨率 + 手柄/触屏适配（**这是重制最大的工作量**） |
| 叙事 | 几乎没有 | 至少给每个剧本一个"目标 + 结局"，给名将 1-2 段事件 |

### 8.3 建议砍掉

- **CD 检测/盘符遍历**（原版遗产，现代毫无意义）
- **640×480 固定分辨率**（除非刻意做复古风）
- **8 位点阵字体**（除非做像素风）
- **"每城每月只能 1 指令"的硬限制**（改为"行动力"资源，更灵活）

### 8.4 风险提示

1. **内容量陷阱**：400 武将 × 61 字段 × 5 剧本 = 24,400 格。**先做 40 个武将的垂直切片**，验证管线，再铺量。
2. **战斗 AI 是最难的部分**：士兵寻路 + 阵形保持 + 武将决策，原版用了大量特例代码（见 04b）。
3. **美术产能**：10,969 个 SHP / 92 MB 是 1999 年手绘的量。今天用 2D 骨骼可以压到 1/5，但仍需**明确的部件规范**。
4. **版权**：所有资源、数值、文本都受版权保护。**本文档的用途是"设计参考"，不是"资源复用"**——新项目必须重画、重写、重配音。

| 层 | 建议 | 理由 |
|---|---|---|
| 引擎 | Unity / Godot / 自研 2D | 需要"大量精灵 + 实时小队"，2D 管线成熟度最重要 |
